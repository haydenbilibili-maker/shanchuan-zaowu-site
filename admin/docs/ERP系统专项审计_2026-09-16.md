# ERP 系统专项审计（2026-09-16）

> 审计对象：`admin/`（Vue 3 + Element Plus，98 个组件，约 11 万行）、其所依赖的 61 个云集合与
> 27 个云函数代理入口、以及它与「小程序超管工作台 / 飞书多维表格」三方的分工。
> 审计方式：**只读**（不改代码、不部署、不写库）+ **线上只读核验**（
> 读取 CloudBase 线上真实安全规则与真实文档样本）。凡涉及「线上实际状态」的结论都标注了取证方式。

> 状态：第一部分（§1 方法与可信度、§2 我亲自线上验证的 P0）为**终稿**；
> §3–§7 为六路并行子审计的结果合并区，标注 ⏳ 的章节尚在汇入。

## 0. 结论摘要

1. **【P0·架构级】ERP 的数据面是「无鉴权」的**：ERP 用 `signInAnonymously` 拿会话
   （`admin/src/cloud.js:99-104`），而**线上 56 个集合的 `read` 是 `auth != null`**
   —— 匿名会话即满足。其中 **24 个是敏感集合**：`orders`（含收货人/地址/手机号/金额）、
   `refunds`、`finance_records`、`finance_settings`、`store_ledger`、`admin_users`、
   `admin_roles`、`admin_login_logs`、`admin_operation_logs`、`purchase_orders`、
   `purchase_intents`、`price_list_items`、`feishu_inventory`、`feishu_purchases` 等。
   另有 **12 个 `read: true`**（完全公开）。**任何能打开站点的人无需口令即可读走整个经营数据库。**
2. **【P0】ERP 有 6 个集合「点保存但不落库」**：`products`(12 处)、`bookings`(4)、`orders`(4)、
   `support_tickets`(3)、`shipping_rules`(2)、`point_records`(1)。这些 ERP 走**匿名 SDK 直写**，
   而**线上规则是 `write:false`** → 写入被拒。典型如 `App.vue:2551`「加入档案」、
   `Bookings.vue:383` 核销、`SupportTickets.vue:281` 工单流转。
3. **【P0】ERP「人工调整积分」是死功能**：`admin/src/components/CRM.vue:316-334` 直写
   `users.points`（线上 `write:false`、且按 `_openid` 限定），写流水 `point_records` 的异常被
   `catch { /* 忽略 */ }` 静默吞掉 → **既改不了余额，也不留台账**。
4. **【P0】ERP 的「权限管理系统」不控制任何权限**：`admin_roles` / `admin_users`
   全仓只有 `PermissionManager.vue` 读写，**没有任何云函数或小程序消费它们**；
   而 ERP 外壳（`App.vue` / `AdminNavHub.vue` / `modulesRegistry.js`）**没有任何按角色过滤菜单的逻辑**
   —— 全仓唯一出现角色门禁的文件是 `StoreStaffPermissions.vue`（那是小程序的店员权限）。
   即：**任何登录者可见可点全部 98 个模块**，真正的门禁只在云函数侧（且只有一部分有）。
5. **【P0】ERP 的退款按钮无法完成退款**：`Orders.vue:531-540` 自己的兜底文案写着
   「Web 匿名身份可能无 admin openid …… 请在小程序『店长后台 → 订单 → 退款』处理真实退款」。
   同时 `Refunds.vue:445/470` 把订单状态改成 `refund_approved` / `refund_rejected` 的
   两次写入因 `orders` 为 `write:false` **静默失败**，却仍弹 `ElMessage.success('已批准')`
   → 退款单已批、订单状态没动，**两边长期不一致**。
6. **【P0】8 个 ERP 配置屏写的数据没有任何消费方**：`search_hot_keywords`、`search_blacklist`、
   `recommend_algorithm_config`、`marketing_rules_config`、`achievement_configs`、
   `user_behavior_config`、`notification_templates`、`points_rules`（遗留）。
   全仓（小程序 + 云函数 + Pages + 官网）**搜不到任何读取点** → 这些屏是「改了也没用」。
7. **【P1】仓库规则文件与线上规则有 19 处不一致**，其中 `home_configs` 最危险：
   仓库写的是 `write:false`，**线上实际是 `write:"auth != null"`**
   —— 意味着「按仓库规则收紧」会把该屏直接改坏，而维持现状则任何人可改首页配置。
8. **【P1】ERP 基本没有操作审计**：`admin_operation_logs` 全仓仅由
   `PermissionManager.vue`（ERP 侧）与 `manageMemberCrm`（注销）写入；经营与资金类操作普遍不留痕，
   而这张日志表本身还是**匿名可读**。

> 一句话：ERP 当前是「**UI 上像后台，架构上像公开站点**」——
> 读写都建立在匿名会话上，真正的授权只在少数云函数里，而同一批业务对象又被小程序/飞书多路写入。

### 1.2 本轮**自己的检查器产生过的假阳性**（必须记录）

这是本会话第四次踩到同一类问题：**机械检查会造出看起来很真、实际是错的 P0**。逐条记录以便别人复核：

| # | 检查器给出的结论 | 复核后的真相 | 假阳性根因 |
| --- | --- | --- | --- |
| 1 | 【P0】ERP 退款流程被打断（`Orders.vue:526` 预写状态失败 → `refundOrder` 拒绝） | **降级 P2**：`refundOrder/index.js:430` 的 `allowFrom` **直接接受 `paid`** 并自行置状态，预写是**冗余**的；注释「refundOrder 只接受 refunding/aftersales」是**过期注释** | 只读了调用点的注释，没读被调函数的准入条件 |
| 2 | 【P1】`booking_rules` 无任何消费方 | **错**：`createBooking` / `getBookingAvailability` / `manageBookingRules` 都在用 | 只匹配**带引号的字面量**，漏掉常量/动态引用 |
| 3 | 【P0】`curated_collections` / `vip_levels` / `feishu_*` 等 7 个集合「规则里没有 write」 | **错**：它们用的是**旧版逐操作规则格式** `{read, create, update, delete}`，`create/update = auth != null` → 实际**可写** | 只找 `write` 键，没兼容另一种合法规则格式 |
| 4 | 首次跑线上规则比对时报「127 个集合全部不一致」 | **解析形状错**：应为 `resp.Data.PermissionList` | 未先用已知良好的样例验证解析器 |

> **教训**：判断「某个写会不会落库」「某个配置有没有人读」这类结论，
> 必须同时看**调用点、被调函数、线上规则、以及 SDK 的失败语义**四者；
> 任何只凭一处证据得出的 P0，都要先当作假阳性处理。

## 2. P0 清单（我亲自线上验证）

### P0-1 ERP 数据面匿名可读（架构级，影响最大）

**证据（线上实测）**：`audit-live-rules.cjs` 输出 ——
`read === true` **12** 个；`read = "auth != null"` 且未按 `_openid` 限定 **56** 个（敏感 24 个）；
按 `_openid` 限定本人的 10 个；`PRIVATE`/`read:false` 49 个。

**身份前提（可证）**：`admin/src/cloud.js:99-104` 调用 `auth.signInAnonymously()`；
第 185 行 `userId: auth.currentUser?.uid || 'anonymous'`。匿名 uid 满足 `auth != null`。

**暴露样本（线上实测，仅取规则与条数，不导出内容）**：

| 集合 | 线上 read | 敏感度 |
| --- | --- | --- |
| `orders` | `auth != null` | 收货人、地址、手机号、金额、openid |
| `refunds` | `auth != null`（**write 也开放**） | 退款金额与审批 |
| `finance_records` / `finance_settings` / `store_ledger` | `auth != null` | 全量财务 |
| `admin_users` / `admin_roles` | `auth != null`（**write 也开放**） | 管理员账号与角色 |
| `admin_login_logs` / `admin_operation_logs` | `auth != null` | 登录与操作审计 |
| `purchase_orders` / `purchase_intents` / `price_list_items` | `auth != null` | 供货价、成本 |
| `feishu_inventory` / `feishu_purchases` | `auth != null` | 库存与采购 |
| `member_welcome_gift` | **`true`**（write 亦开放） | 礼包配置（改它＝改发券面额） |

**影响**：商业数据泄露；`orders` 泄露构成个人信息（PII）泄露；
`refunds` / `admin_roles` / `member_welcome_gift` 可**被任意改写**（后两者可导致权限表污染、
以及把新会员礼券改成任意面额后注册领取）。

**建议（方向，不动手）**：
1. 把 ERP 的**读**也搬进已存在的鉴权通道（`/api/cloud-fn` + `admin-session` 会话），
   然后把 56 个集合的 `read` 收紧为 `false`、由云函数按角色返回。
   这个模式仓库里已经跑通（49 个 PRIVATE 集合、11 条写路径已代理），**是继续推进而非新建**。
2. 过渡期优先且**低风险**的三条：`admin_users`、`admin_roles`、`admin_login_logs`
   先改 `read:false, write:false`（ERP 侧读它们的只有 `PermissionManager.vue` 一处，可一并改走代理）。
3. `refunds`、`member_welcome_gift` 的 `write` 立即收紧为 `false`（写路径已有云函数：
   `refundOrder`、`manageWelcomeGift`）。

### P0-2 ERP 6 个集合「点保存但不落库」

**证据（可证 + 线上实测）**：`audit-write-risk.cjs` 交叉「ERP 直写点」× 「线上规则」：

| 集合 | 直写处数 | 线上 write | 代表证据 |
| --- | --- | --- | --- |
| `products` | 12 | `false` | `admin/src/App.vue:2551`（加入档案 `inArchive`）等 |
| `bookings` | 4 | `false` | `admin/src/components/Bookings.vue:383`（核销 `status:'used'`） |
| `orders` | 4 | `false` | `Orders.vue:526`；`Refunds.vue:445/470` |
| `support_tickets` | 3 | `false` | `SupportTickets.vue:281/295/305` |
| `shipping_rules` | 2 | `false` | `ShippingRulesConfig.vue:165/167` |
| `point_records` | 1 | `false` | `CRM.vue:321`（积分流水） |

**注意**：`orders` 的那 3 处**不是** P0（见 §1.2 #1，`refundOrder` 直接接受 `paid`），
但 `Refunds.vue` 的 2 处**是**（见 P0-5）。

**建议**：这 6 个集合逐一改为经代理云函数写（`manageProducts` 等已存在；缺的补 action），
并为每个屏补上「写入失败必须报错」的处理。**在改之前先确认弹窗是红是绿**（§1.3）。

### P0-3 人工调整积分是死功能

**证据（可证 + 线上实测）**：`admin/src/components/CRM.vue:316-334`
```js
await cdnDb.collection('users').doc(row._id).update({ points: cdnDb.command.inc(val) })
try { await cdnAdd('point_records', {…}) } catch (e) { /* 忽略 */ }
ElMessage.success('积分调整成功')
```
- `users` 线上规则：`{"read":"auth != null && doc._openid == auth.openid","write":false}`
  → 匿名会话**既非本人文档、write 又是 false**，写入必被拒。
- `point_records` 线上 `write:false` → 流水也写不进，且异常被**显式忽略**。

**影响**：调整不了余额、也不留台账；`row.points = row.points + val` 还可能让界面显示假余额。

**建议**：改为调用 `manageMemberCrm`（已有 `admin_operation_logs` 审计与积分流水能力）
或新增受控 action；**删掉 `/* 忽略 */`**。

### P0-4 权限管理屏不控制权限

**证据（可证）**：
- `admin_roles`/`admin_users` 全仓引用文件**只有** `admin/src/cloud.js`（常量）与
  `admin/src/components/PermissionManager.vue`（读 + 写）。
- ERP 外壳无角色过滤：`App.vue` 中 `role`/`permissions`/`canSeeMenu`/`isSuperAdmin`
  出现次数**均为 0**，且**没有 vue-router / 路由守卫**（`vue-router` 出现 0 次）。
  菜单由 `modulesRegistry.js` + `AdminNavHub.vue` / `CommandPalette.vue` / `MainTabsBar.vue` 驱动，
  全量渲染。全仓唯一角色门禁文件是 `components/StoreStaffPermissions.vue`（小程序店员权限）。

**影响**：①运营/投资类账号可见全部 98 个模块（含财务、权限、AI 中心）；
②`PermissionManager` 里配的角色是**装饰品**，会让人误以为权限已受控；
③该表 `write: auth != null` → 任何人可改写（数据污染）。

**建议**：二选一并说清楚 —— 要么把 `PermissionManager` 真正接进门禁
（前端菜单过滤 + 云函数按 `roleCode` 判权，且改为云函数写），要么**下线该屏**并在
`admin/docs/PLATFORM_CAPABILITIES.md` 里明确「ERP 为单层控制台，权限由云函数 `staffGuard` 承担」。

### P0-5 退款：ERP 侧批了，订单没动

**证据（可证 + 线上实测）**：
- `Orders.vue:531-540`：云函数失败时的兜底原文即「…请在小程序『店长后台 → 订单 → 退款』处理真实退款，
  避免 Admin 直改状态导致未退款到账」→ **ERP 退款按钮不产生真实退款**。
- `Refunds.vue:441-451`（`approve`）与 `464-478`（`reject`）：
  `await cdnUpdate(COLLECTIONS.ORDERS, row.orderId, {status:'refund_approved'|…})`
  然后 `ElMessage.success('已批准')`。`orders` 线上 `write:false` → 该写入失败，
  **但 UI 仍报成功** → 退款单已批、订单仍停在 `refunding`。

**建议**：合并为一次云函数调用（`refundOrder` 的审批 action 已在仓库内：
`refundOrder/index.js:492` 注释「将订单置为 refunding（替代客户端直写）」，
说明该治理动作**只做了一半**——服务端有了，前端没接）。
