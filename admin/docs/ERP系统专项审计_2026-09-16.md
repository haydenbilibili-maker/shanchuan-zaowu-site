### P1（高危）

**平台对齐**
- **预约规则 split-brain**：ERP 写 `booking_rules`（`BookingRulesConfig.vue:384`），实际生效的是 `store_booking_rules`（`createBooking/index.js:75`），`manageBookingRules/index.js:2-3` 明示「勿写 Admin 旧 schema」→ **ERP 改预约规则 100% 无效**。
- **财务口径倒置**：`syncFinanceData`（小程序）才是 SSOT，ERP 仍保留写回路径且失败被吞成 `success:true`（`financeSync.js:276-285`）→ 财务页显示「同步成功」但云端零写入。
- **飞书「应用为 HQ 库存」双重失效**：`feishuSync.js:780` 依赖 `feishu_inventory.productId`，而该字段**全仓无写入入口**（`FeishuBridge.vue:226/472` 只读展示"未映射"）；即便有值，`:796` 直写 `products` 也被 `write:false` 拒。
- **飞书库存单向（只有 pull）**：`feishuSync.js` 有 `pushOpsPurchase`/`pushShipments`，无 `pushInventory`；「物业成本」表在驾驶舱宣称已对接（`getStudioDashboard/index.js:664-666`）但**无任何同步代码**。
- **两份 allowlist 共同遗漏** ERP 正在调用的 7 个函数：`manageStudioInventory`、`manageStudioRawInventory`、`manageBookingRules`、`manageStoreConfig`、`manageManageMemberLevels`、`manageWelcomeGift`、`syncFinanceData`、`manageMemberCrm`（→ 走浏览器匿名 `callFunction`）。
- **配置保存会静默重置另一端的字段**（缺省即回落）：`member_welcome_gift` 的 `priority`/券 `channel`（`manageWelcomeGift/index.js:50,59`）；`stored_value_config` 的 `recharge`（`defaults.js:39-44`）；`deposit_rules` 小程序硬编码 `true` 覆盖 ERP 的 `false`；`member_levels` ERP 直写会**清空等级图标**（`MemberLevelConfig.vue:262`）；`gift_settings.nudgeDays` 两端都不发 → 每次保存重置为 `[3,6]`；`member_birthday_gift` 券 `channel` 同上。
- **小程序编辑活动会把 ERP 已关闭活动重新开启并清零报名数**（双端均硬编码 `status:'open'`、`remain:maxPeople`：`Activities.vue:143/144`、`managerPageConfig.js:7372/7373`）。
- **`articles`/`cms_wikis` 互相覆盖**：ERP 强制专题 `status='published'`（`ContentManager.vue:280`）会把小程序草稿/下架/UGC 待审改回 published；小程序保存整对象覆盖 `stats` 清零浏览/点赞。
- **`studio_inventory` 语义冲突**：小程序快照全删重建会把 `feishuRecordId` 置 null（`manageStudioInventory/index.js:185-201`）→ 下次飞书拉取重复建行。
- **飞书回写把小程序已发货单打回 draft**（`feishuSync.js:333/368/376` + `shipmentDefaults.js:101-111` + `manageStoreShipment/index.js:676-688` 覆盖 `status` 与 `source`）。
- **`ops_purchases.source` 两端都硬编码 `'erp'`**（`PurchaseOps.vue:421`、`purchase-ops/index.js:739`）→ 来源统计失真（"一致地错"）。

**权限与审计**
- **审计覆盖率仅 6/27** 云函数；`admin_login_logs` **全仓无写入点** → 登录日志页永远是空表（**误导性安全展示**）；`admin_operation_logs` 在 ERP 侧只读。
- **登录接口无速率限制/无锁定**（`functions/` 内 `rateLimit|429|lockout` 零命中）。
- **`canOperateStore` 默认开放**：无 `storeId` 或 `storeIds` 为空即 true（`staffGuard.js:707-720`）→ **省略参数即跨店**。
- **`_fromApproval` + `_callerOpenid` 身份透传过宽**：经 `/api/cloud-fn`（SCF Invoke，无微信 SOURCE）`isNonClientSource()` 恒真 → 可指定任意 openid，破坏审计归属。
- **会话令牌可离线伪造**：签名密钥回退链 `ADMIN_PROXY_SECRET || ADMIN_PROXY_PASSWORD || ADMIN_OPS_KEY`；令牌无用户标识/nonce，登出仅清 Cookie。
- **本地 Vite 代理无会话校验即注入 `ADMIN_OPS_KEY`**（`admin/scripts/viteCloudFnPlugin.mjs:45-73`，dev 与 preview 都挂载）。

**数据与持久化**
- **门店/员工/薪酬完全无云端持久化**：`sc_store_bundle_v1`（`utils/storeStorage.js:5,99`）、`sc_payroll_*`（`utils/payrollStorage.js:42,65`）**只在 localStorage**；员工花名册含**身份证号与银行卡号**（`feishuRosterSync.js:21-22,204-205`）→ 换机器数据归零。
- **财务设置键双份**：UI 写 `sc_finance_settings_v1`（`Finance.vue:1592`），同步/AI 读 `sc_finance_v12`（`financeSync.js:17`、`financialData.js:106`）→ 文档所称「多端同步」不覆盖 UI 实际保存的键。
- **`customExtraPrice` 由客户端传入**（`makeOrder/index.js:71,204,329`；`pricing.js:330` 仅防负数）→ 定制加价可被少报。
- **小票/外部订单金额优先取 `event.amount`**（`claimStoreReceipt/index.js:301-312`、`bindPlatformOrder/index.js:307-312`）→ 顾客可声明金额（受单笔上限 + 店长复核约束）。
- **ERP 商品库存绝对覆盖 + 标题模糊匹配**（`Finance.vue:3761-3775`、`feishuSync.js:796`）→ 会抹掉服务端 CAS 预占的库存（`makeOrder/stockUtils.js:47-78`）。
- **PII**：`orders` 匿名可读 + `portraitDataLoad.js:9-18` 一次拉 1000 条 + `Orders.vue:381-422` 导出 CSV 无审计；`sensitiveMask.js` 唯一引用方是 `UnifiedEmployeePanel.vue:37,42` → 订单/CRM 全量明文手机号。
- **退款积分冲销流水用户不可见**：`refundOrder/index.js:331` 写 `_openid: ''`（应为 `userOpenid`），而 `point_records` 读规则按 `_openid` 限定。
- **`redeemReward` 新用户回滚失败会丢分**：`doc(null)` 被 `.catch(() => {})` 吞（`:90-98,156,186`）。
- **`verifyStoreCoupon` 有一段无条件 update 兜底**（`:485-504`）→ 旧券可双核销。
- **两套安全规则目录漂移**：`cloudbase/rules/` 127 份 vs `miniprogram/database-rules/` 90 份，36 个集合只在其中一份有定义；`store_point_rules` 两份的 `read` 不同。

**业务流程与对账**
- **ERP 目前不是「更完整的编辑面」，而是多个关键流程的只读镜像**：退款发起、退款审核、预约核销、积分调整、门店营收登记在 ERP 上均无法真正落库；直播与出货单虽云函数已支持 `create`/`start`/`updateShelf`/`setStatus`（`manageLiveSession:1534-1543`、`manageStoreShipment:897-901`），ERP 只接了列表与强制结束（`LiveSessions.vue:113,128,143`、`StoreShipments.vue:107,117`）——与「ERP 是低频但更全面」的原则**相反**。
- **`paid`/`shipped` 单在 ERP 根本没有退款按钮**（`Orders.vue:140,154`）；`ready_pickup` 有按钮但先写 `orders` 抛错 → **`refundOrder` 从未被调用**（`:142,525-530,544-547`）。
- **审批载荷丢失，审批人所见 ≠ 实际执行**：`order_ship_sensitive` 提交的 `note/totalPrice/isReship/orderNo` 在通过时只回传 `carrier`+`trackingNumber`（`manageApprovals:804-820`）；`order_refund` 提交的 `refund/deduct/forceFullRefund` 通过时仅用 `orderId` 并**按实时订单重算**（`:789-802`）→ 审批金额可能与实退金额不一致。
- **审批单无法取消/过期**（`manageApprovals:1542-1568` 无 `cancel`/`delete`；`approvalRules.js:22` 的 `cancelled` 无写入方；`config.json` 无 triggers）→ 孤儿审批永久 pending，只能进数据库控制台手删。
- **三方对账函数 `syncFinanceData` 未被 ERP 接通**（含 `reconcile_online_orders`；ERP 侧唯一引用是 `miniprogramSandboxBridge.js:108` 的文档字符串；不在两份 allowlist；无定时触发器）→ 商城订单 ↔ 门店 POS 对账结果 ERP 永远看不到。
- **财务「对账」实为合并去重并静默删除云端重复**（`financeSync.js:119`、`storeLedgerSync.js:238`，无确认无审计）→ 差异被**抹平**而非暴露；而 `StoreManagement.vue:207` 却承诺「差异在财务对账中处理」，财务侧 `对账|核对|差异` 命中 **0**。
- **飞书同步把库存台账写入失败报告为成功**（`feishuSync.js:707-726` 仍 `success:true`，`FeishuBridge.vue:646-647` 只弹绿）→ 运营看到「台账新建 0 / 更新 0」的成功提示，实际一条未写。

## 5. 业务流程、状态机与流程阻断

### 5.1 状态机与闭环

| 对象 | 状态集合 | 可逆? | 断点 |
| --- | --- | --- | --- |
| `orders` | `pending_pay` `fulfilling` `paid` `paid_awaiting_address` `ready_pickup` `shipped` `received` `refunding` `aftersales` `refund_approved` `refund_rejected` `refunded` `expired_refunding` | 多数可逆（拒绝时 `restoreStatus` 还原） | ①`refund_rejected` **无出边**（P0-17）；②`refund_approved` 无写入方；③`refunded` 无撤销 |

### 5.3 对账能力

| 应有 | 现状 |
| --- | --- |
| 订单 ↔ 出货 ↔ 库存 | **无基础**（`stock_movements` 永远为空；`manageStoreShipment` 不扣库） |

### 7.5 权限模型两条路的差异（待决策，供拍板）

| 维度 | A. 真做 RBAC | B. 下线 `PermissionManager`，明示「单层控制台」 |
| --- | --- | --- |
| **要做的事** | 前端按 `roleCode` 过滤菜单 + 云函数逐个 action 判权限点 + `admin_roles`/`admin_users` 改云函数读写 + 补审计。27 个云函数要逐个补权限点校验 | 删掉该屏（或标注"不生效"）；在 `PLATFORM_CAPABILITIES.md` 写明"ERP 为单层控制台，权限由云函数 `staffGuard` 承担"；补一句给运营的说明 |
| **成本** | 高：横跨 27 个云函数 + 前端外壳 + 权限数据模型，且要处理现有 7 个角色的权限矩阵 | 极低：一次删除 + 一次文档修正 |
| **防护效果** | 能挡住"运营账号误点财务/权限/AI 中心"，能按人最小权限 | **前端可见性不变**（所有登录者仍见全部 98 个模块）。但**真实数据防护本来就在云函数侧**，不依赖此屏 |
| **风险** | 做一半最危险：前端藏了但云函数没判 → 给人"已受控"的错觉 | 承认现状：安全边界清晰（服务端），但**误操作风险不降** |
| **与 P0-1/P0-2 的关系** | 不解决匿名可读/假登录；这两条必须单独修 | 同样不解决 |
| **适用前提** | 有 ≥3 类真实使用者（如运营/财务/投资），且需要按人最小权限 | 实际只有 1–2 类使用者，靠服务端 `staffGuard` 就够 |
| **我的建议** | 若短期不打算投入，**先做 B**；等"按人账号 + 独立密钥"落地（§8 第一批第 4 项）后再评估是否升级到 A。**不要在没做按人账号之前先做 A** —— 那会变成"给共享超管密钥加上一层装饰性角色" | |

> 顺序应是：**按人账号 → 真实权限点 → 前端 RBAC**，而不是反过来。
