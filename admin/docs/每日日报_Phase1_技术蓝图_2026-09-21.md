## 1. 架构决策：**定时生成 + 落库**（不是打开时实时算）

### 1.1 结论
选定 **定时触发 → 计算 → 落库为站内信 → 用户读历史**。

### 1.2 理由（三条，按权重）
1. **可回看要求数字冻结**。若打开时实时算，昨天的日报会被今天的库状态覆盖：订单会退款、
   `store_ledger` 会补录、`analytics_daily` 会继续累加。历史日报必须停留在生成那一刻。
2. **读放大与延迟**。一份日报要跑 4 类查询（`analytics_daily` 1 次、`orders` **7 次归日聚合**、
   按日集合 2 次、`ops_shipments` 1 次）。压在「用户打开小程序那一刻」做，既慢，
   又会随并发重复烧读次数。
3. **本仓已有定时触发器先例**：`sweepExpiredOrders/config.json` 的
   `triggers[].type='timer'`。照它的形态新增即可，不引入新机制。

### 1.3 代价（如实记录）
数字是**生成时点的快照**。日报 payload 记 `generatedAt`，详情页固定显示
「这是一份定时快照：数字取自生成那一刻，之后补录/退款不会回改」。

### 1.4 为什么不走 `dispatchMessage`
`dispatchMessage` 的两条路径都装不下日报：
- 模板路径只认 `templateCode` + `vars`；
- override 路径只认 `title/content/actionUrl` 三件套，**没有结构化 payload 的位置**；
- 它的 `checkDedupe` 是 **24h 窗口**（`dispatchMessage/core.js:39-55`），而日报要的是
  「同一天同一人永不重复」的**确定性**幂等。

因此改为直写 `user_messages` + `notification_logs`，与本仓既有的
`sweepExpiredOrders/inAppMessage.js:75-139`、`managerShipOrder/messageWrite.js:250-266`
同一形态。

## 2. 数据口径表（**本文最重要的一节：未来据此对账**）

机器可读版本：`miniprogram/cloudfunctions/dailyDigest/reportCatalog.js` 的 `METRICS`。
下表与它一一对应；守卫 `check:daily-digest` 会核对「表里登记的集合」与「取数实现真查的集合」
双向一致，所以**这张表不会与代码漂移**。

### 2.0 三个必须先讲清的时区/单位事实（**实测，不是读注释**）

| 事实 | 结论 | 证据 |
|---|---|---|
| `analytics_daily.dateKey` | **UTC 日**，不是东八日 | `trackUserBehavior/index.js:22-28` 的 `getDateKey` 用 `getFullYear/getMonth/getDate`（云函数运行在 UTC）；无 `dateKey` 时兜底 `toISOString().slice(0,10)`（`:96`）。实测北京 00:00–08:00 的事件落进前一个 `dateKey` |
| 订单时间字段 | `createTime` / `paidTime` / `refundTime` / `logistics.shipTime` 都是 **Date**，归日必须交给 `$dateToString{timezone:'Asia/Shanghai'}` | 实测：手算 `$gte/$lt` 边界会差一天；`$dateToString` 分桶正确 |
| `paymentBreakdown.totalFen` | 单位是**分**（整数）；`totalPrice`/`refundAmount` 是**元**（浮点） | 实测样本 `totalFen=8660` 而 `totalPrice=86.6`。同名不同单位正是错题本 E18 的形态 |

| id | 中文 | 取值 | 来源与过滤 |

**必须随数字一起说明的三条**：
1. 门店营收是**人工录入**（Admin「智能日报」粘贴解析 / 店长「记一笔」）。当日未录入 → **无行**，

2. `store_ledger` 与 `daily_revenues` 是**同一次录入的两个落点**，可能不同步；

3. 门店 POS 单数与小程序订单数是**两套口径**，禁止相加。

`purchaseTotal`（`:574`）与全部结算 KPI 都是**全期累计**。它不是"日"数据源，
拿它的 KPI 当「当日营业额」是口径错误。

## 3. 扩展位设计（角色切片怎么做）

### 3.1 一份日报，多种切片
`reportCatalog.ROLE_SLICES` 给每个角色定义 **`sections` + `metrics` 白名单**：

| 角色 | 看到的分组 | 指标 |
|---|---|---|
| `super_admin` ✅**本次启用** | 小程序 + 订单 + 门店 | 全部 phase=1 指标（19 项） |
| `store_manager` | 订单 + 门店 | 单量/发货/退款 + 本店账本 + `x_store_scoped_revenue` |
| `store_staff` | 门店 | 本店 POS 单数 |
| `specimen_artisan` | 门店 | `x_artisan_output`（本人作品产出） |
| `live_host` | 小程序 | 访问/访客 |
| `shareholder` | 门店 | `x_shareholder_slice` |
| `investor` | 门店 + 订单 | 营收 + 线上支付金额 |

### 3.2 加一个角色的代价（**不改架构，只改数据**）
1. 在 `ROLE_SLICES[role]` 里把 `enabled: false` 改成 `true`；
2. 该角色独有的指标若还没实现，在 `METRICS` 里补一条（含 `sources[]` 口径），
   并把 `kind` 归到已有的 4 种取数动作之一（`analytics` / `orderDay` / `dateKeyed` / `simpleDay`）；
3. 在 `loadRecipients(role)` 的角色判定里加上该角色（当前只筛 `roles` 含 `super_admin` 的人）。
**不需要**改：取数层、落库层、消息页、分档、保留策略、守卫结构。

### 3.3 扩展位现在**明确不发车**
`ENABLED_ROLES` 实测只有 `['super_admin']`；`x_*` 三个指标 `phase: 2`，只登记口径不出数。
守卫有一项专测「扩展角色被误启用」。

### 3.4 已知的核心分歧（留给后续，**不要混算**）
门店营收至少有三套既有定义，互不相同：
- **C1** `getAnalyticsDashboard.ledgerNet = max(0, pos+online+cashIncome−refund)`（`:388-404`）；
- **C2** `getShareholderObservatory.ledgerRevenue = net→revenue→amount→total→gmv`（`:236-244`）；
- **C3** ERP 本机 `localStorage shanhai_v12`（`dataSources.js:441-454` 登记为本机镜像，清缓存即 0）。

日报 Phase 1 **只用原始录入字段**（`pos`/`online`/`refundAmount`/`total`）并**并列展示**，
不做 `max(0, …)` 这类再加工 —— 一旦加工，数字就不再与账本可对账。股东切片（C2）必须**独立成段**。

## 4. 调度方式与失败兜底

### 4.1 触发：每小时 + 内部日切（**刻意不赌时区**）
`config.json`：
```json
{ "triggers": [{ "name": "dailyDigestRun", "type": "timer", "config": "0 20 * * * * *" }] }
```
- 本仓既有 8 个 trigger 全是 **7 段**（`秒 分 时 日 月 周 年`，实测 `sweepExpiredOrders` 等），
  但**没有任何一处写明时区**，且腾讯云文档在这一点上的说法不统一。
- 赌错时区的后果是「每天在错误的时间发日报」—— 只有人肉才能发现的故障。
- 因此改为 **每小时第 20 分钟**跑，把正确性交给两个确定性机制：
  1. **日切**：`resolveTargetDayKey(now)` = 「最后一次北京日切之前的那一天」。
     无论 cron 被解释成 UTC 还是东八，北京日切后第一次运行生成的都正是那一天，
     **不会把没结束的一天当成完整一天发出去**；
  2. **幂等**：`dedupeKey = daily_digest:<role>:<dayKey>:<openid>`（**不含时刻**），
     同一天无论触发多少次，每个收件人**只会有一封**。
- **代价（必须让后来人看见）：一天最多 24 次空跑**，不是"一天跑一次"。
  每次空跑的固定开销 = 每收件人 1 次 `user_messages.where({dedupeKey})` 查询
  （命中的那些在 `findExisting` 就返回 `skipped`，**不会重复计算日报、不会重复写库**）。
  按当前 `staff_members` 里 `super_admin` 的规模（1–2 人）估算，一天 ≈ 24–48 次点查 —— 可接受。
  若将来角色扩到全员（比如 16 人都要日报），空跑会变成 24×16 ≈ 384 次点查/天：
  那时应把「先判当天是否已发」提到**取数之前**（现在是先 `collectRaw` 再逐人 `findExisting`，
  即命中已发时仍白跑了一次全量聚合）。**这是本设计下第一个该优化的点，已在 §8 登记。**

### 4.2 幂等（同一问题，另一个答案）
- 键 = `daily_digest:<role>:<dayKey>:<openid>`，**日期 + 角色 + 收件人**三者齐备。
- 守卫 D8 专测：不同日期 / 不同角色的键必须**不同**（否则第二天漏发或角色互相顶掉）。
- 与云库的 `user_messages.dedupeKey` 唯一索引配合（已登记进
  `miniprogram/scripts/ensure-dedupe-indexes.cjs` 的 `usedBy` 与
  `check-dedupe-index-coverage.mjs` 的 `OBSERVED_WRITERS`；**建索引动作由持凭据者执行**）。

### 4.3 失败兜底
| 失败 | 行为 |
|---|---|
| `analytics_daily` 查不到某 action | 该指标 `value = null` → 显示「未取到」，**不是 0**；`missing[]` 随 payload 返回 |
| 某个 `orders` 聚合抛错 | 只该指标变「未取到」，其余照常；错误写 `console.warn` 带指标 id |
| 按日集合当日无行 | 同上（`rowCount=0` → `null`） |
| 单个收件人写库失败 | `results[]` 里记 `success:false`；**不影响其他人**；入口返回 `success:false` 与 `failed` 计数 |
| `notification_logs` 镜像写失败 | 只 warn，主消息仍在（读侧按 `dedupeKey` 合并两表） |
| 某天函数整体没跑 | 次日不会自动补 —— **手动补发**：`{action:'build', dayKey, internalKey}`（见 §7） |

### 4.4 保留策略（"可回看"的边界）
- `RETENTION_DAYS = 90`。每次运行后按收件人清理**更早的日报**：
  `pruneOldDigests({ openid, beforeDayKey })` **只删 `type === 'daily_digest'` 且归属该 openid 的**消息，
  绝不碰别的消息类型。
- 保留期内**可任意回看**：日报就是站内信，历史在「工作信息 → 日报」这一档按 20 条/页翻。

## 5. 投递：怎么进「工作信息」

### 5.1 文档形状（写 `user_messages`，镜像 `notification_logs`）
| 字段 | 值 | 为什么 |
|---|---|---|
| `_openid` / `openid` / `recipient` | 收件人 openid | 读侧 `_.or([{_openid},{openid},{recipient}])`（`getUserMessages:192-203`），命中任一即可 |
| `queue` | `'workflow'` | 读侧 `resolveMessageQueue` 第一判据（`:58-67`） |
| `audience` | `'workflow'` | 第二判据（兜底冗余） |
| `category` | `'digest'` | 第三判据 **＋ UI 分档 id** |
| `type` | `'daily_digest'` | 第四判据（不匹配任何既有前缀，所以前三个必须写） |
| `templateCode` | `'daily_digest'` | 与 `type` 一致（历史读法） |
| `relatedId` | `<YYYY-MM-DD>` | 幂等/回看锚点 |
| `dedupeKey` | `daily_digest:<role>:<day>:<openid>` | 幂等 |
| `payload` | 结构化日报 | 详情页据此渲染口径表 |
| `actionUrl` | `subpackages/manager/manager/index?tab=13&title=数据报表` | 指向「数据报表」工作台；**不能指向信箱自身**（`messageHelper.isInboxSelfUrl` 会当作无跳转） |
| `createTime` / `_createTime` | `db.serverDate()` | 读侧排序取值 |

### 5.2 读侧的**必须**改动
`getUserMessages` 是**白名单式归一化**，`payload` 不在名单里就会被丢掉 → 详情页只剩纯文本。
因此新增 `normalizeDigestPayload(doc)`（只认 `type === 'daily_digest'`，数组长度与字符串长度封顶），
并在 `mergePair` 里加 `payload: primary.payload || secondary.payload || null`
（镜像日志行不落 payload，若按 primary 覆盖会把日报正文抹成 null —— 与 `products` 同一族问题）。

### 5.3 `workNoticeCatalog` / `workNoticeVoice`
新 type 不在语音白名单里 → **静默忽略，不崩、不出声**；工作台角标会自动 +1。
本轮**不**加语音（要加须走 `workNoticeCatalog` 四步 + `npm run tts:work-notice` + `check:work-notice`）。

## 6. 入口：「工作信息顶部单独一档，与待办、审批并列」

### 6.1 两个界面都查了，这是**实际**的入口
- `miniprogram/pages/user/index.js` 的**工作台瓦片阵**（`workbenchTiles`）：
  第一块是「工作信息」（`key: 'workflow'`），其余是各角色工作台。
  → 这是产品负责人说的「与待办、审批并列」的那一排。
- `miniprogram/subpackages/extra/user/messages/index.js` 的 `WORKFLOW_FILTER_TABS`：
  原本是 `全部 / 待办(ops) / 审批(system)` 三档，**日报在这里就是与待办、审批并列的第三档**。

### 6.2 落点（两处都做，语义不同）
| 位置 | 改动 | 作用 |
|---|---|---|
| 工作台瓦片 | 新增 `key:'digest'` 瓦片「日报 / DIGEST」+ `goToDigestMessages()` | **入口**：不依赖未读，随时可进 |
| 工作信息分档 | `WORKFLOW_FILTER_TABS` 加 `{ id:'digest', label:'日报' }` | **分类**：与「待办」「审批」并列的一档 |
| 详情页 | `letter-digest` 块渲染 `digestView` | **口径可对账**：每个数字下方写来源集合 + 时间字段 + 时区 |

角标口径：日报瓦片的角标只数 **`category='digest'` 的未读**（`getUnreadCount{queue:'workflow',category:'digest'}`）。
**不并入** `workflow` 未读 —— 那会把「有几件事等我处理」这个数字搞糊。

### 6.3 「可回看」怎么落地
点瓦片 → `/subpackages/extra/user/messages/index?queue=workflow&category=digest&from=workbench`
→ 走工作信息**已有的**列表（20 条/页、下拉刷新、触底加载）。
即：日报天然带上工作信息已有的分页、已读、保留策略，**不造第二套「读过就没了」的推送列表**。

## 7. 部署清单（**本仓纪律：云函数不由 AI 部署**）

### 7.1 需要新建/改动的云函数
| 云函数 | 动作 | 说明 |

| `getUserMessages` | **改动**（需重新部署） | 放行 `payload` + `mergePair` 合并 payload |

### 7.2 需要配置的东西（**新函数默认什么都没有**，见错题本 E22②）
1. **环境变量**（`tcb fn deploy` 不会配）：
   - `ADMIN_OPS_KEY` —— 与既有函数**同一把**（供 `/api/cloud-fn` 与一次性脚本只读核对）。
     值可从既有函数 `tcb fn env pull` 拉取，只打印长度不回显。
   - `DAILY_DIGEST_INTERNAL_KEY` —— 手动补发用。**不配也不影响定时**（定时不需要它）；
     不配时手动 `{action:'build'}` 会被拒（`INTERNAL_KEY_MISSING`）。
2. **定时触发器**：`tcb fn deploy` 只建函数，**不保证创建 Timer**。
   部署后须在云开发控制台确认 `dailyDigestRun` 已存在；若没有，按 `config.json` 的
   cron `0 20 * * * * *` 手工添加。**在此之前日报不会自动生成。**
3. **索引**（`user_messages`）：
   - `dedupeKey` 唯一索引 —— 已在 `ensure-dedupe-indexes.cjs` 的 `usedBy` 登记，
     **建索引动作由持凭据者执行**（`node miniprogram/scripts/ensure-dedupe-indexes.cjs --execute`）。
   - `type + openid` 复合索引（prune 用）—— 建议，非必须。

### 7.3 不需要改的
- 不需要新建集合（复用 `user_messages` / `notification_logs`，ACL 已是
  `{read:false,write:false}`，只有云函数能写）。
- 不需要改 `cloudbase/rules/**`、`cloudbase/schema/**`、`admin/src/cloud.js`（无新集合）。
- **没有做 ERP 侧 UI**：产品负责人说的「与待办、审批并列」在两个小程序界面里，
  ERP 侧没有「工作信息」这一档。若后续要在 ERP 出日报页，须走 ERP 新增模块三处
  （`modulesRegistry` → `adminNavDomains` → `App.vue`）+ 代理白名单两处同步。

`--live` 的设计取舍（对齐错题本 E16）：它依赖线上凭据与**已部署**的函数，在 CI/他人机器上
必然不可判定，因此**与退出码解耦** —— 能跑就打印真实数字，跑不了就明确打印
「未验证真实数字」，退出码仍由静态判据决定。这样它永远不会变成假绿。
