## 1. P0 · 支付回调可被伪造（0 元购）

### 证据

- `cloudfunctions/payCallback/index.js:65-118`：`exports.main` 直接读取 `event.returnCode / resultCode / outTradeNo`，只要三者形如成功且 `outTradeNo` 存在，就执行 `fulfillOrder(...)` 完成履约。
- 全文件 **`getWXContext` / `SOURCE` / `OPENID` 命中数为 0**（`grep -c` 实测）：既没有调用方身份校验，也没有微信支付签名校验（`sign`/`verify`/`decrypt` 零命中）。
- `cloudbaserc.json` 里 `payCallback` 只有 `timeout/runtime/handler/envVariables`，**没有调用权限限制**；云开发中同名云函数可被本小程序任意用户 `wx.cloud.callFunction` 调用。
- 对比：同仓已有正确写法——`dispatchMessage/index.js:12-22`、`sendInAppMessage/index.js:12` 用 `isClientSource(wxContext.SOURCE)` 识别客户端；`manageArtisanCommission/index.js:55-66` 用 `INTERNAL_KEY` 或 `SOURCE ∈ {scf,wx_cloud}` 识别内部调用。

### 影响

1. **0 元购**：用户下单选微信支付但不付款，直接调用 `payCallback` 传自己的 `outTradeNo`（下单即可获得），订单立即进入履约（`payCallback/fulfillOrder.js`：扣库存、核销券、改状态、发「支付成功」私信、发装裱师佣金）。
2. **可打他人订单**：查找条件是 `orderNo / outTradeNo`，不含 `_openid`——知道他人单号即可替他人「付款」，污染账目与佣金。
3. **数据污染**：库存被真实扣减、优惠券被核销、佣金入账，后续对账与退款会被牵连。

### 修复建议（两条一起做）

1. **调用来源收口**（最小改动，可直接复用现成写法）：

```js
const wxContext = cloud.getWXContext()
const fromClient = ['wx_client', 'wx_devtools'].includes(String(wxContext.SOURCE || ''))
if (fromClient || wxContext.OPENID) {
  // 微信支付回调由平台触发：既没有用户 OPENID，SOURCE 也不是客户端
  return { errcode: 0, errmsg: 'IGNORED' }
}
```

2. **履约前核对金额证据**（纵深防御）：校验 `event.totalFee`（单位分）与订单应付金额一致，不一致拒绝履约；有条件时再调用微信支付查询接口确认订单已支付。

> 上线顺序：先改代码并部署 `payCallback`，再回归一次真实支付——确保平台回调仍能正常履约（平台回调无 OPENID，不会被上面的判断误伤）。

### 临时缓解（改代码之前）

在云开发控制台把该函数的可用性收口（若有按函数粒度的调用限制），或临时把「仅接受无 OPENID 调用」的判断先加上并尽快部署。

## 2. P1 · 三处越权 / 滥用点

### 2.1 `sendCareReminder` 内部动作对客户端开放

- `cloudfunctions/sendCareReminder/index.js:217-233`：任何调用方可传 `action` 触发 `schedule` / `process` / `cancel`。
- `scheduleReminder`（:56）与 `cancelReminder`（:200）的 `openid` 来自 event，**未与调用方身份比对**：可替他人登记/取消养护提醒（骚扰与破坏行为）。
- `process` 会批量发送到期提醒 → 可被反复触发刷消息（含推送成本）。
- **建议**：`process` 只允许定时触发（复用 `sweepExpiredOrders` 的 `isTimerEvent` 写法）；`schedule`/`cancel` 强制 `openid === wxContext.OPENID` 或走 staffGuard。

### 2.2 `sweepExpiredOrders` 可被客户端触发

- `cloudfunctions/sweepExpiredOrders/index.js:231-244`：`if (timer || action === 'sweep' || action === 'sweepExpired' || !action)` ——**不传 action 即执行全量扫描**，客户端可空调用。
- 影响：提前把「已过期」的待支付订单取消并走退款/释放库存逻辑；可被反复调用形成骚扰与账目抖动。
- **建议**：`!action` 不再视为定时触发；仅 `isTimerEvent(event)` 或带 `INTERNAL_KEY` 的调用可执行。

### 2.3 `getUserStatistics` / `getUserStats` 可越权读他人数据

- `getUserStatistics/index.js:7-8`、`getUserStats/index.js:83-84`：`const targetOpenId = event.targetOpenId || wxContext.OPENID`，**没有「目标必须是本人或店员」的校验**。
- 影响：知道他人 openid 即可读取其订单数、消费额、积分、证书、消息等统计（隐私泄露）；`getUserStats` 还会返回 `staffRole` 等身份字段，可被用来探测谁是内部员工。
- **建议**：`targetOpenId !== wxContext.OPENID` 时要求 `assertStaff` 通过（店员查会员是正当场景），否则拒绝。

## 3. P2 · 部署与配置漂移（表现为「功能静默不生效」）

| 项 | 证据 | 影响 |
|----|------|------|
| 今天改动 86 个客户端会调用的云函数 | 107 个改动云函数中 86 个被前端调用 | 未重新部署的函数**代码是新的、线上是旧的**，新字段/新动作取不到 → 表现为「点了没反应/字段空白」 |
| 56 个云函数未登记 `cloudbaserc.json` | 登记 68 / 实际 124 个目录 | 用 `tcb fn deploy`（不带函数名）部署会漏掉这些函数 |
| 7 个函数超时两边冲突 | `dispatchMessage` 20s vs 60s、`payCallback` 20s vs 15s、`manageProducts` 60s vs 90s、`refundOrder` 30s vs 20s，另有 `getStoreConfig`、`manageMemberLevels`、`manageStaff` | 不同工具部署得到不同超时；`dispatchMessage` 若被部署成 20s，批量推送可能中途超时 |
| `payCallback` 超时偏紧 | 履约链路含库存/券/消息/佣金，且会**跨函数调用** `dispatchMessage`；配置仅 15–20s | 高峰期履约超时 → 订单停在 `fulfilling`，需靠重试补偿 |
| ERP 密钥未轮换 | `admin/.env.local` 的 `ADMIN_OPS_KEY`（64 位）仍能在 `HEAD` 的 `public/admin/assets` 两个文件中命中 | 旧密钥仍公开可用，本轮代码修复不生效 |
| ERP 登录 / 集合权限 | `App.vue:1472` 仍前端比对口令；管理集合仍 `read: auth != null`（匿名可读） | 详见 `docs/ERP系统审计_2026-09-14.md` §5 |

**建议**：把「今天改动的云函数全部重新部署」当作本次发版的硬性前置（可用 `scripts/deploy-all-cloudfunctions.sh`），并统一超时来源（建议以 `cloudbaserc.json` 为准，补齐 56 个缺失项）。
