## 1. 一句话定位

**祈福墙 = 黑马标本缺失的那一半（数字补位）。**

店里**不允许触摸标本**，所以"对黑马做点什么"这件事**线下做不到** ——
祈福墙就是那个**唯一被允许的动作**：把顾客"驻足看黑马"的 30 秒，
延长成手机上的一次许愿，并把这次许愿**兑现成一张券**。

它不是"小游戏合集"，也不是"内容板块"。它的价值只有一个链条：

```
线下驻足 → 扫码进墙 → 零门槛做一个动作 → 得到一句只属于今天的话
        → 有"不想丢"的进展 → 一键成为会员（拿新会员礼券） → 成交
```

**任何不服务于这条链的功能，都不该出现在这一页。**

## 2. 场景与物理锚点（这是数字产品的"原件"）

> **⚠️ 2026-09-20 产品负责人口径纠正 —— 这一条推翻了本节初稿的前提**
>
> 线下**真实存在的只有四样**：**黑马标本本体 + 博物黑墙 + 3000K 追光 + 底座黄铜三字「马上有」**。
> **没有做任何互动装置**（鼻尖黄铜没有做）、**不允许触摸标本**；
> 初稿 §2.1 写的"木盘 / 空白愿望卡 / 纸鹤 / 铅笔 / 印章卡"**全部不存在**（2026-09-20 已核实）。
> 核心理念原话仍成立：**「让时间听得见你说话」**。

### 2.0 由此得到的产品推论（本 PRD 最重要的一条）

线下对黑马的体验是**纯被动**的：只能看。没有互动装置、没有可拿走的物料、也不允许触摸
—— 也就是说，**顾客对黑马"什么都做不了"。**

于是**数字祈福墙正好补上这个缺口**：它是顾客**唯一被允许的**"对黑马做一次动作"的方式。
线上与线下的关系**不是「1:1 复制」（线下根本没有可复制的动作），而是「数字补位」：
线下给不了的动作，由线上给。**

> 这条推论把祈福墙从"线下的附属品"升级为"**线下缺失的那一半**"——
> 它不是把店里已有的体验搬到手机上，而是**把店里做不到的那件事做出来**。
> 这是本页存在的理由，也是它配得上一个独立入口的原因。

### 2.1 线下现状 → 线上动作

| 线下现状（**2026-09-20 已核实**） | 线上对应 | 关系 |
|---|---|---|
| 黑马标本 + 博物黑墙 + 3000K 追光（纯展示，**不允许触摸**） | **点灯**（对黑马做一次"被允许的动作"） | **数字补位**（线下给不了的动作） |
| 驻足、凝视、拍照（产品负责人原话："大家看到黑马会驻足停留"） | 扫码进墙（把"驻足"延长成一次参与） | 顺接 |
| 底座嵌黄铜三字「马上有」 | 页头品牌字 + 「马上有…」心愿句式种子 | 1:1 |
| **专门为它做的歌《黑马标本店》** | **⏹ 已否决：不放音乐**（产品负责人 2026-09-20：「**还是别放音乐了，过于突兀**」） | 素材已提供（WAV 2ch/48kHz、239.64s、46MB）。**"完成仪式自动播副歌"的形态被否决** —— 完成动作时突然起音乐是"替你制造情绪"，与这面墙"让人自己说"的克制方向相反 |

**已核实"不存在"的物料（不要为它们造线上对等物）**：木盘、空白愿望卡、纸鹤、铅笔、印章卡、铜牌。
> 这条对线上是**减法指令**：不要为了"和线下对应"而新增任何物件/动作（例如折纸鹤、盖章）。

### 2.2 硬性纪律：本页文案与交互**不得引导触摸标本**

标本保护 + 现场要求：**任何文案都不得引导、暗示或鼓励触摸标本**（适用于线上文案、也适用于将来的线下物料）。
> 记录在案：ERP 经营手册数据里那句「传说摸一下它的鼻子…」与「摸一下它的鼻子，你马上就有。」
> **正因为违反了这条纪律、且线下根本没有这个装置，才必须更正**（见 §2.3）。

## 3. 三条目标（产品负责人 2026-09-20 原文）

### 目标 1 · 把玄学/心理学与**商品推荐**做一次总的关联

**要做成的样子**：顾客抽到的那句话、这面墙偏的那个"求什么"，**决定推荐哪件藏品**；
推荐不是"热卖榜"，而是"这句话对应的那件东西"。

**已建的机制（可复用，不推翻）**：6 个受控祈运标签（求财 / 求安 / 求学 / 求缘 / 求行 / 求成），
每个标签自带引导语与**2 个关联玩法**（`config/blessTags.js`，四处同源，有守卫）；
推荐走云函数 `getBlessProducts`（显式标签优先 → 场景兜底 → 一天一件）。

**验收指标**：抽签结果 → 点推荐的转化率；推荐件与被抽中签语的**相关性人工抽检**（≥ 8/10 合理）。

### 目标 2 · 让数字祈福墙成为**黑马景观的数字延伸**

**要做成的样子**：顾客站在黑马前扫码，看到的不是一个通用小程序页面，
而是**这匹马的另一个形态** —— 同一个词（马上有）、同一套纸/铜质感、同一句铜牌文案。

**验收指标**：扫码到页面可交互 ≤ 3 秒；首屏能认出"这是黑马那面墙"（用户测试/口头确认）。

### 目标 3 · 成为**注册转化钩子**：一键成为会员 + 领新会员礼券

**要做成的样子**（原文）：顾客看到黑马会驻足停留 → 参加数字祈福墙 → **一键转化成会员并得到新会员礼券**
→ 用于转化成交 → **减轻收银台引导注册领券的压力**。

**关键点：这个钩子的价值不是注册数，是"把收银台的动作搬到顾客自己的手机上、并提前到成交之前"。**
所以它必须满足两条：① 注册发生在**顾客已经产生"不想丢"的东西之后**（不是一进页就弹）；
② 注册完成后**券立刻可用且有明确的下一步**（去用掉它，而不是"注册成功"）。

**已建的机制**：H1 注册钩子（`ritualGateProgress` / `shouldOfferRitualGate`：**有进展才谈注册**，
不打断"一进页就弹"）；注册即建档并发放新会员礼包（`manageWelcomeGift` +
`upsertUserProfile`：券 5 元/满 49、10 元/满 99、30 元/满 299，90 天）。

**验收指标（这是本 PRD 最重要的三行）**：
1. 扫码进入 → 7 日内注册转化率；
2. **收银台引导注册的次数下降**（这是产品负责人给的原始痛点，必须能证明它被减轻了）；
3. 注册当日 / 7 日内用券率。

## 4. 产品结构（页面顺序 = 转化顺序）

```
① 页头（黑马的数字牌匾：马上有 + 铜牌短句）      ← 目标 2：认出这是黑马那面墙
② 弹幕墙（别人的心愿在流动）                        ← 社会证明：这里有人在写
③ 发送条（写我的心愿，紧贴墙下）                    ← 主转化动作（内容）
④ 点灯 / 木鱼（零门槛仪式）                          ← 目标 3 的"进展"来源（H1 钩子的燃料）
⑤ 今天的玩法（抽一句 → 结果 → 写成心愿）            ← 目标 1 的入口（玄学 → 推荐）
⑥ 灵感词 / 还可写几条                                 ← 降低"不知道写什么"的摩擦
```

**动线唯一**：抽签 → 结果 → **写成心愿** → 上墙。推荐挂在"结果"这一步（而非首页角落），
因为那是用户情绪最高、最愿意多看一眼商品的一刻。

## 5. 目标 1 的实现口径（玄学 ↔ 推荐）

| 层 | 口径 | 不可越界的事 |
|---|---|---|
| 标签 | 6 个受控标签，一处定义四处同源 | 不得在页面里写死标签名/文案 |
| 命中 | **显式 `blessTags` 优先**；存量商品用 `giftScenes` 场景兜底 | 场景兜底是补丁，不得反客为主（2026-09-20 已修） |
| 排序 | 显式命中 → 同品类 → 销量 → 较新 → 价格适中 | 不得引入随机（同一天同一标签结果必须一致） |
| 变化 | 从排序前 5 件里**按天轮换** | "一天一件"不许退化成"永远同一件"（2026-09-20 已修） |
| 兜底 | **没有命中就返回空**（不推热门） | 推荐与标签脱钩 = 乱推，比不推更糟 |
| 文案 | 「偏「X」· 为你配一件」 | 不许编社会证明（如"同好也在看"——系统里没有这个数据） |

**已知数据问题（非代码）**：入库商品的 `blessTags` 质量决定推荐质量。
真实案例：求缘位曾推出「屏开锦程（孔雀）」（语义是前程/锦绣）。若它是**显式**打了求缘标签，
那是**数据要改**，不是代码要改。

## 6. 目标 3 的实现口径（注册转化）

**触发时机（硬性）**：只在用户**已经有点灯/木鱼等连续进展**、且**这些记录只存在本机（换机就丢）**时，
才谈注册。文案必须说**用户失去了什么**，而不是"注册送券"。（现口径见 `ritualGateProgress`。）

**注册后必须立刻发生三件事**（缺一条这个钩子就白做）：
1. 把已有的进展**存上云**（"你的记录不会丢了"——这是用户能感知的回报）；
2. 新会员礼券**直接进"我的券包"**并可见；
3. 给一个明确的下一步按钮（**去用掉这张券**：去逛 / 去购物车），而不是"注册成功"就结束。

**现有实现与缺口**：①③已建（H1 落库需部署 `wishRitualProfile` + 集合 `wish_ritual_profiles`）；
②已建（`manageWelcomeGift`）；**"给下一步"这一步目前是弱的**（注册成功即结束）→ 见 §9 待办。

## 7. 指标（北极星 + 漏斗 + 护栏）

- **北极星**：**扫码 → 成交**（不是注册数，也不是上墙条数）。
- 漏斗：扫码进页 → 完成一个仪式动作（点灯/木鱼） → 写一条心愿 → 抽一次玩法 → 点推荐 → 注册 → 用券成交。
- 护栏（不许为了漏斗数字牺牲）：
  - 不许一进页就弹注册（打断"驻足"这个动作本身）；
  - 不许编造社会证明/运势承诺（合规口径："文化娱乐向、不涉命理改运"，与 `utils/ritualFeedback.js` 同源）；
  - 推荐失败**不得阻断**玩法（推荐是加分项，不是前置）。

### 7.1 埋点审计（2026-09-20，逐事件核对）

**结论：漏斗可测。** 已在册的事件（`utils/analytics/eventSchema.js`，双端镜像由 `check:analytics-schema` 守）：

| 漏斗步骤 | 事件 | 备注 |
|---|---|---|
| 扫码进页 | `wish_wall_enter`（targetType=`from`） | `entryFrom` 来自入口参数 / 场景值。⚠️ **要按门店归因，码里必须带门店参数**（见 §9-6） |
| 仪式动作 | `wish_wall_lamp` | 点灯 ✓ |
| 写心愿 | `wish_wall_post`（targetId=`ok`） | ✓ |
| 抽玩法 | `wish_wall_play`（`ok` / `to_wish` / `to_product` / `need_profile` / `go_profile`） | ✓ 步骤齐全 |
| 点推荐 | `wish_wall_reco`（targetType=`tap`） | ✓ |
| 注册 | `wish_wall_register_gate`（`show`/`go_register`/`dismiss`/`fail_*`/`resume_success`） | ✓ 完整漏斗；H1 另走 `wish_ritual_gate` |

**⚠️ 一条"看起来是缺口、其实不能补"的事（写在这里防止下一个开发者重犯）**：
**木鱼刻意没有逐次埋点**，而且有守卫守着 —— `onMuyuTap` 体内**一次云端写/上报都不许有**
（写放大防护：木鱼可连点，见 `test:wish-wall` 写放大一节与注入 `cert-writes-per-tap`）；
它的计数通过 H1「连续记录云保存」在**离开页面时**上报一次（注册用户）。
所以：**不要为了"补全漏斗"往 `onMuyuTap` 里加 `trackBehavior`** —— 那会同时破坏一条刻意设计与一条守卫。
仪表盘里的"参与度"代理指标是 `wish_wall_lamp + wish_wall_play + wish_wall_sound`（不含木鱼），这是**口径**，不是遗漏。
