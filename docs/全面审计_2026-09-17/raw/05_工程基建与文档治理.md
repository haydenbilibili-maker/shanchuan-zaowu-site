## 3. 详细发现

### 3.1 CI 与守卫的落差（P0-1）

- **现象**：仓库有 60 个 npm 守卫入口、18 条 `check:admin` 链、7 类链外守卫，但 `.github/workflows/deploy-pages.yml` 只跑 `npm ci` + `npm run build`。
- **证据**：`.github/workflows/deploy-pages.yml:34-38`；实测 `grep` 全文件仅 1 处 `npm run`，即 `npm run build`。触发条件 `:3-6` 无 `pull_request`。
- **影响**：① 任何守卫回归都无法阻止合并/部署；② 由于没有 PR 触发，**构建失败也只在 main 上事后暴露**（对 Cloudflare Pages 而言就是一次失败部署或线上旧包）；③ 仓库投入大量成本的棘轮守卫（静默吞错、色彩残留、写结果校验、数据源 SSOT）当前的执行者是「人记得跑」。
- **建议**：新增 `ci.yml`（`on: pull_request`）执行 `npm ci` + `check:admin` + `lint:wxml` + `audit:collections:strict`；把 `check:nav-dom` 作为夜间/发版前手动门禁（保留其「需浏览器」属性）。`deploy-pages.yml` 在 `npm run build` 前插入 `npm run check:admin`（约 10s，成本可接受）。

### 3.2 `check:admin` 的 `&&` 链会掩盖失败（P1-2）

- **现象**：18 条以单个 `&&` 串联。
- **证据**：`package.json:73`。本次实测：`npm run check:admin` 在**第 1 条** `check:sfc-dev` 抛 `ERR_MODULE_NOT_FOUND`（`:34-38` 调用）后整链中止，后 17 条一条都没跑。
- **影响**：一条守卫因任何原因（环境、依赖、误报）失败时，其余守卫连带失效，且日志只见第一条；「10s 跑完 18 条」的前提是第一条永远绿。
- **建议**：改为串行执行、**汇总全部退出码**（`for`+`fail=1`，末尾统一 exit），或引入 `npm-run-all`/自写 runner 输出「通过 n / 失败 m」表。
