## 0. 一句话结论

现有两个钩子之所以成立，是因为它们**都在用户已经拿到价值、只差「把价值存下来」的那一步才要身份**，并且在注册成功后**自动把被打断的动作续上**。
所以新钩子的正确做法不是「再加一个注册弹窗」，而是**先造一个值得被存下来的东西，再在「存下来」这一步接门禁**。
按这个模板筛出的 7 个候选里，**今夜就能做完且不需要任何产品口径的是 H1「灯不断」**（它直接补一个已被代码证实的资产缺口），
**H3「功德证」可与它共用同一个云函数一次做完**。

### 1.5 现有钩子的**通用形状**（后面每个新钩子都套这个模板）

> **一句话形状：先给完整价值 → 只在「这份价值要被存下 / 被认领」的那一步要身份 → 注册失败就放弃这个动作、绝不阻断页面 → 注册成功自动把刚才被打断的那个动作原样续上 → 两个端都登记漏斗。**

拆成 6 步可执行模板：

| # | 步骤 | 现有实现锚点 | 硬约束（踩过坑的） |
|---|---|---|---|
| ① | **先给价值**：被门禁的东西必须是用户已经看到 / 已经拿到的 | 鉴定结果**已渲染**才弹（`identify/result/index.js:466-467`）；祈福墙浏览与仪式免费（`wish-wall/index.js:941-942`） | 不做「内容门禁」式遮罩 → 制造「看不到」差评 |
| ② | **门禁点 = 落库点**：只拦「写入账号」的那一个动作 | 保存图鉴 / 看结果 / 落愿 | **只拦这一个动作**，页面其余部分照常可用 |
| ③ | **意图先存本地、不丢** | `_pendingWish`（`wish-wall/index.js:948`）、`peekOnboardingReturn()` 回流意图（`identify/result/index.js:451`） | 关弹窗只丢「待发」、草稿保留（`wish-wall/index.js:1053-1056`） |
| ④ | **注册后自动续上** | `_resumeAfterRegister` 跳过门禁再发（`wish-wall/index.js:944-946,1048-1050`）；`pendingResume` 才自动续写（`identify/result/index.js:555-559,569`） | **续发路径必须自己跳过门禁**，否则会话未刷新 → 死循环 |
| ⑤ | **fail-open + 只弹一次** | 会话判定失败当已注册（`wish-wall/index.js:1017-1030`）；`_resultGateShown` 每实例一次（`identify/result/index.js:473-475`） | 宁可少一次曝光，不废一个功能 |
| ⑥ | **漏斗两端登记 + 看板分桶** | `analyticsSchema.js` / `eventSchema.js` 双端 + `admin/src/utils/analyticsSchema.js:211-263` 的 `FUNNELS` + `cloudfunctions/getAnalyticsDashboard/index.js:512-545` 的 `gateBlock` | ⚠️ 看板是**逐 action/step 硬编码计数**（`:515`、`:527-531`），新钩子要在那里补分支，否则「报表里没有这个钩子」 |

**推论（本方案的筛选判据）**：一个候选要算「真钩子」，必须能同时回答
**(a) 用户已经拿到手的价值是什么？(b) 它在哪一步需要账号？(c) 注册成功后自动续的是什么？**
答不上任意一条的，就是「点子」不是「钩子」。

## 3. 候选钩子清单（7 个）

> 命名/开关一律照 `showXxx`。**每个候选的「实现代价」口径**：小 = ≤1 个页面 + 复用现成组件，当夜可完；中 = 需新增 1 个云函数 action 或 1 个新集合 + 两端埋点；大 = 需新集合 + 新治理面 + 不可离线验证的部分（真机 / canvas / 模板配置）。
> 所有「需要产品口径的地方」**一律写出问题本身，不替产品选**。

### H1 · 「灯不断」—— 换手机也记得我点了多少天

- **一句话（用户视角）**：我连着点了 12 天灯，换手机之后它还在。
- **主目标**：**留存**（次：注册）
- **机制（价值交换）**：用户得到 —— 连续点灯天数与灯位层级**跨端不丢**（现在会丢，见 §2.1）、能回看自己的点灯记录；
  我们得到 —— 一个**必须注册才能领**的资产，并且注册后「回来点灯」有了累积成本（迁移成本 = 留存）。
- **落在哪个入口**：`subpackages/feature/wish-wall/index` 的点灯卡片（`index.wxml:146-193` 区）内的次级入口「我的点灯记录」。
  **建议开关名**：`showWishLampRecord`（缺字段默认 **关**，理由同 `showMaShangYou` `contentDisplayFlags.js:49`：新能力由超管显式开启）。
- **复用哪些既有件**：
  - 注册门禁组件（`components/RegisterAuthDialog`，页面已登记：`wish-wall/index.json`）；
  - 门禁形状照抄 **祈福墙落愿那一条**（`wish-wall/index.js:941-952` + `:1034-1051`），包括 `_pendingWish` 式的意图暂存与 `_resumeAfterRegister` 式跳过；
  - 漏斗双端登记（`miniprogram/utils/analytics/eventSchema.js` + `admin/src/utils/analyticsSchema.js` 的 `EVENTS` 与 `FUNNELS`）+ 看板补 `gateBlock` 分支（`cloudfunctions/getAnalyticsDashboard/index.js:512-545`）；
  - 云函数 `manageWishWall`（已是祈福墙的 owner 函数，`COLLECTION = 'wish_wall_messages'` `:50`），**建议新增 action 而非新函数**。
- **需要产品口径的地方**（**卡在这里就必须停**）：
  1. **是否允许把点灯记录落库**？`utils/wishRitual.js:9-12` 当初明确不落库的原因（多一张表 / 多一套权限与治理面 / 与「不接 UGC 审核」口径冲突）**是否仍然成立**？
     本方案的论据是「点灯记录是计数与日期、无 UGC 文本、无内容审核面」，但**这是边界外推，只有产品能拍**。
  2. 记录页面**展示到什么程度**？（只显示连续天数与灯位 / 显示最近 30 天日历 / 显示「累计点灯 N 天」）
  3. 门禁触发**门槛**：无条件弹出 vs 连续 ≥3 天才给入口（后者与 `config/easterEggs.js:173` 的 `minStreak: 3` 对齐，但**会改变彩蛋的稀缺感**，需产品确认不要冲突）。
  4. **旧的本地数据要不要在首次登录时上传**（迁移）？涉及「同一台设备多人登录」的归属判定（本地存储无 openid）。
- **实现代价**：**中**。大在两点：① 新增云集合或 `manageWishWall` 新 action 的**表结构 + 权限规则**（`cloudbase/rules/` 与 `cloudbase/schema/` 需同步，见 `AGENTS.md` 三处同步纪律）；② **没有可离线验证的历史数据**，真机迁移路径（清缓存后首次注册）只能真机走查。
- **怎么证明有效**：
  - 漏斗 action：`wish_lamp_record_gate`，steps = `show` / `go_register` / `dismiss` / `fail_*` / `resume_success`（与 `wish_wall_register_gate` 同构）；
  - 观察指标：**门禁 go_register 率**、`resume_success / show`、以及注册后 **7 日内第二次点灯率**（对照未触发门禁的同期用户）；
  - 前置事实指标：`wish_wall_lamp`（已有，`analyticsSchema.js:182`）在记录功能上线后的**人均点灯天数变化**。
- **风险**：
  - **作弊**：连续天数可被「改手机时间」伪造（`wishWall.js` 的 `lampStreak` 只信本地日期键）；落库后**必须在服务端按服务器日期判连续**，否则就是可刷的假资产。
  - **骚扰**：点灯是低门槛高频动作，门禁若在**第一次**点灯就弹，会把最大的免费入口堵掉 —— 与 `wishRitual.js:4-7` 的设计初衷（点灯是「零门槛的仪式入口」）直接冲突。
  - **合规**：不涉及隐私字段；但记录页若展示具体日期，等于形成一份用户行为时间线，需确认与隐私政策表述一致。
  - **抢注意力**：与既有落愿门禁在**同一页**，用户可能连续遇到两个注册弹窗 → 必须做**互斥**（同一会话内已有门禁曝光过就不再弹）。

### H2 · 「功德证」—— 敲够一百下，给你一张证

- **一句话（用户视角）**：我敲木鱼的功德攒到 100 了，这张证书能存下来。
- **主目标**：**留存**（次：注册）
- **机制（价值交换）**：用户得到 —— 一个**可保管、可回看**的功德凭据（现只显示「功德 N」在墙上回声里，见 `utils/ritualFeedback.js:70-72`）；
  我们得到 —— 注册（存证需身份）+ 一个天然的低成本分享物（证书图）。
- **落在哪个入口**：祈福墙页木鱼按钮附近（`index.js:505-516 onMuyuTap`）在里程点（建议 100 / 500 / 1000）弹出「领证」次级入口。
  **建议开关名**：`showMuyuCertificate`（缺字段默认 **关**）。
- **复用哪些既有件**：注册门禁组件；`wishRitual` 的本地计数（`:144-168`）；**与 H1 共用同一个云函数 action / 同一份持久化**（这是本方案推荐「H1+H3 一次做完」的直接原因）；
  生成图可比照 `cloudfunctions/generateSharePoster`（返回素材、端上 canvas 合成）与 `utils/giftShareCard.js` 的先例。
- **需要产品口径的地方**：
  1. **分享形态**：会话卡片 vs 生成图 —— **与 W1 是同一个问题，不要另开选项，直接沿用 W1 的结论**（本方案不抢跑）。
  2. 里程点数字（100/500/1000？）与证书上要不要写日期 —— 属于口径，不猜。
  3. 「功德」这个词与 `utils/ritualFeedback.js:1-15` 已定的**文化娱乐向、不涉命理改运**口径是否一致（本方案认为一致，因为是计数凭证而非运势承诺，但**这属于合规文案，需产品确认**）。
- **实现代价**：**中**（若 H1 先做，本项可降为**小**：多一个 action + 一张端上 canvas 组件）。「大」的部分与 H1 相同（表结构 / 权限规则），另加**「生成图是静态检查盲区、字宽只能真机验」**（本仓已被此坑过 3 次，见 `AGENTS.md`）。
- **怎么证明有效**：
  - 漏斗 action：`muyu_cert_gate`；steps 同 H1；
  - 观察指标：**证书领取数**、领证后 7 日回访率；**分享回流**用已有的 `identify_share_link` 式渠道参数模式（`analyticsSchema.js:139`）；
  - 注意：**不做分享奖励**（`cloudfunctions/earnPoints/index.js:63-67` 合规硬闸），只做分享入口。
- **风险**：
  - **作弊**：木鱼可连点（`index.js:505-516` 无节流、无上限），云端计数的写入频率会是**写放大**（这正是 `ritualFeedback.js` 头注第 1 条要避免的）→ **必须只在里程点/退出时上报，不能每敲一下写一次**。
  - **骚扰**：连点场景下弹门禁极烦 —— 与 H1 相同，靠门槛 + 互斥控制。
  - **合规**：见上第 3 条。
  - **抢注意力**：木鱼与点灯同在仪式区，两个证书/记录入口要避免视觉并列（否则仪式区变成功能区）。

### H3 · 「还愿」—— 我的心愿，回来给它一个结果

- **一句话（用户视角）**：年初挂上墙的那句「今年要换工作」，成了 —— 我回来把它标成还愿。
- **主目标**：**留存**（次：注册；对成交只有间接口径）
- **机制（价值交换）**：用户得到 —— 自己的愿签有「下落」（现只有「挂上墙」，之后没有任何回访理由，见 `wish-wall/index.js:965-999` 落愿即终点）；
  我们得到 —— 一个**天然的回访触发**，且回访必然带着身份（自己的愿签要挂在自己名下，理由与 `:941-944` 现成的同一条）。
- **落在哪个入口**：愿签卡的次级操作（`index.wxml:442` 的分享入口旁）。
  **建议开关名**：`showWishFulfill`（缺字段默认 **关**）。
- **复用哪些既有件**：**不需要新集合** —— `wish_wall_messages` 加 `fulfilledAt` / `fulfilledNote` 字段（前提：字段白名单允许，须核对 `manageWishWall` 的字段处理）；
  注册门禁组件与落愿门禁形状；订阅通知通道（H5）作为回访的第二种触达。
- **需要产品口径的地方**：
  1. 「还愿」**在墙上的可见性**：只在本人「我的心愿」里可见，还是墙上愿签打一个「已还愿」标记？（后者进公开内容 = 治理面，且与「馆方徽章已去掉」（`祈福墙_待产品负责人拍板` §3#2）同类问题）
  2. 还愿后愿签**要不要归档**（从墙上撤下）—— 影响墙面内容池与 `list` 分页口径。
  3. 时间口径：多久之后允许标记（防误触 / 防恶作剧）。
- **实现代价**：**中**。「大」在：**已有的愿签是匿名 openid 归属 + 有 `hidden` 治理状态**，加「还愿」状态等于给内容集合加一个**新的状态维度**，会连动管理端列表 / 过滤 / 统计（`manageWishWall` 的 `staffList` / `staffSetStatus` / `staffStats`）。
- **怎么证明有效**：
  - 漏斗 action：`wish_fulfill_gate` + 行为 `wish_fulfilled`（targetType = `wish`）；
  - 观察指标：**还愿率**（= 还愿数 / 30 天前落愿数）、还愿用户的 **30 日回访率**、还愿后是否发生成交（与 `order_submit` 同期对照）。
- **风险**：
  - **作弊**：还愿本身无利益 → 动机弱，但若未来把它接任何奖励，会变成刷单式刷「还愿」。
  - **骚扰**：还愿提醒若走订阅消息，属**主动触达**，模板与授权口径要产品定（见 H5 同一卡点）。
  - **合规**：还愿文案属 UGC（若允许写还愿感言）→ **会把祈福墙推回「接 UGC 审核」的口径**，与 `manageWishWall` 头注的现行口径冲突。**建议首版只做「标记」不做「感言」**（本方案倾向，但需产品确认）。
  - **抢注意力**：与 H1 / H2 同在祈福墙，三个新入口会让这一页从「仪式页」变成「任务页」→ **建议同页只放一个**（见 §4 排序依据第 4 条）。

### H4 · 「社区发言要身份」—— 我想发帖，先认个人

- **一句话（用户视角）**：我想把这张图发进山海社区，需要先注册。
- **主目标**：**注册**（次：留存）
- **机制（价值交换）**：用户得到 —— 发言被记录在自己名下、以后能找回自己的帖子；
  我们得到 —— 在**内容生产**这个高价值动作上把游客转成账号（发帖是社区唯一能自我增长的燃料）。
- **落在哪个入口**：`subpackages/feature/community` 的**发布**动作（不是浏览）。
  **建议开关名**：`showCommunityPublishGate`（缺字段默认 **关** —— 与 `showUserCommunity` 默认关 `contentDisplayFlags.js:24` 保持一致，避免「社区入口关着、门禁开着」的矛盾状态）。
- **复用哪些既有件**：注册门禁组件（社区页需自行登记 `register-auth-dialog`，可照抄 `wish-wall/index.json`）；
  落愿门禁的**全部形状**（意图暂存 + 自动续发 + fail-open）；社区发布漏斗已有事件 `community_publish_enter` / `community_publish_success`（`analyticsSchema.js:175-177`）作为前置指标。
- **需要产品口径的地方**：
  1. 社区**当前是否对外可见**？`showUserCommunity` 默认关（`:24`），若社区还没上线，本钩子应**延后**而不是先做门禁。
  2. 发帖的**UGC 审核口径**（社区内容是否已接审核）—— 决定本钩子是「顺手加一个门禁」还是「要连带治理面」。
- **实现代价**：**小**（若社区页已具备会话判定与会话刷新调用，则纯粹是照抄祈福墙的 handler 三件套 + 一个开关）。
- **怎么证明有效**：
  - 漏斗 action：`community_publish_gate`，steps 同构；
  - 观察指标：**发布门禁的 resume_success 率**（注册后是否真的把帖子发出去了 —— 这是「自动续发」有没有生效的唯一证据）、发布用户 7 日留存。
- **风险**：
  - **作弊**：发帖 → 注册 的路径可能被用来「注册小号发广告」，门禁不产生作弊面，但**注册后自动发布**会放大垃圾内容 → 需与社区现有风控一起看。
  - **骚扰**：与祈福墙同构，风险可控（只拦发布）。
  - **抢注意力**：与祈福墙门禁是**两套几乎一样的代码**，长期应抽公共 mixin/behavior，否则两处漂移（本仓的经典坑：两份 `fulfillOrder.js` 漂移，见 `祈福墙_待产品负责人拍板` 附录 A Q4）。

### H5 · 「回来看看」—— 该回来的时候，有人喊你一声

- **一句话（用户视角）**：我的祈福灯好久没点了 / 我收的那件标本快满一岁了，小程序提醒我回来看一眼。
- **主目标**：**留存**
- **机制（价值交换）**：用户得到 —— 不错过自己的纪念日与连续记录；我们得到 —— **一次主动召回**，把沉默用户拉回来（召回是留存杠杆最大的一格）。
- **落在哪个入口**：无需新页面 —— 触达走通知，落地页 = 祈福墙 / 我的养护（`subpackages/feature/care`）。
  **建议开关名**：`showRitualRecall`（缺字段默认 **关**）。
- **复用哪些既有件**：
  - **定时调度已有实现**：`cloudfunctions/sendCareReminder`（`config.json` timer `0 0 10 * * * *`；队列集合 `care_reminder_queue`、`type:'care_tip'`、`scheduleReminder()` `:95-158`）→ **照此扩展一个 `type`，不必另造调度**；
  - 订阅通道 `dispatchMessage` / `payCallback` 两条链路（`docs/服务通知模板清单与注入步骤_2026-09-17.md` §4）；
  - 站内消息兜底：`subpackages/extra/user/messages`（通道不可用时的降级）；
  - 纪念日数据：`cloudfunctions/manageGift/index.js:2044` 已有 `anniversary: { requireYear: true }` 的**日期类型与年月日解析**（`parseMonthDay` `:2090+`）可复用其口径。
- **需要产品口径的地方**：
  1. **发什么**（点灯中断提醒 / 收藏纪念日 / 节气）与**频率上限**（这是「不打扰」的红线，必须产品定一个数字）。
  2. 召回文案的**文化娱乐向**边界（与玩法同一套禁词口径）。
  3. 是否接受**用订阅消息主动触达**（见下「卡点」）。
- **实现代价**：**中**；**但被一个外部人工步骤硬卡住** ——
  **【代码事实】**`docs/服务通知模板清单与注入步骤_2026-09-17.md` §0 明确：**10 个模板 ID 线上一个都没配**，服务通知**目前都不会真的发出去**（不报错、不阻断，只是静默跳过）。
  → **本钩子的完整形态在模板配好前不可能上线**。可先做的**降级版 MVP**：只用**站内消息**（`subpackages/extra/user/messages`）+ 定时队列，先跑通「该回来时会有一条站内信」，把订阅消息作为第二阶段。
- **怎么证明有效**：
  - 行为 action：`ritual_recall_sent`（targetType = 场景 key）+ `ritual_recall_open`（落地页带参）；
  - 观察指标：**召回后 7 日回访率**、召回带来的 `wish_wall_lamp` / `order_submit`；**必须同时看退订/关闭通知率**（骚扰的负向指标）。
- **风险**：
  - **骚扰（本项最大风险）**：主动触达是本方案里唯一可能**净负面**的钩子；频率上限没定之前不应上线。
  - **合规**：订阅消息必须**用户主动授权**（一次性订阅），不能把授权塞进无意识点击；`pages/user/index.js:2911-2913` 已有一条同源纪律注释（订阅授权必须在用户点击入口时发起，不可在 onShow 异步回调里调）。
  - **抢注意力**：召回与节日营销短信式触达不同，文案要克制（与 `wishRitual.js:24-32` 的灯语语气一致）。

### H6 · 「同好这件」—— 从「你在看」到「有人也在看」

- **一句话（用户视角）**：这件藏品，最近有多少人和我一样在看。
- **主目标**：**成交**（次：留存）
- **机制（价值交换）**：用户得到 —— 一个**真实的**同类兴趣信号（不是编出来的社会证明）；我们得到 —— 商详页的成交推力。
- **落在哪个入口**：商详页（`subpackages/feature/detail`）。
  **建议开关名**：`showProductInterestHint`（缺字段默认 **关** —— 社会证明类展示必须可一键下线）。
- **复用哪些既有件**：已有真实行为数据 `product_favorite`（收藏）/ `product_wishlist`（想要）/ `product_stats`（`utils/productStats.js`）/ `wish_wall_reco`（祈运弱推 `analyticsSchema.js:185`）；
  门店侧 `store_zone_*` 系列（`:75-78`）作为「曝光」指标的先例。
- **需要产品口径的地方**（**这条几乎全是口径**）：
  1. **展示什么数字**：收藏数 / 想要数 / 加购数？**必须真实可算**，且要定「低于多少不展示」（避免「3 人想要」的反向劝退）。
  2. 与 `docs/商品销量展示口径_2026-09-18.md` 的关系 —— **该文档已定义销量展示口径，本钩子必须与它对齐而不是另立一套**（本方案未改它，也未复验它，见 §7）。

  - **作弊**：无（收集靠真实鉴定记录）。
  - **骚扰**：无主动触达。
  - **抢注意力**：与既有「山海图鉴」目标一致，属于**存量能力的显性化**，不是新战场 —— 这也是它代价最低的原因。

### 4.3 推荐先做：**H1「灯不断」**，并**同批带上 H2「功德证」**

**为什么是 H1（依据来自 §4.1 的四条，而不是「重要」）**：

1. **它的缺口是本方案里唯一被代码证实、且不需要假设用户偏好的**（§2.1：streak/muyu 云侧 0 命中、`KEEP_DAYS = 30` 会裁旧记录、UI 已展示累积天数与称号）。
   别的候选（H6 数字怎么展示、H7 套系怎么定义、H3 还愿在哪可见）都先要产品给一个「要什么」，H1 要的只是「允不允许」。
2. **H1 是 H2、H3、H5 的前置**：H1 建的那套「点灯记录持久化 + 记录页 + 门禁」一旦落地，
   H2 只是多一个里程点动作、H3 只是多一个状态字段、H5 只是多一个定时场景 —— **一次表结构投入解锁三个候选**。
3. **它可以用开关灰度、且不新增页面**：入口挂在祈福墙页内，`showWishLampRecord` 默认关（与 `showMaShangYou` 默认关同一策略，`contentDisplayFlags.js:49`），超管随时一键下线。

**但必须先解决 H1 的第 1 条口径**（「是否允许把点灯记录落库」）—— 它直接推翻 `utils/wishRitual.js:9-12` 的现有设计决策，
**这是本方案唯一一条「不拍板就不能动手」的硬口径**；其余 3 条口径都可以先用最保守的实现（只显示连续天数、无日历、无迁移）跑起来。

**如果产品暂时不想碰那条硬口径**，则**改推 H2「功德证」单独先行**：它 0 条口径、门槛（里程点）纯前瞻、且同样用到本地计数 —— 但它需要**把木鱼计数落库**才能出证，

**建议的开工包（一次做完，不分开）**：
1. 云函数 `manageWishWall` 加一组 `ritual` action（点灯记录 upsert + 木鱼计数 upsert，**只在里程点/退出时写，不逐次写** —— 见 H2 风险）；

3. 小程序端：记录入口 + 证书入口（复用 `RegisterAuthDialog`）+ 双端埋点登记 + 看板 `gateBlock` 分支；
4. 开关 `showWishLampRecord` / `showMuyuCertificate` 的**五处**改动（§1.3）；
5. 守卫：`test:wish-wall` 补断言 + `--selftest` 注入（`AGENTS.md` 纪律：每条新判据都要能证明自己会失败）。

> 写清否掉的**理由**，比多列点子有价值。

### N1 · 否决「分享得积分 / 分享解锁内容」类钩子

- **理由（代码事实，不是判断）**：`miniprogram/cloudfunctions/earnPoints/index.js:63-67` 已经把这条路**在服务端写死拒绝**：
  ```js
  // 合规硬闸：分享奖励属「诱导分享」，无论线上配置如何一律拒绝
  // （微信《小程序平台运营规范》禁止以利益诱导分享；如需恢复必须先改为非诱导形态）
  ```

  任何「分享 → 奖励」的新钩子都会撞上这条硬闸；要恢复必须先改合规形态，那属于**推翻既有合规决策**，不是创新钩子。

### N2 · 否决「注册即送大额券 / 注册解锁全部内容」类钩子

- **理由**：① 与现有钩子的**价值交换结构相反** —— 现有两个钩子是「先给价值、再要身份」（§1.5 步骤①），
  「注册才解锁」是把价值扣住当人质，会制造「看不到」的差评，而 `identify/result/index.js:466-467` 的注释明确记录了这个教训（「不阻断体验，也不制造『看不到』的差评」）。
  ② 新客礼包口径已有专文（`docs/新客礼包口径变更_99减10券_2026-09-17.md`）且有过**两次发放中断复盘**（`docs/新客礼发放中断_复盘_2026-09-15.md`、`docs/新客礼发放中断_复发_复盘_2026-09-16.md`）——
  在发放链路刚稳定时再加一条「注册即送」的钩子，是往已知的脆弱链路加压。
- **需要先做的**：不是新钩子，而是先确认新客礼发放链路的稳定性（**本方案未验证该链路的当前状态**，见 §7）。

### N3 · 否决「祈福墙玩法结果 → 硬 CTA 成交」类钩子

- **理由（口径已定，不是新判断）**：`docs/需求28_祈福墙_玩法专项规划_2026-09-18.md` §0 已定「玩法结果页先做**弱推**，**不上硬 CTA**，每日免费一次」；

- **替代（已在 H6 / H7 内）**：成交推力放在**商详页与图鉴套系**（用户本来就带着购买意图的页面），不放进仪式页。
