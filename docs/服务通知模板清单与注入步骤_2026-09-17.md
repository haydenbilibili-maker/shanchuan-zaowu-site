## 0. 结论（一句话）

**通道已建成、降级已就绪，但 10 个模板 ID 线上一个都没配** ——
所以今晚所有「服务通知」场景**目前都不会真的发出消息**（不会报错、不会阻断业务，只是静默跳过）。
这 10 个 ID 必须在**微信公众平台**人工创建后注入，是本项唯一的人工卡点。

## 2. 为什么现在不配也安全（已实测的降级行为）

- 模板 ID 为空时**优雅跳过**：`audit:fn-env` 把这类明确归入
  **「B. 可选缺失：订阅消息模板未配置（按设计优雅跳过）」**，不计为硬缺陷；
- `test:pet-artisan` 有一条断言：`未配模板 → TMPL_PENDING（不阻断下单）`；
- `audit:fn-env` 当前结果：**A 区硬缺陷 0** · B 区 4 项（就是本清单的第 7–10 条）· C 区 58 项（`MESSAGE_ADMIN_OPENIDS` 等可选变量）。
  → 也就是说：**没配模板不会让任何业务失败，只是「不通知」。**

## 3. 注入步骤（顺序即依赖）

1. **公众平台** → 功能 → 订阅消息 → 我的模板，按上表逐个申请/选择模板并拿到 `templateId`。
   - 员工侧 6 条建议用「一次性订阅」，在员工进入工作台时请求授权；
   - 顾客侧 4 条建议用「一次性订阅」，在对应动作（下单/收礼/预约直播）时请求授权。
2. **写进云函数环境变量**（注意：**必须选 Merge**）：

   ```bash
   cd miniprogram
   tcb config update fn <函数名> -e cloud1-8gnkty5bfff9f0bf --all
   ```

   ⚠️ 这一步会问 **Override / Merge** —— **必须选 Merge（↓ 再回车）**。
   选 Override 会把该函数**其它环境变量全部清掉**（`MESSAGE_ADMIN_OPENIDS` 等），
   实测踩过一次，靠 `audit:fn-env` 的 A 区告警才发现。
   涉及函数：`dispatchMessage`（1–5）· `payCallback`（6–9）· `manageLiveSession`（10）。

3. **验证**：
   ```bash
   npm run audit:fn-env        # B 区应从 4 项降下来
   npm run check:work-order-notify   # 员工侧场景与模板字段
   npm run test:pet-artisan          # 伴宠场景字段
   ```
4. **真机复验**：订阅授权的弹窗只在**真机**可控，开发者工具不能代替（见发版审计 §3.4）。

## 4. 与 #33 的关系

#33「服务通知场景梳理」的可复用部分是**通道**（上表的 `dispatchMessage` / `payCallback` 两条链路 + 落点守卫），
本清单就是它的场景底稿。要扩到更多场景，只需：
① 在 `workOrderSubscribe.js` 的 `WORK_ORDER_CATEGORIES` 加一条（含 `envKey` / `page` / `logType`）
② 在公众平台加模板并注入 env
③ 跑 `audit:fn-env` 与 `check:work-order-notify`
—— 不需要动客户端。
