## 2. ① 顺手带走一件

### 2.1 档位与排序（纯函数，逐条钉住）

```
档位 1：price ≤ 10      「10 元以下」
档位 2：10 < price ≤ 50 「50 元以下」
（含边界；> 50 不推荐 —— 不硬凑）
排序：① 先档位（¥10 档永远优先于 ¥50 档）② 同档取最便宜 ③ 同价按标题稳定
```

**为什么「同档取最便宜」**：顺手件的本质是「不假思索地拿」，价格越低越不需要犹豫；
**为什么同价要稳定**：否则每次进购物车换一件，看起来像随机抖动。

### 2.2 候选过滤（每条都有理由）

| 规则 | 理由 |
|---|---|
| 排除 `isOffShelf` | 与 C 端列表同口径，不能推荐买不到的东西 |
| 排除 `hasSku: true` | 多规格必须让用户选规格，**不是「一次点按」**；且不带 `skuId` 加车会在购物车里留下无效项（`pages/cart/index.js` 的 skuId 校验） |
| 排除 `stock <= 0` | 售罄不推；但**字段缺失不当售罄**（既有购物车把 NaN/0 视作 99） |
| 排除 `price <= 0` / 无 `_id` | 脏数据不进推荐 |
| 排除已在购物车里的 `productId` | 不推用户已经要买的东西 |
| 内部按 `_id` 去重 | 云端数据可能一条商品多处命中 |

### 2.3 交互

- 位置：**结算栏内部**（`pages/cart/index.wxml` 的 `.checkout-bar` 里，`.bar-main` 之前）——
  随结算栏固定在底部，不随清单滚走（超市吧台位就是要「结账时就在眼前」）。
- 一次点按「带走」→ `toggleCollection` → 重载购物车 → 顺手件**顺位换成下一件**（可以连续带）。
- 可关闭（×）：本次会话内不再出现；下次进购物车重新按优先级挑。

## 3. ②③ 免邮凑单

```
未达门槛：再买 ¥X 免运费  + 进度轨（合计/门槛）  + 【凑单件】加购 →
已包邮  ：回落既有规则文案（两行不重复出现）
活动期（全场免邮）：显示活动 label，不再劝凑单
已选免邮券：显示「已用免邮券 · 本单免运费」，不再劝凑单
```

**凑单件的挑选规则**：只在 `缺口 ≤ price ≤ 缺口 + 运费` 区间内挑，取最便宜的一件。

- 为什么有**下界**：价格低于缺口，加了也到不了免邮（凑单失败）。
- 为什么有**上界**：`缺口 + 运费` = 「加它比直接付运费多花的钱不超过运费本身」。
  例：缺口 ¥8、运费 ¥18 → 加一件 ¥9.9 是明显划算的（多花 ¥1.9 换一件藏品 + 免 ¥18 运费）；
  缺口 ¥480、运费 ¥18 时区间是 [480, 498]，低价池里没有 → **不硬推**（推一件 ¥50 的毫无意义）。
- **已用免邮券时不再推凑单**：券的节省额就是运费，两个提示同屏会互相打架
  （这一条是写守卫时才发现的：原先 `reached` 判据冗余，且完全没考虑券）。

## 5.1 真机反馈修复：未达门槛时**没有**出现「再买 ¥X 免运费」+ 进度轨（2026-09-18 当晚）

**反馈**：在开发者工具真机上，不满包邮门槛时免邮凑单行**整块不出现**。

### 根因（实测，不是猜）

`computeFreeShipping` 原先把 `fee <= 0` 也当成「已免邮」。而 `calcShippingFee` 在**没有任何勾选**时
（`goodsAmount = 0`）同样返回 0 —— 于是「刚进购物车」这一状态被误判成已包邮，整块隐藏。

而**「刚进购物车」恰恰是最常见的第一眼状态**：`cloudfunctions/getCartList/index.js:137`
对所有条目写 `row.selected = false`（`_loadCollectionClient` 同样 `item.selected = false`），
所以进页面时合计是 **¥0.00**、结算按钮是禁用态。

### 修法（判据收紧到「真的不用付运费」）

| 情形 | 旧判据 | 新判据 |
|---|---|---|
| 全场免邮活动 | 显示「活动 label」 | 同左（`reached`） |
| 已选免邮券 | 显示「已用免邮券」 | 同左（`reached`） |
| 规则本身不收运费（`shippingFee = 0`） | 隐藏 | 隐藏（`reached`） |
| **已勾选且合计 ≥ 门槛** | 隐藏 | 隐藏（`reached`） |
| **未勾选任何商品（合计 ¥0）** | ❌ **隐藏** | ✅ **显示**进度与缺口 |
| 已勾选但未达门槛 | 显示 | 显示 |

另外两处配套：
- **文案分档**：未勾选时不说「再买」（没有可"再"的基数），改为中性的「藏品满 ¥500 免运费」，进度 0%；
  已勾选才说「再买 ¥x 免运费」。
- **fail-safe**：`shippingFee`/`flatFee` 两个字段都缺失（异常配置）时按**要收运费**处理 ——
  宁可多提示一次，也不要把可能省下的运费吞掉。

### 守卫为什么会漏（比 bug 本身更值得记）

原守卫**没有覆盖「未勾选 / 合计 ¥0」这一状态** —— 所有用例都至少给了 `goodsAmount > 0`，
于是 98 项断言全绿，真机仍是错的。这正是错题本 E8「只看静态分析就认为对了」的典型形态。

已补：
- 断言：`未勾选（合计 ¥0）仍要显示免邮行` / `缺口 = 门槛` / `进度 0` / `当前运费仍报 ¥18 而不是 ¥0` /
  `文案改中性` / `规则不收运费时隐藏` / `运费字段缺失时 fail-safe`；
- 注入 `gap-hides-when-nothing-selected`（把旧判据 `|| fee <= 0` 写回去 **必须被检出**）——
  这条注入就是「这个 bug 若重来，守卫会不会红」的证明。

**状态矩阵（实跑 `computeFreeShipping`，非推演）**：

```
未选任何商品（合计 0）     reached=false gap=500  fee=18  → 显示 ✅
已选 ¥300 标本           reached=false gap=200  fee=18  → 显示 ✅
已选 ¥499 标本           reached=false gap=1    fee=18  → 显示 ✅
已选 ¥150 纯饰品          reached=false gap=50   fee=18  → 显示 ✅
已选 ¥520 标本（已达标）    reached=true  gap=0    fee=0   → 隐藏（已包邮，回落规则文案）
已选免邮券 ¥300          reached=true                 → 隐藏（已用免邮券 · 本单免运费）
云端开启全场免邮 ¥300      reached=true                 → 隐藏（当前全场免邮）
```

真图：`docs/assets/结账台_免邮凑单_未勾选态_预览_2026-09-18.png`（合计 ¥0 + 空进度轨 + 中性文案）。
