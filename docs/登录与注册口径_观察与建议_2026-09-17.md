# 小程序「登录 vs 注册」口径：观察与建议（2026-09-17）

> 结论先说：**并不是完全没区分** —— 页面里已经有 `phoneOnly`（绑定态）/ `giftClaimed`（已领）/ 已注册静默返回；
> 但「新客 / 老客」这个事实**服务端知道却不回传**，于是文案与反馈只能靠猜；
> 且**没有「登录」这个显式动作**：同一微信号靠 openid 隐式登录没问题，一旦同一手机号换了微信号就硬失败。

## 一、微信侧的客观事实（决定了方案边界）

小程序里唯一的身份入口是 `<button open-type="getPhoneNumber">` → 云函数 `authPhone`。
这一个动作在服务端**同时**承担两件事：

- openid 在 `users` 里**没有**记录 → 建号（`registerGiftClaimed: false`，注册）
- openid 在 `users` 里**已有**记录 → 只更新手机号（登录/绑定）

也就是说「登录」与「注册」在协议层就是同一个手势 —— 这不是缺陷，是微信的设计。
**关键推论**：`getPhoneNumber` 返回的号码是**微信实名绑定的号码**，因此它本身就能证明手机号归属
→ 这为「换微信号的人也能登录」提供了安全依据（见 §四 L2）。

## 三、影响（按严重度）

1. **换微信号 = 丢账号**（第 9 条）：同一手机号在另一个微信号上授权 → 直接劝退找专员。
   这是「登录/注册不分」**最实质**的一处 —— 因为系统没有「这是同一个人，让他登录」的路径。
2. **老用户被承诺新客礼**（第 4/5 条）：授权页首屏按注册态渲染，礼包卡与「领取新客礼」文案先出现；
   若用户没等到会话返回就点了授权，感受就是「说好给我券，结果没有」。
3. **完成页措辞与事实不符**（第 6 条）：重新授权的用户会看到「注册完成」+ 空的礼包卡。
4. **注册漏斗不可度量**（第 8 条）：无法回答「新客转化率」「登录占比」，改动也没有回归依据。
5. 合规/信任：授权即建号这一点**已披露**（「未注册将同步建档」）✓，但缺少「你已有账号，本次仅登录」的正向确认。

## 四、建议（按投入从小到大，可分批独立上线）

### L0 · 表达层：不再让老用户看到「注册」（约半天，零协议改动）
- 注册页首屏用**中性态**（骨架 + 「正在确认账号…」，按钮不可点或点击后立即进入确认中），
  `loadSession()` 后再落到「注册」或「登录」两套文案 —— 消除第 4 条的竞态。
- `COPY_BY_FROM` 的 4 个入口各补一份「登录态」文案（`loginTitle` / `loginDesc` / `loginCta`）：
  登录态用「授权手机号 · 继续」，不出现「注册」「领取新客礼」。
- 完成页按新老分支：新号 →「注册完成，新客礼已放入账户」；老号 →「欢迎回来，手机号已确认」+ 不渲染礼包卡。
- 退出登录后的路径**保持现状**（已经是对的），只在引导语上补一句「重新授权即恢复账号与礼券」。

### L1 · 事实层：把「新客/老客」说出来（约半天，含守卫）
- `authPhone` 返回 **`isNewUser`**（`selfRes.data.length === 0`，成本几乎为零）+ 可选 `existingNickName`（用于「欢迎回来，X」）。
- `getUserSession` 返回 **`isRegistered`**（`users` 有记录即 true）。**明确不要**用 `authState` 当登录态
  —— 它是完善度口径，会把「已注册但资料空」判成 `guest`（这是个现成的坑，值得在文档与守卫里写死）。
- 客户端据此在**授权前**决定渲染哪套文案（`isRegistered ? 登录态 : 注册态`），不再依赖「券是否领过」推断。
- 埋点分开：`auth_register_success` / `auth_login_success`（带 `from`），漏斗即可分开看。

### L2 · 登录兜底：手机号已被别的微信号占用（1–2 天，需产品定义，建议分两期）
**安全前提**：`getPhoneNumber` 的号码来自微信实名绑定 → 能证明「当前微信持有该号码」。
因此「同一手机号换微信号」是可以安全处理的，不该一律劝退。

- **一期（识别 + 人工，低风险，建议先做）**：`authPhone` 在「号码属于其他 openid」时不再只报错，
  而是返回可识别信号（`phoneBoundToOther: true` + 尾号 + 该账号的脱敏昵称），
  前端给出「该手机号已有账号（尾号 1234）。如需在**当前微信**继续使用，请联系专员协助转移」+ 客服入口。
- **二期（自动换绑/合并，需先定规则）**：允许「解绑旧 openid + 绑定到当前 openid」，
  但要先定义**数据归属**：积分 / 成长值 / 礼券（未使用）/ 订单 / 收藏 是否随迁。
  建议默认**只迁账号与未使用资产**，已核销券与历史订单留在原记录（避免对账口径被改写），并留操作留痕（`identityMerges` 集合）。
- 不做：短信验证码登录（小程序内短信成本与到达率都不划算，微信授权已更强）。

### L3 · 不建议做自建账号体系
只有在出现「多端（App/网页）+ 手机号验证码」需求时才值得；当前引入密码/验证码只会增加流失与合规面。

## 五、改完怎么证明（验收口径）

1. **新号路径**：清缓存 → 授权 → 完成页显示「注册完成 + 5 张券」；埋点 `auth_register_success`；库中 `registerGiftClaimed=true`。
2. **老号路径（本机已登录）**：进注册页**首屏不得出现「注册」字样与礼包卡**；完成后显示「欢迎回来」；
   埋点 `auth_login_success`；**券数不变**（幂等）。
3. **退出后路径**：退出 → 「重新进入」（不经过注册页）→ 账号与券恢复；若误入注册页，文案须为登录态。
4. **换微信号路径**（L2 一期后）：另一个微信号授权同一手机号 → 给出「已有账号 + 联系方式」的可识别提示，而不是「请联系专员」四个字。
5. **守卫**：把「老号不得出现注册文案/礼包卡」做成行为断言（本仓惯例：真源码 + 注入回归），
   并把「`authState` 不得用于登录判定」写成源级断言。
