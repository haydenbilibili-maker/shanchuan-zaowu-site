## 1. 问题回顾

山海有信的订单类信件**只写订单号**，用户看不出买的是哪件：

- 多数调用方只传 `productNames`（一串**纯名称**，无规格、无图片）；
- 装裱 / 包装 / 启程三封**只传 `orderNo`**；
- `dispatchMessage` 的 `productLine` 能力（`core.js` 里已有）只有在调用方传 `vars.products` 时才生效，而多数调用方没传；
- 消息文档结构里**根本没有商品字段**，前端无从渲染。

## 3. 三个只在运行时才暴露的坑（本条的真正难点）

### 3.1 内部字段不能随信外泄

`order.products[]` 里除了展示口径，还有：

| 字段 | 为什么不能进私信 |
|---|---|
| `price` | 成交价快照 —— 送礼场景下收礼人能据此推出送礼人花了多少钱 |
| `craftType` | **内部枚举码**（`accessory` / `cloche` / `wing_art`），需要前端 `craftTypeLabel()` 才能显示成中文 |
| `framerName` | 混着 `NATURE` / `Amber Light` 这类品牌与带空格的名字 |
| `tags` / `memberDiscountEnabled` | 内部风控与折扣口径 |

所以**落库前单独裁一遍**，只留 `id / title / image / skuLabel / count`。
守卫用「注入 `price` 必须被检出」证明这条锁是活的。

### 3.2 通知日志行会把商品卡抹掉

`getUserMessages` 会把 `user_messages` 与 `notification_logs` 按事件键合并。日志行**永远没有商品字段**，
而 `normalizeMessage` 会给它补上 `products: []` —— 一个**存在的空数组**。
对象展开 `{...secondary, ...primary}` 中 `[]` 会覆盖掉另一侧真实的卡片。

修复：合并时显式取「有卡的那一侧」。守卫注入 `merge-overwrites-products` 复现该场景（两条同键 `user_messages` 行，一旧一新）。

### 3.3 模板改了不等于线上生效

线上 `message_templates` 已有记录且优先于代码里的 `DEFAULT_TEMPLATES`。
`seedTemplates` 不带 `syncCodes` 时**只跳过**，因此正文文案必须走一次带 `syncCodes` 的 seed。
（**商品卡不受此影响** —— 它由消息文档驱动，部署云函数后立即生效。）

## 4. 展示粒度落点

```
信件详情页
┌─────────────────────────────┐
│ 信中藏品                2 项 │
├─────────────────────────────┤
│ [图] 黑马标本·马上有         │
│      规格 · 大号             │
├─────────────────────────────┤
│ [山] 蓝闪蝶标本          ×2  │   ← 无图时走「山海」占位，不留破图
│      规格 · 单件             │
└─────────────────────────────┘
```

- **名称**：`title`（缺失回落「藏品」）
- **图片**：`image`（空则占位块，`hasImage` 由客户端判定）
- **规格**：`skuLabel`（缺失显示「规格 · 单件」，不隐藏整行）
- 信箱列表额外给：最多 3 张缩略图 + 「首件 等 N 项」

## 7. 已知边界

- **历史消息不补卡**：旧消息文档没有 `products`，一律不渲染卡片（不造默认图、不猜商品）。
- **未做**：商品卡点击跳转商品详情。当前卡片是纯展示；跳转需要把 `productId` 一起下发并处理下架商品，属产品决策，未擅自加。
- **`notification_logs` 不存商品**：只在 `user_messages` 留卡；日志表保持轻量（它是运维排查用，不是用户界面）。
