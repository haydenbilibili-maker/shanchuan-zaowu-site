## 3. 推断方法：用了哪些字段 / 文本，为什么可信

### T1 · 机械可复算（附录 A 主表的骨架）

```
scripts/product-theme-candidates.result.json   ← 商品身份事实：_id / title / rootCategoryName / price
        （只读扫描落盘，at=2026-09-17T15:59:15Z，194 条在售）
   ↓  scripts/giftSceneRules.mjs:38-79  proposeScenes({price, rootCategoryName})
        （纯规则的确定性函数：R0 排除 → R1 生日+致谢 → R2 陈列类≥¥300 加乔迁/新婚/纪念日 →
          R3 ≤¥800 加升学/毕业/新工作 → R4 首饰馆只加纪念日 → R5 ≥¥3000 去轻礼、≥¥10000 只留纪念日）
   ↓  miniprogram/config/blessTags.js:79-88  SCENE_BLESS
   ↓  miniprogram/config/blessTags.js:97-101 blessTagsFromScenes（受控、去重、按 SSOT 顺序、截断到 3）
建议标签
```

**为什么可信**：这条链**就是系统当前在跑的兜底逻辑**（`resolveBlessTags`，:104-111）——
把它写进字段，只是把"已经在对用户生效的推断"显式化，**不引入任何新的语义判断**。
规则阈值来自实际价格分位（`giftSceneRules.mjs:12` 注释：p25=198 / p50=499 / p75=1200 / p90=2300）。

**落盘佐证**（同一批商品、同一套规则真的执行过）：
`scripts/apply-gift-scenes.result.json` = `{total:197, changed:194, ok:194, failed:[]}`；
`scripts/apply-gift-scenes-rollback.result.json` 记录了 194 条**写入前**原值，其中**仅 1 条**非空
（即回填前几乎无人有场景标签）；执行结果见 `docs/礼赠场景标签_扫描与建议_2026-09-17.md` §7。

**为什么有限**：`root` + `price` 只是"陈设 / 轻礼 / 收藏级"的**经营口径**，**不含物种语义、不含文案语义**。
加上 R1 无条件给生日+致谢，导致 **192/194 都拿到"求安"** ⇒ 主表真正的信息量在 **求学 / 求缘 / 求成** 三列。

### T2 · 人工已上线文案（用于印证 / 分歧信号）

`scripts/product-theme-selection.json` 的 `overrides[_id].themeName / .themeNote`：**194 条人工圈定**的
主题名与题记（该文件 `note` 自述"同名校验后的圈定结果……基于既有候选，未额外调 AI"）。
它们已被写入线上 `products.themeName / themeNote`：`scripts/apply-product-theme-names.result.json`
= `{planned:194, changed:8, ok:8}`，`scripts/apply-product-theme-names-rollback-before-dedupe.result.json`
记录 194 条写入前为空。

用途：文案里出现可核对的**祈愿表述**（如「贺少年初入学堂」「新居初暖」「愿岁岁丰足」）时，
用它给规则链的结论做**同向印证**或**分歧标记**。
⚠️ **匹配用的关键词表由本分析者定义，不是仓库产物**（§4 列了全部词表）——它只用来"告诉人该去看哪一行"，
**不作为建议本身**；每一条的判断依据都是文案原文。

### T3 · 只用来看、不构成建议

`scripts/product-theme-candidates.result.json` 的 `candidates[].note` 是 **AI 生成的候选文案**
（`scripts/scan-product-theme-candidates.mjs:86-118` 的 `askAi` 调 DeepSeek）。本清单**不**用它推标签，
只在 §5 把 4 条与「求财 / 求行」相关的文本线索列出来交人判断。

**明确没有使用的**：物种名 / 拉丁学名（`docs/学名分类一致性审计_2026-09-17.md`、`check:product-copy-species`）、
`productStats` 口径、商品详情页 `description`（仓内无落盘产物）。
物种名与"求什么"之间**没有可核对的映射**，拿它推标签就是猜 —— 本仓明确禁止（`blessTags.js:11`）。

### 4b. 一个必须知道的口径效应：3 条上限按 SSOT 顺序截断，**系统性丢掉「求成」**

`blessTagsFromScenes` → `sanitizeBlessTags`（`miniprogram/config/blessTags.js:128-132`）取
`BLESS_TAG_KEYS` 顺序的**前 3 个**（顺序：求财 求安 求学 求缘 求行 求成，:67）。
当场景链一次推出 4 个标签（`peace, study, bond, success`）时，**排在最后的「求成」被静默截掉**。

实测（本 worktree 复算）：**53 条**商品的原始推导结果是这 4 个标签，
全部落在 **R3 的 ¥800 以内**价位段，被丢掉的标签**一律是 `success`**（计次 53/53）。
这也是 §4 表里「求学 128 / 求成 75」差额（128−75=53）的**全部**来源 ——
不是规则不同源，而是**上限截断**。

对打标的含义：这 53 条里，「求成」与「求学」由**同一组场景**（升学/毕业/新工作）推出、证据强度相等，
只是排序靠后。既然「求安」是 192/194 的兜底，**用「求成」换掉「求安」是零信息损失的更优选择**
（3 个名额：求学 · 求缘 · 求成）。本清单在附录 A 给这些条目标了复核要点，**建议由人确认后再打**。

> 计数口径：53 条截断项中有 3 条同时是 §6 的分歧项（复核要点栏优先显示分歧文本），
> 因此附录 A 里显式标「截断」的有 **50 条**；两类合计 **58 条**需要人工看一眼，其余 136 条可按建议直接打。
