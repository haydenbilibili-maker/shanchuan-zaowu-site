# 支付事故复盘：钱包充值未到账 + 支付成功仍显示待支付

**报告时间**：2026-09-15  
**现象**：① 钱包充值 1 元未到账；② 支付成功后订单页仍显示「待支付 / 立即支付」。  
**结论**：**同一个根因** —— 2026-09-14 为 `payCallback` 加固时，用「回调是否带 OPENID」判定客户端伪造，而 `cloudPay` 回调本来就带付款人 OPENID，导致**所有真实回调被判为伪造并返回 SUCCESS**（微信不再重试），支付完成后履约链路完全没走。

---

## 1. 事故链路

```
下单/充值 → payOrder / manageStoredValue.createRecharge
          → cloud.cloudPay.unifiedOrder({ openid, functionName: 'payCallback' })
          → 前端 wx.requestPayment 成功（钱已实扣）
          → 微信回调 payCallback
❌ 被 rejectClientForgery() 判为伪造（因为 wxContext.OPENID 存在）
          → 返回 { errcode: 0 } = SUCCESS ⇒ 微信认为投递成功，不再重试
          → 商品订单：orders.status 停在 pending_pay ⇒ 页面继续显示「待支付 / 立即支付」
          → 钱包充值：stored_value_recharge_orders 停在 pending ⇒ 余额不到账
```

### 证据

- 加固代码（2026-09-14 20:03 未提交改动）：
  `cloudfunctions/payCallback/index.js` →
  `if (isClientSource(wxContext.SOURCE) || wxContext.OPENID) return { errcode: 0, errmsg: 'IGNORED' }`，
  注释写着「平台支付回调无用户 OPENID」——该假设错误。
- 下单是**带 openid** 的：`cloudfunctions/manageStoredValue/index.js` 的
  `cloud.cloudPay.unifiedOrder({ ..., openid, functionName: 'payCallback' })`；
  `payOrder` 同款。回调上下文自然携带同一 OPENID。
- 客户端在支付成功后只调用 `confirmPayment` / `confirmRecharge`，而这两个函数在**生产（配置了 SUB_MCH_ID）刻意不自行入账**：
  `confirmRecharge` 返回 `AWAITING_CALLBACK`、`payment.js` 也把失败吞成 `pendingConfirm: true`。
  于是履约 100% 依赖回调 —— 回调一挂，前端、后台都不会补。
- 返回 `errcode: 0` 使微信认为通知成功，**不会重试**，所以事故期间没有自愈。

## 2. 修复（本次已落地）

| # | 位置 | 修复 |
|---|------|------|
| 1 | `cloudfunctions/payCallback/index.js` | **根因**：`rejectClientForgery()` 改为**只按 `SOURCE` 判定**（`wx_client` / `wx_devtools` 才算客户端）；不再用 OPENID 判定。每次回调打印 `context: { source, hasOpenid, outTradeNo }` 便于排障 |
| 2 | `cloudfunctions/manageStoredValue/index.js` | 新增超管**补单入账** `action: 'reconcileRecharge'`（仅超管；复用幂等键 `recharge:{outTradeNo}`；写 `reconciledBy/At/Note` 审计） |
| 3 | `cloudfunctions/confirmPayment/index.js` | 新增超管**补履约** `action: 'adminFulfill'`（仅 Admin Web 代理携带 `ADMIN_OPS_KEY` 可调用；补写支付证据后执行 `fulfillOrder`，幂等） |
| 4 | `admin/src/components/Orders.vue` | 订单管理新增「补履约」按钮（`pending_pay` 单可见，弹窗要求先核对微信商户平台流水） |

## 3. 事故期间已实扣的两类单如何恢复

1. **钱包充值 1 元**：填 `SV…` 商户单号（或充值单 ID）→ 入账；两个入口等价：
   - ERP → 我的钱包 → 「补单入账」
   - 小程序超管台 → 钱包配置 → 「补单入账」
   入账前请在微信商户平台确认该笔交易状态为「支付成功」；服务端 `manageStoredValue.reconcileRecharge`（仅超管 `staffGuard`）幂等。
2. **商品订单**：找到仍显示未支付的单 → 「补履约」；两个入口等价：
   - ERP → 全渠道订单 → 操作列「补履约」（`confirmPayment.adminFulfill`，凭 `ADMIN_OPS_KEY`）
   - 小程序超管台 → 订单管理 → **待支付** 子页签 → 「补履约」（`managerShipOrder.fulfillPaidOrder`，凭超管 `staffGuard`，内部转发同一个 `adminFulfill`）
   同样请先核对商户平台流水；执行后会扣库存、核销券、发通知（与正常履约一致）。

> 「待支付」页签展示 `pending_pay` 与 `fulfilling` 两种状态，专门用于定位回调异常导致的卡单；非超管只能查看，补履约按钮会提示「仅超管可补履约」。

> 两个入口都只对超管开放，且都幂等：重复执行不会重复加钱、不会重复扣库存。

## 4. 复盘要点（流程）

- **加固「回调类」函数时，判定依据只能来自平台上下文**（`SOURCE`），不能依赖"回调里没有某个字段"这类反证假设；写反了会**静默成功**、连重试都没有。
- 支付链路里 `errcode: 0` 的含义是"我已处理完"，**任何提前 return 都必须确认语义**：判定为伪造时也应考虑是否需要平台重试。
- 生产环境的支付履约存在**单点**：`confirmPayment`/`confirmRecharge` 刻意不自行入账（防客户端伪造入库），因此必须有**人工补单通道**——本次已补上，后续如遇同类问题可直接自助恢复。
- 建议后续加一条**支付对账任务**（定时比对微信商户平台流水与本地订单/充值单，自动补单或告警），把"回调丢失"从人工事故降级为自动恢复。
