### ★ 根因：`navigateTo:fail timeout` 不是「代码错」，是 feature 分包在运行期装不下

用户现象是「主包内页面正常，但凡点进 feature 的页面全部无效」：

```
bannerNav.js:175 openBannerItem navigate failed /subpackages/feature/gift/hub/index
  {errMsg: "navigateTo:fail timeout"}
点商品 → /subpackages/feature/detail/index 同样 timeout
```

**为什么工具不报 feature 超限，页面却打不开**：工具的大小校验用的是**源文件大小**
（feature 2023 KB < 2048 KB → 校验通过），而**运行期加载的是编译后的包**，
WXML 要编译成 JS，**编译后通常比源文件更大** → 编译后越过 2048 KB → 整个分包加载失败
→ **该分包内每一个页面**的 `navigateTo` 都超时。这正是「全局点击无效」的真相：
不是点击逻辑坏了，是目标分包整体没加载成功。feature 从 2023 → 1606 KB（−20%）后越线风险消除。

> 结论：**包体在 2M 边缘时，「分包内页面全部打不开」本身就是包体问题**，
> 不要再去逐个页面找代码错。本次先后做了 7 轮静态扫描（页面完整性 / usingComponents / 未声明标签 /
> require / WXSS @import / WXML import / 326 个 JS 语法）**全部干净**，这个「干净」恰恰是包体问题的旁证。

这类断链**静态扫 navigation 调用点扫不到**：目标是**字符串拼接**出来的

这就是为什么必须新增「把拼出来的结果拿去核对 app.json」的守卫。

### 同步开发仓的坑（本次踩到并修好）

`check-miniprogram-sync.mjs --fix` **只复制、从不删除**（设计如此：不擅自删本机文件）。
所以搬迁后**旧路径文件会留在开发仓**，开发者工具仍然编译它们 —— 包体不变、甚至出现重复页面。
本次手工剔除 **179 个陈旧旧路径文件**并清理空目录，之后双仓 `1946 → 1947 个文件`一致。
→ 以后任何搬迁：`--fix` **之后必须**按「开发仓多出」清单删旧的，否则等于没搬。
