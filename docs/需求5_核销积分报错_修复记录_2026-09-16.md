# #5 券核销「积分申请失败 / 请先登录」修复记录（2026-09-16）

> 对应需求清单第 5 条（P0）。本文记录**取证结论、根因、修复范围、验证证据、部署清单**。

## 1. 现象与初步归因的修正

**现象**：店员核销代金券 → 券核销成功，但积分行显示「积分申请失败 / 请先登录」。

**最初假设（已被推翻）**：外层 `verifyStoreCoupon` 未登录。
**推翻依据**：若外层 `verifyStoreCoupon:656` 真未登录，`field/index.js:1009-1012` 只会弹 toast 并 return，
**根本渲染不到「积分申请失败」结果卡**（`field/index.wxml:583-588`）。所以失败**只可能发生在内层云函数互调**——
即店员 openid 有效、券已核销成功，只有积分联动那一步失败。

**B 假设（线上未部署）也已排除**：修复前跑 `check:fn-sync -- grantStorePoints verifyStoreCoupon` →
「检查 2 个函数：一致 2，不一致/异常 0」。线上与仓库一致，故不是旧代码问题。

## 2. 根因（已用可执行证据确认）

云函数互调时 `wxContext.SOURCE` 会**继承客户端标记形成逗号合并串**（如 `"wx_client,scf"`）。
同一文件里存在两套互相矛盾的判定：

| 判定 | 实现 | 对 `"wx_client,scf"` 的结果 |
|---|---|---|
| `isNonClientSource()` | 负向子串 `!/wx_client\|wx_devtools/i.test(src)` | ❌ 判为「客户端来源」 |
| `isInternalSource()` | 分段精确 `source.split(',').some(seg => seg==='scf')` | ✅ 判为「服务端互调」 |

入口 `grantStorePoints` 用前者把守 `_callerOpenid` 转发：
```js
if (!openid && isNonClientSource() && event._callerOpenid && event._fromCouponRedeem) { ... }
```
判定失败 → 无 openid → 落到 `if (!openid && ...) return fail('请先登录')` → 前端显示「积分申请失败 / 请先登录」。

**实测差异**：该负向判定在 9 个真实 SOURCE 取值上**错 4 例**。

## 3. 同族缺陷（比原报障更严重的一类）

穷举全仓后发现**两种**缺陷形态、共 **18 个云函数**：

| 形态 | 影响 | 函数 |
|---|---|---|
| **A. 负向子串正则** | 互调转发被拒 → 误报「请先登录」 | `grantStorePoints` `verifyBooking` `manageInvoiceRequests` `refundOrder` `claimStoreReceipt` `getStorePointRules` `managerShipOrder` `manageGift` `manageDeposit` `sendBookingReminder` `sendCareReminder` `bindPlatformOrder` `claimBirthdayGift` `sweepExpiredOrders` |
| **B. 全等比较** | 合并串被判「非客户端」→ **跳过店员权限校验（安全门被绕过）** | `dispatchMessage` `sendInAppMessage` `payCallback` |
| C. 全等判 scf | 内部调用被拒 | `manageArtisanCommission:29`（`SOURCE === 'scf' \|\| SOURCE === 'wx_cloud'`） |

**B 类比报障本身更值得修**：`dispatchMessage` 有 **42 个调用方**，安全门被绕过意味着
客户端发起的链路可能不经店员鉴权就发出站内信。

## 4. 修复方案

### 4.1 收敛为单一真源 `sourceOrigin.js`

云函数之间不能跨目录 require，故按仓库既有惯例（`orderSummary.js` 13 份、`staffGuard.js` 55 份）
**每个函数各留一份完全一致副本** + sync 脚本。

**判定改为「正向证据」**：云函数互调由平台注入 `scf` 段，客户端无法注入该段。

```js
function classifySource(raw) {
  const segs = parseSource(raw)
  if (!segs.length) return { nonClient: true, client: false, internal: false }  // 定时触发
  const internal = segs.some(s => s === 'scf')
  const client   = segs.some(s => s === 'wx_client' || s === 'wx_devtools')
  return { segments: segs, nonClient: internal, client, internal }
}
```

- `nonClient=true` → 可信到可接受 `_callerOpenid` 转发（修复报障）
- `client=true` → **强制店员鉴权**（修复绕过；合并串带客户端标记即判真，严格即安全）
- 比旧判定更严格：`"scf,wx_client"` 这类旧版会**误放行**的串，现按客户端处理
- 判定逻辑抽为**纯函数**（`parseSource` / `classifySource`），使模块本体可被真实单测

### 4.2 安全边界未放松

判定只决定「是否接受 `_callerOpenid` 转发」与「是否强制店员鉴权」；
被接受的 openid 仍要经 `assertStaff` 校验员工身份与权限。故修正不引入越权。

### 4.3 诊断增强

`grantStorePoints` 无身份分支新增 warn 日志（`source` 段、是否带 `_callerOpenid`、来源标记），
线上若再出问题可直接区分「确实未登录」与「互调转发被拒」。

## 8. ⚠️ 修复过程事故与恢复记录（必须留痕）

**事故**：为批量收敛 18 处内联判定，我用了一个 Node 脚本做 in-place 替换。该脚本对 **16 个文件**
执行了错误的 splice，**静默删除了文件头（顶部注释 + 全部 `require` + `cloud.init`/`db` 初始化）**，
其中 `manageGift`、`sendBookingReminder` 另被截断为 54 / 52 行（原为 2815 / 201 行）。
若直接提交并部署，这 16 个云函数会因 `cloud`/`db` 未定义而**全线崩溃**。

**发现路径**：在取 #30 的代码锚点时发现 `manageGift/index.js` 只有 54 行（审计报告引用到 2700+ 行），
由此触发全量结构核查。

**恢复与证明**（没有依赖「看起来对」）：

1. 从 `git HEAD` 恢复 2 个被截断文件 + 8 个头部被删文件（共 10 个）；
2. 其余 8 个用 `edit` 工具逐个手工重做（放弃脚本）；
3. **规范化比对**：剥除注释与空白后，与「HEAD − 内联函数」**逐行一致** → 18/18 通过，证明**语义无损**；
4. **结构损坏检测**：18/18 完好、0 损坏；
5. **依赖完整性**：每个文件的 `cloud` / `db` 定义与 `sourceOrigin` 导入均存在；`node --check` 全过；
6. `check:admin`、`lint:wxml`、双仓一致性全绿。

**教训（已落为约束）**：

- **禁止用批量正则脚本改写业务源文件**。本轮两次踩坑：第一次脚本静默截断（本事故），
  第二次检测脚本因正则跨函数误匹配而**误报完好**——两次都是「工具比被改的代码更危险」。
- 批量改动必须**先备份、后验证**，且验证要能证明**结构完整**（行数 + 骨架比对），不能只看「语法通过」。
- 本项目 `check:sfc-dev` / `check:wxml` 这类守卫之所以存在，正是同一类教训。
- **已补守卫**：`miniprogram/scripts/check-cloud-functions-integrity.mjs`（`check:fn-integrity`，已接入 `check:admin`）
  检查每个云函数入口：有 `exports.main`、用 `cloud` 必有 `require('wx-server-sdk')` + `cloud.init()`、
  用 `db` 必有 `cloud.database()`、文件不得 <5 行、顶层本地 require 必须指向真实文件。
  已自验：**能抓到本轮的真实损坏形态**（对损坏样本报 3 处问题），且对现有 **129 个云函数 0 误报**。
