## 2. Q6 的"条件"（这是本次最重要的技术裁决）

**接受"不用跨文档事务"，但必须同时满足两条，缺一不可：**

1. **每条钱写入都必须是单文档条件更新**：把不变量写进 `where`（如余额 `>= n`、状态 `= 'unused'`），
   并用**受影响行数**判定是否抢占成功；**禁止** read → 判断 → write。
   （单文档条件更新本身就是原子的，这才是"不需要事务"能成立的原因。）
2. **唯一索引必须存在，且其存在性可被只读校验。**

> **为什么第 2 条是硬条件**：没有事务兜底时，`dedupeKey` 唯一索引就是幂等的**唯一**载体。
> 索引不存在 → `earnPoints`/`refundOrder`/`upsertUserProfile` 那些"已修"全部退回 read-then-write，
> **幂等是纸的**。而今天实测：索引存在性**在仓库内无任何只读手段可查**（需 `TCB_SECRET_*`）。
> 所以 C2 的冻结口径里必须写死一句：**"索引未证实存在之前，不得改动任何钱路径代码。"**

### R1 · 2026-09-18 · Q2 的**前提被推翻**：裁决改为「无需改代码」

**修订前**（§1 Q2）：把「`order_refund_credit` 带不带轮次」升级给产品负责人拍板，
描述为「现状 `:566` 带 `attempt`、`:691` 不带」。

**复核后的事实**（我逐行读了 `miniprogram/cloudfunctions/manageStoredValue/account.js`）：

| 位置 | **真实 key** | 所属函数 | 语义 |
|---|---|---|---|
| `:566` | **`order_pay_refund:${oid}:${attempt}`** | `refundCreditForOrder` | **待支付订单**回账（微信支付失败/用户取消，把已扣的钱退回钱包） |
| `:691` | `order_refund_credit:${oid}` | `creditOrderRefund` | **订单退款**回账（流水 `type=refund_credit`） |

- 这是**两个不同的 key**，不是同一个 key 的两种写法 → **「不对称」是误报**。
- `order_refund_credit` 全仓**只有一处、本来就不带轮次** → 产品负责人的口径（不带 = 一单一退）
  **现状已满足，不需要任何代码改动**。
- `order_pay_refund` 的 `attempt` **必须保留**：待支付订单的**每次支付尝试各自扣了一笔钱**，
  各自需要回账。**若按字面"统一"去掉 attempt，第二次支付失败的用户扣款不会回账 → 静默资损。**

**产品负责人意见（2026-09-18）**：「不带 = 一单一退」。**执行口径**：

| key | 执行 |
|---|---|
| `order_refund_credit:<orderId>` | 不带轮次 —— **保持现状** |
| `order_pay_refund:<orderId>:<attempt>` | **保留 attempt**（不同维度，不受该口径约束） |

**要求 C2 补两件**：① 契约里把这两个 key 的**语义差异写成显式注释**；
② 加一条守卫：**禁止**去掉 `order_pay_refund` 的 `attempt`、**禁止**把两个 key 合并。

#### §2 判据修正（**替代**原「条件 2」）

原文写的是「唯一索引必须存在，且其存在性可被只读校验」。**这条不够**：实测索引**存在但是
`Sparse=true`**，**缺字段的文档不占唯一槽位** —— 所以那 48 条缺键记录**仍不受幂等保护**。

**修正后的 C2 红线**：一条钱写入要被认定为「有幂等保护」，必须**同时**满足三条：

1. 目标集合的 `dedupeKey` 唯一索引**存在**；
2. 该索引**不是 `Sparse`**（或者该集合缺 `dedupeKey` 的文档数为 **0**）；
3. 该集合的**重复键组数为 0**（有重复时索引根本建不上）。

**三者缺一 → 视为未证实 → 不得改动对应钱路径代码。**
