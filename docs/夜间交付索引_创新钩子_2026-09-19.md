## 1. 为什么选「连续记录云保存」作为主钩子

### 既有钩子的通用形状（读代码得出，带出处）

| 钩子 | 触发时机 | 用户换到什么 | 我们的收益 | 出处 |
|---|---|---|---|---|
| AI 识别 | 想保存图鉴 / 想看结果 | 结果被保存 / 被解锁 | 注册 | `analyticsSchema.js` 的 `identify_save_atlas_gate` / `identify_result_gate` |
| 祈福墙 | 落愿之后 | **自动续发**心愿（不白写） | 注册 | `wish_wall_register_gate` |

**通用形状**：**用户已经完成了一个动作、且这个动作有「未兑现的价值」时，用注册把它兑现。**
（不是进门就拦 —— 那是骚扰，不是钩子。）

### 这次找到的缺口（实测，不是推测）

祈夆墙的**连续点灯天数**与**木鱼功德**目前：

```
wishRitual.js:75-89   wx.getStorageSync / wx.setStorageSync   ← 只存本地
manageWishWall/index.js   搜 'lamp' / 'lit' → 零命中            ← 云端完全没有
```

→ **换手机 / 清缓存即丢**。这是「注册能换到真实价值」的现成缺口：
用户**已经攒了进展**，注册能把它**存住**，而且断签前能被提醒。

**它同时打三个目标**：注册（存记录）· 留存（连灯不断 + 断签提醒）· 成交（推荐位）。
比「再做一个抽签玩法」更省、更可验，也**不需要先拍产品口径**。

## 3. 早上建议这样验收（按优先级）

### 第一优先：主钩子是否成立（**能不能真的兑现**）

| # | 要看什么 | 在哪看 | 通过的标准 |
|---|---|---|---|
| 1 | 钩子的**触发条件**是不是克制 | `feat/ritual-register-gate` 里 `shouldOfferRitualGate` 之类的纯函数 + 注释 | 不是「一进页就弹」，而是「已有可丢的进展」才谈 |
| 2 | 注册后**真的把记录存上云了**吗 | 同分支的门禁回调 + 云函数调用 | **这是钩子成立与否的关键**：只弹窗不同步 = 空承诺 |
| 3 | 三条**降级路径** | 开关拉取失败 / 云函数未部署 / 用户拒绝授权 | 三条都不得影响点灯·木鱼·落愿 |
| 4 | 开关能力 | `contentDisplayFlags.js` 的 `showRitualProfile` | 默认关（新 UGC/身份能力由超管显式开启，照 `showMaShangYou` 先例） |

### 第二优先：判据是否可信（**它会不会失败**）

| # | 要看什么 | 怎么验 |
|---|---|---|
| 5 | 新钩子的判定逻辑有没有断言 | 跑该分支的测试；**并要求它证明「注入回归会被检出」** |
| 6 | 埋点双端是否镜像 | `npm run check:analytics-schema` |
| 7 | 有没有弄坏既有断言 | `npm run test:wish-wall`（`feat/wish-wall-refine` 起是 **662/662**；**低于这个数就是弄坏了**） |
| 8 | 守卫清单自洽 | `npm run check:guards-coverage`（当前基线 **89** 条） |

### 第三优先：方案本身值不值得做

| # | 要看什么 | 在哪看 |
|---|---|---|
| 9 | 候选钩子清单与**否掉的点子** | `feat/innovation-plan` 的产出文档 |
| 10 | 每条的「价值交换」是否成立（他得到什么 / 我们得到什么） | 同上 |
| 11 | 哪些卡在**产品口径**上（**没有替你决定**） | 同上 + `祈福墙_待产品负责人拍板_2026-09-19.md` |

| 项 | 为什么没做 |

  ```bash
  git fetch origin --prune

    | grep -v '^docs/' && echo "🚨 冻结被破坏" || echo "✓ 冻结有效"
  ```
