## 4. item 5 的契约（先定接口，再写四个玩法）

```
config/ritualPlays.js  玩法注册表：{ id, name, 一句话, 图标, 需要哪些用户字段, 每日/每次, 输出形态 }
     ↓
utils/ritualPlay.js    纯函数：play(input) → { title, body, line, share, hook }
     ↓
components/play/*      每个玩法一个组件，只负责渲染 + 交互（不含业务规则）
     ↓
pages: 祈福墙玩法区 / 详情页弱入口
```

- **每日确定性**：同一用户同一天同一玩法给同一结果（seed = 用户标识 + 日期 + 玩法 id），
  与弹幕布局、每日灯语同一条铁律（否则"刷新就换一个"，仪式感归零）。
- **内容池 + AI 生成**：池子保证"没有 AI 也能用"；AI（`qwenText`）只做个性化润色，
  失败回落池子 —— 与 AI 播种第一批弹幕同一套降级口径。
- **每个玩法都必须**：① 反馈层接 `pushEcho('play', { text })`；② 埋点双端登记；③ 断言 + 注入；④ 隐私开关。

## 5. item 6 的字段设计（先立契约，再动 ERP）

```js
// 商品级祈运标签（受控枚举，不是自由文本 —— 自由文本无法做推荐匹配，也无法守卫）
blessTags: ['求财', '求安', '求学', '求缘', '求行', '求成']
```

- 三处同改：`manageProducts.ALLOWED_FIELDS` + 小程序藏品表单 + ERP 商品表单；加结构断言；
- 用途：① 详情页玩法推荐；② 祈福墙入口文案（"这匹马适合求什么"）；③ 推荐排序权重；
- **不做**：不让 AI 自动推断标签（不可解释、且会写脏数据）；先人工打标，跑通再谈半自动。
