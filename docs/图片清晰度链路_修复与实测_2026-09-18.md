# 图片清晰度链路 · 修复与实测（2026-09-18）

> 触发：产品反馈「现在的图片清晰度较低不符合要求」。
> 本文是该链路的**唯一现状记录**：根因、实测数据（可复现命令）、修复内容、守卫、存量图处置。

## 0. 一句话结论

清晰度低是**三层叠加**，其中第一层是**上传侧把图压糊**（原图入库那一刻就废了）：

| 层 | 问题 | 量级 |
|---|---|---|
| **P0 上传侧** | `wx.compressImage({quality})` **只降质量、不改边长**，而循环的退出条件依赖"边长变小" → 条件恒真 → 所有长边 >2400 的手机原图被**累积压 4 代、落到 quality 35** | 入库即糊，URL 侧无法挽回 |
| **P1 详情大图** | 宽度按「**2 倍屏**」写死 750 | 3 倍屏需 1170 → **放大 1.5 倍显示** |
| **P2 列表缩略** | 一个常数 480 打天下；且 `thumbnail/<w>x` **无 `>` 会放大小图** | 该清晰的欠采样、不需清晰的过采样，小源图被放大还多花 83% 字节 |

## 1. 真图实测（可复现）

线上真实图（`stores/store_shanhaizaowu.png`，实际存储为 JPEG，1024×684 / 176,442 B）：

```bash
B="https://636c-cloud1-8gnkty5bfff9f0bf-1387508856.tcb.qcloud.la/stores/store_shanhaizaowu.png"
curl -sS -o /tmp/x "$B?imageMogr2/thumbnail/1170x>/quality/90"
sips -g pixelWidth -g pixelHeight /tmp/x; stat -f%z /tmp/x
```

| 参数 | 返回尺寸 | 字节 | 结论 |
|---|---|---|---|
| 原图 | 1024×684 | 176,442 | — |
| `thumbnail/360x>/quality/90` | 360×240 | 30,969 | rail 档（横滑小卡） |
| `thumbnail/560x>/quality/90` | 560×374 | 62,780 | list 档（两列栅格） |
| `thumbnail/750x>/quality/90` | 750×501 | 99,922 | 旧"2 倍屏"档 |
| `thumbnail/1170x>/quality/90` | **1024×684** | 176,224 | 3 倍屏档；**只缩不放**（源图仅 1024 → 不放大） |
| `thumbnail/1600x>/quality/90` | **1024×684** | 176,224 | 上限档，同样不放大 |
| `thumbnail/1170x>/quality/40` | 1024×684 | 60,854 | **质量参数确实生效**（同尺寸下 q90 是 q40 的 2.9 倍字节） |
| `thumbnail/1170x>/quality/90/format/webp` | 1024×684 | 132,632 | webp 省 25%（未启用） |
| **`thumbnail/1600x`（无 `>`）** | **1600×1069** | **323,052** | ⚠️ **被放大**：+83% 字节、画质更差 |
| `thumbnail/1600x>` | 1024×684 | 176,224 | `>` = 只缩不放（正确形态） |
| `thumbnail/3000x>` | 1024×684 | 176,224 | 永不放大的兜底 |
| `imageView2/2/w/1600` | 1024×684 | 176,224 | 旧接口同样只缩不放 |

**两条硬结论**：
1. **必须带 `>`**——否则小源图会被放大（花更多字节买更差的画质）；
2. `quality/90` 有效，且等于该管线默认值 → 选 90 是"清晰优先**且不涨体积**"。

## 2. 修复内容

### 2.1 上传守卫（P0，`subpackages/manager/utils/imageUploadGuard.js`）

| 旧（已删） | 新 |
|---|---|
| `wx.compressImage({quality})`（边长不变） | `compressedWidth`/`compressHeight` **真正等比降边长**（长边 ≤ 2400） |
| 退出条件含 `!stillLarge`（边长不变 → 恒为真） | 条件改为「**字节达标 且 边长达标**」，且边长确实会变 |
| `outPath = compress(outPath, …)`（**压上一次的输出**） | **每次都传原图路径**（`src` 恒为原图）→ 不累积代际损失 |
| 起步 q80、步长 −15、无地板（落到 **35**） | 起步 **q88**、步长 −10、**地板 q70**（宁可变大也不糊） |
| 地板仍超预算 → 拒绝 | 地板仍超预算 → **放行并标记 `overBudget`**（不阻塞管理员）；仅 >12MB 硬上限才拒绝 |
| 不支持降边长时同样一路压到 35 | 不支持时只降质量（**清晰度不降**）并标记 `edgeReduced:false` |

### 2.2 详情大图按设备 DPR（P1，`utils/imageUrl.js`）

```js
detailTargetWidth() = clamp(windowWidth × pixelRatio, 750, 1600)
```
实测口径：iPhone 3×（390pt）→ **1170**；iPhone SE 2×（320pt）→ 750（下限）；iPad（768×2）→ **1536**；>1600 夹断。

### 2.3 列表缩略分档（P2）

| 档 | 宽度 | 槽位（实测渲染宽） |
|---|---|---|
| `railUrl` | 360 | 详情「更多细节」「相关推荐」200rpx=100pt、首页横滑卡 220rpx=110pt |
| `midUrl` | 480 | 首页「为你推荐」280rpx=140pt |
| `thumbUrl` | 560 | `ProductList` 两列栅格 ≈341rpx；礼赠/标本师/百科/定制/工作台沿用（≥原 480，清晰度只升不降） |

统一附 `quality/90` 与 **`>`**（只缩不放）。

## 4. 存量图片（必须知道）

**本次修复只保证此后新上传的图清晰**；已入库的糊图不会被自动修好。重传优先级：

1. 详情页**主图 / 长图文**（用户停留最久、观感影响最大）；
2. 首页「博物藏品室」横滑卡与「为你推荐」（首屏）；
3. 列表/工作台缩略图（可后置）。

> 判据口径：原图长边 < 1600 或肉眼可见块状/色带/蚊噪即为旧压缩产物。
> 如需自动化清单，可按存储对象的尺寸/字节抽样（需 TCB 凭据）。

## 5. 未做 / 风险

- **未启用 `format/webp`**：实测省 25%，但需确认 iOS 老版本与 `wx.previewImage` 的兼容性，本轮不动。
- **`imageThumbEnabled` 开关只覆盖 URL 派生**，不影响上传侧压缩——上传守卫恒定生效（这是刻意的：清晰度不该被一个列表开关左右）。
- **列表档位未逐点实机校验**：礼赠/标本师/百科/定制/工作台沿用 list 560（比原 480 更清晰，纯收益）；若某页实测卡宽 < 140pt，可降档省流量。
- 存储侧样本仅一张真实图（门店图 1024×684）。**若藏品原图本身就是 1024 量级**，详情大图的天花板由素材决定，需先提高入库分辨率（上传守卫不再压糊，但不会凭空增加细节）。
