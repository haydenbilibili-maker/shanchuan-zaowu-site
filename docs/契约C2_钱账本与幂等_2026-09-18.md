## 3. 幂等语义契约（核心）

**结论：所有钱相关写必须满足「先落幂等键（唯一索引挡）、再动余额、再置 done」三步；条件更新一律用 `where(条件).update()` + `stats.updated` 判抢占；本仓不用事务（沿用已拍板的决策）。**

### 3.1 `dedupeKey` 构造规则（确定性 key）

**总规则**：
1. **形状**：`<动作域>:<业务稳定标识>[:<主体>]`，**只用业务侧稳定且不可变的值**（订单 `_id`、`orderNo`、`outTradeNo`、`purchaseId`、`claimId`、`clientRequestId`、`openid`）。
2. **禁止**：`Date.now()`、`Math.random()`、自增计数、数组下标、任何「每次调用都不同」的值。**唯一已知违例**：`manageApprovals/inAppMessage.js:46`。
3. **同一业务动作重放时 key 必须逐字节相同** —— 这是全部幂等的前提。调用方生成的 `clientRequestId` 必须**在用户进入页面时生成一次并复用**（连点重试必须复用同一串），否则 key 变化即等于没有幂等。
4. `dedupeKey` **必须在 `add()` 的同一份 `data` 里**（不能先 add 后 update 补键）。

| 动作 | 现行 key 形状 | 来源 | 评价 |
|---|---|---|---|

| 新客礼包（积分） | `register_gift:<openid>` | `upsertUserProfile/index.js:74-76` | ✅ |

### 3.2 动作语义表

**命中已有记录时的行为，按动作类型分三档**；下表是 C2 的**强制口径**：

| 动作 | 幂等键形状（应然） | 命中已有记录时的行为 | 允许部分重放 |
|---|---|---|---|
| **发放类**（积分/券/成长值） | `earn:<业务来源>:<业务单号>:<userId>` 或既有等价形状 | `status==='done'` → **返回原结果（`success:true, alreadyGranted:true, points:<原值>`）**；`status==='pending'` → **返回「处理中，请稍后刷新」**（不报错、不重发）；`status==='rolled_back'` → **允许重试**（复用同一条 `_id`，不得 `add` 新记录） | 是（`rolled_back` 可重放；`pending` 不可） |
| **扣减类**（兑换/核销/下单锁券） | `spend:<业务来源>:<clientRequestId>:<userId>` | `done` → 返回原结果；`pending` → **抛错**「上一次正在处理中」 | **否**（扣减不可部分重放） |
| **入账类**（充值/退款回账） | `credit:<渠道>:<渠道单号>` | 已存在流水 → 返回 `alreadyCredited:true` + 当前余额 | 否 |
| **状态迁移类**（退款执行） | 不靠 `dedupeKey`，靠 **CAS 占位**（`status: refunding → refunding_claimed` 之类） | CAS 失败 → 返回「已有退款在处理中」 | 否 |
| **通知类**（站内信） | `<eventType>:<relatedId>:<openid>` | 已存在 → 静默跳过 | 是 |

**三条硬约束**：
- **P1**：`rolled_back` 的重试路径**必须复用原 `_id`**（`upsertUserProfile/index.js:357-372` 已正确示范）。若走 `add`，唯一索引会挡住，然后**必被 `isDuplicateKeyError` 分支接住**——但那个分支必须返回原结果，不能报错。
- **P2**：**幂等键写入必须先于余额变更**（`exchangeCoupon/index.js:127` 注释「先落幂等键（唯一索引挡住连点）」）。
- **P3**：**`success:true` 只在真完成时返回**。`pending` 必须用 `success:false` + 明确文案，或 `success:true, pending:true` 且前端识别。禁止「假装成功」。

### 3.4 扣减不可为负的写法

**规矩一句话：把 `>= n` 写进 `where`，不要写进 `if`。**

```js
// ✅ 正确（本仓已有范式：manageStoredValue/account.js:478-508）
const res = await db.collection('stored_value_accounts').where({
  _id: account._id,
  version,                              // 乐观锁
  availableFen: _.gte(payFen)           // 余额下限进 where
}).update({ data: { availableFen: nextAvailable, version: version + 1 } })
const claimed = Number(res.stats && res.stats.updated) || 0
if (!claimed) return { success: false, code: 'VERSION_CONFLICT' }   // 没抢到 = 不扣

// ❌ 错误（earnPoints/receiveCoupon/transferCoupon/exchangeCoupon 的现写法）
const cur = await db.collection('coupons').doc(id).get()
if (cur.data.totalStock <= 0) return fail('已领完')     // ← 这个窗口就是竞态
await db.collection('coupons').doc(id).update({ data: { totalStock: _.inc(-1) } })
```

**四类扣减的统一写法**

| 类型 | `where` 条件 | 备注 |
|---|---|---|
| 余额扣减（钱包） | `availableFen: _.gte(n)` + `version` | 现有范式 |
| 库存扣减（券/权益） | `totalStock: _.gte(1)` / `stock: _.gte(1)` | 需新增 |
| 次数扣减（限领/限兑/日限） | 落一张「计数文档」+ `used: _.lt(limit)`，或直接用唯一键把次数变成「键的条数」（更稳） | 需新增 |
| 状态占用（退款/履约） | `status: _.in([合法前置态])`（+ 本轮单号不存在） | 退款需新增 |

> **`stats.updated` 的兼容读法**（本仓已有两种写法，统一取后者）：
> `Number(res.stats.updated != null ? res.stats.updated : res.stats.updatedCount) || 0`
> 出处：`confirmPayment/fulfillOrder.js:36`、`makeOrder/index.js:384`。
