## 3. 今天修掉的 5 个 P0（**根因 + 证据**，夜班别重犯）

### P0-1 · 日报线上订单指标**全部取数失败**（真调用才抓到）
```
db.collection(...).aggregate(...).append is not a function
```
`append` 是 manager-node / `@cloudbase/node-sdk` 的形态，**`wx-server-sdk` 没有这个 API**。
本地用 `tcb db nosql`（真 Mongo）验是绿的 ⇒ **「本地验过 ≠ 线上能跑」**。
**同族第二处**：取数失败被混成「当日无数据」⇒ 日报平静地报"订单当日无数据"，读者以为那天真没生意。
现在 `missing`（确实无数据）与 `failed`（取数失败，带原因）分两档，入口回包带 `failed`。
**判据**：`check:daily-digest` D10（取数不许 `.append(`、必须有 fluent `.end()` 与东八日兜底、两档必须分、回包必须带 `failed`）。

### P0-2 · 礼笺写满 200 字 → **贴纸上正文整段消失**
用真渲染台二分：**155 字 ✓ 全部落墨 / 158 字 ✗「正文只画了 0/8 行」**，
而 UI 上限是 200 ⇒ 写满的顾客贴纸上没有正文。贴纸正文带**永不截断**（缩字 → 压行距 → 否则一行不画），
所以容量是**悬崖**。已定 `GIFT_NOTE_MAX_CHARS = 140`（放 `utils/giftShareCard.js`，常量处写了推导与复跑命令）。
**判据**：`test:gift-note-variants`（常量 ≤155、编排页不许写死 200、界面必须说清"为什么要限"）。

### P0-3 · 礼赠封缄页音频放不出来 / 状态不随留址变
① 云函数 `getGiverShare` **一直在返回** `voiceTempUrl`，只是页面把「含语音」渲染成不可点的纯文本
⇒ 录制者发出去后再也听不到自己的话。② 头部文案只按 `deliveryType` 分支、从不看 `addressStatus/status`。
均已修。**判据**：`test:gift-mygifts`（封缄页必须真的调到播放、状态机必须覆盖已留址/已寄出/已送达）。

### P0-4 · 订单详情缺礼赠入口 + 中文人名乱码
礼赠动作原来全在底栏、只在特定状态出现 ⇒ 礼赠进入"已领取/已发货/已送达"后**没有任何回看入口**。
`contactName` 只做了发端 `encodeURIComponent`、收端没解码 ⇒ 界面显示 `%E5%8E%89…` 且筛选匹配不到。

### P0-5 · `user_messages.dedupeKey` 的语义结论（**我先前判断错了一次，以此为准**）
我先把 9 组重复 `dedupeKey` 判成"并发竞态/顾客被重复发私信"，**查清后更正**：
同一 `dedupeKey` 在本集合**允许重复**，因为两条语义并存 ——
`toggleCollection` / `payCallback·inAppMessage` 是**永久**去重；`dispatchMessage/core.js` 是 **24 小时窗**去重
（`DEDUPE_HOURS = 24`，跨天再发生同一事件**有意再发一次**，例：顾客隔几天再进店应该再谢一次）。
实测佐证：`store_visit_thanks:store_x:openid` 在 2026-05-24 / 05-27 / 08-15 各有一条。
因此：**① 那 10 条历史消息没删**（是正常记录）；**② 唯一索引不但建不起来、还会把正常写入打成失败**；
**③ 改建成普通索引** `dedupeKey_1`（线上已确认存在，`unique = None`），spec 加 `nonUnique: true` + 理由。

## 6. 夜班开工前必须知道的三件事

### 6.1 内循环别跑全套（实测 124.5s vs 2.5s）
```bash
npm run check:quick -- <域>      # 本域 + quickWith 点名的跨域，约 2.5s
npm run check:admin              # 全套 111 条，约 125s —— 只在收口/提交前跑一次
```

### 6.2 两个"会说谎"的地方**已经修好**，但规律要记住
- **`deploy-drifted.sh`**：`tcb` 的失败可能发生在**上传成功之后的回执**上。
  判断部署是否真生效，**一律以第 3 步"线上拉回来复比"为准**，不看 `tcb` 的成败字样。
- **判据自身会失效**：今天又修了 4 处（注释被匹配、读错文件、注入锚点错位、注入与判据不同层）。
  规律：**负向断言必须看"去注释"的源码；几何判据必须跟实现取同一个算式；每条判据都要能被注入证伪；
  注入必须与判据同层**（给文本级判据注入"函数早退"是抓不到的）。

### 6.3 别在共享工作区跑 `check:admin:selftest`
它会对源码注入→还原。要跑就在 `/tmp` 建隔离副本（rsync 排除 `node_modules`/`.git`/`.tmp`，再软链 `node_modules`）。

## 8. 今天踩过的 6 个坑（过程纪律，写进来免得重犯）

| # | 坑 | 代价 / 修法 |
|---|---|---|
| 1 | **提交信息里的反引号被 shell 执行**（本会话**第 6 次**） | 信息被吃掉一半，只能 `--amend` 重写。**一律用引号 heredoc**（`<<'MSG'`），别用 `-m "…"` |
| 2 | **子代理与我共用同一个 git 工作树** | 一路子代理 `git checkout -b` 把我的分支一起切走了，三条流的未提交改动混在一棵树里。修法：派发前先确认隔离（独立 worktree），或把自己的在写内容先提交干净 |
| 3 | **注入与判据不同层** | 给文本级判据注入"函数早退"永远抓不到 ⇒ 自检报"漏检"。不是判据弱，是**注入弱** |
| 4 | **判据匹配到注释**（今天 2 次） | 我在源码里写的说明注释正好含被禁的字样 ⇒ 判据误红。加 `stripComments()` |
| 5 | **判据读错文件** | "工作信息瓦片不见了"那条读的是 `.js`，而瓦片是 WXML ⇒ 恒判缺失。判据要跑一遍"未注入时应通过" |
| 6 | **差点误删顾客消息** | 我先把 9 组重复判成"重复发送 bug"，**幸好先做了全量备份 + 查清语义**才发现是设计行为。**动生产数据前先备份、先证伪自己的假设** |
