## 3. 纪律：每轮必做 / 收尾才做 / 禁止

**每轮（内循环，秒级）**
- `npm run check:quick -- <域>`（本域 + 点名跨域），可加 `--jobs auto`；或直接点名跑单条守卫。
- 改了哪条守卫的被注入文件，只跑那**一条**的 `--selftest`（且在隔离副本里跑会写源文件的那种）。
- 体积只用 `npm run check:main-package-size`；不手写 `find`/`du`。

**收尾（一个批次一次）**
- `npm run check:fast`（**全套 125 条**并行，~7 s；与 `check:admin` 同清单同判据）。提交前如需与 CI 完全同形，再跑一次 `check:admin`（~48 s）。
- **出图 / Chrome 探针每轮最多 2 次**：改前看问题 1 次 + 交付 1 次，每次一次出齐要看的图（2026-09-28 产品负责人拍板）。
  两次之间的迭代只靠静态守卫与 `check:quick`；第 3 次想出图 = 该拆轮了。
- 云函数：`bash miniprogram/scripts/deploy-drifted.sh <本流函数…>`，只比对/部署本流改过的函数。
- `npm run sync:miniprogram`（`--fix`）每轮结束推一次，不复跑校验。

**禁止**
- 内循环里跑全套 `check:admin` / `check:admin:selftest`；在共享工作区跑任何会注入源码的自检。
- 全量云函数比对/部署（`--all` 仅限产品负责人点名）。
- `pkill -f` 宽匹配（`--headless`、`chrome`、`check-cloud-functions-sync`、`render-`…）；杀进程只杀**自己启动并记下 PID** 的。
- 为了「等它跑完」写 `sleep N; tail log` 轮询：先查本篇 §1.2 的实测耗时，秒级命令直接前台跑。
- 反复整读同一份大文档（`docs/README.md`、错题本、蓝图）：读一次，之后 `rg` 定位。

## 4. 已落地（改前 / 改后，同机实测）

| 项 | 改前 | 改后 | 验证 |
|---|---:|---:|---|
| 全套并行 `npm run check:fast`（新增） | 67.8 s（串行） | **7.4 s**（astro 缓存未命中时 11.7 s） | 失败项与串行一致（仅既有的 `check:miniprogram-sync` 双仓漂移）；跑前跑后 `git status` 一致 |
| `npm run check:admin`（串行，CI 用，行为不变） | 67.8 s | 48.5 s | 同上 |
| `check:quick -- manager --jobs auto` | 1.3 s | 0.38 s | — |
| `test:wish-wall` | 9.5 s | 1.5 s | 通过；管道下输出完整 |
| `check:gift-holder` | 1.8 s | 0.37 s | 通过；自检 61 条注入全检出（隔离副本） |
| `check:astro` | 10.5–11.8 s | 缓存命中 0.03 s | 自检新增「注入探针后输入哈希改变」断言，隔离副本通过 |

实现要点：
- `scripts/run-guards.mjs` 新增 `--jobs N|auto`（不带时执行顺序、输出格式、退出码与旧版一致，只在汇总后多一段耗时排行）：N 路并发、绕过 `npm run`
  启动（直接执行 package.json 中该脚本的命令，PATH 前置 `node_modules/.bin`）、按上次耗时最长优先排程
  （`node_modules/.cache/run-guards-timings.json`，临时文件 + rename 写入）；输出按条缓冲、完成一条打印一条；
  两种模式都在汇总后打印**耗时排行 Top 10**。`--selftest` 忽略 `--jobs`（自检会改源文件，必须串行）。
- `guards/_meta.json` 新增 `serialGuards`（起 Chrome / vite / 写固定名临时文件的守卫）：并行时走一条互斥通道
  依次执行；`check:guards-coverage` 校验每项都在清单里（附注入自检）。
- 执行器自检新增场景 4：`--jobs 3` 下失败夹在中间、最慢的最后完成，4 条都执行、2 条失败都进汇总、退出码 1。
- `test:wish-wall` / `check:gift-holder` / `test:legacy-remap` / `check:wall-qr`：成功路径冲刷 stdout 后 `process.exit()`
  （不带参数，保留已有 exitCode；失败路径与判定逻辑不动）。后两条的耗时主要是真实计时器，本次无收益，只是统一形态。
- `scripts/check-astro.mjs`：通过缓存（输入 = tsconfig include 范围 + lockfile + 本脚本 + Node 版本的内容哈希；
  `CI` 或 `CHECK_ASTRO_NO_CACHE=1` 一律真跑；跑的过程中输入被别的流改了就不写缓存）；优先用 `node_modules/.bin/astro` 省掉 npx 解析。

## 5. 未落地项与原因

- **`check:changed`（按改动文件选守卫）**：守卫与文件的对应关系散在 125 个脚本里（很多是整目录扫描），
  按文件名反查会**漏选**，等于悄悄降覆盖。全套并行已压到 ~7 s，与 `check:quick` 同一量级，覆盖不打折 → 不做。
- **#11 / #12 真实计时器改虚拟时钟**：要改守卫内部的时序语义（600 ms 定时器 vs 700 ms 等待），在并行负载下
  压缩比例不当会变成偶发红；应由守卫所属的流（祈福墙 / 注册与旧路径）在自己的测试里改。
- **`check:admin:selftest` 并行化**：自检会注入并还原真源码，并行 = 互相覆盖，不做。
- **`deploy-drifted.sh` 及其比对脚本**：另一条流在修，本次不碰。

## 6. 产品负责人裁决（2026-09-28）

1. **CI 的 verify job 改用 `check:fast`** —— 已落地。针对「新守卫共享临时文件却没登记 `serialGuards`」加两道防线：
   - **静态拦截**（`check:guards-coverage`）：守卫入口脚本（去注释后）命中 `--headless` / `--remote-debugging-port` /
     puppeteer / playwright / `import('vite')` / `.listen(<端口>)` 却未登记 `serialGuards` → 判红。
     自检注入：把 `check:sfc-dev`（vite）、`check:toast-style`（Chrome）分别从名单摘掉必须检出；只读守卫不误报。
   - **运行时兜底**（`--retry-serial`，`check:fast` 默认带）：并行失败的逐条**串行**复跑 ——
     串行仍失败 = 真失败（判红）；串行通过 = 「并行冲突嫌疑」（不判红、汇总里单列、CI 打 `::warning`）。
     串行即 `check:admin` 的原判定，所以兜底**不放过任何串行下会红的回归**；执行器自检场景 5 用「锁文件」造出
     只在并发时失败的守卫 + 一条恒失败守卫，证明两者被正确区分、退出码 1。
   - 为什么不只做其中一种：写固定名临时文件的冲突静态扫不准（几乎每个守卫都有 `writeFileSync`，多在自检分支），
     只靠静态会漏；只靠复跑则 Chrome/vite 这类确定冲突每次都要白跑两遍。两者叠加最稳。
   - `check:astro` 的缓存在 CI 不生效：GitHub 注入 `CI=true`、全新安装无 `node_modules/.cache`，workflow 再显式设
     `CHECK_ASTRO_NO_CACHE=1`。本机 `CI=true` 实测真跑 10.6 s。
2. **出图纪律：每轮最多 2 次**（改前看问题 1 次 + 交付 1 次）—— 已写入 §3、AGENTS.md、错题本 E25。
