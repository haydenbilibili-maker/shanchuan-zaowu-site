# 施工与发布流程（唯一事实源）· 2026-09-17 立

> 由产品负责人定义。**AI 施工方必须先读本节**，它决定了「哪些动作我可以自己做、哪些必须等验收」。

## 一、流程（六步，顺序即门禁）

| 步 | 动作 | 谁做 | 说明 |
|---|---|---|---|
| 1 | 在**施工仓（测试环境）**写代码 | **AI** | 所有施工只在施工仓进行 |
| 2 | 在**施工环境验收效果是否符合预期** | **产品负责人** | 未确认前，后续步骤一律不做 |
| 3 | 验收通过后**同步到开发仓（生产环境）** | AI（在收到「验收通过」之后） | 即 `npm run sync:miniprogram` |
| 4 | **提交上传编译到体验包** | **产品负责人手动** | 工具：微信开发者工具。**AI 不代做** |
| 5 | 人工验收通过后**提交微信审核** | 产品负责人 | — |
| 6 | 审核通过**发布到线上环境** | 产品负责人 | — |

### 两仓在开发者工具里怎么分（2026-09-17 加）

两仓内容按设计**逐字一致**，所以工具里光看内容分不出来。做法是给各自一个**显示名**：

| 仓 | 路径 | `project.config.json` 的 `projectname` |
|---|---|---|
| 施工仓 | `Business_Projects/shanchuanzaowu/miniprogram` | `山海造物·施工仓-改代码` |
| 开发仓 | `Business_Projects/WeChatProjects/shanchuanspecimens-只上传` | `山海造物·开发仓-只上传` |

- 该字段**允许两仓不同**（`check-miniprogram-sync.mjs` 里按字段例外，其余字段仍逐字比对；
  自检含「仅显示名不同 → 通过」「appid 不同 → 仍检出」两条，证明例外是窄的），
  因此 `npm run sync:miniprogram` **不会**把开发仓的名字覆盖掉。
- 改完名字后需在开发者工具里**重新打开项目**（或重新导入）才会显示新名称。

## 二、AI 施工方的三条禁止（在验收通过前）

1. **不部署云函数**。部署耗时长、且会把未验收的实现推给线上；
   代码与守卫可以先做完，部署等确认。
2. **不执行 `npm run sync:miniprogram`**（同步到开发仓）。开发仓是「已验收」的镜像，
   未验收就同步等于把测试态灌进生产态。
3. **不执行 `cli preview` / `cli upload`**（体验包上传/编译）。第 4 步是产品负责人手动完成的。

允许的动作：在施工仓改代码、跑**只读**守卫（`check:*` / `test:*`）、写文档、提交 commit。
其中「真实编译」类校验（`cli preview`）也在禁止之列 —— 需要编译结论时，由产品负责人在 IDE 里完成并把结果反馈。

## 三、反馈闭环

- AI 每次交付后应给出：**改了什么 / 在哪看（页面路径与入口）/ 期望看到什么 / 已知不确定项**，
  便于产品负责人在施工环境一次验收到位。
- 验收不通过时，只回「哪一条不符合预期 + 实际现象」，AI 在施工仓继续改，**不进入第 3 步**。

### 2026-11-23 订正：开发仓实际位置与「静默跳过」陷阱

- 本机开发仓实际在 `~/Documents/LifeOS_Workspace/_归档/Business_Projects/shanchuanspecimens-只上传`
  （显示名仍是「山海造物·开发仓-只上传」），**不在** `Business_Projects/WeChatProjects/`。
- `scripts/check-miniprogram-sync.mjs` 的默认目标指向后者；目录不存在时它按设计「安全跳过」并 **exit 0**
  —— 于是开发者工具里的开发仓长期停在 10-10 的版本（2026-11-23 实测：图鉴仍是 16 页，施工仓 80 页，漂移 237 处），
  而所有守卫全绿。**「双仓一致：安全跳过」不等于已同步。**
- 同步方式（二选一）：
  - `SYNC_DST="<开发仓绝对路径>" node scripts/check-miniprogram-sync.mjs --fix`（写入工作区外，需放开沙箱）；
  - 或把开发仓移回 `Business_Projects/WeChatProjects/shanchuanspecimens-只上传`，恢复脚本默认路径。
- ⚠️ **不要 `--fix --prune` 一起跑**：脚本的 prune 分支在前，发现内容不一致会先 `exit(1)`，结果一个文件都没修。
  正确顺序：先 `--fix` → 复查一致 → 需要时再 `--prune`。
