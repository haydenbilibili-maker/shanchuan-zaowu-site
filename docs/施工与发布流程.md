# 施工与发布流程（唯一事实源）· 2026-09-17 立

> 由产品负责人定义。**AI 施工方必须先读本节**，它决定了「哪些动作我可以自己做、哪些必须等验收」。

## 一、流程（六步，顺序即门禁）

| 步 | 动作 | 谁做 | 说明 |
|---|---|---|---|
| 1 | 在**施工仓（测试环境）**写代码 | **AI** | 所有施工只在施工仓进行 |
| 2 | 在**施工环境验收效果是否符合预期** | **产品负责人** | 未确认前，后续步骤一律不做 |
| 3 | 验收通过后**同步到开发仓（生产环境）** | AI（在收到「验收通过」之后） | 即 `npm run sync:miniprogram` |
| 4 | **提交上传编译到体验包** | **产品负责人手动** | 工具：微信开发者工具。**AI 不代做** |
| 5 | 人工验收通过后**提交微信审核** | 产品负责人 | — |
| 6 | 审核通过**发布到线上环境** | 产品负责人 | — |

## 二、AI 施工方的三条禁止（在验收通过前）

1. **不部署云函数**。部署耗时长、且会把未验收的实现推给线上；
   代码与守卫可以先做完，部署等确认。
2. **不执行 `npm run sync:miniprogram`**（同步到开发仓）。开发仓是「已验收」的镜像，
   未验收就同步等于把测试态灌进生产态。
3. **不执行 `cli preview` / `cli upload`**（体验包上传/编译）。第 4 步是产品负责人手动完成的。

允许的动作：在施工仓改代码、跑**只读**守卫（`check:*` / `test:*`）、写文档、提交 commit。
其中「真实编译」类校验（`cli preview`）也在禁止之列 —— 需要编译结论时，由产品负责人在 IDE 里完成并把结果反馈。

## 三、反馈闭环

- AI 每次交付后应给出：**改了什么 / 在哪看（页面路径与入口）/ 期望看到什么 / 已知不确定项**，
  便于产品负责人在施工环境一次验收到位。
- 验收不通过时，只回「哪一条不符合预期 + 实际现象」，AI 在施工仓继续改，**不进入第 3 步**。
