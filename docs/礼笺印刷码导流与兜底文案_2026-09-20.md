# 礼笺印刷码：导流文案 + 识别兜底 + 颜色根因（2026-09-20）

> 产品负责人原话两段：
> ①「目前的打印条件使得二维码的识别是一件很难的事情，让我们把二维码替换成一个 🦋 的水印吧，
> 参考预约卡片的水印样式，看看打印效果如何」
> ②「但是**我们仍然需要引导顾客到我们的小程序上**，我觉得文案可以更改一下，如：继续放二维码，
> 文案可以在下方说明：查看标本养护说明，如二维码识别困难可在微信上搜索山海造物」
>
> **②覆盖①**：码不换水印（换了就断了导流），改文案 + 修真正的可读性根因。

## 1. 结论先说（三件事，都能复现）

| # | 结论 | 证据 |
|---|---|---|
| 1 | 印刷用的**小程序码原来是品牌黄铜色 #C4A76C**，在米白卡面上对比度只有 **1.66:1** | `render-gift-print-preview.mjs` 实测；`generate-store-qr.js` 里 `line_color: BRASS` |
| 2 | 热敏头**没有灰阶** → 1.66:1 的中灰只能抖成 ~50% 散点，**亮模块也被点上黑点**，码在热敏模拟里是噪声 | 热敏成图（见交付对比图右下）；成块度 0.017 |
| 3 | 换 `--mono`（纯黑）后对比度 **16.6:1**，模块成块、可扫 | 同上，成块度回到正常 |

**所以"识别难"的主因不是"该不该印码"，而是"码印成了品牌色"。**
这句是本次最重要的结论：文案兜底是保险，**颜色才是根因**。

## 2. 改了什么

### 2.1 文案（A6 与贴纸**同源常量**，不再各写一份）

`miniprogram/utils/giftShareCard.js`

```js
const PRINT_QR_COPY = {
  miniprogram: '扫码看养护说明',
  service: '客服微信',
  hint: '二维码识别困难？微信搜索「山海造物」'
}
```

- 旧文案 `扫码进店` **只说"扫"，没说扫了能得到什么** —— 顾客无法判断值不值得扫；
- 新文案把**好处写在码下**，再补一行**识别困难时的第二条路**（微信搜一搜），
  这正是产品负责人要的"文案可以在下方说明"。
- 出现在两处（A6 页脚带 + 贴纸页脚带），**必须同源**：只改一个规格 = 同一份礼笺两个说法。

### 2.2 竖排位置：码块上提 `qrLift = 3mm`

贴纸白区 75mm 的纵向余量**只剩 23px**（原码底 863 → 纸底 886），放不下第二行小字。

`STICKER.qrLift` 把码块整体上提 3mm，把纸底让给「码下小字 + 兜底文案」两行。
上提**不会撞到右侧署名/日期**：

- 码右缘 `qrRight ≤ stampLeft − 2mm = 543`
- 署名下划线左端 `≥ axisRight − sigMaxW = 847 − 271 = 576`
- **543 < 576 ⇒ 横向不相交**（守卫「码块由 qrTop 定位 + 上提量在表里」钉住）

### 2.3 印刷码改纯黑 + 换落地页（**这条是根因修复**）

- `generate-store-qr.js` 新增 `--mono`（= `--lineColor 000000`）与 `--lineColor`；
  **默认仍是品牌黄铜**（不默认改，否则门店立牌那几张屏幕码会跟着掉品牌色）。
- 重新生成 `subpackages/manager/assets/qrcode/miniprogram-code-print.png`：
  - 落地页 `subpackages/feature/care/guide/index`，`scene=from=gift_print`（原来 300×300、无清单、指向未知）
  - 430×430 / 透明 / **纯黑**
- 侧车清单 `scripts/qr-assets/gift-care-code-print.json` 记下 page/scene/width/hyaline/**lineColor**/generatedAt。
  守卫**读清单**核对"纸上的文案承诺的落地页 = 码真正指向的页" —— 没有清单 = 无法核对 = 判红。
  （印出去就改不了，必须留证。）
- `subpackages/feature/care/guide/index.js`：解析 `options.scene`（getUnlimited 传的是整串 scene，
  不是 `from=xxx`），并新增 `contextKind === 'gift'` → 「来自礼笺 / GIFT NOTE」。

## 3. 为什么不是"把码换成 🦋 水印"

- **预约卡片的水印规格已查到**：`subpackages/business/booking/index.wxss:70-75`
  —— 🦋 emoji、260rpx、`opacity .08`、`rotate(-15deg)`、`grayscale(1) contrast(1.2)`、`bottom:-20rpx; right:-10rpx`。
- **但原样搬到贴纸上是非法的**（两处硬冲突）：
  1. 预约卡是**右下角**锚定，而贴纸右下 24mm 是**实物预印印章**（`stampLeft=567 / stampTop=727`，零落墨判据）；
     按 260/670 换算成 344px、右 −13 / 下 −47 → `x1=899>886`（出纸）且 `y≈933`（压在印章上）。
  2. 礼笺自己的规矩是**「黄铜纹样，禁 emoji」**（`feature/gift/compose/index.wxml:110`）。
- 更关键：**水印 0.08 的淡影在热敏上没有灰阶可表达** —— 要么被抖没，要么抖成噪声；
  而它替代掉的是**唯一的导流入口**。产品负责人第二句话正是把这个方向收回来了。

**结论：水印不做。** 若以后要，只应作为**正文区**的淡纹（不是右下角），且必须先真机打印验证。


真 Chrome + 真 `paintGiftPrintCard` + **真码素材**（data URL 喂进画布 —— 第一版没喂，
出图"假装很干净"），再做 Floyd–Steinberg 抖动，量四件事：

| 判据 | 下限 | 实测（贴纸 / A6） |
|---|---|---|
| 预印印章区零落墨 | 0 | 0（A6 无印章，不适用） |
| 页脚带真有墨（两枚码画上了） | 20000 | 24691 / 24009 |
| 兜底文案真有墨 | 400 | 3059 / 3845 |
| 兜底文案热敏存活 | ≥ 25% | 32% / 32% |
| **码的印刷对比度** | **≥ 4:1** | 小程序码 16.6:1、客服码 48.5:1（改前黄铜码 **1.66:1**） |

踩过的三个坑（都写进脚本注释了）：热敏模拟**必须先把纸白归一**（否则整张纸抖成麻点）、
量测区**必须先裁进画布**（越界像素是透明黑，会被算成满区落墨）、页脚放大图**不能用随手写的坐标**。

`test-gift-note-variants.mjs:218` 的「卡上不得有『山海』水印」锚点是 `card.indexOf('// 页脚带：左＝署名')`，

## 6. 仍未解决 / 待办

1. **24mm 预印印章位置仍是影像预估** —— 贴纸到货后必须印校准网格回填 `STICKER` 表（E8）。本次没动它。
2. **`stampTop` 挂在 `footerTop` 上**（`stampTop = STICKER.footerTop + STICKER.stampTopPad`）：
   以后谁为了收空间上移 `footerTop`，**模型里的印章会跟着上移而物理印章不会**，
   且所有判据都用同一张表复算 → 会**一起变绿**，属于静默失效。要动 `footerTop` 之前先把它改成绝对坐标。
3. **礼笺码未登记进 `utils/analytics/qrMaterial.js` 的 `QR_MATERIALS`** ——
   所以"礼笺扫码转化"目前没有单独归因。登记它属于那条并发流的文件，本次没动。
4. 兜底文案在热敏上存活 32%（1.78mm 字高）。真机印出来若偏糊，下一档是加粗或加大到 24px
   （白区纵向已排满，需与 `qrLift` 一起重新分配）。
