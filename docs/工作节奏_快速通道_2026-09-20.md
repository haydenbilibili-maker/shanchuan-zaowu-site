# 工作节奏：内循环提速（2026-09-20）

> 触发：产品负责人问「为什么每一轮任务要这么久」，并直接裁定
> 「**验证的工作我可以自己在开发仓库做，之后的对齐和同步的流程不要每次都做**」。
> 这份是那次核查的**实测数据**与**改后的节奏**。它约束的是**我（施工方）**怎么跑，不改业务逻辑。

## 1. 实测：慢在哪（本机实测，同一台机器同一天）

| 步骤 | 实测耗时 | 内循环需要吗 |
|---|---|---|
| `node scripts/run-guards.mjs`（全套 109 条） | **124.5 s** | ❌ 只在收口跑一次 |
| `node scripts/run-guards.mjs --domain gift-print` | 1.1 s | ⚠️ 会漏（见 §3） |
| **`npm run check:quick -- gift-print`**（本域 + 点名跨域） | **2.5 s**（4 条） | ✅ **内循环就用它** |
| 直接点名跑 3 条相关守卫 | **0.22 s** | ✅ 最快的那个 |
| 单条守卫（如 `check-gift-sticker-layout`） | 0.09 s | ✅ |
| `check-gift-sticker-layout --selftest`（26 条注入，无 Chrome） | 2.0 s | ✅ 改了被注入的文件才跑 |
| `render-gift-ops-card --selftest`（含 Chrome） | **93.7 s** | ⚠️ 攒着一起跑 |
| `test-wish-wall --selftest`（含 Chrome/intl） | **125.4 s** | ⚠️ 同上 |
| 施工仓 → 开发仓同步（`--fix`） | 0.83 s | ⚠️ **但每次要我以外的人批准沙箱**，真正成本在这 |

**结论**：单次往返里，"跑全套守卫"占了 **124 秒**，而真正需要的判据只要 **0.2 秒**。
2026-09-20 那两轮我在内循环里跑了 **7 次全套**（≈14 分钟纯等待）——这不是验证的代价，
是**把收口动作塞进了内循环**。同一轮里 Chrome 探针反复迭代又占掉约 20 分钟。

## 2. 核查出的「非必要流程」（都是我加的，不是仓库要求的）

| # | 我做的 | 仓库实际要求 | 判断 |
|---|---|---|---|
| 1 | 每改一点就跑**全套** `check:admin` | AGENTS.md 只要求「改了**被某条自检注入**的文件后，在隔离 worktree 里跑 `check:admin:selftest`」；全套是**收口/CI** 的事 | ❌ 过度 |
| 2 | 每轮都同步开发仓 + **复跑校验** | 只要求「**上传前**两仓一致」 | ❌ 过度 |
| 3 | 每个小改都写 `docs/` 交付记录 + 登记 `docs/README.md` | AGENTS.md 写的是「**新模块**先落 `admin/docs/` 蓝图、上线后登记索引」 | ❌ 过度（按钮排版不是新模块） |
| 4 | 每轮 push + 等 CI（1.5 min/次） | CI 是给 `main` 兜底的 | ⚠️ 应攒批次 |
| 5 | 用手工索引（`git hash-object`/`update-index`）+ 临时 worktree 复验来绕开并发流的改动 | —— | ⚠️ 这是**症状**：根因是开工没划文件边界 |

**真正必要的、不能砍的**：静态守卫 + 注入自检（证明判据会红）、真渲染探针（这一轮就是靠它查出
"码印成品牌黄铜色、热敏上 1.66:1 抖成噪声"——**任何静态检查都查不出这个**）、提交信息写清理由。

## 3. 顺手补的一个真缺口：`--domain` 会漏跨域守卫

`guards/_meta.json` 的 `crossWith` 是"把**整个** cross 域（62 条）拉进来"，太重；
而 `gift-print` 根本没在 `crossWith` 里 —— 所以 `--domain gift-print` **不会**跑
`test:gift-note-variants`，而我改礼笺文案**正好会打破它**（2026-09-20 就是漏到了最后才被外部报告点出来）。

补法：`_meta.json` 新增 `quickWith` —— 每个域**点名**那几条会互相打破的跨域守卫（不是整域）。

```json
"quickWith": {
  "gift-print": ["test:gift-note-variants"],
  "wish-wall":  ["test:gift-note-variants"],
  "manager":    ["check:product-fields-entry"]
}
```
（跨流扩充请各流 owner 自己加；改别人的域走变更请求。）

## 4. 新节奏（我照这个执行）

**内循环（每次改动，秒级）**
```bash
npm run check:quick -- <域>            # 本域 + quickWith 点名的跨域，约 0.2~2.5s
node miniprogram/scripts/<单条守卫>.mjs  # 需要时点名，0.1s
```

**收口（一个批次一次）**
```bash
npm run check:admin                    # 全套 109 条（124s）—— 一个批次只跑一次
npm run check:quick -- <域>            # 改动落在哪个域，其 --selftest 也要过
git commit && git push                 # 然后才等 CI
```

**开发仓同步：只在两种情况做**
1. 产品负责人说「我要在开发仓验」；
2. 发版收口。
平时**不同步、也不复跑校验**。产品负责人自己在开发仓做验证时，一条命令即可：
```bash
node scripts/check-miniprogram-sync.mjs --fix     # 施工仓 → 开发仓（单向推送）
```

**文档：分级**
- 小改（文案/版式/字段）：只写**提交信息**（要写清"为什么"），不额外落 `docs/`；
- 跨域改动 / 有产品裁决 / 有事故：落一份 `docs/` 记录并登记索引。

**开工先划文件边界**（10 秒，省掉后面 5 次往返）
```bash
git status --short      # 标出「我的文件 / 并发流的文件」
```
共享文件（`miniprogram/app.js`、`docs/README.md`、`package.json`、`guards/_meta.json`）
改动做到**最小且单独提交**，绝不整文件 `git add`。
