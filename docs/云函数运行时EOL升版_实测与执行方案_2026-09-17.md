## 2. 为什么升不掉：三条通道的实测结果

| 通道 | 结果 |
|---|---|
| `tcb fn deploy <name>` | ❌ **不应用 runtime**。我把 4 个函数的 `cloudbaserc.json` 改成 20.19 后部署，云端仍是 16.13。CLI 帮助也只声明它应用 `envId` / `timeout` / `memorySize` / `description` / `envVariables` —— **没有 runtime** |
| `tcb config update fn <name> --runtime Nodejs20.19` | ❌ **报成功但没生效**。CLI 打印「Updated: runtime=Nodejs20.19」，而 `tcb config diff` 显示云端仍是 `Nodejs16.13`（Cloud 16.13 / Local 20.19） |
| `tcb config update --all fn <name>` | ⛔ **危险，禁用**：`--all` 是「**配置文里的全部 130 个函数**」，不是「所有字段」 |

### ⚠️ 两个必须知道的坑

1. **`tcb config update fn <name>` 会覆盖环境变量**（这正是 CLI 在 diff 里建议你跑的命令）。
   `tcb config diff fn getStorePointRules` 的原文警告：

   ```
   ℹ Environment variable differences:
   ℹ   - ADMIN_OPS_KEY  (Cloud only)
   ℹ   - MESSAGE_ADMIN_OPENIDS  (Cloud only)
   ```

   「Cloud only」= 只存在于云端、本地 `cloudbaserc.json` 没声明。**跑那条命令就会把它们清掉**。
   在没有把 `envVariables` 写进 `cloudbaserc.json` 之前（而密钥**不该**进仓库），**不要用这条命令**。

2. **控制台升的版不会被 `tcb fn deploy` 打回**。
   我先前写过「下次部署会把它打回 Node16」—— **这是错的**，已更正：deploy 根本不碰 runtime
   （`getShippingRules` 升级后我再没部署过它，而同期我部署的 55 次里含 4 个试飞函数，
   它们的 runtime 一个都没变）。**所以控制台升版是安全的、持久的。**

## 3. 执行方案（只能走控制台，建议分包分批）

1. **入口**：微信开发者工具 → 云开发控制台 → 云函数 → 逐个「版本与配置」→ 运行时 → `Nodejs20.19`。
   （控制台支持多选批量改；若界面不支持批量，则按下面顺序分组，一组一组来。）
2. **建议分批顺序**（风险从低到高，每批之后做一次验证）：
   - 批 1：**纯只读**（`get*` / `list*`）：约 55 个 —— 无副作用，出错只影响读
   - 批 2：**管理/写入**（`manage*` / `upsert*` / `toggle*`）：约 45 个
   - 批 3：**支付与回调**（`payCallback` / `payOrder` / `refundOrder` / `confirmPayment` / `makeOrder` / `createDepositIntent` / `verifyStoreCoupon` / `authPhone`）：**最需要真机回归**
   - 批 4：**定时与通知**（`sweepExpiredOrders` / `dispatchMessage` / `send*` / `pushMessage` / `syncFinanceData`）
3. **每批的验证**（都很快）：
   ```bash
   cd miniprogram && tcb fn list -e cloud1-8gnkty5bfff9f0bf -l 300 --json   # 统计 runtime
   tcb config diff fn <抽查的函数> -e cloud1-8gnkty5bfff9f0bf              # 单函数权威复核
   node ../scripts/check-cloud-functions-sync.cjs                          # 代码仍与仓库一致
   npm run audit:fn-env                                                    # 环境变量没丢（A 区必须仍为 0）
   ```
4. **批 3 的真机回归清单**（Node16→20 唯一有实际风险的地方）：
   - 下单支付 → 支付回调落库 → 订单详情金额/状态
   - `authPhone` 手机号授权注册（依赖 `cloud.openapi.phonenumber.getPhoneNumber`）
   - 退款、优惠券核销、门店自提核销
5. **回滚**：控制台把运行时改回 `Nodejs16.13` 即可（配置项，秒级，无需改代码）。

## 4. 顺带查出的真实缺陷（非本轮引入）

**`manageWishWall` 缺 `DASHSCOPE_API_KEY` 与 `MESSAGE_ADMIN_OPENIDS`。**

- 证据：01:25 的 `audit:fn-env` 就已把它列在 **C 节（其它缺失）**；今天 12:26 复核仍是如此。
  **不是我这两天的部署弄丢的**（部署前后它都只有 `ADMIN_OPS_KEY`）。
- 后果：需求 28 的「**AI 生成一批心愿**」在生产**静默不可用**（代码里 `WISH_WALL_SECURITY`
  是刻意默认关闭的审核开关，那一个**不要补**；缺的是 DashScope 的 key）。
- 补法（控制台）：`manageWishWall` → 环境变量 → 从 `assistProductCopy`（或 `identifySpecimen`）
  复制 `DASHSCOPE_API_KEY` 的值；`MESSAGE_ADMIN_OPENIDS` 从 `manageProducts` 复制。
  **务必用「新增/合并」而不是「覆盖」** —— 覆盖会清掉现有的 `ADMIN_OPS_KEY`。
- 验证：`npm run audit:fn-env` 的 C 节里 `manageWishWall` 应从 3 项降到 1 项（仅剩刻意关闭的
  `WISH_WALL_SECURITY`），并在真机试一次「AI 生成一批心愿」。

## 5. 一句话交接

> 运行时升版**只能在控制台做**（CLI 的两条路都不生效/有破坏性），**做了不会被部署打回**；
> 131 个函数按「只读 → 管理写入 → 支付回调 → 定时通知」四批推进，批 3 必须真机回归。
> 另一个独立缺陷：`manageWishWall` 缺 `DASHSCOPE_API_KEY`，导致祈福墙 AI 生成在生产是哑的。
