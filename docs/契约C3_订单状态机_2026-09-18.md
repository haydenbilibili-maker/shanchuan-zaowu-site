# 契约 C3 · 订单状态机全枚举（草案 v1）

> **持有流**：`order`（订单）｜**状态**：草案，待产品负责人过目 + 集成官裁决
> **证据基线**：本 worktree 快照（分支 `feat/order`，快照自 `f0f22df` + 约 100 个他流未提交改动；**C3 只读这些改动，未提交任何一个**）
> **口径（E10）**：`文件:行号` 全部为**本轮逐行读源码实测**，不抄审计/不抄文档。
> 读不出写入方的，一律写「**未证实**」，不做推测填空。
> **与 C2 的关系**：C2（`pay` 持有）管「钱侧允许在哪些状态上动钱」；C3 管「状态枚举 + 迁移图 + 谁能写」。
> 两者在 §5 的 3 个接口点对齐。**C3 不改任何钱路径代码**（裁决 §2 红线 + 本任务书明令）。

## 1. 状态全枚举（从当前源码实证）

### 1.0 枚举口径说明（防 E7 假枚举）

本节**不**用 `grep "status: 'x'"` 单一形状枚举，因为实测有两种漏判形状：

- **变量式写入**：`const nextStatus = invite ? 'paid_awaiting_address' : (isRegularStorePickup ? 'ready_pickup' : 'paid')`（`confirmPayment/fulfillOrder.js:283-285`）—— 字面量在**赋值**行，不在 `status:` 行；
- **动态构造写入**：`refundOrder/index.js` 的售后分支把 `status` 放进 `updateData` 对象后整体 `update({ data: updateData })`（`:463`），`status:` 与字面量**不在同一行**。

所以下表把三种形状都算了，并逐条给出可复验的 `文件:行号`。**凡写入方只在白名单/读条件里出现的，一律进 §1.3「写入方未证实」，不进「在用」。**

## 5. 回答 C2 留给 C3 的 3 个接口点（裁决 §3）

### ① `refund_rejected` 是否合法终态？

**裁决建议：不是合法终态。应从枚举与全部代码路径移除（含 §4.2 的 M1–M13）。**

**理由（全部实测）**：

1. **服务端 0 写入方**（`refundOrder` 全文 919 行，`refund_rejected` 0 命中；`git grep refund_rejected` 在 `miniprogram/cloudfunctions/**` 0 命中）。
2. **服务端也没有「出边」**：`refundOrder:413`（买家申请）与 `:484`（店长发起）的 `allowFrom` 都不含它 → 即便出现也是死锁。
3. **设计意图本来是「回到原状态」而不是「进入被拒态」**：`refundOrder.staffRejectRefund`（`:529-583`）写的是 **`status: restoreStatus`**（动态值，来自 `statusBeforeRefund`，`:576`），并写 `refundRejectReason` / `refundRejectTime` 作为**拒绝证据**（`:577-578`）。
   → **正确的口径是：拒绝退款 = 状态回退 + 两个证据字段，而不是一个新状态。**
4. **它与 C2 已定的「钱侧只认 `refundNo`+`refundTime`」不冲突**：拒绝路径不写这两个字段，所以「钱没出」是可判定的。
5. **唯一「说它存在」的地方全在无法生效的路径上**：ERP 直写（被 `write:false` 拒）+ 客户端展示分支。

**给 C2 的联合口径（请 C2 在 v2 引用）**：

> **`refund_rejected` 不是 `orders.status` 的合法取值。**
> 「退款被拒」由一个**三元组**表达：`status = statusBeforeRefund`（回退到原状态） + `refundRejectReason`（非空） + `refundRejectTime`（非空）。
> 因此 **`orders.status` 的白名单里不得出现 `refund_rejected`**；任何依赖它做分支的代码是死代码。
