## 0. 结论（只看这段也能执行）

**三句话**

1. **现在不存在"并行开发"，只存在"多个进程轮流写同一个工作目录"。** 391 次提交、**0 次 merge**、只有 `main` 一条分支；
   我实测时（21:24）**最近 40 分钟内有 17 个文件被别的进程写过**，其中 `miniprogram/config/blessTags.js` 是 21:21 落的盘。
   这不是并行，是**没有隔离的串行**——写快点就撞车，写慢了就等。
2. **真正的瓶颈不是写代码，是七条流共用的少数几个"多写点"。** `package.json` 在近 200 次提交里被改了 **49 次（24.5%）**，
   全仓第一，第二名 `App.vue` 只有 14 次。而它承载的守卫清单是**一行 2690 字符、86 条 `&&` 串联**——
   任意两条流同时加守卫 = **100% 文本冲突**，且每次都要跑全量。
3. **治理顺序不能反**：**先物理隔离 → 再冻结契约 → 再分域门禁 → 最后放量**。
   先放量再补契约，必然返工（本仓已返工过：`docs/需求5_核销积分报错_修复记录_2026-09-16.md` §9 记录了并发提交把 `HEAD` 停在半成品上；
   `docs/发版审计_1.1.1_2026-09-16.md` N5 记录了并发跑守卫互相删固定临时目录、给出**假失败**）。

**五层模型（本文的架构主张）**

```
L0 冻结层  Freeze      先声明"谁能改什么"，零成本、立刻可做          ← 缺
L1 契约层  Contract    先冻结接口（字段/事件/签名/开关/令牌），再并行  ← 缺（祈福墙已部分在做）
L2 归属层  Ownership   每个多写点一个单写者(Single Writer)           ← 只有散文约定（施工总纲 W6 的交接清单）
L3 隔离层  Isolation   一流一 worktree + 短分支 + PR                  ← 完全没有
L4 门禁层  Gates      86 条单链 → 域链 + 受影响面                     ← 单链，无分域
L5 观察层  Metrics     用数字代替感觉                                 ← 没有
```

## 3. 架构思路

### 3.1 L0 冻结层：先把"谁能改什么"写成机器能读的东西

现状：冻结只存在于**散文**里，且只覆盖一条流 —— `docs/v1.1.2_全局细节雕刻_施工总纲.md` 的 W6 交接块：

> 「本 agent **不再改动**以下文件，避免冲突：`wish-wall/**`、`utils/wishWall.js`、`scripts/test-wish-wall.mjs`」

**这个方向是对的，但它挡不住人**：不写进注册表、不进守卫，下一个 agent 不知道，也拦不住。

**做法**：新建 `docs/并发工作流注册表.json`（**不动 `package.json`**，所以现在就能落地、与任何在飞的流都不冲突）：

```jsonc
{
  "version": 1,
  "streams": [
    {
      "id": "wish-wall",
      "owner": "agent:wish-wall",          // 单写者
      "phase": "W1",                        // 放量波次
      "owns": [                             // 排他：任何路径只能属于一条流
        "miniprogram/subpackages/feature/wish-wall/**",
        "miniprogram/utils/wishWall.js",
        "miniprogram/utils/wishRitual.js",
        "miniprogram/config/ritualPlays.js",
        "miniprogram/config/blessTags.js",
        "miniprogram/scripts/test-wish-wall.mjs"
      ],
      "consumes": [                         // 只读消费，不得改
        "miniprogram/styles/**",
        "miniprogram/components/AppModal/**",
        "miniprogram/components/RegisterAuthDialog/**"
      ],
      "guards": ["test:wish-wall", "check:bless-tags-sync", "check:wall-qr", "check:wall-monitor"],
      "switch": "showWishWall",             // 默认关，验收后开
      "invariants": ["弹幕布局确定性(禁 Math.random)", "轨道刻度成对", "图标为内联 SVG data-URI"]
    }
  ],
  "frozen": ["miniprogram/subpackages/feature/wish-wall/**"],
  "sharedBudgetKB": { "manager": 0, "feature": 64, "extra": 0 }
}
```

配套守卫 **`check:workstream-ownership`**（必须带 `--selftest`），四条判据：

| 判据 | 拦什么 |
|---|---|
| **互斥** 任何 `owns` 路径匹配到 ≥2 条流 → 红 | 两个流抢同一个文件（正是 R5 的三方撞车） |
| **冻结** `frozen` 路径出现在 `git diff --name-only <base>...HEAD` 且提交者不是 owner → 红 | "本 agent 不再改动" 从散文变成闸门 |
| **真实** `owns`/`consumes`/`hotFiles` 里的路径必须存在 → 否则红 | 注册表自身腐化 |
| **覆盖** `app.json` / `cloud.js` 的新增条目必须能被某条流的 `owns` 覆盖 → 否则红 | "谁的页谁不管"（新增页面无人认领是 R8 的前身） |

### 3.2 L1 契约层：七条流不是七份代码，是七个契约包

**原则**：**接口先冻结，实现后并行。** 谁要改契约，交"契约变更单"（一行 diff 写进本文 §4），由持有者落地，**不直接改文件**。

九张契约面（每一张都有现成的守卫落点，不许新造机制）：

| # | 契约面 | 冻结什么 | 持有流（单写者） | 消费流 | 校验方式（已有/待建） |
|---|---|---|---|---|---|

**还原动作会把它新写的内容回退掉**（R1 的活体演示）。

正确姿势是**在隔离副本里跑**（这正是决策 1 要买的保险）：

```bash
cd <repo>
rm -rf /tmp/wt-selftest && mkdir -p /tmp/wt-selftest
rsync -a --exclude node_modules --exclude backups ./ /tmp/wt-selftest/
ln -sfn "$PWD/node_modules" /tmp/wt-selftest/node_modules
cd /tmp/wt-selftest && npm run check:admin:selftest
```

> 前置事实（本轮实测）：`check-miniprogram-sync.mjs --selftest` 用 `mkdtempSync` 自造 fixture，
> **不碰真开发仓**；其余守卫的写入都限于自己的 ROOT 或 `mktemp -d`。所以隔离副本是安全的。
