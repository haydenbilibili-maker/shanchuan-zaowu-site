# 工作流信息 · 接入 / 类型 / 通报方式 / 音频覆盖 核查（2026-09-16）

> 核查对象：员工侧（超管 / 店长 / 标本师 / 主播 / 店员）与「工作流」相关的信息，
> 从**接入层**（谁把数据喂给前端）→ **类型**（有哪些工作流事件）→ **通报方式**（怎么告知人）→
> **音频覆盖**（#29 声音覆盖了哪些、漏了哪些）四层逐一核对。
>
> 结论一句话：**通报通道有 5 条，声音只覆盖「已进入 hub 预取且带计数」的 15 类；
> 仍有 5 类真实待办队列没有进入 hub 预取，因此既无角标也无声音；另有一条通道（微信订阅消息）6 个模板里只有 1 个可用。**

---

## 2. 类型：工作流事件全清单

### 2.1 员工待办（`dispatchMessage/templates.js` 判定为 workflow 受众，共 11 个模板）

| eventType | 业务含义 | 触发方 | 前端是否有计数 | 声音 |
|-----------|----------|--------|----------------|------|
| `staff_order_paid` | 新订单待处理 | payCallback / confirmPayment | ✅ `newOrderUnreadCount`(+ids) | ✅ `order` |
| `wishlist_restock_request` | 藏家想要补货 | wishlist 相关云函数 | ✅ `wishlistUnreadCount` | ✅ `wishlist` |
| `staff_deposit_paid` | 孤品定金已付 | manageDeposit | 标本师 ✅ `depositTodo`／hub ❌ | ✅（标本师 `artisanDeposit`） |
| `staff_deposit_balance_window` | 尾款窗口开启 | manageDeposit | 同上 | ✅（同上） |
| `staff_deposit_forfeited` | 定金罚没 | manageDeposit | 同上 | ✅（同上） |
| `staff_deposit_settled` | 定金结算 | manageDeposit | 同上 | ✅（同上） |
| `invoice_request_staff` | 新开票申请待办 | manageInvoiceRequests | ✅ `invoicePendingCount` | ✅ `invoice` |
| `approval_submitted` | 新审批待办 | manageApprovals | ✅ `approvalPendingCount` | ✅ `approval` |
| `approval_approved` / `approval_rejected` | 审批结果 | manageApprovals | ✅（同上，回落为计数） | ✅（同上） |
| `staff_artisan_sku_sold` | 藏品已售出（标本师） | 订单/商品链路 | ❌ **无计数**（仅站内信） | ❌ |

### 2.2 顾客通知（63 个模板，`customer` 受众）

订单/礼赠/预约/伴宠/鉴定/积分/小票/外部订单/生日礼/荣誉馆长……**面向顾客**，不是员工待办。
核对要点：`custom_inquiry_received`『定制意向已入册』、`pet_memorial_received`『伴宠记忆意向已入册』、
`store_receipt_submitted`『小票认领已入册』、`platform_order_submitted`『外部订单已入册』、
`support_ticket_received`『留言已入册』——措辞都是**「已入册」的顾客回执**，容易与员工待办混淆，
但受众是顾客，**不该进工作台声音**。

## 3. 通报方式：5 条通道 × 覆盖

| 通道 | 实现 | 穿透能力 | 覆盖范围 | 现状 |
|------|------|----------|----------|------|
| ① 菜单红角标 | `menu` 渲染各 `*Count` | 仅工作台内 | 8 组预取里的 6 类 | ✅ |
| ② 经营信号灯 + 信息流跑马灯 | `refreshOpsSignals()` / `buildOpsInfoFeed()` | 仅工作台内 | 订单/售后/客服/心愿/礼赠/审批/开票/工单/招募 + **直播中** + **营收环比↓** | ✅ |
| ③ 弹窗 | `maybeShowNewOrderPopup()`（按消息 id 去重，本地留 80 条） | 仅工作台内 | **只有新订单** | ✅ |
| ④ 站内信（工作流队列） | `getUserMessages{queue:'workflow'}` + `dispatchMessage` 落 `notification_logs`/`user_messages` | 小程序内、可回溯 | 11 个 workflow 模板 | ✅ |
| ⑤ 微信订阅消息 | `requestStaffAllSubscribe()` | **小程序外**（真正能叫醒人） | **6 个模板 ID 里只有 `STAFF_ORDER_PAID` 已上线**，工单类 5 个（审批/开票/定金/补货/伴宠指派）ID 为空 → 云函数 `TMPL_PENDING` 优雅跳过 | ⚠️ **1/6 可用** |
| ⑥ 声音（#29，新增） | `utils/workNoticeVoice.js` + `WorkNoticeVoice` 组件 | 仅工作台内（进/回工作台、下拉刷新时判定） | 15 类（见 §4） | ✅ |

**通道能力对比（这是本次核查最重要的结论之一）**：
- ① ② ③ ⑥ **都只在「工作台页面活着的时候」有效** —— 人不在小程序里就没有任何提示；
- 真正能穿透到小程序外的只有 ⑤，而它现在**只有新订单一条模板可用**；
- 因此「值班时不在工作台 → 漏掉售后/审批/开票/定金」是当前架构固有的缺口，属于需求 #16/#33（统一通知层）的范围。

## 4. 音频覆盖范围（#29 实测）

### 4.1 已覆盖（15 类，全部挂在真实计数上）

| 类型 | 计数来源 | 角色 | 首次接入通道 |
|------|----------|------|--------------|
| `order` | `newOrderUnreadCount` + `newOrderUnreadIds` | 超管/店长 | ① ② ③ ④ ⑤ |
| `aftersale` | `opsOrderCounts.aftersale` | 超管/店长 | ② |
| `workOrder` | `supportTickets.length` | 超管/店长/标本师 | ② |
| `customOrder` | `customOrders.length` | 超管/店长/标本师 | ② |
| `artisanMake` | `jobPendingMake` | 标本师 | ③（artisan 页待办区） |
| `artisanShelf` | `workPendingShelf` | 标本师 | 同上 |
| `artisanShip` | `jobPendingShip` | 标本师 | 同上 |
| `petOrder` | `petOrderTodo` | 标本师 | 同上 |
| `artisanDeposit` | `depositTodo` | 标本师 | 同上 |
| `booking` | `bookings.length` | 超管/店长 | ② |
| `invoice` | `invoicePendingCount` | 超管/店长 | ① ② ④ |
| `approval` | `approvalPendingCount` | 超管/店长 | ① ② ④ |
| `gift` | `giftTodoCount` | 超管/店长 | ① ② ④ |
| `wishlist` | `wishlistUnreadCount` | 超管/店长/标本师 | ① ② ④ |
| `recruit` | `framerRecruitApps.length` | 超管 | ① ② |

**覆盖口径**：声音覆盖 = 「hub 8 组预取的落库字段」∪「标本师工作台待办计数」。
15 类之外，hub 还渲染了 2 条**非待办**信息流（`直播中`、`营收环比↓`），
它们不是「新的工作信息」，因此**刻意没有声音**。

**按角色可播条数**（同一个引擎按角色过滤，不是三套逻辑）：超管 **10** 类 / 店长 **9** 类 / 标本师 **8** 类
（+ 每位都有 1 条试听样音）。

### 4.2 未覆盖（有真实待办队列，但没进 hub 预取）

| # | 待办 | 证据（字段/来源） | 现状 | 要有声音需要什么 |
|---|------|------------------|------|------------------|
| 1 | **门店待自取核销** | `subpackages/manager/staff/field/index.js` `pendingPickups`（`managerShipOrder{action:'listPendingPickups', storeId}` 返回的「待自取订单」列表） | 只在现场核销台页内可见；无角标、无信息流、无声音。⚠️ 还依赖 `managerShipOrder` 已部署该 action（未部署时页面提示「待自取列表需先更新云端版本」） | hub 预取加一组 loader（`menu.verify \|\| menu.staffConsole`）→ 加 `pickupsPending` 类型 |
| 2 | **定金待付 / 待付尾款（超管视角）** | `deposit-ops/index.js` `counts` / `countsTotal`（`listIntents` 返回，页签为「待付定金 / 待付尾款」，`guardStaffPage('super_admin')`）；hub 侧只有**指标**：`analytics.deposit.{counts,paidDepositAmountFmt,settledCount}`（金额与已结算数，不是待办队列） | 标本师侧已有声音（`artisanDeposit`），**超管/店长侧没有** | hub 预取加 `menu.depositOps` → `depositPending` 类型（先确认 `counts` 键语义） |
| 3 | **出货单待出货** | `shipment-ops`（`dashboard` / `list`，工作台菜单有入口） | 无 hub 计数 | 先在 hub 接入计数（`dashboard` 返回值里挑「待出货」）再谈声音 |
| 4 | **采购单待收货** | `purchase-ops`（同上） | 无 hub 计数 | 同上 |
| 5 | **成品库存待上架审核（超管视角）** | `inventory-ops`；标本师侧 `workPendingShelf` 已覆盖 | 超管/店长侧无计数 | 先确认 `inventory-ops` 是否有「待上架」计数 |

### 4.3 有信号但不该发声（附理由，避免被当成漏做）

| 信号 | 为什么不做声音 |
|------|----------------|
| `直播中`（信息流 `live`） | 是**状态**不是「新的工作信息」；开播/预约提醒应走订阅消息 |
| `营收环比↓`（信息流 `mom`） | 经营指标，非待办 |
| 库存规模（`dashStock`） | 只有 `onShelf/offShelf/stockTotal`，**没有安全库存阈值** → 挂上去只会是个永远为 0 的假信号 |
| 门店积分规则「待超管审核」 | `store-points.pendingApproval` 是**布尔状态**（保存后进入审核），不是待办队列 |
| 顾客侧 63 个模板 | 受众是顾客，不是员工待办（见 §2.2） |

### 4.4 一条"有事件但缺计数源"的缺口

| 事件 | 现状 | 可行做法 |
|------|------|----------|
| `staff_artisan_sku_sold`（藏品已售出，发给标本师） | 有站内信（category `ops`、queue `workflow`），**没有任何前端计数** | 用未读工作流消息数做信号（与新订单同法），或在 artisan 页加「已售出」计数 |

## 5. 结论与建议（按优先级）

| 优先级 | 动作 | 理由 |
|--------|------|------|
| **P0** | 补**门店待自取核销**（`staff/field.pendingPickups`） | 顾客在店里等，是唯一"人在现场、必须立刻知道"的待办，却完全没有提示 |
| **P0** | **微信订阅消息工单类 5 个模板 ID 回填** | 现在只有新订单能穿透到小程序外；审批/开票/定金/补货/伴宠全靠"人恰好在工作台"，等于没推送 |
| **P1** | hub 接入**定金待办**（超管/店长），加 `depositPending` 类型 | 同一业务标本师有、超管没有；`deposit-ops` 已有 `counts` |
| **P1** | 加**审批超时**类型（`approvals.overdueCount`） | 数字已经有了，只差一个类型与一条音频；超时审批是真正会烂尾的工作流 |
| **P2** | hub 接入**出货单待出货 / 采购待收货**计数，再决定是否发声 | 需要先有计数（当前 ops 模块只有状态列表） |
| **P2** | 加**藏品售出**（标本师）通知 | 有事件无计数；需先定义计数源（建议用未读工作流消息） |
| — | 不做：直播中 / 环比 / 库存 / 积分规则待审 | 见 §4.3 |

**架构级提醒**：①②③⑥ 都依赖"工作台页面活着"，真正的值班提醒能力取决于 ⑤（订阅消息）。
建议把「工作流事件 → 订阅消息模板」的映射补全，与需求 #16/#33 的「统一通知层」合并推进，
否则声音做得再好，也只是"打开小程序的人听得见"。
