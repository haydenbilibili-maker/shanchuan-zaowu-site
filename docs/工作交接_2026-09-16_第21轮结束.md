且不给「枚举谁点赞了」留口子。若将来要做「点赞列表」，**不要放宽规则**，应在云函数里出聚合。

## 6.8 审计 P0-11 剩余三集合已创建（产品负责人指示）

`vip_cards` / `equity_goods` / `feishu_shipments` 三个集合已创建。
但**只建集合是不够的** —— 建之前我先读了代码，发现两件必须先处理的事：

### ① 规则口径不是「随便选一个」

ERP 前端是**匿名登录**（`signInAnonymously`），所以：
- ❌ `write: "auth != null"` = 任何拿到匿名身份的人都能写（**开天窗**）
- ✅ 仓库既有约定是 `read: "auth != null"` + **`write: false`**，写入一律经 `manageStoreContent` 代理
  （对标最接近的同类 `rewards`）

三个集合都按该约定创建，规则两份（`cloudbase/rules/` ↔ `miniprogram/database-rules/`）逐字一致。

### ② 只建集合会让 ERP「从『无法保存』变成『保存报权限错』」

`Marketing.vue` 走 `cdnAdd/cdnUpdate`，其中：
- 集合**在** `STORE_CONTENT_WRITE_COLLECTIONS` → 走 Pages 代理 → `manageStoreContent`（店长/超管鉴权）
- 集合**不在** → 浏览器直写 CDN → 被 `write:false` 拒绝

这三个集合此前**都不在名单里**。所以同时补齐了**两处允许名单**（缺一侧即不可用）：
- 服务端 `manageStoreContent.ALLOWED_COLLECTIONS`
- 前端 `admin/src/utils/cloudbaseCdnDb.js` 的 `STORE_CONTENT_WRITE_COLLECTIONS`

并**部署了 `manageStoreContent`**（否则服务端名单还是旧的，会回「集合未授权」）。

### ③ 顺手把「两份名单必须一致」变成守卫

仓库里原本有一个**孤儿守卫** `admin/scripts/check-proxy-allowlist-sync.mjs`
（写好了、有自检，但**从未被任何 npm 脚本调用**）。它只管**函数级**名单；
而集合级名单（我这次依赖的那对）**根本没人管**。故：
- 扩展它同时校验**集合级**名单（`extractObjectKeys` 只取顶层键，避免把 `configs` 的子键当集合名）
- 接入 `check:admin` 与 `:selftest`
- 上次盘点说「不敢擅自接线别人的脚本」——这次它是我改动正确性的直接依赖，必须接

### ④ 修掉一个真实的并发缺陷

核对部署结果时 `check-cloud-functions-sync.cjs` 连续报
`ENOTEMPTY: directory not empty, rmdir '/tmp/dsh-fn-drift'`。**根因不是权限或网络**：
它用**固定临时目录** `/tmp/dsh-fn-drift`，两个进程并发跑（部署脚本 + 手动核对，或与并行流程）
会互相 `rmSync` 对方正在下载的目录。
已改为 `mkdtempSync` 唯一目录 + 容忍清理失败；**实测两个进程同时跑都通过**。
