## P1 · 本轮应当修（4 条已由集成官独立复跑确认为真）

### P1-1 云函数把「查询失败」伪装成 `success:true` + 空列表

- **现象**：集合/索引异常时，弹幕墙显示「墙面还是空的 · 做第一个许愿的人」，愿签区「还没有人许愿」，
  「我的心愿」显示「你还没写过」。**用户看到的是一个假事实。**
- **证据**：`miniprogram/cloudfunctions/manageWishWall/index.js:225-228`（`listPublic` 的 catch
  返回 `{ success: true, list: [], fallback: true }`）、`:315-317`（`listMine` 同）；
  页面只认 `result.success`（`subpackages/feature/wish-wall/index.js:955-965`）；
  假事实分支 `index.wxml:123-128`、`:514`。
- **影响**：目标 2 的第一印象 + **把本批刚做的 `loadError` / `quota.unknown` 诚实修复在网络层之下全部架空**。
- **为什么守卫没抓到**：守卫只在 **WXML 层**断言「失败不说空」，**不测云函数回包形状**。
- **集成官复核**：✅ **已复跑确认**（`manageWishWall/index.js:226` 实为 `return { success: true, list: [], inspiration, productKey, fallback: true }`；
  页面 `:955` 只判 `result.success`）。
- **修法**：云函数 catch 回 `success:false`（或页面显式识别 `fallback`）；两侧都要。
  **光改一边没用** —— 只改云函数而页面仍只认 `success` 会继续渲染空墙。

### P1-2 主注册路径（落愿门禁）不把仪式进展存云 → PRD §6「注册后立刻发生三件事①」断链

- **现象**：在落愿弹窗注册成功、心愿自动续发后，连灯/木鱼记录**仍只在本地**，换机即丢。
- **证据**：`index.js:1398-1415` 的 `onRegisterSuccess` 只有 `justRegistered` + refreshSession + 续发，
  **没有** `syncRitualToCloud()`；该函数只在 `:1577`（H1，开关默认**关**）、`:1705`/`:1800`（H2，已停用）被调。
  `restoreRitualFromCloud`（读）在 `onLoad:349` 无条件跑，**但主路径从不写**。
- **影响**：**目标 3**。PRD §6 原文：「注册后必须立刻发生三件事（**缺一条这个钩子就白做**）」
  —— ① 把已有进展存上云（"你的记录不会丢了"，这是用户能感知的回报）。
- **集成官复核**：✅ **已复跑确认**（`onRegisterSuccess` 体内无 `syncRitualToCloud`）。
- **修法**：`onRegisterSuccess` 里补一次 `syncRitualToCloud()`（fire-and-forget，失败不得影响续发）。

### P1-3 漏斗终点埋点 `targetId` 与 ERP 监测表口径不一致 → **落愿行恒 0**

- **现象**：ERP「祈福墙 · 注册转化监测表」的「落愿成功（上墙）」行与按来源转化率**永远是 0**。
- **证据**：客户端发 `trackBehavior('wish_wall_post', 'ok', '1')`（`index.js:1361`）——
  按签名 `trackBehavior(action, targetType, targetId, extra)`（`utils/analytics/index.js:198`）
  即 **targetType=`ok`、targetId=`1`**；
  而 PRD §7.1 写的是 **`targetId=ok`**，ERP 也按 `String(ev.targetId) !== 'ok'` 过滤
  （`admin/src/utils/wishWallMonitor.js:39` `target:'ok'`、`:67` 比较、`:142` 归来源）。
- **影响**：北极星（扫码→成交）与目标 3 的 §9-5 数据关联**都测不出来**。
- **为什么守卫没抓到**：`check:wall-monitor` 用**合成行** `targetId:'ok'` 自测，
  **从不核对客户端实发值** —— 所以 27/27 全绿也盖不住。
- **集成官复核**：✅ **已复跑确认**（两侧原文都已打印核对）。
- **修法**：改客户端为 `trackBehavior('wish_wall_post', ..., 'ok')`（**以 PRD 为准**）；
  并给守卫补一条**端到端一致性**断言（客户端实发 `targetId` == 监测表期望值），否则同类错还会复发。

### P1-4 玩法资料缓存 `_playProfile` 永不失效 → 补完资料回来仍被挡

- **现象**：点「星座签/MBTI」被引导去补资料 → 填好 → 返回 → **再点同一张瓦片仍要求去补**。只有退出页面重进才恢复。
- **证据**：`index.js:474` `if (this._playProfile) return this._playProfile`，`:480` 连**空串也缓存**；
  全仓 **0 处重置**、`onShow` 不失效。
- **影响**：**目标 1** 的「抽一句 → 写成心愿 → 推荐」对缺资料用户是**死路**。
- **为什么守卫没抓到**：`test-wish-wall.mjs:4130` 把 `loadPlayProfile` **整个桩掉** → 877 条断言看不见它。
  （与交付记录里那个 P0 同一类盲区：**桩住了被测对象**。）
- **集成官复核**：✅ **已复跑确认**（全仓仅 474/480 两处出现 `_playProfile`，无重置）。
- **修法**：进资料页/`onShow` 时失效缓存（一行级别）。

### P1-5 「我的心愿」没有加载态/错误态

- **现象**：进页后立刻切「我的心愿」，或 mine 读失败后切过去 → 显示「你还没在这面墙上写过心愿」+ 条数 0。
- **证据**：`applyView`（`index.js:1007-1020`）用 `this._mineRows || []`，**无 loading 标志**；
  `loadMine` 的 catch（`:1149-1170`）只改 `quota.unknown`，不标 mine；`index.wxml:514` 只看 `!items.length`；
  全仓 grep 无 `mineLoading` / `mineError`。
- **影响**：目标 3（第一眼被劝退）+ 诚实口径。
- **集成官复核**：⬜ 未逐行复核（与 P1-1 同源，随 P1-1 一起修）。
- **修法**：补 `mineLoading` / `mineError` 两个状态 + WXML 三态渲染。
