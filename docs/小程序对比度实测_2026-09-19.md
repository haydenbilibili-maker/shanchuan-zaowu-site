## 0. 一页结论

| 项 | 结果 |
|---|---|
| 扫描范围 | `miniprogram/**/*.wxss` 172 个文件（已排除 `node_modules`） |
| 「同一规则内同时写了 `color` 和 `background`」的配对 | **602 对** |
| 其中按 WCAG 算出来 < 4.5:1 的 | **79 对** |
| 按家族去重后的**确证违规** | **62 条**（A 家族 15 / B 家族 21 / C 家族 18 / D 家族 7 / E 家族 1） |
| **疑似**（静态推不准，不许猜） | **15 类**（§5 的 S1~S15，含渐变跨线 / 条件类名 / 跨组件作用域） |
| **禁用态豁免**（WCAG 1.4.3 例外） | 8 条 |
| **已排除的假阳性** | 4 类（见 §7，含 3 处我第一轮算错、后来自己推翻的） |

**三个最重要的结论：**

1. **`--color-text-muted` (#6B6560) 是本仓最大的系统性隐患。**
   它被用了 **783 次**，但在**三种标准深色面上全部不达 4.5:1**：`#1A1814` 上 3.09、`#1F1D1A` 上 2.93、`#262320` 上 2.72。
   → 只要它出现在深色面上，**不需要知道父容器是谁，就已经违规**（这是少数可以「与父面无关」直接判定的情形）。
   其中相当一部分是禁用态（WCAG 豁免），但**空态提示、图例、次级说明等真实内容也大量在用它**。

2. **「亮金/铜金写回浅色面」的假绿形态在小程序里是真实存在的，而且比 ERP 那处更严重。**
   `#C4A76C` 在深色面上是 7.67（很安全），但在浅色面上一路掉到 **2.14 / 1.86 / 1.50 / 1.25**（`brass-50/100/200/300`）。
   实测到的确证点：会员卡 `level-skin-2` 木质浅面 + `#8B6F47` = **2.82~3.61**；祈福墙羊皮纸浅面上的 `#8A7530` = **3.31~3.74**。

3. **`#D64045`（错误红）自带两种互斥的用法，两种都踩线。**
   - 当**文字**压在 8%~16% 红 tint 上（状态胶囊/标签，**21 处**）：**3.00~4.02**，在**所有**合理父面上都不达 4.5。
   - 当**背景**反白字：`#fff` on `#D64045` = **4.49** —— 差 0.01 过线，一个巨大的簇（11+ 处）全卡在同一个值上。

## 1. 方法与证据边界（**先读这一节**）

### 1.1 单位口径 —— rpx 到底等于多少 pt

小程序 WXSS 的 `rpx` 是**随屏宽缩放**的长度单位：`750rpx = 屏宽`。换算到 WCAG 用的 CSS px：

| 设备屏宽 | 1rpx | WCAG「大字」阈值（常规，24px） | WCAG「大字」阈值（粗体，18.66px） |
|---|---|---|---|
| 320px | 0.427px | 57rpx | 44rpx |
| **375px（参考口径）** | **0.5px** | **48rpx** | **≈38rpx** |
| 414px | 0.552px | 44rpx | 34rpx |
| 428px | 0.571px | 43rpx | 33rpx |

**这条口径决定了绝大部分判定**：本仓 4495 处 `font-size` 里，绝大多数 ≤ 36rpx。
换句话说，**在本仓几乎所有文字都按「正文」口径走，阈值是 4.5:1 而不是 3:1**。
只有 48rpx 及以上（或 ≥38rpx 且粗体）才够格走 3:1 —— 本次实测到的确证项里**只有 1 处**（`.pass-qr-stamp`，64rpx）够格，
而它连 3:1 都不到（1.26~2.36），所以口径之争不影响结论。

> 本报告统一按 **375px 参考宽度**（iPhone SE/8 类，`1rpx = 0.5px`）判定；更宽的机型会让阈值略降，
> 但不会把任何一个 < 3.0 的项救回 4.5，也不会把 4.49 救回 4.5。**边界结论对机型不敏感。**

### 1.2 三轮静态扫描做了什么

| 轮次 | 方法 | 产出 |
|---|---|---|
| A | 解析 `app.wxss` 的 `page { --x: ... }` 得到令牌表；逐规则抓「同一规则内既有 `color` 又有 `background`」的配对；`var()` 递归展开（含 fallback），`rgba()` 按父面做 alpha 合成 | 602 对，其中 79 对 < 4.5 |
| B | 抓「只写了 `color`、同规则没有 `background`」的声明（**1002+878+719+... 共 3000+ 条**），按**解析后的颜色值**聚合，对 `#1A1814/#1F1D1A/#262320` 三个标准深色面各算一遍 | 找出「三种深色面全不达」的颜色 → 与父面无关即可判定 |
| C | 用 WXML 解析出元素的**祖先链**，再按祖先 class 反查 CSS 里最近的 `background` | 把「跨规则 / 跨元素」的底追出来（本次 5 处深挖全靠它） |

### 1.3 证据边界：什么证得了、什么证不了

**证得了（可作为结论）：**

- 同一规则里同时给出、且**背景不透明（alpha = 1）**的前后景 → 比值是**算出来的**，与父容器无关。**这是最硬的一档。**
- 半透明底（如 `rgba(214,64,69,0.12)`）→ 我把它在 `#1A1814/#1F1D1A/#262320/#FAF6ED/#F2EDE4/#EFE8DA/#FFFFFF`
  七种候选面上各合成一次。**若七种面全部 < 4.5，则「无论父面是谁都违规」**，同样可以定案
  （B 家族全部满足此条件；A 家族的 `.pass-qr-stamp` 也满足）。
- 父面**不透明且已由祖先规则证明**的情形（§4 抽样复核）→ 可以定案。

**证不了（一律进「疑似」，不猜）：**

- 渐变的**中间过渡带**：文字落在浅色高光带还是深色带上，静态判不出。只能给出区间的两端（本次 `level-skin-*` 全部如此）。
- 父面来自**半透明叠层**、`backdrop-filter`、`filter: brightness()`、图片/纹理、或运行时注入的样式。
- **条件类名**（`{{cond ? 'a' : 'b'}}`）互斥分支里只有一支能生效，静态判不出实际渲染的是哪支。
- **跨组件 `styleIsolation`**：本报告的祖先追踪是**同 Page 的 WXML 树**；自定义组件的样式隔离边界见 §9。
- 小程序 `text-shadow`（如 `level-skin-5` 的激光雕刻描边）**不能按 WCAG 公式计入** —— 本报告严格不计，所以对 skin-5 是**偏悲观**的判定。

### 2.2 字阶令牌（契约 C7）

`--fs-16 … --fs-48` 共 14 档，定义在 `app.wxss` 第 75–88 行。

（`fs-20`×2、`fs-24`×1、`fs-26`×1、`fs-28`×1、`fs-34`×2，其余 0）
→ 结论：**字阶令牌目前是「定义了但没用」的状态**。这不影响对比度判定（对比度与字号只在「大字/正文」分档处相关），

### 2.3 命名/层级要点

- 同一颜色常有 **2~3 个别名**（`--gold` = `--primary` = `--brass-400` = `--color-text-latin` = `#C4A76C`）。
  守卫若按「令牌名」写判据，必须先把别名归并，否则会漏。
- 深色面上「同级」的文字色有 `--color-text-primary/secondary/body/muted` 四档，
  **只有 `muted` 一档不达 4.5** —— 这意味着修起来可以很局部（抬亮一档即可），不必动设计语言。

## 4. 抽样复核：背景色到底是怎么确定的

**至少 3 处**「确证违规」回源码复核。核心不是「看到那一行」，而是**把生效的背景色追出来**。

### 复核 1：`styles/badges.wxss` `.badge-info` —— 3.88（最硬的一档：不透明同规则）

**结论：`#FFFFFF` on `#5A86A8` = 3.88，阈值 4.5。**

背景是怎么确定的（**五步，不靠猜**）：

1. `read styles/badges.wxss` 第 60–67 行，`.badge-info` 规则**内部**同时写了
   `background: #5A86A8;`（:61）与 `color: var(--color-text-primary);`（:63）；
   紧随其后 `.badge-info text { color: var(--color-text-primary); }`（:65–67）覆盖子 `<text>`。
2. `#5A86A8` 是**不透明字面量**（无 `rgba` alpha、无 `var()`、无渐变）→ **父容器是谁都不影响**。
3. 令牌展开：`--color-text-primary: #FFFFFF`（`app.wxss:33`）。
4. 字号复核：基类 20rpx（`:22`）、`.badge-sm` 16rpx（`:97`）。按 §1.1 口径 20rpx = 10px = 7.5pt，
   **远不到大字**（需 24px 或 18.66px 粗体），故阈值 4.5。
   `font-weight: 600` 也不足以改判 —— 粗体大字门槛是 18.66px，而这里最多 10px。
5. 可达性：`grep -rn "badge-info" --include=*.wxml` → 8 处真实使用（含 `manager:241` 待办计数）。

**结论：确证。** 唯一残留不确定性：若某处父级用 `!important` 或行内 `style` 覆盖了 `background`，则该处失效——
`grep -rn "badge-info" --include=*.wxml` 的 8 处均为类名，未见行内 `style`。

### 复核 2：`subpackages/manager/manager/index.wxss:2380` `.vc-btn` —— 2.47（跨文件作用域证明）

**结论：`#fff` on `#52B788` = 2.47，阈值 4.5。**

这一处**难点不在颜色，而在「这条规则到底生不生效」** —— 因为它的使用点在**另一个目录**的 WXML 里：

1. 规则在 `subpackages/manager/manager/index.wxss:2380`：`background: #52B788; color: #fff; font-size: 26rpx; font-weight: bold;`。
   → **不透明字面量**，同规则配对，父面无关。
2. 使用点在 `subpackages/manager/manager/workspace/_subviews.wxml:1055`。
3. **样式作用域链**：`workspace/index.wxss` 第 1 行是 `@import '../index.wxss';`
   → 所以 `manager/index.wxss` 的 `.vc-btn` **确实作用于 workspace 页**。
4. **模板包含链**：`workspace/index.wxml:7` 是 `<include src="_subviews.wxml" />`
   → 所以 `_subviews.wxml` 的内容**确实渲染**（不是孤儿文件）。
5. 字号：26rpx = 13px ≈ 9.8pt，粗体但远低于 18.66px → 阈值 4.5。

**结论：确证。** 若只查 `manager/index.wxml` 会误判为「死 CSS」——这正是本仓反复踩的坑（静态 ≠ 事实）。
同类还有 `.btn.verify`（`:1508`，同样 2.47，用在 `_subviews.wxml` 6 处）。

**⚠️ 反例对照（我第一轮判错、已排除的）**：`.btn.verify` 与 `.vc-btn` 在第一轮「类名是否出现在 WXML 文本里」的
粗筛中被判为死规则 —— 因为使用点在 `_subviews.wxml` 而非主 WXML。**粗筛不可信，必须追 include/@import。**

### 复核 3：`subpackages/feature/wish-wall/index.wxss:202` `.ww-scope` —— 3.31~3.74（**追父面把 2.95 修正为 3.74 上限**）

## 8. 能不能据此立一条守卫？

### 8.1 判断：**能立，但只能立一条「窄而硬」的守卫；立宽的一定是假闸门。**

**理由是数据本身给的：**

- ✅ **可守的**：同一规则内 `color` + `background` 的配对（本次 602 对）。这档**不依赖父面、不依赖运行时**，
  是纯静态可判定的，而且本次 **62 条**确证里有 **60 条**落在这一档
  （另 2 条是 `app.wxss` 的全局类 `.signal-legend-text`/`.empty-text`，需要追父面）。
  它**能被证明会失败**（符合本仓对守卫的硬要求）。
- ❌ **不可守的**：任何需要「父面 / 渐变位置 / 条件类名 / 运行时数据」的判定。
  本报告 §5 已经证明：同样一条规则，换个父面就从 1.73 变 5.37（假阳性），
  或从 6.80 变 2.11（假阴性）。**把这类写进守卫 = 制造本仓最忌讳的假闸门。**
- ⚠️ **最容易写错的一条**：按「令牌名」守（「`--color-text-muted` 禁用」）。
  数据说 **`#6B6560` 在浅色面上是 4.93 ✅**（会员卡纸白卡就在这么用）。
  按令牌一刀切会**同时**产生假阳（浅面合规用法被拦）和假阴（`#8B6F47`、`#302810` 等写死值绕过）。
  → **判据必须是「解析后的颜色值 × 解析后的背景值」，不是令牌名。**

### 8.2 建议的判据形态（**只是建议，本报告不实现**）

```
守卫名（域内）：check:mp-contrast
作用域：miniprogram/**/*.wxss（排除 node_modules）

只检查一个条件 —— 同一规则块内同时出现 color 与 background(-color)，且：
  1. background 解析后 alpha == 1（不透明），或
     background 为 rgba() 且该 tint 在 {#1A1814,#1F1D1A,#262320,#FAF6ED,#F2EDE4,#EFE8DA,#FFFFFF}
     七种标准面上合成后**全部** < 阈值（即「与父面无关的不达」）；
  2. 两端的 var() 能递归解析到字面量（含 fallback）；解析不到 → 跳过并计入 skipped 清单（不判违规）；
  3. 阈值按字号分档：
       - font-size >= 48rpx            → 3.0
       - font-size >= 38rpx 且 bold    → 3.0
       - 其余（含未写 font-size）       → 4.5
     （font-weight >= 600 视为 bold；字号解析不到 → 按 4.5，从严）
  4. 白名单（每一条都要写明理由，不许「因为红了所以加」）：
       - 选择器含 disabled / [disabled] / submitting / is-disabled / .card-inactive  → WCAG 1.4.3 豁免
       - 纯装饰/水印类（.card-specimen-back / .hero-watermark / .bg-texture / ::before 内容为空）
       - 已在 §3 登记、且产品负责人明确「接受」的条目（附 issue 号）
  5. 输出必须区分三档：violation（确证）/ suspect（父面/渐变/条件类，只统计不拦）/ pass。
     suspect 一律**不**让守卫变红 —— 但**必须打印**，否则「疑似」会永远没人看。
  6. 必须配 --selftest：注入一组已知违规（例如把某个 4.5 合规对改成 2.0）必须被检出，再还原。

禁止在这个守卫里做的事：
  - 不要追踪跨元素父面（证明不了，会引入假阳/假阴）
  - 不要按令牌名判定
  - 不要把 suspect 当 violation
  - 不要为了「让 CI 变绿」而扩大白名单
```

**建议的起步阈值与基线**：若要立棘轮，基线应设为
**「确证违规数 ≤ 62」（即本报告实测值）**，而不是从 0 开始 ——
因为从 0 开始等于要求本次发现的 62 条同批修完，会把守卫变成阻塞项。
棘轮只许降不许升，与 `check:guards-coverage` 的总数棘轮同构。

### 8.3 哪些**不该**进守卫（要进也应该进「报告」而不是「闸门」）

- 渐变跨线（S1~S5）：只能报区间，不能判红。
- 边框/非文字 3:1：本仓**没有一条**边框令牌达标（1.00~1.74）。
  真要守，应该先改设计令牌（`--color-border` 从 1.0:1 提到 3:1 是**视觉重做**，不是修 bug），
  否则守卫一上线就是满屏红。**这属于产品决策，不属于守卫范围。**
- 字阶令牌采用率（7 / 4495）：属 C7 契约的落地问题，与对比度正交。

## 9. 我的方法覆盖不到的部分

诚实边界清单：

1. **跨组件 `styleIsolation`**：
   本报告的祖先追踪基于**同一 Page 的 WXML 树**。自定义组件（`components/*`）默认 `isolated`，
   组件内的 `color` 与宿主页的 `background` **不共享作用域**；若组件声明 `apply-shared`，全局样式会渗入。
   本次**没有逐个核对 15 个组件的 `styleIsolation` 配置** → 所有「组件的文字 × 宿主的底」的判定都未纳入确证。
   （`components/*` 内部的同规则配对不受影响，仍是确证的。）
2. **运行时注入**：`wx.setStyle` / 行内 `style="{{...}}"` / 云配置下发主题色 → 静态完全看不见。
   （本次未在 WXML 中发现行内 `style` 承载颜色，但**没有做穷尽核查**。）
3. **条件类名**：`{{cond ? 'a' : 'b'}}` 只判到「可能取值集合」，判不出实际渲染（S14）。
4. **渐变位置**：文字落在高光带还是暗带，静态判不出（S1~S5）。
5. **`filter` / `backdrop-filter` / `mix-blend-mode` / `opacity` 继承**：
   `app.wxss:226` 对所有 `img` 施加了 `filter: brightness(0.93)...`；
   另有大量 `.card-grain`、`.card-sheen`、纹理 `background-image` 叠层 —— 它们会**改变实际底色**，本报告一律未计入。
6. **`linear-gradient` 只取「第一个色停靠点」的条目**（本轮 2 条：`.stamp-used`、`.plate-avatar`）：
   `.plate-avatar` 已人工核实两端（3.86~4.17，两端都违规），`.stamp-used` 仍是近似值。
7. **`!important` 与特异性**：本次靠「后声明覆盖前声明」+ 人工抽查，**没有做完整的层叠模拟**。
   §5 的 S13（`.btn.retry`）就是被这条卡住的例子。
8. **真实渲染像素**：本报告**全部是静态计算**，没有任何一条经过真机/开发者工具渲染后取色。
   → 本仓纪律要求「静态 ≠ 事实」。建议后续对 §3 的 top-N 用开发者工具**取实际像素**复核；
   在那之前，本报告的定位是**「可复核的实测数据 + 明确标出的证据边界」**，不是「已实测的渲染结论」。
9. **太阳底下没有的新事**：`#D64045`/`#6B6560` 等值在 WXSS 里以字面量、`rgba()`、`var()` fallback 三种形态出现，
   本报告的解析覆盖了这三种；但**不覆盖** JS 里拼接样式字符串的情形（本次未发现，但未穷尽）。

## 10. 附：复算方法（可复核）

本次分析**没有**在仓库里留下任何脚本（本文件是唯一新增文件）。复算路径：

1. 令牌表：`miniprogram/app.wxss` 第 5–99 行的 `page { --*: ... }`。
2. WCAG 相对亮度：`L = 0.2126·R + 0.7152·G + 0.0722·B`，其中每通道 `c<=0.03928 ? c/12.92 : ((c+0.055)/1.055)^2.4`（c 为 0–1）。
3. 对比度：`(L_light + 0.05) / (L_dark + 0.05)`。
4. alpha 合成：`C = α·C_fg + (1-α)·C_bg`（逐通道，先合成背景到不透明，再合成文字 alpha）。
5. 行号口径：**先把注释替换成等长空白（保留换行）**，再数行 —— 否则注释块会让行号漂移（本次踩过）。
6. 三个标准深色面：`#1A1814` / `#1F1D1A` / `#262320`；浅色面：`#FAF6ED` / `#F2EDE4` / `#EFE8DA` / `#FFFFFF`。
