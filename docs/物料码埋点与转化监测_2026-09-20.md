## 2. 归因设计（为什么不是"在每个转化点各埋一遍"）

**问题**：三张码此前在埋点里**无法区分**。`utils/analytics/session.js` 只把 `wx.getLaunchOptionsSync().scene` 记成**数字场景值**（1011/1047…），而三张码都是"扫码进入"→ 数字场景值完全相同 → 报表里三张码的转化只能合成一个数。

**做法**（复用既有 `session.scene` / `session.referrerPage` 的思路，不新增存储）：

```
扫码 → app.js#maybeTrackQrMaterial（解析 scene → 物料 key）
     → session.setEntrySource('qr:<key>')        ← 写进 analytics 会话
     → analytics/index.js#buildPayload           ← 此后会话内**所有**事件都带 entrySource
     → 云端 trackUserBehavior 落 user_behaviors.entrySource
```

于是"扫码 → 到达目标页 → 关键转化"整条漏斗都能按物料切开，**不必在每个转化点各埋一遍**，也不会漏掉将来新增的页面/动作。

关键实现点：

| 点 | 处理 | 为什么 |
|---|---|---|
| 取 scene 串 | `wx.getEnterOptionsSync()` 优先，`getLaunchOptionsSync()` 兜底 | 前者每次进入都更新（热启动/后台扫码），后者只反映冷启动那一次 |
| 冷/热启动都要覆盖 | `setEntrySource` 是**显式覆盖**，不只在建会话时算一次 | 会话 TTL 30 分钟，用户可能先在别的页、再扫立牌；不覆盖就会算进"无来源" |
| 未登记物料 | 不归因（返回空） | 避免报表里出现"有来源但没有对应漏斗"的孤儿行（如别的墙 `k=otherwall`、分享海报的记录 id） |
| 字段名 | `entrySource`（云端 `BEHAVIOR_ALLOWED_FIELDS` 白名单内） | 白名单外的字段会被**静默丢弃** → 归因全丢、漏斗只剩首环（守卫已拦） |

## 3. 事件与字段

| 事件 | targetType / targetId | 何时发 |
|---|---|---|
| `qr_material_enter` | `qr_material` / 物料 key | 扫码进入时 `step='open'`；页面解析不到且无法重映射（**码已失效**）时 `step='fallback_home'` |

- 漏斗**归因不靠这个事件**（靠 `entrySource` 全事件携带）；它只负责算漏斗第一环「扫码进入」，并让"码失效"变成可监测信号。
- `step` 随 `properties` 落库（与既有 `*_gate` 漏斗同一机制）。

## 4. ERP 报表位置与口径

位置：**超管工作台 → 客户经营 → 行为洞察（模块 44）→ 行为看板**，新增卡片「📱 物料码转化监测」。

| 环节 | 判据（在 `user_behaviors` 明细上） |
|---|---|
| 扫码进入 | `action='qr_material_enter'` 且 `step='open'`，按 `entrySource='qr:<key>'` 过滤，去重用户数 |
| 到达目标页 | 同来源过滤下 `action='page_view'` 且 `page=<targetPage>`，去重用户数 |
| 关键转化 | 同来源过滤下 `action=<convertAction>`，去重用户数 |
| 总转化率 | 关键转化 ÷ 扫码进入；**分母为 0 显示「—」**（不是 0%） |
| 码失效告警 | `step='fallback_home'` 条数 > 0 → 提示"扫进来落到了首页 = 码已失效" |

**为什么读明细而不是 `analytics_daily`**：`analytics_daily` 是**动作级日汇总**（`_id = <dateKey>::<action>`），**没有来源维度**，按物料切不开。该页既有漏斗已是同一取舍（页面里已有同样说明）。

**为什么物料漏斗没有放进「核心转化漏斗」通用区**（刻意的）：通用渲染 `funnelData` 只按 `action` **全局**聚合 —— 既不看 `material` 也不看步骤上声明的 `page`。放进去会渲染出 3 条「扫码进入 = 三张码之和 / 到达目标页 = 全站 `page_view` 总量」的**虚高且互相重复**的漏斗。**数字错比没有更糟**，所以只在卡片里给按物料拆分的正确口径；若将来要搬进通用区，先把 `funnelData` 改成支持 `material` / `page` 过滤（`analyticsSchema.js` 里已留注释说明）。

## 5. 口径边界（诚实列出，未验项不得当作已通过）

0. **已验**：三张码的 scene 解析 → 物料 key（含百分号编码形态与未登记物料的负例）、app 级入口事件与 `entrySource` 写入（Node 驱动真实 `app.js`）、浏览器里卡片真的画出（`docs/物料码埋点与转化监测_2026-09-20.md` §4ter）。
1. **历史数据不可回溯**：埋点自含本次改动的**新版本发布后**才有数据；此前三张码的扫码量查不到。
2. **同一会话内多次扫码 → 只归因最后一次**。`entrySource` 是会话级覆盖语义：先扫 A 再扫 B，A 之后的转化会被算成 B。若要"每次扫码各自成环"，需改成扫码级 short-id（本次**未做**）。
3. **会话 TTL 30 分钟**：扫码后 30 分钟内的行为都算该物料，**可能高估**该物料的转化（跨物料的用户会被重复计入不同物料，但同一会话内只算最后来源）。
4. 本次为**客户端 + ERP 侧改动**，小程序需**重新发版**（`app.js` / `utils/analytics/**`）；云端 `trackUserBehavior` **无需改动**（`entrySource` 早已在白名单内）。
5. **真机未验证**：埋点是否真上报，需在真机上扫码后到 ERP 行为看板看该物料是否出行（浏览器实测只能证明"页面画得出来 + 合成数据算得对"，**不能**证明真机扫码会上报）。

## 6. 守卫（`npm run check:analytics-schema` 的 E/F 段）

### E 段：物料码契约（8 条，对着"静默失效点"）

- 双端 `QR_MATERIALS` 必须同 key（ERP 缺一张 = 报表里没有这行）；
- `targetPage` 必须是 `app.json` 注册页（页面搬过家 → 第二环永远算不出）；
- `convertAction` 必须已登记（且 ERP 镜像也有）→ 否则末环恒 0；
- **`entrySource` 必须在云端字段白名单内** → 否则整条归因被静默丢弃；
- `app.js` 必须埋 `qr_material_enter`，且 `onShow` 真的接线（判据带 `this.` 前缀 —— 不带的话方法**定义**本身就满足它，是空判，自检抓到的）；
- `buildPayload` 必须携带 `entrySource`；`session.js` 必须有 `setEntrySource`；
- 登记表的 `scene` 必须能被解析判据解析回该 key（写进表却解析不出来 = 等于没埋）；
- 未登记 scene（`s3` / `k=otherwall` / 空串 / 海报记录 id）**不得**被误归因。

### F 段：门禁漏斗的合成 action（防上面那个真缺陷回归）

- `buildGateStepRows` 不得引用未定义标识符（带词边界 —— `STEP_GATE_ACTIONS` 含子串 `GATE_ACTION`，裸匹配会误报）；
- 合成 action 必须是 `${ev.action}:${step}`；
- `STEP_GATE_ACTIONS` 必须仍从 `FUNNELS` 派生（否则新增门禁漏斗恒 0，2026-09-18 踩过）；
- 判据先剥注释再匹配（修复说明里会引用坏标识符的名字，不剥就会把"解释这个坑的注释"当成"又踩了这个坑"）。

### 自检

**10 条 E 合成判据 + 4 条 F 合成判据 + 3 条真实注入**（拿掉云端白名单 `entrySource`、拆掉 `onShow` 接线、把门禁合成 action 改回未定义的 `GATE_ACTION`），全部必须判红并**还原源码**。

> ⚠️ 注入型自检必须在**隔离 worktree** 里跑（它会写源码）。2026-09-20 在另一条守卫上实际踩到：
> 注入失败分支把 `process.exit(1)` 写在 `try` 里，而 **`process.exit()` 不会执行挂起的 `finally`** →
> 注入被**留在源文件中**（`app.js` 的 `onShow` 接线被删掉且未还原）。两条守卫的 `inject` 已统一改为
> "先还原再判成败"。
