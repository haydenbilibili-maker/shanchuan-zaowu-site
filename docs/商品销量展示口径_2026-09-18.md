# 商品销量展示口径（2026-09-18）

> 触发：产品反馈「新增的藏品默认销售数量为 0，建议上架时给一个美化数据」。
> 本文记录**现状成因、拍板决定、实现口径、以及刻意没做的两件事**。

## 0. 决定（2026-09-18 产品负责人拍板）

| 事项 | 决定 |
|---|---|
| 新建藏品「已售 0」的展示 | **方案 A：零造假** —— 0 销量不再显示「已售 0」；建档 **7 天**内的新品打「**馆方新藏**」标；否则整条不显示 |
| 窗口宽度 | **7 天**（2026-09-18 产品负责人定；依据见 §5bis 的线上分布实测：14/30 天几乎等价于全站，会把标签印在约 180 张卡上而失去信号）|
| 既有的「蝴蝶 0–50 / 甲虫 0–20」稳定随机销量 | **暂不动**（保留现状；风险见 §5） |
| 是否往 DB 的 `soldCount` 写默认值 | **不写**（技术理由见 §3） |

## 1. 现状成因（取证）

`utils/productStats.js:65-81` 是既有的美化 SSOT，**只在展示层生效**：

```js
孤品 / 镇店之宝 → null（卡片不显示销量，改打孤品标）
蝴蝶类        → 稳定随机 0–50
甲虫类        → 稳定随机 0–20
其它          → 真实 soldCount
```

而 `ProductCard/index.js` 原来是 `showSold: !oneOfAKind && sold != null` —— **非昆虫新品**的真实值是 `0`（不是 `null`），于是卡片实打实渲染出 **「已售 0」**。

> 顺带修掉一个隐藏分支：`stableRandomInt(seed, 50)` **值域包含 0**，所以昆虫卡也会偶发「已售 0」。

## 2. 新口径（唯一出口 `productStats.getSoldDisplay`）

| 条件 | 卡片显示 |
|---|---|
| 孤品 / 镇店之宝 | 不显示销量（孤品角标承载） |
| 展示销量 > 0 | `已售 N` |
| 展示销量 = 0 且**建档 ≤ 7 天** | `馆方新藏`（铜色小标，非销量文字） |
| 展示销量 = 0 且建档 > 7 天 / 无建档时间 | **什么都不显示**（拿不到时间时退回卡片 NEW 角标信号，见 §5bis）|

**不变量：任何组合下都不会渲染「已售 0」**（守卫逐组合断言）。

**判据字段为什么是 `createTime`**：C 端「最新」排序用的也是 `createTime`（`ProductList/index.js:11`），
拿同一字段说「新藏」与用户已看到的排序口径一致。取不到时间 → **不算新品**（宁可什么都不显示，也不乱打标）。
⚠️ 商品文档**没有**独立的上架时间字段（`manageApprovals` 上架只置 `isOffShelf:false`）——所以「建档但晚上架」的老货不会拿到新藏标，这是刻意的保守选择。

## 3. 为什么没写 DB（这条比文案更重要）

`soldCount` 是**真实台账字段**，不是展示字段：

```js
// admin/src/utils/b2bFulfillment.js:227,235
soldCount: (parseInt(product.soldCount, 10) || 0) + it.quantity
```

- 假基数一旦入库，就会与真实销量**永久混合**（基数 30 + 真实 2 = 32），事后**无法区分**；
- `manageProducts/index.js:668` 的 `sortBy:'sales'` 与 `:1158` 的统计聚合都读它 → 排序与报表从此不可信；
- 好消息：库存/成本聚合用的是 `stock` 而非 `soldCount`，所以**不会直接造成超卖/资损**。

一句话：**美化只能待在展示层**。这也是既有实现的正确之处，本次沿用。

## 4. 合规提示（留档）

对**在售商品**虚构销售状况，涉及《反不正当竞争法》第 8 条（虚假或引人误解的商业宣传，含虚构交易）、
《电子商务法》第 17 条（不得虚构交易、编造用户评价），罚则可至 20–100 万并记入信用记录；微信小程序运营规范亦禁止数据造假。
「馆方新藏」之所以合规，是因为它**陈述的是真实事实**（该藏品确为近期建档）。

## 5. 未做 / 风险（明确标注）

- **既有昆虫随机销量（蝴蝶 0–50 / 甲虫 0–20）保留**：产品负责人 2026-09-18 决定暂不动。
  它在性质上仍属"展示层虚构在售商品的销售状况"，**是同类合规暴露**；若日后要收口，
  建议按同一口径改为「馆方新藏 / 首批 / 真实互动数」，实现上只需改 `getDisplaySoldCount` 一处 + 更新本守卫。
- 详情页**没有销量位**（只有「已售罄」），故本次无需改动。
- `ProductList` 的「销量」排序仍按展示值排（孤品记 0）——与卡片口径一致，未改。

## 5bis. 2026-09-18 复查：「馆方新藏」没显示 —— 两个真缺陷 + 一次真实数据测量

产品反馈截图：卡片有 `NEW` 角标、却没有「馆方新藏」。用 **ERP 自己的云端连接只读实测**（`admin/.env` 凭据，未改任何数据）得到事实：

| 实测项 | 结果 |
|---|---|
| 截图那两件商品的 `createTime` | 乌桕叶标本 `2026-09-18T07:28:40.714Z`、星月菩提果植物手链 `2026-09-18T07:00:44.250Z` —— **都是 Date，且都在 30 天内** |
| 它们的 `soldCount` | **字段缺失**（205 件里 191 件缺 `soldCount`，且**没有一件是 `soldCount === 0`**） |
| 把真实文档喂给 `getSoldDisplay` | 返回 `{kind:'new', text:'馆方新藏'}` ✓ 逻辑本身是对的 |

### 找到并修掉的两个缺陷

1. **NEW 角标与「馆方新藏」两套"新"的定义**（这就是观感 bug 的根源）：
   角标原来读 `info.isNew` —— 那是 `ProductList` 的**排序上下文**（`isNew: sortKey === 'new'`，按最新排序时**每张卡**都是 true），而我加的 chip 按建档时间算。
   两者不一致时就会出现"有 NEW 角标却没有新藏标"。
   **现改为同一个 `isNewArrival()` 驱动角标与 chip**，不可能再分叉；**拿不到建档时间时退回角标那个信号**（老数据/缺字段不丢标），**拿得到时间时以时间为准**。
2. **时间形态不够鲁棒**：新增 秒级时间戳（10 位，会被当 1970 → 静默失效）、Mongo 扩展 JSON `{$date:{$numberLong}}`、`_createTime`（云开发自动字段）三种形态。

### 顺带量到的分布（决定窗口该开多宽）

205 件商品的建档年龄分布：**1 天内 8 / 3 天内 9 / 7 天内 38 / 14 天内 186 / 30 天内 186**，最老 118 天。
即**186 件集中在 7–14 天前**（一次批量导入），另有 19 件更老。

> ✅ **已按产品负责人指示收到 7 天**（`NEW_ARRIVAL_DAYS = 7`，2026-09-18）：命中面从约 180 张卡收到 **最多 38 张**
> （7 天内 38 件 × 其中 0 销量者），「这周新到」才真正成为信号。窗口是一个常量，守卫会跟着断言；**改它就等于改口径**，需同步本文件。
