# 仪式感 / 祈福 / 彩蛋 —— 长线开发框架

- 日期：2026-09-16
- 首个落地对象：需求 28「马上有」弹幕祈福墙（见 `需求28_马上有祈福墙_交付记录_2026-09-16.md`）
- 适用范围：小程序全站。本文是**接入契约**，不是待办清单。

---

## 1. 为什么要先定框架

这三类机制的共同点是**"没有它也能用"**，所以最容易在后续迭代里被写坏而无人发现：

| 机制 | 写坏时的表现 | 为什么现有守卫抓不到 |
|---|---|---|
| 彩蛋 | 每次进页面都弹同一个窗 | 不报错、不失败，只是惊喜变骚扰 |
| 仪式 | 同一天进来两次看到不同的话 | 用 `Math.random()` 也能"看起来正常" |
| 祈福内容 | 墙上全是重复/跑偏的句子 | 接口全 200，只是内容没人看 |

因此框架的目标不是"加功能"，而是**把这三类机制的失灵变成会失败的断言**（守卫见 §6）。

---

## 2. 三层机制与各自的落点

| 层 | 承载物 | 存储 | 失败时 |
|---|---|---|---|
| **祈福内容** | `wish_wall_messages` 集合（UGC + AI 基础内容同表） | 云端 | 列表降级为空数组，页面仍可用 |
| **彩蛋** | `config/easterEggs.js` 注册表 + `components/EasterEggNote` | 本地（`shanhai_easter_eggs_v1`） | 只影响一句提示，不阻断主流程 |
| **仪式** | `utils/wishRitual.js`（点灯 + 每日一句） | 本地（`shanhai_wish_ritual_v1`） | 视为"今日未点灯"，不阻断主流程 |

**共同原则**：

1. **彩蛋与仪式不落云库。** 它们不是资产，不需要跨端一致；一旦落库就要多一张表、多一套权限与治理面，
   与「祈福弹幕不接 UGC 审核、治理收敛在超管内容开关」的口径直接冲突。
2. **彩蛋与仪式绝不阻断主流程。** 所有调用点都包在 `try/catch` 里并记录 warn；
   存储失败 = 降级，而不是让用户发不出弹幕。
3. **不挂到支付、下单、退款路径**（注册表头部注释里已写成约定，守卫 §6 会断言）。

## 3. 彩蛋：注册表驱动 + 四种触发类型

注册表是 `config/easterEggs.js` 的 `EGGS`。页面**只报事件，不认 egg id**。

| 触发类型 | 由谁发起 | 语义 | 重复行为 |
|---|---|---|---|
| `longPress` | 用户（`easterEggHost` behavior） | 长按某个挂了 `data-egg-id` 的元素 | **可重看** |
| `secretKeyword` | 用户（搜索提交） | 搜到某个关键词 | **可重看** |
| `tapCount` | 用户 | 窗口期内连点 N 次 | **可重看** |
| `pageEnter` | 页面（自动） | 进入注册表指定的路由 | **只弹一次** |
| `wishPosted` | 页面（自动） | 某个动作成功后 | **只弹一次** |
| `lampStreak` | 页面（自动，**带门槛**） | 连续点灯天数够（`minStreak`） | **只弹一次** |
| `wishCount` | 页面（自动，**带门槛**） | 我的心愿条数够（`minCount`） | **只弹一次** |

### 3.0 门槛写在注册表里，页面只报事实

`lampStreak` / `wishCount` 是**门槛型**自动触发。页面调用时只说事实：

```js
easterEgg.tryLampStreak({ page: this, streak: 5 })   // 我连续 5 天了
easterEgg.tryWishCount({ page: this, wishCount: 3 }) // 我写了 3 条
```

"几天 / 几条才算数"由注册表的 `minStreak` / `minCount` 决定 —— 调门槛不用改页面，
也避免把业务阈值散落在各个页面里（这正是"彩蛋注册表驱动"的意义）。

### 3.1 自动触发为什么必须"只弹一次"

`pageEnter` 每次进页面都会命中。若沿用"可重看"语义，用户每次进来都吃一个弹窗 ——
彩蛋就从惊喜变成骚扰。实现方式是在 `discover()` 里区分：

```js
const AUTO_TRIGGER_TYPES = ['pageEnter', 'wishPosted', 'lampStreak', 'wishCount']
// tryTriggerType 里：自动类型带 skipIfDiscovered
const skipIfDiscovered = AUTO_TRIGGER_TYPES.indexOf(ctx.type) !== -1
```

- 自动触发 → 已拾得直接 `return null`（不弹、不埋点）；
- 用户主动触发 → 维持原语义（长按可以再读一遍那段话）。

### 3.2 页面侧只需一行

```js
// 进页
easterEgg.tryPageEnter({ page: this, source: 'xxx' })
// 动作成功后
easterEgg.tryWishPosted({ page: this, source: 'xxx' })
```

页面还必须做到两件事（缺一彩蛋就是"静默失败"）：

1. `index.json` 注册 `"easter-egg-note": "/components/EasterEggNote/index"`；
2. wxml 里放 `<easter-egg-note id="easterEggNote" />`（`present()` 靠这个 id 找挂点，
   找不到会退化成 toast —— 能用，但少了质感和"收入博物笔记"的仪式感）。

### 3.3 新增一个彩蛋的步骤

1. `config/easterEggs.js` 的 `EGGS` 追加一条（**id 稳定、勿复用**，语义与藏品/动作相关）；
2. 配 `triggers`：自动类型填 `pages: ['<页面路由>']`；用户类型按 §3 表格留钩子；
3. 目标页按 §3.2 接线；
4. 跑 `npm run test:wish-wall`（含彩蛋注册表与触发语义断言）。

## 4. 仪式：本地、确定性、可复现

`utils/wishRitual.js` 提供「点灯」——零门槛的入场动作：一进来先有一个可做的小事，
做完得到**当天那一句**。它解决的是祈福墙转化门槛最高的问题（`input` 输入）。

设计约束：

- **每日一句必须确定性**。`pickDailyLine(lines, dayKey)` 用 FNV-1a 把 `YYYY-MM-DD` 映射到词表，
  同一天两次进入看到同一句。用随机数的话"仪式"会变成抽奖。
- **日期键按 Asia/Shanghai**（`shanghaiDayKey`），与云函数频控同口径。
  容器/设备时区不保证，故手工 +8 换算，测试里有跨 UTC 边界用例。
- **连续天数是"含今日"的**。今日未点灯返回 0 —— 靠昨天充数会让"断了"也显示连续，
  仪式就失去了反馈价值。
- **存储按 `KEEP_DAYS=30` 收敛**。存储不是账本，无限增长早晚撑爆上限。
- **点灯幂等**：同一天重复点不覆盖首次时间。

### 4.0 灯位层级与节气签（升级第一期）

只有"亮/没亮"两种状态时，连续第 7 天得到的反馈和第一天一模一样 —— 坚持没有累积感。
所以加了两层可见性：

| 机制 | 纯函数 | 口径 |
|---|---|---|
| **灯位层级** | `lampTier(streak)` | 1 天=1 盏「初见」/ 3 天=3 盏「守夜」/ 7 天=5 盏「长明」；`daysToNext` 告诉用户还差几天；到顶不再升。阈值刻意低 —— 祈福墙不是养成游戏 |
| **节气签** | `solarTermOn(dayKey)` / `solarTermGap(dayKey)` | 节气**当天**用节气灯语并显示节气名，否则用通用每日灯语。24 节气用**公历近似日**表（±1 天），但确定性、可断言 |

两条都属于"没有也能用"，所以各自配了注入（`lamp-tier-flat` / `solar-term-off`）——
不分层、不命中都不会报错，只有注入能证明断言不是空的。

### 4.1 新增一个仪式的步骤

1. 纯逻辑（日期键、选择、统计）加到 `utils/wishWall.js`（保持无 `wx` 依赖，可直接断言）；
2. 读写与词表放到 `utils/*Ritual.js`，`wx` 调用一律 `typeof wx === 'undefined'` 兜底；
3. 页面接线，并**只在本地持久化**；
4. 补断言 + 至少一个"写坏必须被检出"的注入。

## 5. 祈福内容：全站拓展 = 加一个 `productKey`

一面祈福墙由字符串作用域隔离，**页面代码零改动**：

| 要做的事 | 落点 |
|---|---|
| 第二面墙 | 藏品记录加 `wishWallKey: '<key>'`（`[a-z0-9_-]`，≤40 字） |
| 让某个藏品挂墙 | 藏品记录加 `wishWallEnabled: true`（或标题含「马上有」，仅为过渡兜底） |
| 新页面放入口 | json 注册组件 + wxml 一行 `<wish-wall-entry enabled="{{开关}}" product="{{product}}" from="xxx" />` |

作用域解析顺序（`utils/wishWall.js`）：

```js
resolveWishWallKey(product)   // 显式 wishWallKey 优先；否则回落 'mashangyou'
```

**为什么入口必须收成一个组件**：入口判定 = 「内容开关 开」**且**「藏品命中」。
留在各宿主页面里就会写第二份、第三份，早晚出现"开关关了但某个页面还亮着"。
`components/WishWallEntry` 是唯一实现（详情页已改用它，旧副本已删除）。

### 5.1 基础内容（AI 创作 + 人工基线兜底）

祈福墙是**空墙悖论**最重的场景：第一个进来的人看到空白就不会写，没人写就一直空。
因此上线第一天墙上必须有内容：

- 基线文案：`cloudfunctions/manageWishWall/wishSeeds.js` 的 `SEED_WISHES`（人工审校，24 条）；
- AI 生成：`staffSeedAi`（超管/店长）走 DashScope `qwen-plus`，提示词带**风格样本 + 已存在清单**，
  输出经四道闸（句式 / 长度 / 与墙上全部状态比对 / 批内去重）；
- **AI 不可用时用基线补齐**，不会出现"AI 挂了就连第一批内容都拿不出来"；
- 灵感轮换：`list` 附带按上海自然日轮换的 4 条，作为输入框上方的 chip（确定性）。

**句式前缀跟着墙走（多面墙之后的硬要求）**：

- 前缀是**参数** `normalizePrefix(raw)`（去空白、截 6 字、空则回落「马上有」），
  句式闸 / 提示词 / 输出示例都用它。写死前缀会让第二面墙长满「马上有XX」（别的墙的话），
  而且句式闸会把 AI 写对的那些**全部丢掉**，最后是一条都不剩的空墙；
- **风格样本只给默认前缀**：那 12 条样本本身是「马上有XX」写的，套到别的墙上正是带偏句式的原因；
- **人工基线只兜默认前缀**：24 条基线同理。自定义前缀下没内容就返回可辨识的 `NO_NEW_SEED` ——
  **铺错内容比不铺更糟**，这条口径写进了拒绝文案。

## 6. 守卫：每条都能证明自己会失败

`npm run test:wish-wall`（在 `check:admin` 里）覆盖：

- 集合只读 / 服务端昵称 / 频控与长度 / 状态可见性 / 开关闸门 / 弹幕布局（基础层）；
- **AI 基础内容**：句式闸、四类 AI 返回格式解析、去重（含已存在与批内）、灵感确定性、提示词内容；
- **彩蛋**：注册表 id 唯一、自动触发「只弹一次」、主动触发可重看、`triggerMatches` 三态、
  新彩蛋不在支付路径；
- **仪式**：每日一句确定性 + 按天轮换、日期键跨 UTC 边界、连续天数断档、点灯幂等、存储收敛；
- **全站拓展**：`wishWallKey` 生效与净化、入口 URL 参数、详情页已改用组件；
- **入口可达性**：治理行必须在「内容开关」面板（工作台磁贴短名「开关」，tab 16）内、
  「内容管理」(tab 9) 也有直达入口 —— 磁贴名不承担可发现性，直达条才承担；
- **开关字段齐备**：把云函数 `saveFlags` 读取的字段名逐个抽出，要求小程序端归一化与默认值全部覆盖
  （缺一个 = 保存时该字段被重置为默认，会抹掉另一端的设置）；
- **开关真的会生效**（本轮新增，两次实测反馈换来的）：弹窗按钮文案 ≤4 字（超了 `showModal`
  静默失败）、弹窗必须带 `fail`、C 端口禁要接住 SWR 的 `onUpdate`、保存后失效本机缓存、
  面板要提示「有未保存的改动」；
- **云函数版本漂移要能自解释**（第三次反馈）：`未知 action: X` 必须映射为
  「云函数版本过旧，请重新部署」，且漂移部署脚本的复比只针对本次目标。

`npm run test:wish-wall:selftest` 用 **66 个回归注入**证明这些断言真的会失败，包括：

| 注入 | 模拟的缺陷 |
|---|---|
| `seed-ignores-existing` | 播种不与已有内容去重 → 重复铺墙、绕过人工隐藏 |
| `seed-allows-off-pattern` | 丢掉句式闸 → 跑偏内容上墙 |
| `seed-skips-staff-guard` | 播种不校验身份 → 任何人可批量写入公开墙面 |
| `egg-pageenter-repeats` | 自动彩蛋不再"只弹一次" → 每进必弹 |
| `lamp-fixed-line` | 每日一句不轮换 → 仪式感消失 |
| `entry-key-hardcoded` | 作用域写死 → 第二面墙内容全落进「马上有」 |
| `tab9-entry-removed` | 摘掉「内容管理」的直达入口 → 按内容模块直觉找的人又找不到 |
| `flags-field-dropped` | 小程序端漏带一个开关字段 → 保存时把另一端的选择抹成默认 |
| `modal-text-too-long` | 弹窗按钮 5 个字 → `showModal` 静默失败（点了没反应） |
| `detail-flags-no-onupdate` | 详情页丢掉 SWR 新鲜值 → 开关开了也看不到入口 |
| `gate-flags-no-onupdate` | 祈福墙页同一问题 → 开关开了仍显示「暂未开放」 |
| `save-skips-cache-invalidate` | 保存后不失效本机缓存 → 最长 ~24h 不生效 |
| `dirty-hint-dropped` | 摘掉「未保存」提示 → 拨完开关以为已生效 |
| `stale-fn-error-raw` | 云函数版本漂移只回原始「未知 action: X」→ 运营不知道要部署 |
| `deploy-all-recompare` | 漂移部署脚本复比退回全量 → 单函数部署被拖到超时 |
| `tile-label-drift` | 工作台磁贴名被改回全称 → 与产品口径的短名「开关」不符 |
| `lamp-tier-flat` | 灯位不再分层 → 连续 7 天与第一天反馈一样，坚持没有累积感 |
| `solar-term-off` | 节气判定永不命中 → 节气灯语与节气名成死代码 |
| `egg-streak-ignores-threshold` | 门槛型彩蛋不看门槛 → 第一次点灯就弹「连续三天」彩蛋 |
| `mine-not-marked` | 不标记「我的」→「我的心愿」视图与愿签印记全失效且不报错 |
| `relics-focus-dropped` | 图鉴入口丢定位参数 → 点进去落在成就页顶部，找不到那一片 |
| `manager-wall-hardcoded` | 治理页写死默认墙 → 第二面墙的弹幕无人可治（UGC 无兜底） |
| `staffwalls-unprotected` | 列墙不鉴权 → 任何人都能枚举全部墙 |
| `wall-switch-not-persisted` | 切墙不落本地 → 每次进来都回到默认墙 |
| `entry-copy-hardcoded` | 入口文案写死「马上有」→ 第二面墙挂着别人的商品名 |
| `seed-prefix-ignored` | 句式闸忽略传入前缀 → 第二面墙长满别墙的话，且写对的全被丢掉 |
| `seed-baseline-for-custom-prefix` | 自定义前缀也用「马上有XX」基线兜底 → 铺错内容（比不铺更糟） |
| `seed-prefix-not-sent` | 页面不把前缀发给云端 → 云端永远按默认前缀生成 |
| `product-field-not-allowlisted` | 商品字段没进 `manageProducts` 白名单 → 保存时被静默丢弃（全站拓展永远开不出第二面墙） |
| `wishwall-preset-off` | 载入不按"实际是否挂墙"回填 → 打开任意藏品保存一次就把墙摘了 |

（另有视觉重设计一组约 20 条注入由并行流程补入，见 `docs/需求28_…` §15.3。）

另有独立守卫 `npm run check:modal-text`（棘轮）：全仓扫描 `confirmText`/`cancelText` 超 4 字的写法，
把现存 5 处登记为基线，**只许减少不许新增** —— 那 5 个弹窗目前**永远弹不出来**，
且都在退款/履约/物流降级路径上。

新增机制时**必须同时新增注入**，否则等于没有守卫（AGENTS.md 的硬要求）。

> **两轮自证**：
> ① 写 `tab9-entry-removed` 时发现断言只搜了裸函数名（注释里也有），"入口被摘掉"照样通过；
> ② 写 `detail-flags-no-onupdate` 时又犯了同一类错 —— 裸词 `onUpdate` 会命中 `__onUpdateRemoved`。
> 两次都是**注入当场抓出来**。断言写虚了，只有注入能证明；这类"子串匹配"错误值得专门警惕。

## 7. 明确不做（以及为什么）

| 不做 | 原因 |
|---|---|
| 彩蛋/仪式落云库 | 不是资产，且会引入第二张 UGC 表与新的治理面 |
| 彩蛋挂支付/下单/退款路径 | 这三条链路的失败代价远高于彩蛋的价值 |
| 祈福弹幕点赞/回复 | 需求只要求"弹幕祈福墙"；社交化会带来新的治理面（见需求 28 §9） |
| 用随机数决定彩蛋/仪式内容 | 不可断言、不可复现，且用户会觉得"内容在乱跳" |
| 给基础内容开"免治理"通道 | 与用户弹幕同表同字段，超管内容开关可隐藏/删除，治理只有一处 |
