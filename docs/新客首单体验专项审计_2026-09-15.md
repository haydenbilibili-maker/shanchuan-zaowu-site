# 新客首单体验专项审计：注册 / 下单 / 发券 / 用券 / 耗时 / 无感化

> **审计对象**：小程序「新用户从冷启动到首单支付完成」的完整链路。
> **审计方式**：代码级链路走查（页面跳转、云函数调用次数与串并行关系、必填校验、幂等保护），未做真机计时。
> **一句话结论**：**登录做到了完全无感、注册时机也放在了"真正需要时"，但首单路径仍有三个明显卡点**——提交后才被弹去注册（体验断点）、新客券门槛与首单金额不匹配（获得感落空）、结算页 6 次请求中 4 次串行（进入即等待）。

---

## 1. 实际链路（代码走查结果）

```
冷启动
 └─ login（静默取 openid，用户零操作）                        ← 无感 ✓
浏览 / 加购 / 看券（无任何注册要求）                          ← 无感 ✓
进入结算页 onLoad（共 6 次请求，其中 4 次串行）
 ├─ getShippingRules        （并行）
 ├─ manageAddress           （默认地址）
 ├─ manageStoredValue       （钱包可用余额）
 ├─ getUserStats            （会员折扣）
 ├─ fetchMyCoupons → getBestCoupon   （串行：先取券包，再自动选最优券）
 └─ makeOrder{previewOnly}  （服务端定价预览）
点击「提交订单」
 └─ 若未绑定手机号 → 整页跳转注册（onboarding）
     ├─ 勾选协议（必填，未勾选点授权会被拦截）                ← 强制交互 1
     ├─ 微信手机号授权                                        ← 强制交互 2
     ├─ authPhone{finishRegistration:true}（内部完成建档发券）
     └─ 返回结算页 → 重跑 getUserSession / getUserStats / fetchMyCoupons / getBestCoupon / makeOrder(previewOnly)（再 5 次）
再点「提交订单」
 ├─ makeOrder（真单）
 ├─ payOrder → 微信支付面板
 └─ confirmPayment（1–4 次短轮询，最长约 4.5s）
```

**首单路径总耗时构成**：约 **13–16 次云函数往返** + 1 次手机号授权 + 1 次支付面板。其中结算页进入即占 6 次，注册返回后又补 5 次。

---

## 2. 做得好的部分（先说结论再谈问题）

| 项 | 现状 |
|----|------|
| 登录无感化 | openid 由 `login` 云函数静默获取，**全程没有"授权登录"按钮**；浏览、加购、看券都不要求注册 |
| 注册时机 | 后置到「提交订单」这一刻（`requirePhone` 在下单提交处触发），不在启动或首屏拦截 |
| 用券自动化 | 结算页自动调用 `getBestCoupon` 选中**最优券**，用户不需要手动进券包挑选 |
| 结账场景做减法 | 注册页在 `from=checkout` 时隐藏资料扩展项（昵称/头像/生日/兴趣），只留协议 + 手机号 |
| 注册页有激励预告 | 结账场景会展示新客礼包（`showGiftPack`），让用户知道授权后能拿到什么 |
| 返回后续接 | 返回结算页会重新加载折扣与券，并提示「新客礼已放入本单」 |
| 幂等保护 | 发券幂等键 `register_gift:{openid}` + `users.registerGiftClaimed`，重复提交不会重复发 |
| 中断可恢复 | 去注册前 `persistCheckoutForAuth()` 落盘结算快照，返回后 `resumeAfterAuthIfNeeded()` 续接 |

## 3. 卡点与风险（按影响排序）

### 🔴 A. 提交后才被弹去注册 —— 首单最大的体验断点

用户完整走完结算页（选地址、看金额、点「提交订单」），此时才被整页跳转到注册，需要**勾选协议 + 微信手机号授权**两步才能回来继续。

- 证据：`subpackages/business/confirm-order/index.js` 的提交处理里 `if (!hasPhone(session)) { persistCheckoutForAuth(); await requirePhone({ direct: true, resumeSubmit: true, ... }) }` —— `direct: true` 表示**不弹确认框、直接跳页**。
- 影响：这是"以为要付钱了却被推去注册"的经典落差；且注册页回来后还要再点一次提交。
- 建议（择一）：
  1. **前置**：在结算页进入时就轻提示"首次下单需绑定手机号，可提前完成"（不做强制），把注册动作提前到用户心态更放松的时刻；
  2. **收敛**：若产品接受"先付后绑"，把手机号要求后移到发货前，首单可零注册完成（需评估通知/物流触达）；
  3. **兜底**：至少在提交按钮上方常驻一行"首次下单将绑定手机号"的说明，避免意外跳转。

### 🔴 B. 新客券门槛与首单金额不匹配 —— 发券了但用不上

新客礼默认四档券：**满 100 减 10 / 满 200 减 30 / 满 300 减 50 / 满 500 减 100**（30 天有效）。

- 证据：`cloudfunctions/upsertUserProfile/welcomeGiftDefaults.js` 的默认券档。
- 影响：首单若低于 ¥100（例如一件 ¥58 的标本或文创），**一张都用不了**。用户刚完成注册、看到"新客礼已到账"，进结算却提示券不满足门槛——比不发券更伤。
- 建议：增加一档低门槛券（如满 49 减 10，仍满足折扣纪律 ≤25%），或由服务端按首单金额挑一张"能用且最划算"的券展示并在注册页直接预览"本单可省 ¥X"。

### 🟠 C. 结算页进入即 6 次请求，其中 4 次串行

`onLoad` 中 `loadUserDiscount() → loadCoupons() → walletReady → syncServerPricingPreview()` 是**串行**链，等于把三次网络往返排队；`ensureShippingRules()` 与 `loadDefaultAddress()` 并行但仍占一次往返。

- 影响：网络一般时，从点进结算页到金额/券稳定大约需要数秒，且期间用户看到的是"金额在变"。
- 建议：
  1. 把 `getUserStats`（折扣）与 `fetchMyCoupons` 改为**并行**（两者互不依赖）；
  2. 定价预览 `makeOrder{previewOnly}` 与券的自动选择合并为一次服务端调用（服务端本来就掌握券与价格，可一次算完）；
  3. 结算页做骨架屏/金额占位，避免数字跳动。

### 🟠 D. 注册返回后重跑 5 次请求，提示只停留 4.2 秒

`resumeAfterAuthIfNeeded()` 里依次 `ensureSession(force)` → `loadUserDiscount()` → `loadCoupons()` → `syncServerPricingPreview()`，又是一串串行往返；结果提示 `showAuthResumeHint` 仅 4.2 秒后隐藏。

- 建议：返回结算页时只强制刷新"券 + 定价"两项（会话可用本地缓存），并把提示改为**常驻到用户下次操作**（例如贴在券行旁边）。

### 🟡 E. 支付后确认最长等待约 4.5 秒

为覆盖支付回调延迟，我把 `confirmPayment` 改成 4 次 × 1.5 秒短轮询（配合订单页 2 分钟重复支付冷却）。

- 权衡：容错换来了最长约 4.5 秒的 loading；回调正常时第一次就成功（无额外等待）。
- 建议：把间隔改为 1 秒 × 3 次（最长 3 秒），或先本地标记"支付中"再后台静默确认，让用户立刻看到结果页。

### 🟡 F. 细节瑕疵

- 注册返回后的提示文案是「新客礼已放入本单，可在优惠券中选用」，但此时券**已经自动选中**，文案会让用户以为还要手动操作一次。
- 提交拦截后 `_authNavigating` 仅锁定 1.6 秒，若用户在注册页迅速返回并连点提交，存在二次跳转注册的可能（影响很小，但可加一次会话校验代替定时解锁）。

## 4. 已实施的优化（2026-09-15 本轮落地）

| 原问题 | 实施内容 | 位置 |
|--------|----------|------|
| **B 券门槛用不上** | 新客礼默认档新增 **满 49 减 10**（折扣纪律下限为 `ceil(10/0.25)=40`，合规），排在券档首位 | `cloudfunctions/upsertUserProfile/welcomeGiftDefaults.js` + `admin/src/utils/welcomeGift.js`（两端默认对齐） |
| **C 结算页串行** | 券包网络请求与会员折扣**并行**预取；券的可用性计算仍在折扣就绪后进行（保持依赖正确）。`loadCoupons(prefetched)` 支持外部传入已取回的券包，其他调用点行为不变 | `subpackages/business/confirm-order/index.js` |
| **D 回流重刷 5 次** | 注册返回后优先用**缓存会话**（注册页返回前已强制刷新过），仅在缓存缺手机号时才强制重取；折扣与券包并行；**提示不再 4.2 秒自动消失**，由用户点「收起」或提交订单时关闭 | 同上 |
| **E 支付后等待** | 支付结果确认由 4 次 × 1.5s 收紧为 **3 次 × 1s**（商品订单与钱包充值两条路径一致） | `subpackages/{business,feature}/utils/payment.js`、`subpackages/feature/user/stored-value/index.js` |
| **F 文案不一致** | 回流提示按券的**来源字段** `couponSource === 'register_gift'` 判断（不再猜标题关键词）：已自动选中时提示「新客礼已自动选用「满49减10」，本单省 ¥10」，未选中时才提示「可在优惠券中选用」 | `subpackages/business/confirm-order/index.js` |

### 关于「定价预览与选券合并为一次服务端调用」的实现取舍

结论是**已省掉一次往返**，但用的是**本地选优**而非服务端合并，原因如下：

- 结算页现在的链路是 `fetchMyCoupons（列表，用于展示）→ 本地选最优券（0 次网络）→ makeOrder{previewOnly}（服务端权威定价与校验）`，客户端往返从 3 次降到 **2 次**。
- 「最优券」的判定复用列表构建时**已经算过的** `calculateClientPricing(...).couponSaved`（同一份券规则），只是取其中节省额最大且未禁用的一张，不引入新逻辑。
- 若改成"由 makeOrder 内部再调 getBestCoupon"，需要给 `getBestCoupon` 增加"接受显式 openid"的内部调用分支——那是一层新的鉴权面（且与 2026-09-15 支付事故同属"靠上下文反推来源"的坑）；而且云函数互调要走一次冷启动，很可能比省下的那次客户端往返更慢。
- 服务端依然是权威：预览与正式下单都会重新校验该券，不可用时走既有分支清券并重算（`couponRejected` 路径）。

> 如果后续希望"最优券"只由服务端决定（单一事实来源），建议的做法是给 `makeOrder.previewOnly` 增加 `autoCoupon` 参数、并把选券规则抽成两端共用模块，而不是让函数互调。

**仍需产品拍板的两项**（代码已就绪，等口径）：

- **A 注册时机**：当前仍是「提交订单时才要求绑定手机号」。要么按建议在提交按钮上方常驻说明，要么把绑号后移到发货前（首单零注册）。这属于产品流程选择，未擅自改动。
- **券档数值**：默认档已是满 49 减 10；若希望更低门槛（如满 39 减 10），受折扣纪律限制需同时下调面额（例如满 39 减 9）。

> ⚠️ **一项人工动作**：若线上 `member_welcome_gift` **已保存过配置**，云库配置优先于代码默认，新档位不会自动出现——需在 ERP「新会员礼包」页把「满49减10」这一档补上（或点「恢复默认」）。
