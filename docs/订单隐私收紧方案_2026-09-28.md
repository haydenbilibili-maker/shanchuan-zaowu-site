## E. 第二轮执行记录（2026-09-28，S1 → S2/R1）

### E.1 N0 规则语义实测（临时集合 `zz_rule_probe_*`，测完已删）

| 事实 | 结论 |
|---|---|
| Web 匿名 JWT | `openid: ''`（空串，不是 null） |
| `auth.openid != null` | **匿名能过** → 该写法无效 |
| `auth != null && auth.loginType != 'ANONYMOUS'` | 匿名被拒 ✅ |
| `auth != null && auth.openid != null && auth.openid != ''` | 匿名被拒 ✅ → **选定为 R1**（小程序身份 openid 必非空：现有 `doc._openid == auth.openid` 规则已依赖这一点，故无需真机） |
| R2（doc 级 `doc._openid == auth.openid \|\| ...`） | 仅 `_id` 的查询（`where({_id})` / `doc(id).get()`）**对所有人都被拒** → R2 前必须改写小程序 7 处 `doc(id).get()`，并把 17 处 C 端读改为 `where({_openid})` 或云函数 |

## 1. 事实确认

### 1.1 仓库规则 vs 线上规则 —— 一致

- 仓库：`cloudbase/rules/orders.json` = `{"read":"auth != null","write":false}`；副本 `miniprogram/database-rules/orders.json` 相同。
- `miniprogram/database-rules/orders.field-level.desired.json` 是**死愿望稿**（平台不能可靠落含 `request.data` 的规则，见 `docs/契约C3_订单状态机_2026-09-18.md:113`），**未生效**，且它的 `read` 也是 `auth != null`。
- **线上**（本轮只读实测）：`cd admin && node scripts/apply-database-rules.mjs --dry-run`（只调 `describeResourcePermission`，不写）→ **`orders` 已一致**，线上 = `auth != null`。全量结果：116 个集合与仓库一致、24 个不一致（见 §1.4）、3 个集合线上不存在。

### 1.2 公网暴露面 —— 线上实测

实测方法：Node 直连 CloudBase Web 网关（与浏览器 SDK 同一协议），**只做 `count()`**，不取任何文档内容（探针代码见附录 A）。

### 2.3 小程序内现存越权读路径（与收紧无关，本身是缺陷）

## 4. 方案

### 4.1 规则候选（CloudBase 安全规则能力边界）

CloudBase 自定义规则**是文档级**：可用 `auth.*` 与 `doc.*`（含嵌套字段）写布尔表达式、支持 `||` / `&&`；**不支持字段级读隐藏**（客户端 `.field()` 投影不是安全边界）。查询时要求**查询条件是规则的子集**（`where` 必须显式带上能证明规则成立的条件）；`doc(id).get()` 按该文档实际内容判定。

| 代号 | 规则 `read` | 关闭公网？ | 关闭小程序用户互读？ | 会坏的客户端 |
|---|---|---|---|---|
| R0 现状 | `auth != null` | ❌ | ❌ | — |
| **R1 排除匿名** | `auth != null && auth.loginType != 'ANONYMOUS'`（备选写法 `auth.openid != null`） | ✅ | ❌ | **仅 ERP 15 处** |
| **R2 本人或受礼人** | `auth.openid != null && (doc._openid == auth.openid \|\| doc.giftMeta.receiverOpenid == auth.openid)` | ✅ | ✅ | ERP 15 + 店长页 10 |
| R3 纯本人 | `auth.openid != null && doc._openid == auth.openid` | ✅ | ✅ | ERP 15 + 店长页 10 + 受礼人 7（C 5 + D 2） |

**必须先实测的三件事**（规则语义不能凭文档推断 —— 本仓库「静态分析 ≠ 事实」教训）：
1. 小程序身份的 `auth.loginType` 取值、Web 匿名身份的 `auth.openid` 是否为空 → 决定 R1 用哪种写法；
2. R2 下 `where({'giftMeta.receiverOpenid': openid})` 是否被判为规则子集（嵌套字段 + `||`）；
3. R2 下 `doc(id).get()` 对受礼人是否放行。

实测方式：在同一环境建临时集合 `zz_rule_probe_orders`（2–3 条假数据），逐个套 R1/R2，用附录 A 的匿名探针 + 微信开发者工具真机各跑一遍，测完删集合。**这一步会在生产环境建临时集合，须产品负责人放行**（不碰 `orders` 本身与任何真实数据）。

### 4.4 字段级脱敏（可行性与代价）

- **平台层面做不到**字段级读隐藏 → 只能「拆存储」或「读全走云函数」。
- **R2 之后仍残留的隐私面**：礼赠单的 `orders.address` 是**受礼人**填的地址与手机（`manageGift` 写入，`index.js:673`）。`manageGift` 给送礼人看的是脱敏视图（`index.js:197-199` `maskAddress`/`maskPhone`），但送礼人作为 `_openid` 本人**直读自己的订单文档就能拿到受礼人明文**。这是礼赠的产品语义问题（送礼人该不该知道受礼人地址），**需产品负责人裁决**。
- **拆存储方案**：受礼人地址移到仅云函数可读的 `order_private`（或复用 `gift_receiver_verify` 模式），`orders` 只留脱敏字段 → 牵动 `makeOrder`、`manageGift.submitAddress`、`managerShipOrder` 发货/面单、ERP 订单详情、打印链路，**改契约**，约 3–5 人日，且与礼赠流正在改的 `makeOrder`/`giftMeta` 直接冲突 → 建议礼赠流收口后再议。
- **全走云函数方案**（R3 + 详情接口按视角脱敏）：隐私最干净，但要改 C 端 17 处读、依赖新版覆盖率，工作量最大（+3–4 人日）且旧版 C 端受礼人路径会坏。

## 附录 A · 匿名探针（只读，只做 count）

本轮实测用的最小探针。**只返回数量，不取任何文档内容**；每次运行会在环境里产生一个匿名用户（CloudBase 匿名登录的正常副作用）。

```js
// node probe.mjs [collection,...]
const ENV = 'cloud1-8gnkty5bfff9f0bf'
const API = `https://${ENV}.ap-shanghai.tcb-api.tencentcloudapi.com`
const H = { 'content-type': 'application/json;charset=UTF-8', 'x-device-id': 'probe-' + Date.now() }
const { access_token } = await (await fetch(`${API}/auth/v1/signin/anonymously`, { method: 'POST', headers: H, body: '{}' })).json()
for (const c of (process.argv[2] || 'orders').split(',')) {
  const j = await (await fetch(`${API}/web?env=${ENV}`, {
    method: 'POST', headers: H,
    body: JSON.stringify({ action: 'database.countDocument', dataVersion: '2020-01-10', env: ENV, access_token, collectionName: c, queryType: 'WHERE' }),
  })).json()
  console.log(c, j.data ? `READABLE total=${j.data.total}` : `DENIED ${j.code || ''}`)
}
```
