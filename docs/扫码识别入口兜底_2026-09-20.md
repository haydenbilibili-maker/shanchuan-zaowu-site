# AI 扫码识别入口兜底（2026-09-20 安卓真机反馈）

> 现象：**iOS 扫识别码正常进 AI 页；安卓扫码落到首页**。本文记录可证事实、根因判断、修复与仍待确认项。

## 1. 已核实的事实（都不是推测）

| 项 | 结论 | 证据 |
|---|---|---|
| 生成侧参数 | **正确** | `getStoreQRCode`：页面白名单校验 + `scene` 必填 + `checkPath:false` + `envVersion` 白名单（默认 `release`）；CLI `generate-store-qr.js` 同口径；`generateSharePoster` 指向 `subpackages/feature/identify/result/index`，同样 `checkPath:false` / 默认 release |
| 码指向的页面是否存在 | **存在** | `subpackages/feature/identify/index`、`identify/result/index`、`feature/detail/index`、`feature/wish-wall/index` 均登记在 `app.json`；`identify` 目录**从未搬过家**（无 rename 提交） |
| 分包体积 | **未超限** | feature 1892KB / manager 1783 / extra 1811 / business 1053（上限 2048） |
| 内容开关会不会拦 | **不会** | `showAiIdentify` 缺字段/取数失败都归一为**开**（`src.showAiIdentify !== false`），失败路径也回落默认开启 |
| 印刷码清单 | **原先缺失** | `qr-assets/identify-store-qr.png` 生成于 **2026-09-15 14:46**，当时脚本还没有 `--manifest`；祈福墙那张（2026-09-18）才有 |

## 2. 根因判断：入口路由（不是生成参数）

真机上"落到首页"只有两条可达路径，**两条都在 `app.js`**：

1. **热启动不重走目标页**：小程序在后台时扫码，**部分安卓机只把小程序切到前台**、不重走码里指定的页面，
   用户停在上一次那页（常见就是首页）。App 里**只有图鉴 spot 码**做了 app 级兜底路由（`maybeOpenAtlasSpot`），
   **识别码没有**。
2. **任何 404 一律 `goHome()`**：`onPageNotFound` 原先在没有可重映射路径时**直接 `switchTab('/pages/index/index')`**
   → 用户被丢回首页。

## 3. 修复

| 改动 | 位置 |
|---|---|
| 新增 `maybeOpenIdentifyEntry(options)`：`from=store_qr` → 识别主页；24 位 hex（分享海报 `scene=record_id`）→ 识别结果页；**冷启动入口页已是目标页则不重复跳**；同 scene 4s 去重 | `miniprogram/app.js` |
| 热启动 options 可能是旧的 → 缺失场景用 **`wx.getEnterOptionsSync()`** 再取一次（基础库 2.20.1+） | 同上 |
| `onPageNotFound`：路径含 `identify` 时**先回识别页**（带 `record_id` 就走结果页），不再落首页 | 同上 |
| 识别码**回填侧车清单**（如实标注 `provenance: backfilled-2026-09-20` + 参数出处，不冒充生成时记录） | `scripts/qr-assets/identify-store-qr.json` |
| 守卫扩展：识别码生成参数锁 + 入口路由**接线**与**行为** + 清单 page 必须在 `app.json`；注入 5 条 | `scripts/check-wall-qr.mjs`（域 wish-wall） |

## 4. 仍待真机确认（诚实边界）

- **我没法在真机上复现**，所以修的是"能产生该现象的两条机制"。请在安卓机上按顺序验：
  1. **杀掉小程序**（后台划掉）→ 扫码：应进 AI 页（冷启动路径，一直没问题）；
  2. **让小程序留在后台**（或停在首页）→ 扫码：**修复前会停在首页，修复后应跳到 AI 页**；
  3. 若修复后仍停首页 → 说明该机微信**根本没把 scene 交给 App**（或该机微信/基础库过旧，无法直接从码进入**分包页**）。
     此时下一步是**重新生成一张识别码**：`generate-store-qr.js` 支持 `--via cloud`（需 `STORE_QR_OPS_KEY`）或 `--via wechat`（需 AppSecret），
     并会写侧车清单；同时建议**把新码指向主包页**（`pages/index/index`）+ `scene=from=store_qr`，
     由本次新增的 App 级路由转发到识别页 —— 这样即使是很旧的安卓微信也能进。
- 旧码（已印出去的那张）无法改：能救它的只有本次的 **404 重映射 + 入口兜底路由**。

## 5. 同一类问题第二次发生：收银台「新用户注册」立牌（2026-09-20 下午核查）

> 触发：产品负责人提出「之前做的扫码应该是直接跳转到新用户注册页面，核查现在的链路有何变化」。
> 结论：**链路变了，而且这批注册码现在是死码**（扫码必然落首页）。下面是可核证据。

### 5.1 时间线（全部来自 git，不是推测）

| 日期 | 提交 | 事实 |
|---|---|---|
| 2026-09-15 | `b424752` | 注册页**首次新增**，路径 = `subpackages/feature/user/onboarding/index` |
| **2026-09-15 15:03** | （非 git） | `scripts/qr-assets/register-counter-qr.png` **生成时间戳** → 当时该页就在上面这条路径上 |
| 2026-09-16 | `db02ec0` | 注册页改版：**去掉进页自动跳转**，改由用户选择去逛馆 / 去礼券夹 |
| 2026-09-17 01:18 | `b312a0f` | 「拆出 extra 分包解决超限」→ `R098`：注册页搬到 `subpackages/extra/user/onboarding/index` |
| 2026-09-17 | `28bf776` | 区分登录与注册：首屏中性文案 + 按 `isRegistered` 落文案（老号不再看到「注册即领新客礼」） |

**码里写死的 `page` 是 09-15 那一代路径，页面在 09-17 搬走了 —— 印刷品改不了。**

### 5.2 现在扫这张码，链路上断了三段

| # | 环节 | 现状 |
|---|---|---|
| ① | 微信解析 `page=subpackages/feature/user/onboarding/index` | 当前版本里**不存在** → 走 `onPageNotFound` |
| ② | `onPageNotFound` → `utils/messageHelper.js` 重映射 | 表里只有「主包 → 分包」那一代（`/pages/user/*`）；**分包内部搬迁这一代完全没覆盖** → 重映射后仍是死路径 |
| ③ | app 级 scene 兜底 | 此前只认 `from=store_qr` 与 24 位 hex 记录 id，**`from=counter_qr` 无人兜** → 最终 `goHome()` = **首页** |

也就是说：**注册页自己的 scene 处理（`from=counter_qr` → 独立注册入口）是好的，但用户根本到不了那一页。**
（这也解释了这类"iOS 正常、安卓落首页"的观感差异：凡是靠 404/scene 兜底才能到位的入口，平台与热启动路径一不同就分叉。）

### 5.3 链路本身还变了两处（即使能进页面，行为也和当初不同）

- `from=counter_qr` 被注册页视为**独立注册入口**（`isStandalone`）：**不继承**历史回流意图（不读 `peekOnboardingReturn()` 的 `returnUrl`），完成注册后留在本页承接；
- 完成注册且已绑手机号 → `wx.redirectTo('/subpackages/business/coupons/index')`（去券夹领新客礼），不是回首页；
- 老号（会话 `isRegistered`）→ 走 `LOGIN_DEFAULT`「欢迎回来 / 授权手机号即可确认身份」，**不出现「注册」「新客礼」字样**。

### 5.4 修复

| 改动 | 位置 |
|---|---|
| 新增**第二代（分包内搬迁）别名表** `MOVED_SUBPACKAGE_ALIASES`：`feature/user`→`extra/user`、`user`→`extra/user`、以及 17 条 manager 页 → extra（**逐页列举**，因为 manager 分包仍在、还有 19 个页，绝不能整根替换）；按 `from` 长度倒序，长前缀优先 | `miniprogram/utils/messageHelper.js` |
| 别名命中即整段替换并把 **query 原样带过去**（`scene` 丢了注册页就不再是「独立注册入口」） | 同上 |
| 新增 `maybeOpenRegisterEntry(options)`：`scene` 含 `from=counter_qr` → `/subpackages/extra/user/onboarding/index?scene=from%3Dcounter_qr`；冷启动入口页已是注册页则不重复跳；带 `wx.getEnterOptionsSync()` 热启动兜底 | `miniprogram/app.js`（`onShow` 接线） |

### 5.5 诚实边界与待办

- **仍然无法在真机复现**（同上文 §4）。要验的是：**安卓机杀掉小程序后扫这张注册立牌**，应进「注册领新客礼」页而不是首页。
- 本次是**纯客户端改动**（`app.js` + `messageHelper.js`），**必须重新发版**才生效；旧码**不需要重印**（`page`/`scene`/`envVersion=release` 都无需改，只是路径要由新版本的重映射接住）。
- ⚠️ **`register-counter-qr.*` 至今没有侧车清单**（`scripts/qr-assets/identify-store-qr.json` 那种）。本次结论中"码指向 `feature/user/onboarding`"是**由生成时间戳 + 当时的路径事实反推**的，不是从码里解出来的（小程序码无法本地解码）。建议下一批物料生成时同时落清单，把「它指向哪」变成可核对记录。
- ⚠️ 本次改了 `miniprogram/{app.js,utils/messageHelper.js,scripts/test-legacy-remap.mjs}` → `check:miniprogram-sync` 会红，**直到按流程在验收通过后同步开发仓**（`npm run sync:miniprogram`）。政策上验收前不代跑同步，故留给产品负责人。

## 6. 排查中发现并修掉的**第二个**印刷物料问题：祈福墙立牌被识别路由抢走

> 起因：本次顺手把 `scripts/qr-assets/*.json` 里的**每一张印刷码**都拿 `app.json` 核了一遍
> （不只核注册码），发现祈福墙立牌踩了同一个 `from=store_qr` 令牌。

### 6.1 事实

| 项 | 值 |
|---|---|
| 码 | `wish-wall-store-qr.png`（清单 `generatedAt: 2026-09-18T12:12:53Z`，**已印**） |
| page | `subpackages/feature/wish-wall/index`（**注册页存在，页面是活的**） |
| scene | `from=store_qr&k=mashangyou` ← **与门店识别码共用 `from=store_qr` 令牌** |
| 祈福墙页自身 | 有 `parseWishWallScene('from=store_qr&k=mashangyou')` 与测试（`test-wish-wall.mjs:4547`），处理是好的 |
| 冲突源 | 2026-09-20 新增的 `maybeOpenIdentifyEntry` 只判 `from=store_qr`，**不看 `k`** |

**实测（驱动真实 `app.js`，不是推理）**：

```
冷启动（入口页=祈福墙）scene=from=store_qr&k=mashangyou
  → ["/subpackages/feature/identify/index?from=store_qr"]   ← 被抢走
热启动（停在首页）
  → ["/subpackages/feature/identify/index?from=store_qr"]   ← 被抢走
```

即：**祈福墙立牌自 2026-09-20 起扫了会进 AI 识别页**（连"页面本来就打开了"的冷启动也在 600ms 后被 `reLaunch` 走）。

### 6.2 修复（`miniprogram/app.js`）

在识别路由取到 scene 后、判 `isStore` **之前**加一段让路逻辑：

- `k=mashangyou` → **让给祈福墙**：冷启动入口页就是祈福墙则不动；热启动按**同一 scene 契约**转发到
  `/subpackages/feature/wish-wall/index?scene=<原样编码>`；同 scene 4s 去重；`cur === target` 不重复跳。
- 其它 `k=…` → **不认识就不抢**（把页面留给对应物料自己处理，避免下一个物料再踩同一坑）。

守卫：`test-legacy-remap.mjs` 增加 4 条行为断言（冷启动不被抢 / 热启动转发到祈福墙 / 未知 `k=` 不被抢 /
**识别码与海报码不被误伤**）+ 1 条注入（拆掉让路分支必红）。
副作用核对：祈福墙域 `npm run check:domain -- wish-wall` 只红在同步守卫，`test:wish-wall` / `check-wall-qr` 仍全绿。
