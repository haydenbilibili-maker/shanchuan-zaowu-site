出货表字段：物品名称、出货编号、出货日期、客户名称、规格型号（只有 2 条有值）、数量、单价、分类（标本/工具）、状态、快递公司、运单号、关联库存（全空）、备注、总价。

## 2. SKU 的结构（写入前已核实）

- 集合 `studio_shipment_skus`，写入方是 `manageStudioSettlement` 的 `sku.*`（仅超管），归一化函数是 `settlementDefaults.buildSkuRow`。
- 一个 SKU = 原材料（`studio_material_prices` 的行）× 等级 × 包装方式（`studio_packaging_prices` 的行）× 尺寸 + 是否造景 + 默认手工费率。
  其中材料和包装是必填项；勾了造景就必须填造景成本。
- **SKU 本身不存价格**。开单时按当时的价目表现算：（原材料 + 包装）×（1 + 手工费率 30%）+ 造景成本，
  然后快照进出货单。所以「价格留空」不需要在 SKU 上写空值。飞书的历史单价只作为参考价写进 `note`，不参与算价。
  算不出价的 SKU 在页面上显示「待核价」，并且不能保存出货单，不会被算成 0 元（现有逻辑，未改动）。
- 算价内核对显式等级、尺寸是严格匹配的：价目表里没有这个等级或尺寸就判为「未匹配」，不会静默回落到默认行。
  所以导入时等级和尺寸都写成价目表里真实存在的值，并且每条都用生产内核试算过。

## 3. 梳理规则

1. **只认三要素都有证据的组合**：物种（原材料）、包装方式、尺寸。
   - 小件玻璃罩 → `玻璃罩 球形10`。证据有两条：成品库存写的是「10cm玻璃罩（小球）」；出货表「玻璃罩 10*10」卖 ¥8，与价目表「球形10」¥8 一致。
   - 「+6寸中空相框」→ `黑木纹立体中空相框 2cm深高方6寸`。这是价目表里唯一的中空 6 寸行；出货表「方形相框 6寸」单价 ¥7.41，也与这一行相同。
   - 冰箱贴 → `冰箱贴 磁吸相框款`（价目表只有这一行）。
   - **只写了「玻璃罩」、没写尺寸的大件**（价目表玻璃罩有 10x18 / 球形10 / 球形15 / 15x22 四档）**不按默认尺寸猜**，单独列为「待补尺寸」。
2. 等级：名称里写了（春型 / 夏型）就用写的；没写就取价目表该材料的默认等级行，并在 `note` 里注明。
3. 名称变体只在证据明确时归并：「华艳色䗓」→「华艳色蟌」（错字）；「熊峰王 / 雄峰王」→「熊蜂王」（飞书备注原文已经说明）；
   「未展翅」→「没展翅」。**名称不全等的材料不归并**，例如红腋星蛱蝶 ≠ 红星蛱蝶、异型紫斑蝶 ≠ 异形紫斑蝶，一律列入「需新建资料」。
4. 价格：同一产品所有有单价的记录（排除备注写「参考历史价 / 待确认」的）单价一致，才算价格明确；否则列入「价格留空」，并写明历史单价范围。
5. 去重：先按 `skuKey` 判断，再看出货中心里是否已有人工建的同材料 × 同包装 SKU（只差尺寸）。是的话视为同一产品，标「已存在」，不重复写入。
6. 不新建原材料和包装资料。缺资料的组合列入「需新建资料」，等产品负责人点名后再建。

| 命令 | 作用 |
|---|---|
| `node scripts/import-shipment-skus.mjs` | dry-run：按线上现状重新核对引用、去重并试算（只读） |
| `node scripts/import-shipment-skus.mjs --apply` | 先全量备份到 `backups/shipment-sku-batch1/<时间>-before-apply/`，逐条写入，再逐字段读回核对 |

`sku.update` 的部分更新不会写这三个字段，所以编辑或停用 SKU 不会冲掉待复核标记（守卫钉住）。

## 8. 9.21 起的出货单 → 草稿箱（2026-10-09 产品负责人追加）

原话：「将9.21至今的出货单全部写入小程序出货中心，作为草稿存入草稿箱；等待后续人工审核和修改」。

**为什么另建集合**：`ops_shipments` 已有 `draft` 状态，但看板、日报、账单、对账、应收这些读取方**只排除 `cancelled`**，

`cloudbase/rules/ops_shipment_memos.json`、`cloudbase/schema/ops_shipment_memos.md`），任何统计都读不到它。

**分组规则**：同一「出货日期（东八区）」+ 同一「客户名称」= 一张单（飞书「出货编号」每行一个，不能用来合单）。
门店按 `guessStoreId`（与飞书同步同规则）；认不出的标「门店待匹配」，在草稿里选。

**跳过规则**（写进报告，不改任何既有单据）：
1. 该行已作为飞书同步单进了 `ops_shipments`（按 `feishuRecordId`）；
2. 同日同门店已有正式单（草稿口径：未删且未取消）；
3. 同 `importKey` 已导入过（含已删除的草稿，不复活）—— 脚本因此可重复运行。

**行明细**：飞书原文（品名、规格、数量、单价、总价、备注、分类、状态、快递、运单）照存；只按首批 SKU 的来源记录自动对应 SKU，
对不上的标「待匹配」。金额同时存**飞书原始金额**与**系统参考金额**（按当时价目表，与正式开单同一个算价内核）及差额；
飞书总价为 0 且没有单价的行记为「无价」，不当成 0 元。

**草稿能做什么**（小程序 出货中心 →「单据」→「草稿箱」，仅超管）：选门店、每行选 SKU / 换 SKU / 取消匹配、改数量、删行（可恢复）、
删除整张草稿、**转为正式出货单**。转正式调用的就是正式开单 `createFromSkus` 本身，金额与直接开单一致，
**也会照常给门店发「待支付」通知**；转正式前不通知、不扣库存、不进结算。门店或任何一行还待匹配时不能转正式。
