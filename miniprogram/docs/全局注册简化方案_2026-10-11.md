## 1. 现状（2026-10-11 代码取证）

注册的服务端链路只有一条：`authPhone{ finishRegistration:true, patch }` → 内部调 `upsertUserProfile{ completeOnboarding:true }`
（建档 + 幂等发新客礼包 + 资料奖励）；客户端唯一出处 `subpackages/feature/utils/registerPhone.js`，注册页另有一份同链路实现。

| 入口 | 现状步骤（用户要做的动作） | 跨页 |
|---|---|---|
| A「我的」→ 注册 | ①点「注册 / 登录」→ 进注册页（等会话返回才出新客礼卡）→ ②（选填）头像、藏家代号 → ③勾选协议 → ④点「授权手机号 · 领取新客礼」→ ⑤微信授权弹窗点「允许」→ 完成页 → ⑥选「逛馆 / 去礼券夹」 | 3 页 |
| B 门禁（结算、预约、礼赠核验；`requirePhone(..., { direct: true })`） | ①点原动作 → **直接跳**注册页 → ②勾选 → ③点授权 → ④允许 → 回原页（有回流时跳过完成页）→ ⑤预约 / 礼赠要**再点一次**原动作（结算带 `resumeSubmit` 自动续） | 2 页 |
| C 收银台注册码（`scene=from=counter_qr`，**印出去的码改不了**） | ①扫码 → 注册页 → ②勾选 → ③授权 → ④允许 → 完成页 → ⑤去礼券夹核销 | 2 页 |
| D 原地弹层（图鉴详情 / 鉴定结果 / 祈福墙的 `RegisterAuthDialog`；礼赠领取的注册引导卡） | ①勾选 → ②授权 → ③允许（可「先不注册」关闭） | 不跳页 |

**结论**：注册页本身已经是「勾选 + 授权」，**多出来的步数在页外**：门禁的系统弹窗 + 跳页、完成页、回来再点一次；
以及注册页上的头像 / 代号（选填但占首屏，且要等会话返回才定版式）。D 形态已是目标形态。

## 2. 方案

| 编号 | 改动 | 步数变化 |
|---|---|---|
| S1 门禁原地化 | `requirePhone / requireRegistered` 的「系统弹窗 → 跳注册页」改为页面内弹 `RegisterAuthDialog`（与 D 同一组件、同一条 `registerWithPhone`）；注册成功后**自动续做**原动作 | B：6 步 → 3 步（勾选 / 授权 / 允许），不跳页 |
| S2 注册页瘦身 | 注册页只留：新客礼卡 + 协议勾选 + 授权按钮；头像 / 藏家代号移出首屏（见 §3 后补） | A：6 → 4（点注册 / 勾选 / 授权 / 允许） |
| S3 完成页合并 | 无回流入口（A、C）的完成页改为注册页**原页成功态**（礼包明细 + 「去礼券夹 / 逛馆」），不再 redirect 新页 | A、C 少一次跳页；C 的「去礼券夹」保留 |
| S4 统一口径 | 门禁、原地弹层、注册页三处的协议勾选、`agreedTermsAt` 留痕、埋点 `from` 统一；收敛成一份「注册面板」实现 | 不改步数，降漂移 |

**建议顺序**：S4（先统一口径，含 §5 的留痕补齐）→ S1（收益最大）→ S2 → S3。每步单独点名、单独发版。

## 3. 简化后哪些字段后补

| 字段 | 现状来源 | 简化后 | 后补时机 |
|---|---|---|---|
| `phone / phoneVerifiedAt` | 授权手机号 | **不变**（注册唯一必需） | — |
| `agreedTermsAt` | 注册页 patch | **必须保留**，所有入口随注册一起写 | — |
| `nickName` | 注册页选填，空则「藏家」 | 默认「藏家」（authPhone 建号已是此值） | 「我的」资料页；或首次需要署名时（收藏证书、祈福墙）就地提示，不拦流程 |
| `avatarUrl` | 注册页选填 | 空 | 「我的」资料页 |
| `gender / birthday / interests / mbti / zodiac / bio` | 本就在资料页 | 不变 | 资料页（「完善资料」奖励照旧在那里领） |
| `onboardingStep` | 注册页写 1 | 原地入口同样写 1（或保持缺省，服务端不依赖） | — |

## 4. 对注册云函数契约与下游的影响

| 下游 | 影响 | 说明 |
|---|---|---|
| 注册云函数（`authPhone / upsertUserProfile`） | **零契约改动** | 入参 `patch` 本就全可选；`completeOnboarding` 语义不变 |
| 会员号 | 无 | `memberNo` 由微信身份推导（`buildMemberNo(openid)`），不落库、不随注册入口变化 |
| 新客礼包 | 无 | 仍在 `completeOnboarding` 时幂等发放（`register_gift:{openid}` 去重）；礼包卡展示从「注册页」挪到弹层时要保留「老号不承诺礼包」判据（`isRegistered`） |
| 门店归属 | 无 | 注册时不写门店字段（现状即如此）；门店归属来自后续消费 / 储值，不受影响 |
| 收银台注册码 | **页面路径与 `scene=from=counter_qr` 处理必须保留** | 码已印出；`app.js` 三层兜底与注册页 `onLoad` 识别逻辑不动；S3 仅把完成页并进原页 |
| 埋点 | 需补口径 | 现有 `onboarding_start / onboarding_complete / phone_bind_success / auth_register_success / auth_login_success`；原地弹层组件本身**不报注册事件**，由各宿主页各报一套（`wiki_register_gate`、`wish_wall_register_gate`、礼赠 `gift_reg_guide_*`），全站注册漏斗拼不起来。S4 统一为「注册面板」一套事件 + `from` 区分入口；物料码转化（`qrMaterial` 的 `convertAction: onboarding_complete`）须继续能统计到 C 入口 |
| 资料完善奖励 | 无 | 仍按 `onboardingDone` 触发、幂等；头像 / 代号后补不影响 |

## 5. 隐私合规红线（不可突破）

1. 协议**默认不勾**，必须用户主动勾选；未勾时授权按钮不带 `open-type="getPhoneNumber"`（只提示）；点协议名只打开协议、不等于勾选；
2. 不静默建号、不静默取号：建号只发生在用户点「允许」之后；
3. 必须给「先不注册」出口（2026-10-11 微信审核驳回整改口径），门禁页关掉后能返回；
4. 所有入口随注册写 `agreedTermsAt`（同意留痕）；
5. 所有入口登记进 `check:privacy-consent`。

> **已修（2026-10-11 产品负责人点名）**：共用注册弹层与资料页绑号已补记同意时间，`check:privacy-consent` 钉住「每个入口都记录」。原取证：原地弹层 `RegisterAuthDialog` 注册时**不写 `agreedTermsAt`**（注册页会写）——
> 勾选本身合规，但「何时同意」没有留痕。礼赠注册引导卡本轮已补（礼赠流自己的组件）；`RegisterAuthDialog` 属他流 / 稳定期组件，**未改**，建议随 S4 一并修。

## 7. 风险

1. **分包与体积**：`RegisterAuthDialog` 在 `feature` 分包；结算 / 预约在 `business` 分包，小程序不能直接引用别的分包组件。
   选项：a) 放主包（主包仅余约 3 KB，**不可行**）；b) 分包异步化（`componentPlaceholder`，需基础库 ≥ 2.11.2，首次弹出有加载延迟）；
   c) 每个分包一份副本 + 漂移守卫（仓库已有同类做法，但多一份副本）。另：`feature` 分包正在做体积治理，不宜再往里加。
2. 门禁自动续做：结算外的动作（预约、领券）当前不续做，原地化后若不续做，用户仍要再点一次；逐个补续做会触到这些稳定期页面。
3. 老用户「欢迎回来」文案与礼包承诺的首屏竞态（2026-09-17 修过）在弹层里要重新守住。
4. 收银台码：完成页并入原页后，「去礼券夹核销」路径要真机回归，避免店员现场引导断链。
5. 审核：弹层形态已过审（D 入口），但门禁场景面积变大，需保留「先不注册」出口。
