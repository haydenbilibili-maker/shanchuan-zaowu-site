## 2. 背景与问题陈述

### 2.1 一期交付回顾（M1/M2）

| 能力 | 状态 | 说明 |
|---|---|---|
| Tab「这有店」替换原「预约」 | ✅ | `pages/store/index` |
| 双店切换 + 记忆门店 | ✅ | `preferredStoreId` |
| 展陈分区列表 + 详情 swiper | ✅ | `store-zone` 分包 |
| 导航 / 电话 / 预约参观 CTA | ✅ | 埋点已接入 |
| 本店活动（按 storeId 过滤） | ✅ | 客户端过滤，非 DB 索引查询 |
| 预约写入 storeId | ✅ | `createBooking` |
| 云库覆盖 + 种子降级 | ✅ | `getStoreConfig` + `storeDefaults` |
| 关于品牌 / 探索入口跳转 | ✅ | switchTab store |

### 2.2 二期要解决的核心缺口

| 缺口 | 现状 | 用户 / 业务影响 |
|---|---|---|
| **运营无法自助改店** | 门店文案、图片、分区 largely 依赖代码种子 + 手动改库 | 换图、调价目说明、临时闭店需开发介入 |
| **预约未分店主** | 各店共用同一套时段与名额逻辑 | 主店参观与工坊课程无法独立控量 |
| **展陈内容偏薄** | 分区仅封面 + 短描述，无关联馆藏 / 百科 / 代表藏品 | 「先逛再买」决策链断裂 |
| **到店转化不可衡量** | 无签到、无到店记录、无 LBS 引导 | 无法评估 Tab 对线下客流贡献 |
| **跨模块联动浅** | 探索无门店卡片；商品无「本店可体验」；定制 / 伴宠默认店规则未产品化 | 线下服务与线上交易割裂 |
| **消息触达缺门店维度** | 山海有信有 `storeId` 规划，门店公告 / 临展通知未落地 | 活动预告、闭店通知无法精准推送 |

### 2.3 二期一句话目标

> **让「这有店」成为可运营的线下前台：运营能改、用户能逛深、预约能分店、到店能闭环。**

## 3. 产品定位与边界

### 3.1 定位（延续一期）

> 把「这有山里的山海造物」搬进手机——选一家店，看展陈、查信息、约到店。

二期在**不改变 Tab 定位**的前提下，加强**内容深度**与**运营工具**，仍不做：

- 门店内 SKU 货架式电商（本店有货为**轻量标注**，非独立卖场）
- 直播 / 打卡营销话术
- 多商场多城市扩张（架构预留，本期仍聚焦这有山双店）

### 3.2 与相邻模块分工

| 模块 | 二期与这有店关系 |
|---|---|
| **探索** | 新增「走进这有店」入口卡片，可 deep link 至指定门店 |
| **馆藏 / 商详** | 商品展示「可到店体验 · XX 店」标签 |
| **预约** | 分店主时段、闭店日、改期规则；入口仍从门店 + 我的 |
| **标本工坊 / 伴宠** | 到店确认默认星宸；门店页服务行直达 |
| **山海有信** | 预约提醒、门店公告、临展通知 |
| **店长后台** | 门店 / 展陈 / 临展 / 预约按店管理 |

### 3.3 北极星指标（二期）

| 指标 | 定义 | 目标方向 |
|---|---|---|
| 门店 Tab 有效访问率 | 进入后发生切换 / 导航 / 预约 / 展陈详情任一行为 | 较 M2 基线 +30% |
| 展陈详情完读率 | 进入 `store-zone` 且滚动至 CTA 区域 | ≥ 45% |
| 预约创建来源 · 门店占比 | `from=store` 的预约 / 总预约 | ≥ 40% |
| 预约到店率 | 签到或核销 / 已确认预约 | 可度量（二期建立基线） |
| 运营配置生效时效 | 后台改图 / 文案 → C 端可见 | < 5 分钟（含缓存刷新） |

### 5.2 E1 · 运营可配置（P0 · 阶段 2.1）

#### 5.2.1 店长后台 · 门店管理

**入口**：店长后台 → 新增 Tab「门店管理」

| 功能 | 说明 |
|---|---|
| 门店列表 | 两店只读 ID，可编辑展示字段 |

| 预览 | 保存后提示「约 5 分钟内 C 端生效」；支持清除 `getStoreConfig` 侧缓存 **【待确认是否做主动 purge】** |

**权限**：仅 `manager` / `admin` 角色可写；C 端只读。

#### 5.2.2 云函数与数据

| 任务 | 说明 |
|---|---|
| `manageStoreConfig`（新） | action: `listStores` / `updateStore` / `listZones` / `updateZone` |
| `getStoreConfig` 增强 | 支持 `If-Modified` 或版本号；C 端下拉刷新强制拉新 |
| 种子同步 | `storeSeed.js` 与 `storeDefaults.js` 保持字段一致，云库为空时降级 |

#### 5.2.3 C 端修复（技术债）

| 项 | 现状 | 二期 |
|---|---|---|
| `store-zone` 详情 | 仅读本地 `storeDefaults` | 与首页一致走 `getStoreConfig` 云数据 |

| 联系电话 | 占位号 | 运营在后台维护真实号码 |

**验收**：

### 5.3 E2 · 预约分店主（P0 · 阶段 2.1）

#### 5.3.1 业务规则 **【待确认】**

| 规则 | 建议默认 |
|---|---|
| 主店 | 入店参观：10:00–21:00，每 30min 一档，每档上限 8 人 |
| 工坊 | 手作课程：按 `activities` 名额；参观预约可选更少时段 |
| 闭店日 | 每店独立 `closedDates[]`；法定假可共用模板 |
| 提前预约 | 最早 7 天，最晚提前 2 小时 |
| 改期 / 取消 | 对齐 [优化方向梳理](./优化方向梳理.md) 预约 P0 |

#### 5.3.2 数据模型扩展

**集合 `store_booking_rules`（新）**

```javascript
{
  storeId: 'store_shanhaizaowu',
  visitSlots: [{ start: '10:00', end: '10:30', capacity: 8 }],
  closedDates: ['2026-10-01'],
  advanceDays: 7,
  minAdvanceHours: 2,
  updatedAt: 1234567890
}
```

**`bookings` 已有 storeId** → 创建时校验该店当日该时段 `count < capacity`。

#### 5.3.3 交互

| 页面 | 变更 |
|---|---|
| `booking/index` | 顶部门店条可点击切换（Sheet）；时段按 storeId 加载 |
| `store/index` | CTA 预填当前店；闭店日显示「今日不可约」 |
| `my-bookings` | 卡片展示 storeName + 地址摘要 |

**云函数**：扩展 `createBooking`（校验名额）、新增 `getBookingAvailability`（按 storeId + date 返回可用时段）。

**验收**：

- [ ] 主店某时段满员后，同时间段不可提交
- [ ] 工坊课程仅展示 `activities.storeId = store_xingchen` 的活动
- [ ] 预约成功站内信含正确门店名与地址

### 5.4 E3 · 展陈内容深化（P0 · 阶段 2.2）

#### 5.4.1 展陈详情升级（`store-zone`）

在现有 swiper + 文案基础上增加：

| 区块 | 内容 |
|---|---|
| 策展长文 | `zone.longDesc`（事实 → 感受 → 连接，200–400 字） |

| 关联百科 | 0–3 篇 `relatedWikiIds`，跳 wiki-detail |
| 物种铜牌 | 可选 `featuredSpecies[]`（中文名 + 拉丁学名） |
| CTA | 「预约参观此区域」→ booking，带 `storeId` + `zoneId`（统计用） |

#### 5.4.3 内容生产流程 **【待确认】**

## 7. 页面与交互要点

### 7.1 门店首页（增量）

| 元素 | 二期行为 |
|---|---|
| 闭店日 | Hero 区域显示「今日店休」，预约 CTA 置灰并说明 |
| 临展条 | 有 active exhibition 时 Hero 下金色细条 **【P2】** |
