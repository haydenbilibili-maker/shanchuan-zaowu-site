## 1. 先配环境变量（必做，最高优先级）

以下云函数在云开发控制台需配置环境变量 `MESSAGE_ADMIN_OPENIDS`，值为**店长/超管 openid，多个用英文逗号分隔**：

| 云函数 | 用途 | 未配置的后果 |
| --- | --- | --- |
| `manageStaff` | 角色管理、whoami | 无人能开通店员，后台入口全部不可见 |
| `grantStorePoints` | 门店赠分 / 撤销 | 店员无法赠分 |
| `getStorePointRules` | 赠分规则读写 | 规则无法配置（读取仍走默认值降级） |
| `storeCheckIn` | 到店签到统计 | 签到统计接口拒绝 |
| `getMemberPass` | 会员码核销 | 店员无法核销会员码 |
| `pushMessage` | 群发站内信 | 群发拒绝 |
| `manageStoreConfig` | 门店配置 | 门店配置无法保存 |
| `getAnalyticsDashboard` | 数据看板 | 看板拒绝 |
| `syncFinanceData` | 财务账本同步 / 商城对账 | 账本读写与对账拒绝 |

`getUserSession` / `getUserStats` 也读这个变量（用于「我的」页入口显隐），建议一并配上，否则店长在「我的」页看不到后台入口。

获取自己 openid 的最快方式：小程序里进「我的 → 关于/客服」，或在云开发控制台的 `users` 集合按 `nickName` 找 `_openid`。

**拒绝时的错误码**（`staffGuard.js`）：

- `NOT_LOGGED_IN` —— 拿不到 openid
- `ADMIN_UNCONFIGURED` —— 环境变量为空**且**该用户在 `staff_members` / `users.isAdmin` 里都查不到，提示文案已写明要配 `MESSAGE_ADMIN_OPENIDS`
- `FORBIDDEN` —— 已识别身份但角色不够、缺权限点，或跨门店操作

**兜底逃生口**：`staffGuard` 的第三级兜底是 `users.isAdmin === true`。若线上已有 `isAdmin` 的店长账号，即使忘配环境变量也仍是 manager，不会被立刻锁死。但**不要依赖它**——`users` 集合客户端可写的风险面比环境变量大，环境变量仍是唯一可信的超管来源。

## 3. 建集合与索引

### 新增集合

| 集合 | 权限建议 | 说明 |
| --- | --- | --- |
| `staff_members` | 仅云函数可读写（关闭所有客户端权限） | 店员/店长角色表 |
| `store_purchases` | 仅云函数可读写 | 门店消费记录（赠分凭据） |
| `store_point_rules` | 所有人可读 / 仅云函数可写 | 赠分规则 |

### 索引

| 集合 | 索引字段 | 唯一 | 作用 |
| --- | --- | --- | --- |
| `store_purchases` | `dedupeKey` | **是** | 赠分幂等，同一笔消费不会重复发分 |
| `store_purchases` | `storeId` + `createTime`(降序) | 否 | 门店流水与当日汇总 |
| `store_purchases` | `userOpenid` + `createTime`(降序) | 否 | 顾客维度查询 |
| `point_records` | `dedupeKey` | **是** | 兑换幂等；注意历史数据 `dedupeKey` 缺失，唯一索引需勾选**稀疏/忽略空值**，否则建不上 |
| `point_records` | `userOpenid` + `createTime`(降序) | 否 | 积分明细分页 |
| `staff_members` | `openid` | **是** | 一人一条 |
| `store_point_rules` | `storeId` + `status` | 否 | 规则查询 |

> `dedupeKey` 唯一索引是原子性方案的核心（幂等键 + pending 状态机 + 补偿），**不建等于没有防重**，务必先建索引再放量。
> `point_records` 需保留「仅创建者可读」以上的读权限：「我的」页的今日签到判断仍是客户端直查该集合。

### 需要补字段的既有集合

- `users`：新增 `storeSpendTotal`（门店累计消费）、`storePointsTotal`（门店累计得分）、`staffRole`（冗余角色，供入口显隐）、`pointsDebt`（撤销超额时的欠分）。均由云函数自动写入，无需手工建。
- `user_coupons`：兑换发券会写 `source: 'points_exchange'`、`costPoints`、`sourceRefId`，券包会显示「积分兑换 · N 积分」。
- `rewards`：店长后台的权益表单新增 `expireDays`（券有效天数，缺省 30）、`limitPerUser`（每人限兑，0 为不限）。**存量 coupon 类权益建议补一次这两个字段。**

## 4. 配置赠分规则

规则遵循「代码默认值 + 云端集合覆盖 + 异常降级」（同 `getSupportConfig`），**不建集合也能跑**，跑的是代码默认值。

默认值（`getStorePointRules/defaults.js`，与方案 §推荐默认值一致）：

| 字段 | 默认 | 含义 |
| --- | --- | --- |
| `mode` | `perThreshold` | 每满 X 送 Y |
| `threshold` / `pointsPerThreshold` | 1 / 1 | 每满 ¥1 送 1 分（1 元 = 1 积分） |
| `ratio` | 1 | 仅 `ratio` 模式生效（1 元 = 1 分） |
| `minAmount` | 1 | 起赠金额 |
| `maxAmountPerRecord` | 50000 | 单笔金额上限（防录错） |
| `applyMemberMultiplier` | false | 门店消费不叠会员倍率（强制固定为 false） |
| `dailyPointsCapPerUser` | 5000 | 单顾客单日赠分上限 |
| `dailyPointsCapPerStore` | 50000 | 单门店单日赠分上限 |
| `dailyRecordCapPerUser` | 3 | 单顾客单日录入笔数上限 |
| `revokeWindowDays` | 30 | 撤销窗口（天） |

改规则有两条路：
- 店长后台 → 门店积分 → 规则页，直接改（走 `getStorePointRules` 的 `save`）。
- 或手工往 `store_point_rules` 插一条 `status: 'active'` 的文档；带 `storeId` 为单店规则，不带为全局规则，单店优先。

> **注意**：若云库 `store_point_rules` 已有旧文档（如 threshold=1000 / points=100），会**覆盖**代码默认值。升级到 1 元=1 分后，须在店长后台把门槛改为 `1` / `1`，或更新/停用旧文档，否则前端仍会显示旧规则。
>
> **兑券**：代码不写 `rewards` 库。请运营在积分商品中配置至少一档 `type=coupon`、`cost=100`、面值 `10` 的线上代金券，与「100 积分 → ¥10」说明一致。

三种模式：
- `fixed`：满 `threshold` 元送固定 `points` 分（一次）
- `perThreshold`：每满 `threshold` 元送 `points` 分（可累计）
- `ratio`：按 `ratio` 比例折算

## 5. 权限边界

| 能力 | manager 店长 | staff 店员 |
| --- | --- | --- |
| 会员码核销 `verifyMemberPass` | ✅ | ✅ |
| 门店赠分 `grantStorePoints` | ✅ | ✅ |
| 撤销赠分 `revokeStorePoints` | ✅ | ❌（默认不给） |
| 到店签到统计 `viewStoreVisits` | ✅ | ✅ |
| 赠分规则配置 `manageStorePointRules` | ✅ | ❌ |
| 角色管理 `manageStaff` | ✅ | ❌ |
| 门店配置 / 数据看板 / 群发 | ✅ | ❌ |
| 财务、库存、商品、内容 | ✅（店长后台） | ❌ |

店员看到的流水默认只有**自己**录的（`mine: true`）；有 `revokeStorePoints` 权限的才能看全店并撤销。
店员可被限定门店（`storeIds`）；留空表示不限门店。跨门店操作会被 `STORE_DENIED` 拒绝。

### 如何给某人开通店员

1. 让对方先登录一次小程序（产生 `users` 记录）。
2. 拿到其 `_openid`（云开发控制台 `users` 集合按昵称找）。
3. 店长进「我的 → 店长后台 → 门店积分 → 店员」，点新增，填 openid、姓名、角色（staff/manager）、可选门店。
4. 对方重进小程序，「我的」页即出现「店员后台」入口。

停用：同一页面点「停用」，把 `status` 置为 `disabled`，服务端立即拒绝。
超管兜底：环境变量 `MESSAGE_ADMIN_OPENIDS` 里的 openid 永远是 manager，即使 `staff_members` 里没有记录，避免把自己锁在门外。

> 客户端口令 `admin888`（`utils/managerAuth.js`）只是 UI 门帘，**不构成服务端信任依据**。所有写操作都由云函数的 `staffGuard.js` 独立校验。

## 6. 上线前自测路径

1. 店长在「我的」页能看到「店长后台」，店员只看到「店员后台」，普通顾客两个都看不到。
2. 顾客「我的 → 会员码」出示，店员后台「核销」页扫码 → 显示等级与权益。
3. 店员后台「赠分」页扫同一个会员码 → 录入金额 → 试算 → 确认赠分。
4. 顾客侧我的积分「积分明细」出现一条门店入账；**会员等级与成长值不变**（门店消费只加 `bonusPoints`）。
5. 同一笔重复提交（连点或断网重试）→ 返回「已录入过」，积分不翻倍。
6. 断掉会员码（等 60 秒过期）后用手机号后 4 位兜底查找，能查到并赠分。
7. 我的积分兑换一张代金券 → 券包显示「积分兑换」来源 → 下单时能抵扣（`makeOrder/pricing.js`）→ 支付后核销（`fulfillOrder`）。
8. 店长在门店积分页撤销刚才那笔赠分 → 积分扣回，顾客收到站内信，记录状态变为「已撤销」。
9. 店员账号访问店长后台 → 被拒绝并退回。

## 7. 已知限制与待决策

- **成长值口径**：`pointsBalance.js` 沿用既有 `orders .limit(100)` 汇总线上消费，老用户订单破百会失真。这是仓库原有隐患，本次未改动口径，避免影响等级与折扣。
- **手机号兜底**：按后 4 位模糊匹配，最多返回 5 条候选，需店员当面核对昵称。候选列表不显示可用积分（逐个汇总线上订单成本过高），选定顾客后由试算返回准确余额。
- **撤销超额**：顾客积分已花光时撤销，`bonusPoints` 会扣成负数（即欠分），差额同时写入 `users.pointsDebt` 供运营查看，后续入账自动抵扣。顾客侧暂无欠分提示页面。
- **超窗撤销**：超过 `revokeWindowDays` 只有超级管理员（`MESSAGE_ADMIN_OPENIDS` 里的 openid）能撤，普通店长会被拒。
- **每日上限**：`dailyPointsCapPerUser` / `dailyPointsCapPerStore` / `dailyRecordCapPerUser` 三道闸门在试算阶段就会提示，触顶后赠分被拒。风控字段只下发给店员/店长，普通用户读规则时会被裁掉。
- **多门店规则**：单店规则覆盖全局规则，但没有「门店继承 + 局部覆盖」的字段级合并，改单店规则要填全。
- **券的适用范围**：MVP 按方案定为「全站通用 + minSpend 门槛」，未加 `scope` 字段。若后续要做品类券/单品券，需要同时改 `makeOrder/pricing.js`。
- **店长后台 `manager/index.js` 体积**：该文件已过大，本次新功能没有继续往里加 tab，而是独立成 `store-points` 与 `staff` 两个页面，从店长后台跳转。后续建议按模块拆分该文件。
- **消费金额来源**：目前靠店员手工录入，没有与收银/POS 对接，依赖小票号 `receiptNo` 做人工对账。
