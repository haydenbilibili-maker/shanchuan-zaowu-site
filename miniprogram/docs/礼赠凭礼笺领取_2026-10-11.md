# 礼赠 · 凭礼笺领取（不知道对方手机号也能送）（2026-10-11）

> **需求来源（产品负责人点名，礼赠为稳定期模块，本文件即点名范围）**：
> 「目前礼赠的身份识别是通过手机号，但是礼赠场景有一种可能是不知道对方手机号码的情况下会增加用户侧的沟通确认成本，优化这个环节。」
>
> **拍板（2026-10-11 两轮）**：方案 A（凭礼笺领取）+ 可选 6 位领取口令；手机号改选填（推荐填）；只有「邀请 TA 填地址」「门店自提」可不填号；
> 有效期沿用；送礼人可作废并换新链接（截止对方填地址 / 到店领取前）；**打开不算领取，须主动点「收下」**；
> **领取不强制注册**（第二轮更新），以微信身份收下，保留非强制、可关闭的引导注册卡片（领取场景内「少步骤」注册，协议仍须主动勾选）；
> 不做转赠；凭礼笺领取的礼赠关掉「发朋友圈」；送礼人可见领取人；「不设核验」后门改为「转为凭礼笺领取」；
> 私密消息防二次转发本轮只出真机验证步骤，默认不启用。
>
> **第三轮拍板（2026-10-11 晚）**：「寄给我自己」也改为手机号选填（推荐填写），不填即凭礼笺领取，规则见 **§10**；
> 引导卡文案通过不改；自提不加 7 天过期；旧版小程序不限制（提示升级即可）；私密消息等真机验证；全局注册页简化只出方案
> （`miniprogram/docs/全局注册简化方案_2026-10-11.md`，不改代码）。
>
> **纪律**：已填号的定向礼赠行为**逐字不变**；历史礼赠（无新标记）行为不变；只加可选入参 / 可选字段 / 新 action；
> 不改订单状态机、不改 `giftMeta.js` 五副本、不改注册云函数与全局注册页 / 注册弹层组件、不改生产数据。

## 1. 现状卡点（调研结论，证据见上一轮汇报）

| 环节 | 卡点 |
|---|---|
| 送礼编排页 | 四种交付方式一律必填受礼人手机号，不填付不了款 |
| 寄给我自己 | 也要求填号（东西寄给送礼人，号码无意义）—— 第三轮拍板放开为选填，见 §10 |
| 领取 | 号码对不上就领不了，受礼人无自助出口 |
| 后门 | 下单后「不设核验」可清号 → 退回「谁先打开谁领」；礼笺还能发朋友圈且带领取凭证 |

## 2. 新流程

### 2.1 送礼人

1. 编排页「怎样交给 TA」下：选「邀请 TA 填地址」或「门店自提」时手机号标注「推荐填写」，下方有「不知道 TA 的手机号？凭礼笺领取 ›」；
   切过去后显示说明 + 可勾「加 6 位领取口令（只你看得到）」+「知道 TA 的手机号？改为手机号核验」。
   选「直寄 TA」时手机号仍必填（与现状一致）；「寄给我自己」第三轮起同样可选凭礼笺领取（§10）。
2. 付款 → 送礼成功页：显示「凭礼笺领取 · 口令 123456」（有口令时）或「凭礼笺领取」；点开管理面板可：
   加 / 去掉口令、**作废并换新链接**（对方填地址 / 到店领取前）、改用手机号核验。
3. 对方收下后，成功页与「我的礼赠」显示领取人：`称呼（或「未留名的微信用户」）· 尾号（已注册才有）· 收件人姓氏（填了地址才有）· 收下时间`。
4. 凭礼笺领取的礼赠：成功页 / 订单详情**隐藏「分享到朋友圈」**，朋友圈卡也不带领取凭证。

### 2.2 收礼人

1. 打开礼笺：仪式、礼笺、藏品照常看；**不会被记为领取人**。
2. 有口令 → 先输 6 位口令（每人每单每小时 5 次、每单每小时 20 次，沿用核验限次）。
3. 可选留一个称呼（给送礼人看）→ 点「收下这份山海」→ 以当前微信身份收下（**无需注册**）。
   一份礼笺只能被一个微信身份收下；其他人再点得到「这份山海已有去处」。
4. 收下后照旧：填址礼赠去留地址；自提礼赠出现门店领取码；之后看物流、签收、证书与养护都按原链路。
5. 收下后（以及之后再进礼笺）：未注册者看到一张可关闭的引导卡片（见 §4）。

## 3. 身份保障（未注册领取）

| 风险 | 对策 |
|---|---|
| 群里随手点开就被领走 | 打开不绑定；须主动点「收下」 |
| 链接被转发给别人 | 领取凭证 128 位随机；可加口令；送礼人看得到谁收下，发现不对可作废换链接，旧链接立即失效、原领取人解绑 |
| 朋友圈扩散 | 凭礼笺领取的礼赠关朋友圈分享入口，朋友圈卡不带凭证（单页模式打不开领取） |
| 冒领后填址寄走 | 填址前送礼人可作废；填址须是已收下的同一微信身份 |
| 口令暴力猜 | 6 位 × 限次（同号码核验）：7 天内命中率约 0.3% |
| 两人同时点「收下」 | 收下是**条件写入**（仅当仍无人收下且链接未换过才写），只有一人成功，另一人得到「已有去处」 |
| 口令过了就算领了？ | 口令通过只记「这个微信过了口令」，仍须本人点「收下」；别人过了口令不代表你也过了 |
| 注册后「找不回」礼赠 | 账户与微信身份同源：注册不换微信身份，已收下的礼赠天然在其名下（无需迁移） |

## 4. 引导注册（领取场景内，非强制）

- 位置：领取页「收下」成功后 + 已收下者再进领取页；可点「先不注册」关闭（本机记住，同一礼赠不再出现）。
- 完成方式：卡片内**直接完成**（不跳注册页）：①勾选「我已阅读并同意《用户服务协议》和《隐私政策》」（**默认不勾**）②点「微信手机号一键注册」→ 微信弹出手机号授权，用户点「允许」（未勾时按钮不带授权能力，只抖动并提示勾选）。
  走与注册页同一条链路 `subpackages/feature/utils/registerPhone`（注册云函数与全局注册页 / 注册弹层组件不动）。
  收下时留了称呼 → 卡片上多一行「昵称用『X』（之后可在「我的」里改）」，**默认勾选、用户可取消**，随注册一起提交；昵称未过内容审核时不带昵称完成注册（号已绑上，不让用户重来）。
  收件地址本就记在这份礼赠订单上，不需要再复制进账户。
- 卖点（只写确实存在的，**文案待产品负责人审阅**）：
  - 新客礼包自动到账（首次注册，按微信身份只发一次）；
  - 收藏证书署上你的名字（证书持有人名取会员昵称）；
  - 卡片底注：签收后的标本养护指南与提醒照常送达你（无需注册）。
- 埋点：`gift_reg_guide_expose / click / done`。
- 红线：不默认同意、不静默建号、不静默取号；`check:privacy-consent` 新登记本入口。

| | 改前（必须注册才能收下） | 改后 |
|---|---|---|
| 收礼最少步骤 | 点收下 → 跳注册页 → 勾选 → 授权手机号 → 返回 → 再点收下（5–6 步、跨页） | 点收下（1 步，不跳页） |
| 想注册时 | 同上（跨页） | 卡片内：勾选 → 授权（2 步，不跳页） |

## 8. 私密消息（防二次转发）· 真机验证步骤（本轮不启用）

验证通过前不接代码。真机步骤（需两台以上手机、三个微信号 A 送礼 / B 收礼 / C 第三人）：
1. 服务端用 `cloud.openapi.updatableMessage.createActivityId()` 生成 `activityId`（临时云函数或云开发控制台调试即可）；
2. A 在送礼成功页分享前调用 `wx.updateShareMenu({ withShareTicket: true, isPrivateMessage: true, activityId })`，再把礼笺发给 B（单聊）；
3. B 点开：领取页 `onLoad` 读 `wx.getEnterOptionsSync().shareTicket`，调用 `wx.authPrivateMessage({ shareTicket })`，记录 `valid` 是否为 true；
4. B 把这张卡再转发给 C；C 点开后同样调用 `authPrivateMessage`，确认 `valid` 为 false（或卡片显示「私密消息」不可转发提示）；
5. 分别在 iOS / 安卓、微信最新版与较旧版本各测一次；再测「A 发到群」时群内多人点开的表现；
6. 记录：是否需要用户额外授权、卡片外观变化、低版本表现。三项都可接受再决定是否接入（接入只改送礼成功页与领取页，不改契约）。

## 10. 「寄给我自己」不填号（第三轮，2026-10-11）

**这类礼赠的本质**：藏品寄到送礼人自己手里，再当面转交；物流、收货地址、签收都在送礼人这边，与收礼人身份无关。
收礼人身份只决定一件事 —— **这份礼「记在谁名下」**：TA 的「我收到的」、持有人卡、签收后的收藏证书与养护提醒。

**归属与领取规则（与 §2 / §3 凭礼笺规则同一套，只有作废窗口不同）**

| 项 | 规则 |
|---|---|
| 下单 | 手机号标「推荐填写」；不填 → 凭礼笺领取（可加 6 位口令）。填了号 → 手机号定向，**行为不变** |
| 物流 | 照旧寄到送礼人填写的地址；收礼人收不收下都不影响发货与签收 |
| 收礼人 | 送礼人把礼笺转给 TA（当面交付时扫码 / 私聊转发均可）→ TA 主动点「收下」（有口令先输口令）→ 这份礼记在 TA 名下；**不用注册、不用手机号** |
| 一人一份 | 同 §3：条件写入，只有第一个点「收下」的微信身份成功 |
| 没人收下 | 礼赠照常完成（货本就在送礼人手里）；只是没有受礼人的「我收到的」记录 —— 与今天「填了号但 TA 一直没打开」等价；**不设过期、不退款** |
| 作废并换新链接 | **订单未结束前都可以**（待发货 / 已发货 / 已签收），已收下的人会被解除。理由：货在送礼人手里，作废只改「记在谁名下」，不牵动任何实物；而当面转交往往发生在签收之后 —— 若沿用「发货前」截止，送礼人在最常用的时刻反而无法纠错 |
| 口令加 / 去 | 同作废窗口，且仅在无人收下前 |
| 朋友圈 / 领取人可见 / 「不设核验」 | 同 §2 / §3：关朋友圈；送礼人看得到称呼与收下时间；已填号的礼赠清号 = 转为凭礼笺领取（寄给我也适用） |
| 收藏证书 | 规则不变：持有人取「收下的那个人」；签收（送礼人这边确认收货）后对 TA 可见 |

**契约增量（向后兼容）**
- `giftReceiverPhone.CLAIM_LINK_DELIVERY` 追加 `ship_to_self`（两份逐字副本）；`makeOrder` 无其它改动；新能力标记**不新增**：
  旧客户端从不对寄给我发 `giftClaimMode:'link'`，缺号仍拒，行为不变。
- `manageGift`：凭礼笺领取的作废 / 口令窗口按交付方式取值（寄给我 = `paid / shipped / received`，其余不变）；
  `getReceiverVerify` 新增可选出参 `resetHint`（管理面板「何时之前可作废」的说明，旧客户端忽略）。
- 送礼页 / 确认页：可免填号的交付方式追加「寄给我」；寄给我在凭礼笺说明里换成「货寄到你处，TA 收下后记在 TA 名下」。
- 部署：先 `makeOrder` → `manageGift`，再发小程序。云函数先上线时旧版小程序行为不变。

**兼容边界**：寄给我 + 凭礼笺领取的礼赠，收礼人若停在旧版小程序，打开后没有「收下」按钮（同自提，§5），
货不受影响；按第三轮拍板不限制、提示升级即可。

## 11. 「犒劳自己」按普通下单填地址（2026-10-12）

问题：关系选「犒劳自己」时交付仍默认「邀请 TA 填写地址」，下单后要顾客自己去礼笺里留址，常找不到入口。

- 送礼页：选「犒劳自己」→ `selfTreat`，交付固定 `ship_to_self`，隐藏邀请填址 / 其它交付方式 / 受礼人手机号，显示「寄到我的收货地址」；换成其它关系或点「其实是送给别人？」恢复原交付方式。
- 确认页：和普通下单一样填收货地址与手机号；领取核验号码取收货地址手机号（`pendingGiftSelfTreat` / `pendingGiftReceiverPhone`），缺号或不足 11 位在地址校验处就地提示，不退回送礼页。
- 不变：云函数与 `makeOrder` 入参出参（仍是 `ship_to_self` + `giftReceiverPhone`），普通「寄给我」与其它交付方式。守卫：`check:gift-claim-link` H 组。

## 12. 代填地址 / 犒劳自己文案 / 交付方式入口（2026-10-12 第二轮）

起因：订单 ORDMV4Y5YPR765（机械独角仙 ¥399）是 075a9cbf 生效前下的「犒劳自己」单，走了邀请填址，核验号码就是下单人本人手机，而送礼人不能收下自己的礼 → 下单人没有任何入口填地址；顾客把地址线下告诉了门店，店员只看到「待填址禁发货」。
