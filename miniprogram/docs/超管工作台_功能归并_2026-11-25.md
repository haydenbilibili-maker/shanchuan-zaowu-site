# 超管工作台 · 功能归并与分类优化（2026-11-25）

> 现状：**7 个分区 / 52 个一级入口**（`subpackages/manager/manager/hubNav.js` 的 `HUB_ENTRIES`）。
> 产品负责人：「超管功能已经超过 52 个，看看有哪些是可以合并同类项的，大幅度优化功能分类与数量」。
> 本文是**归并方案**（只做减法与换位，不删能力）。实现按「阶段」推进，每阶段都能单独上线。

---

## 0. 现状盘点（52 项）

| 分区 | 项数 | 入口 |
|---|---|---|
| 订单履约 | 7 | 订单、工单、礼赠履约、礼赠管理、发票、审批、孤品定金 |
| 经营数据 | 3 | 账本、报表、门店 |
| 商品内容 | 8 | 藏品、内容、评价、开关、审核、装修、活动、主播 |
| 会员触达 | 8 | 会员 CRM、权益、有信、会员调级、荣誉馆长、积分、新人礼包、生日礼包、钱包配置 |
| 工作室 | 13 | 仪表盘、供应商、采购、出货中心、SKU 维护、库存、工作室账单、物业、飞书同步、标本师、合作申请、标本师提成 |
| 门店组织 | 7 | 核销验票、店员工作台、员工、权限、股东、工资条、工资维护 |
| 系统监测 | 6 | 运费规则、预约规则、客服入口、微信通知、AI 鉴定、博物君 |

**问题不在数量本身，而在「同一件事被拆成多个一级入口」**：
- 会员的「权益 / 调级」、「新人礼包 / 生日礼包」各自占一格，但都是「等级与礼遇」一件事；
- 工作室的「供应商 / 采购 / 库存 / SKU 维护」是一条第 1 段到第 4 段的同一价值链；
- 门店的「员工 / 权限 / 工资维护 / 我的工资条」是同一份人事数据；
- 系统的「运费 / 预约 / 客服 / 微信通知」全是**一条一条的规则设置**；
- 商品的「装修 / 开关 / 审核」是同一个「上线前的店铺状态」。

---

## 1. 归并原则（三条）

1. **同一份数据 / 同一条动线，只留一个入口**，内部用分档（子 Tab）复用它已有的页面能力；
2. **一级入口=任务**（我要干什么），**二级=对象**（给谁、哪一类）——不按系统模块名建入口；
3. 归并后**每个入口的权限键保持不变**（`keys` 只增不减地映射到原菜单键），不做权限收紧或放宽。

## 2. 目标结构：7 分区 → **5 分区 / 30 项**

| 新分区 | 项数 | 入口（粗体=归并后的新入口） |
|---|---|---|
| 订单与履约 | 5 | 订单、工单、**礼赠**、**审批与发票**、孤品定金 |
| 经营与数据 | 2 | 账本、报表 |
| 商品与上线 | 5 | 藏品、内容、评价、**上线准备**（装修 / 开关 / 审核）、**馆内运营**（活动 / 直播） |
| 会员 | 6 | 会员 CRM、有信、**会员等级**（权益 / 调级）、积分、**会员礼包**（新人 / 生日）、钱包配置 |
| 工作室与门店 | 8 | **货品**（供应商 / 采购 / 库存 / SKU）、出货中心、仪表盘、**成本与账单**（账单 / 物业）、**标本师**（名单 / 合作申请 / 提成）、**员工**（名单 / 权限）、**工资**（维护 / 我的工资条）、核销、店员工作台、股东 |
| 系统 | 2 | **设置**（运费 / 预约 / 客服 / 微信通知）、**AI 监测**（鉴定 / 博物君） |

> 门店组织并入「工作室与门店」后，门店资料（原「经营数据 → 门店」）回到「门店」自己这一组，不再挂在数据区。

## 3. 分阶段实施

| 阶段 | 内容 | 减少 | 工期 | 风险 |
|---|---|---|---|---|
| **P1** | 「换入口」与「双档」里最省事的 5 组：礼赠、审批与发票、馆内运营、会员等级、AI 监测 | 52 → 43（−9） | ~2h | 低（都在已有页面加一档 / 改跳转） |
| **P2** | 会员礼包、货品、成本与账单、员工、工资 | 43 → 35（−8） | ~3h | 中（要动库存 / 员工 / 工资页的结构） |
| **P3** | 上线准备、设置（两个新壳页） | 35 → 30（−5） | ~2.5h | 中（新壳页 + 三/四档路由） |
| **P4** | 分区从 7 收敛到 5（订单与履约 / 经营与数据 / 商品与上线 / 会员 / 工作室与门店 / 系统 —— 实际 6 个） | 数量不变 | ~1h | 低（只动 `HUB_SECTIONS` 与磁贴分组） |

> 注：P4 的「5 分区」若把「系统」并进「工作室与门店」就是 5 个；建议保留「系统」独立（运维与业务混在一起最难找人）。

## 4. 归并后仍需守住的

- `check:hub-entries`：磁贴 ↔ 清单逐枚一致、每枚有 16 字内说明、无重复入口；
- 权限：每个新入口的 `keys` 必须覆盖被吸收入口的全部菜单键（**只并入口，不放宽权限**：原先需要 `invoice` 的人，合并后仍需 `invoice` 才能看到「审批与发票」里的发票档）；
- 深链：`switchTab idx=` 与 `?tab=` 深链保持可用（合并后旧的 idx 仍要映射到新入口的对应档，避免历史通知里的链接失效）；
- 埋点：归并只改入口，不改事件名（`switchTab` 的 tabTitle 变化不影响事件）。
