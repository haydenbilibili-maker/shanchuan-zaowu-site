### 5.1f 仍无法用代码闭合的一项（需架构改动）

**`products.costPrice` 成本价外泄**：`products` 集合为 `read: true`（**免登录可读**），而小程序端有 **33 处直接读 `products`**、ERP 亦然。因此单靠云函数剔除字段无法解决——必须二选一：

### 5.4c 集合写权限收紧（2026-09-15 第六轮）——含一次「差点改坏 ERP」的排查

代理鉴权上线后，才能开始收紧 `write: "auth != null"`（含匿名登录，任意人可改后台配置）。

**本轮收紧 3 个集合**（线上 apply + 回读 `matched=true`）：

| 集合 | 变更 | 依据 |
| --- | --- | --- |
| `admin_login_logs` | `write: auth!=null` → `false` | ERP 仅有 `cdnCount`/`cdnQueryPage`（读）；小程序 0 引用 |
| `admin_operation_logs` | 同上 | 同上 |
| `points_rules` | 同上 | 仅 `fetchCollectionLimit` 读取（遗留集合，非线上 SSOT） |

> `read` 一律**保持不动**（ERP 要读这些集合），只收紧写。

**方法论（重要）**：静态分析连续三次给出**错误的「可安全收紧」结论**，若照做会打断 ERP：

1. 只匹配 `cdnUpdate/cdnAdd/cdnRemove/...` → **漏掉 `cdnSet` 与 `cdnUpsertByWhere`**（这两个正是 `benchmark_research_docs`、`user_behavior_config` 的写入方式）；
2. 只匹配 `collection('字面量')` → **漏掉 `db.collection(COLLECTIONS.X).update(...)`**（`financeSync.js` 就是这样写 `finance_settings` 的）；
3. 全局别名表把各组件里同名的 `const COLLECTION = ...` 互相覆盖 → 误判 `price_list_items`；
4. 还有 `contentDb.js` 的**集合名作参数**写法（`saveDoc(collectionName)` → `cdnAdd(collectionName)`），静态无法解析 → `content_*` 五个集合也会被误判为「无写入」。

最终采用的判据：**文件级作用域 + 完整写 helper 清单（含 `cdnSet`/`cdnUpsertByWhere`）+ 原生 `collection(...).add/update/remove/set` + 参数化写路径人工排查**，并对每个「可收紧」结论做逐处人工复核。

**仍需 ERP 迁移后才能收紧的 22 个**（附证据文件，供后续迁移排期）：

**为什么线上仍然是好的**：Cloudflare Pages 自己的 Git 集成也在从 `main` 构建部署——已验证线上确实是新代码：

| 探测 | 结果 |
| --- | --- |
| `GET /api/cloud-fn` | `{"success":true,"msg":"admin proxy online"}`（不再回显白名单） |
| `POST /api/cloud-fn`（无 Cookie） | **HTTP 401** |
| `GET /admin/` | HTTP 200 |

也就是说两条部署通道里，**Pages Git 集成这条是通的，GitHub Actions 这条是废的**。风险是：每次推送都留一条红色 CI，且如果有人误以为「CI = 部署」，会在 Actions 挂掉时误判线上未更新。

**建议二选一（需你操作，代码无法闭合）**：
1. GitHub 仓库 → Settings → Secrets and variables → Actions → 新增 `CLOUDFLARE_API_TOKEN`（Cloudflare → My Profile → API Tokens → 模板「Edit Cloudflare Workers」或 Pages 权限）；或
2. 既然 Pages Git 集成已覆盖部署，直接停用/删除该 workflow 的 deploy job，避免长期红灯掩盖真实故障。

### 6.0e 回归修复：ERP 登录后立刻「管理会话已过期」（2026-09-15 第六轮，已上线验证）

**这是上一轮代理鉴权改造自己引入的回归，且是 P0 级（ERP 完全无法使用）**，由使用方实测发现。

**根因**：`establishAdminSession()` 用 `import.meta.env.BASE_URL` 拼接口地址。ERP 的 Vite `base` 是 `/admin/`，于是请求打到了 `/admin/api/admin-session` —— 该路径不存在，Pages 返回 **405**。

原逻辑把 405/404 当作「未部署 Functions，本地开发降级」并返回 `ok: true`，于是：

```
登录页 → POST /admin/api/admin-session → 405 → 当成"开发环境降级"放行
      → 前端 isLoggedIn = true（看起来登录成功）
      → 服务端 HttpOnly 会话 Cookie 从未下发
      → 之后每个管理类云函数经 /api/cloud-fn 都 401
      → 前端 dispatch sc-admin-session-expired
      → 弹「管理会话已过期，请重新输入口令」，且重新登录永远无效
```

**为何上一轮没测出来**：我只用 curl 从**站点根**验证了 `/api/admin-session` 与 `/api/cloud-fn`（这条链路一直是好的），没有按 SPA 实际拼出的路径走一遍——即「服务端对了，客户端调错地址」。

**修复**：
1. 会话接口改为站点根绝对路径 `/api/admin-session`（POST 与 DELETE 两处）。站点 Functions 固定在根，不受 SPA `base` 影响。
2. 新增 `isLocalDevHost()`：只有 `localhost`/`127.0.0.1`/`*.local` 才允许「未部署 Functions」的降级放行；线上遇到 404/405 **或 HTML 响应**直接报错，不再"假成功"。这类失败今后会立刻可见，而不是伪装成会话过期。
3. `AICenter` 提示文案从 `VITE_DEEPSEEK_API_KEY` 改为服务端 `DEEPSEEK_API_KEY`（`VITE_` 变量已从 Pages 移除，旧文案会误导运营把密钥重新塞回前端包）。

**验证（线上实测）**：

| 步骤 | 期望 | 实测 |
| --- | --- | --- |
| 错误口令 POST `/api/admin-session` | 401 | ✅ 401 |
| 正确口令 POST `/api/admin-session` | 200 + 下发 Cookie | ✅ 200 |
| 带 Cookie POST `/api/cloud-fn` | 200 | ✅ 200 |
| DELETE `/api/admin-session`（退出） | 200 | ✅ 200 |
| 线上 admin 产物 | 根路径、无 `/admin/api/admin-session` | ✅ `index-Bf1y2t5H.js` 内 `fetch(\`/api/admin-session\`)` ×2，错误路径 0 处 |

**顺带确认**：服务端 `DEEPSEEK_API_KEY` 已生效——`GET /api/ai` 实测 `configured.deepseek = true`（此前为 `false`，ERP AI 不可用）。

> **同类隐患（未修，属既有缺失）**：`utils/ossCompanionTts.js`、`utils/aliyunCompanionTts.js` 同样用 `${base}/api/...` 拼路径。实测这些接口在根路径与 `/admin/` 前缀下**都是 404**——即对应 Pages Functions 从未实现，属功能缺失而非本次回归，需要时另行补齐。

### 6.0f 修复：AI 智能中心误报「DeepSeek 未配置」（2026-09-15 第六轮，已上线验证）

**现象**：Cloudflare Pages 已配置服务端 `DEEPSEEK_API_KEY`，`GET /api/ai` 实测
`configured.deepseek = true`，但 ERP「AI 智能中心」仍显示 **DeepSeek 未配置**。

**根因**：`getAIProviderConfigStatus()` 是**纯本地同步函数**——只统计前端 `VITE_*`
环境变量与 localStorage 里的浏览器备用 Key，**从不询问服务端网关**。
上一轮为消除密钥内联，把 `VITE_DEEPSEEK_API_KEY` 从 Pages 移除后，本地计数必然为 0，
状态卡于是恒显「未配置」，**与真实可用性完全相反**（实际对话请求走 `/api/ai` 网关、
由服务端注入密钥，一直是通的——见下方端到端实测）。

**修复**：
1. `aiHelper` 新增 `fetchAIGatewayStatus()`：`GET /api/ai`，**以网关自述为准**；
   `getAIProviderConfigStatus(gateway)` 合并该状态，新增 `deepseekGateway` /
   `gatewayReachable`，`deepseekConfigured` 改为「本地或服务端」二者之一。
2. `AICenter` 挂载即拉取网关状态；标签区分「已配置（服务端）」/「已配置」；
   探测未完成时显示「正在检测…」而不是直接判定未配置；新增「配置来源」一行；
   其他厂商 Key 标注（服务端）；说明文案按来源区分。
3. 顺带修正 `aiGatewayUrls()` 顺序：根路径排最前。ERP 的 Vite `base` 是 `/admin/`，
   原实现每次都先打 `/admin/api/ai` 拿 405 再回退，白费一次请求
   （与 §6.0e 的会话接口是同一类 `base` 前缀问题）。

**验证**：

| 项 | 结果 |
| --- | --- |
| `GET /api/ai` | `{"ok":true,"configured":{"deepseek":true,...}}` ✅ |
| 线上 admin 产物 | 新包 `index-Btnd-YiY.js` / `AICenter-CcGBN3sn.js` 内含「DeepSeek 已配置（服务端）」「配置来源」「正在检测…」✅ |
