### 6.0e 回归修复：ERP 登录后立刻「管理会话已过期」（2026-09-15 第六轮，已上线验证）

**这是上一轮代理鉴权改造自己引入的回归，且是 P0 级（ERP 完全无法使用）**，由使用方实测发现。

**根因**：`establishAdminSession()` 用 `import.meta.env.BASE_URL` 拼接口地址。ERP 的 Vite `base` 是 `/admin/`，于是请求打到了 `/admin/api/admin-session` —— 该路径不存在，Pages 返回 **405**。

原逻辑把 405/404 当作「未部署 Functions，本地开发降级」并返回 `ok: true`，于是：

```
登录页 → POST /admin/api/admin-session → 405 → 当成"开发环境降级"放行
      → 前端 isLoggedIn = true（看起来登录成功）
      → 服务端 HttpOnly 会话 Cookie 从未下发
      → 之后每个管理类云函数经 /api/cloud-fn 都 401
      → 前端 dispatch sc-admin-session-expired
      → 弹「管理会话已过期，请重新输入口令」，且重新登录永远无效
```

**为何上一轮没测出来**：我只用 curl 从**站点根**验证了 `/api/admin-session` 与 `/api/cloud-fn`（这条链路一直是好的），没有按 SPA 实际拼出的路径走一遍——即「服务端对了，客户端调错地址」。

1. 会话接口改为站点根绝对路径 `/api/admin-session`（POST 与 DELETE 两处）。站点 Functions 固定在根，不受 SPA `base` 影响。

3. `AICenter` 提示文案从 `VITE_DEEPSEEK_API_KEY` 改为服务端 `DEEPSEEK_API_KEY`（`VITE_` 变量已从 Pages 移除，旧文案会误导运营把密钥重新塞回前端包）。

### 6.0j 环境变量专项：57 个函数读取 `ADMIN_OPS_KEY`，其中 27 个未配置（已补齐）

**发现方式**：交叉核对「代码里 `process.env.*` 读取的变量」与「云端 `Environment.Variables` 实际配置」。
共 48 个函数引用了未配置的变量（多为 fail-closed，功能不可用但不失安全）。

**`ADMIN_OPS_KEY` 部分（本轮处理）**：

| 项 | 结果 |
| --- | --- |
| 代码读取该密钥的函数 | 57 个 |
| 已配置 | 30 个 |
| **未配置** | **27 个** ← 已全部补齐 |
| 补齐方式 | 读取现有变量 → 合并（**不删除任何原有键**）→ 写回 → 逐函数回读校验 |
| 校验结果 | 27/27 成功；原有变量一个不少；值与基准一致 |

**值一致性核查（重要）**：已配置的 30 个里，**29 个使用同一值，1 个不同** —— `assistProductCopy`。
并未盲目覆盖（那是密钥轮换决策，不是脚本该做的），留待使用方确认。

**补齐的实际效果（实测，不是"配了就完事"）**：

| 组 | 判据 | 实测结果 |
| --- | --- | --- |
| A 组 11 个 | 代码里会透传 `adminOpsKey` | ✅ **补密钥即生效**：`getSupportConfig` / `getUserAchievements` / `getStudioDashboard` 现返回 `success:true`；`dispatchMessage` 已通过鉴权进入业务逻辑（报"缺少 openid 或 eventType"而非鉴权错误） |
| B 组 16 个 | 代码**完全没提** `adminOpsKey` | ❌ 补密钥**无效**：`assistExhibitionCopy` / `getMemberPass` / `getPointRecords` / `messageAdmin` 仍返回 `NOT_LOGGED_IN` |

**B 组与 `assistProductCopy` 是同一类代码缺陷**：它们调用
`assertStaff(db, openid, { permission })` 却**从不把 `event.adminOpsKey` 传进去**，
而 `assertStaff` 只比较 `options.adminOpsKey`（`staffGuard.js:575-604`）。
后果：ERP 经 `/api/cloud-fn`（代理会把密钥注入 `payload.data`，见
`functions/_lib/cloudbaseCallFn.mjs:229-233`）调用时，**永远无法通过密钥鉴权**。

**另有 3 个函数不在代理允许名单**：`assistExhibitionCopy`、`assistProductConcept`、
`assistYouxinCopy` 不在 `ALLOWED_FUNCTIONS`（26 个）内 → ERP **根本无法经代理调用**；
`assistProductCopy` 在名单内，但因上述缺陷同样不可用。

> 结论：`ADMIN_OPS_KEY` 只是"密钥存在"，**能否用取决于代码是否透传**。
> 本轮已把"存在"补齐；"透传"属代码改动，需与使用方确认后再动（涉及 16 个函数 + 4 个 AI 文案函数）。
