# PRD · 藏品「新版本审核」快照上架 / 下架（2026-11-25）

> 产品负责人原话：「在藏品-风险管理模块新增新版本审核一键上架与下架功能，即目前已经处于上架状态的产品为我已经审核过的无风险产品，
> 将这些产品作为后续一个集合，即上线审核之前这些商品为上架状态，其它商品都下架，产品审核通过之后恢复所有产品的上架状态。」

状态：**规划中（未开工）**。落点：小程序 · 管理端工作台 → 藏品库 → **风险管理** tab。
不改 C 端、不改订单/礼赠/支付链路。

---

## 1. 问题与目标

微信每个新版本提交审核时，审核员看到的是**线上实时在售的商品**。运营在开发期陆续上新（新藏品、含保护类的新档案），
这些新品还没被审核过；审核员一旦翻到，可能以「售卖保护动物制品 / 信息不实」驳回，拖慢整个版本。

现状：风险管理里只有两把粗粒度按钮——

| 现有能力 | 代码 | 作用域 |
|---|---|---|
| 已下架 → 一键上架 | `bulkRelistOffShelf` → `_applyShelfBulk(ids, true)` | 全库 `isOffShelf === true` |
| 在售 → 一键下架 | `bulkOffShelfOnSale` → `_applyShelfBulk(ids, false)` | 全库 `isOffShelf !== true` |

它们解决的是「全开 / 全关」，**没有「上一次审核通过时的可见集合」这个概念**，所以：
- 审核前全下架 → 审核期店铺空着，正常转化归零；
- 审核后全上架 → 会把**还没来得及自查的新品**也一起放出去。

目标：引入**审核基线（已审核无风险集合）**与**审核快照**，把这件事变成一次可逆的操作。

---

## 2. 术语与口径

| 术语 | 定义 |
|---|---|
| **审核基线** `baselineIds` | 上一次审核通过后，确认「已审核、无风险、允许在审核期展示」的商品 id 集合 |
| **审核快照** | 进入审核模式那一刻的**在架集合** `beforeOnIds`，用于审核通过后原样恢复 |
| **审核模式** | 状态机中的 `reviewing`：只有 `baselineIds` 在架，其余全部下架 |
| **隐藏集合** `hiddenIds` | 本次因进入审核模式被我们下架的 id（= `beforeOnIds ∖ baselineIds`），恢复时只动它们 |

**「在架」的唯一判据**：`products.isOffShelf !== true`（与 C 端列表、`productShelfCounts` 完全同口径）。

---

## 3. 状态机

```
        ① 标记基线                 ② 进入审核                ③ 审核通过
idle ───────────────▶ ready ─────────────────▶ reviewing ─────────────────▶ approved
  ▲                     │                        │  │
  │                     │ ②' 直接进入（无基线=空集）│  └── ④ 审核未通过（继续隐藏）──▶ reviewing
  └─────────────────────┴── ⑤ 放弃 / 回滚（恢复弹窗里的 hiddenIds，不动基线）
```

| 状态 | 允许的动作 | 页面主按钮 |
|---|---|---|
| `idle` 无基线 | 标记基线（= 当前在架） | 「标记当前在架为已审核」 |
| `ready` 有基线、未进入审核 | 进入审核 / 重标基线 | 「进入审核模式」 |
| `reviewing` 审核中 | 审核通过并恢复 / 恢复原状（放弃） | 「审核通过 · 恢复上架」「放弃并恢复」 |
| `approved` | 重标基线（下一次审核准备） | 「更新审核基线」 |

**关键语义（必须写死在云函数里，不靠 UI 纪律）**

1. **进入审核**：`hidden = beforeOnIds ∖ baselineIds` → 只把 `hidden` 下架；`baselineIds` 保持上架。
   - `baselineIds` 为空（从未标记）时，等价于「除已下架外全部下架」，UI 必须先弹二次确认并提示「本次会让店铺只剩 0 件在售」。
2. **审核通过 · 恢复**：把 `beforeOnIds` 重新上架；**不**把审核前就已下架的商品上架（它们本来就不该可见）。
   - 恢复完成后自动把基线刷新为 `beforeOnIds`（这批新品如今已过审，成为新的白名单）。
3. **放弃并恢复**：只恢复 `hiddenIds`，**不**刷新基线。
4. **幂等**：`approve` / `cancel` 重复调用返回同一结果（按 batch `status` 短路），不重复写审计。
5. **审核期间新增的商品**：不自动加入基线；它们天然是「下架」态，审核通过恢复时**也不会**被上架（不在 `beforeOnIds` 里）——
   这是刻意的：新品要等下一次标记基线。

## 4. 数据模型

### 4.1 新集合 `product_review_batches`（一行一个审核批次）

```js
{
  _id: 'auto',
  status: 'reviewing' | 'approved' | 'cancelled',   // 进行中只允许一条
  baselineIds: ['p1', 'p2'],      // 标记基线时的在架集合（进入审核时快照存一份，防基线被并发改）
  baselineAt: Date,
  baselineBy: 'openid',
  beforeOnIds: ['p1', 'p2', 'p9'],// 进入审核那一刻的在架集合（恢复目标）
  hiddenIds: ['p9'],              // 本次被我们下架的
  enteredAt: Date,
  enteredBy: 'openid',
  finishedAt: Date | null,
  finishedBy: 'openid',
  note: '',                       // 版本号 / 审核批次备注（如「v1.4.2 审核」）
  // 统计（写入时定格，供列表与审计读取）
  counts: { total: 0, beforeOn: 0, baseline: 0, hidden: 0 },
  createTime: Date,
  updateTime: Date
}
```

约束：
- 同一时间**最多一条** `status === 'reviewing'`（云函数写入前先查，命中则拒绝并返回该批次，UI 引导去「审核通过 / 放弃」）；
- `_id` 与批次号分离，`_id` 用云自动 id，`note` 里写版本号；
- 集合权限：`read: false / write: false`（只走云函数），登记 `cloudbase/schema/` + `admin/src/cloud.js` 的 `COLLECTIONS` + `sensitive.serverOnly`。

### 4.2 商品侧字段（复用，不新增）

进入审核写：
```js
{ isOffShelf: true, shelfUpdatedAt: serverDate(), shelfReviewHidden: true }   // 新增一个标记位，便于「只恢复我们下架的」
```
恢复写：
```js
{ isOffShelf: false, shelfApprovalStatus: 'approved', shelfReviewHidden: false, shelfUpdatedAt: serverDate() }
```

> `shelfReviewHidden` 是**幂等与安全阀**：恢复时只上架 `shelfReviewHidden === true` 的商品；
> 若有人在审核期手动下架了某件（本该在架），我们不会把它误上架。

## 5. 云函数 `manageProductReview`（新建）

```
actions: status | markBaseline | enter | approve | cancel
```

| action | 入参 | 行为 | 返回 |
|---|---|---|---|
| `status` | — | 读最近一条 reviewing / 最近一次 approved 批次 + 当前在架/下架/基线计数 | `{ batch, counts }` |
| `markBaseline` | `note?` | 全库分页取 `isOffShelf !== true` 的 id → 写批次 `baselineIds`（status 保持 idle/approved 语义用 `baselineAt/by` 更新） | `{ baselineCount, at }` |
| `enter` | `note?` | 校验无进行中批次 → 取当前在架集合 `beforeOnIds` → `hidden = beforeOnIds ∖ baselineIds` → 分批下架（每批 20，带 `shelfReviewHidden`） → 写批次 `reviewing` | `{ batchId, hidden, beforeOn, baseline }` |
| `approve` | `batchId` | 校验批次 `reviewing` → 按 `beforeOnIds ∩ shelfReviewHidden` 分批上架 → 批次 `approved` + 基线刷新为 `beforeOnIds` | `{ restored, failed, baselineCount }` |
| `cancel` | `batchId` | 只恢复 `hiddenIds` 中仍 `shelfReviewHidden` 的 → 批次 `cancelled` | `{ restored, failed }` |

实现要点：
- **权限**：`assertStaff(..., { requireSuperAdmin: true })`（与 `museumGuideMonitor` 同口径）。店长端只能看，不能操作。
- **批量写**：CloudBase 单次 `update` 只能一条 doc，用 `Promise.all` 分批（每批 20，参考 `_applyShelfBulk` 的 8 并发，服务端可放到 20）。
- **部分失败**：逐件记录失败 id 返回，批次状态：`enter` 失败 → 批次保持 `reviewing` 且 `hiddenIds` 只写**已成功**的，
  并置 `partial: true`；UI 给「重试剩余」按钮（重新跑 `enter(continue: true)`）。
- **审计**：每个动作 `writeAuditLog`（`action: 'product_review_enter' | '..._approve' | '..._cancel' | '..._baseline'`，`detail` 带 counts）。
- **通知**：不改现有消息体系；仅在页面给结果提示（避免稳定期改通知契约）。

## 6. UI 落点（小程序 · 风险管理 tab）

插入位置：`_subviews.wxml` → `productLibTab==='risk'` → ① 分层概览之后、现有「已下架 / 在售」两条 bar **之前**（审核是更高一层的动作，先看到它）。

### 6.1 一块「审核守护」卡（仅超管可见，`canSeeMenu` 判 `CONTENT_FLAGS` 或新菜单键）

```
┌─────────────────────────────────────────────┐
│ 版本审核 · 快照上架                                   │
│ 已审核无风险 128 件 · 当前在售 131 件                  │
│ 状态：未进入审核                                      │
│ [ 标记当前在架为已审核 ]   [ 进入审核模式 ]              │
└─────────────────────────────────────────────┘
```

审核中：
```
│ 状态：审核中 · 已隐藏 3 件（恢复后自动上架）             │
│ [ 审核通过 · 恢复上架 3 件 ]   [ 放弃并恢复 ]           │
```

- 「进入审核模式」二次确认文案：`将把 3 件不在基线的商品下架，审核期店铺可见 128 件。可随时「放弃并恢复」。`
- 「审核通过」二次确认：`把审核前的 131 件全部恢复上架，并把基线更新为这 131 件？`
- 失败态：`有 2 件没下架成功` + `重试剩余`。

### 6.2 与现有两条 bar 的关系

- 保留「已下架一键上架 / 在售一键下架」（日常运维仍要全开全关）；
- 审核模式进行中时，这两条 bar 置灰并提示「审核进行中，请先完成审核或放弃」——避免与快照互相踩。

### 6.3 数据加载

`loadRiskOverview` 里并行拉 `manageProductReview status`（失败不影响风险概览，单独 toast 一次）；
切换 `productLibTab==='risk'` 时刷新。

## 7. 守卫计划（新增 `check:review-shelf`，1 条，`miniprogram` 域）

用内存假 db 跑状态机：

| 用例 | 断言 |
|---|---|
| R1 | `enter` 只下架 `beforeOn ∖ baseline`；基线的保持上架 |
| R2 | 空基线时 `enter` 下架全部在架，返回 `baseline: 0`（UI 需二次确认，静态断言确认文案存在） |
| R3 | `approve` 只上架 `beforeOnIds ∩ shelfReviewHidden`；审核前就已下架的仍下架 |
| R4 | `approve` 后基线刷新为 `beforeOnIds` |
| R5 | `cancel` 只恢复 `hiddenIds`，不改基线 |
| R6 | 并发：已有 `reviewing` 时再 `enter` 被拒并返回既有批次 |
| R7 | 幂等：重复 `approve` / `cancel` 不重复写审计、不重复改商品 |
| R8 | 权限：非超管调用五个 action 全部返回 `code: 'forbidden'` |
| R9 | 部分失败：模拟 1 件 update 抛错 → 返回 `failed` 列表、批次 `partial: true`、已成功的仍写进 `hiddenIds` |
| R10 | 页面：卡片只在 `productLibTab==='risk'`、仅超管可见；审核中两条日常 bar 置灰；二次确认文案含件数 |

再加 1 条注入（「恢复时把审核前已下架的商品也上架」→ R3 必须红），守卫总数 187 → 188。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 审核期被顾客/审核员看到 0 件在售 | 空基线时**强制二次确认** + 卡片常驻显示「审核期可见 N 件」 |
| 部分下架失败导致「以为全隐藏了」 | 服务端返回 `failed` 列表；页面状态显示「已隐藏 3 / 应隐藏 5」，红字 + 重试 |
| 与店长端「一键下架」互相踩 | 审核中禁用日常 bar；云函数侧 `enter` 拒绝并发批次 |
| 基线过期（商品被删） | 读取时按现存 id 求交集；删除的 id 忽略并在返回里给 `stale: n` |
| 稳定期契约风险 | 不改 `products` 既有字段语义、不改 `manageApprovals`、不新增消息；只加法 + 一个新云函数 + 一个标记位 |
