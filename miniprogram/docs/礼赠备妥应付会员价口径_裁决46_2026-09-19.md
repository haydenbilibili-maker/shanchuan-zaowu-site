# 礼赠编排「备妥应付」的会员价口径（裁决 46）

> ⚠️ **2026-10-12 产品负责人撤回编排页报价**：送礼页不再显示「备妥应付」，价格与会员折扣只在第 3 步确认页给一次；`subpackages/feature/utils/memberPayable.js` 已删除，守卫 `check:member-pricing-sync` 改判反方向（见 [礼赠凭礼笺领取 §15.3](./礼赠凭礼笺领取_2026-10-11.md)）。本文其余内容为历史记录。

> 立此文档的原因：这是**口径变更**（页面显示的价格从「原价」改为「会员价」），
> 且它天然要和结算页保持同源 —— 靠口头约定会漂移，故落文档 + 落守卫。
> 日期：2026-09-19 ｜ 归属流：gift-print（`subpackages/feature/gift/compose/**`）

## 1. 一句话口径

**编排页底部「备妥应付」显示该会员的当前等级会员价（折后），旁边划掉原价，
并固定标注「以结算页为准」。**

## 2. 裁决 46-a（产品负责人 2026-09-19）

> 问题（真机反馈）：编排页「备妥应付」显示的是**原价**，会员看到的价格与结算页不一致。

产品负责人选择方案 **(a)**：

| 方案 | 内容 | 结论 |
|------|------|------|
| **(a)** | 显示**当前等级**会员价 + 「以结算页为准」 | ✅ **采用** |
| (b) | 连「本单可达等级」（投影定级）一起算 | ❌ 投影定级要券/运费/自提参与口径，那是结算页的职责 |

**推论（重要）**：编排页**不做**投影升级提示（结算页 `resolveProjectedUpgrade` 才做）。
同一个订单在编排页与结算页可能显示不同等级价 —— 这是**设计如此**，不是 bug，
由「以结算页为准」这句话兜住。

## 3. 为什么必须放主包件（不是随手复制）

微信分包硬约束（`check:subpackage-refs` 会拦）：

- 分包可以引用**主包** + **自己**；
- **分包之间不能互相 require**（跨包会让该分包内页面全部起不来）；
- **主包不能 require 分包文件**。

而结算页的真源 `subpackages/business/utils/memberPricing.js` 在 **business 分包**里，
编排页在 **feature/gift 分包**里 ⇒ **编排页无法直接引用它**。

⇒ 唯一合法形态：把定级用的三个**纯函数**逐字抽到主包件
`utils/memberPayable.js`，两处并存。
⇒ 副本就有漂移风险（改了 business 那份，编排页会静默按旧口径报价）——
故配守卫 `check:member-pricing-sync`（§6）。

## 5. 与结算页的关系（为什么没动结算页的乘法）

结算页 `orderPricing.calculateClientPricing` 的会员乘法是：

```js
vipTotal = round2(discountedSubtotal * discountRate + nonDiscounted)   // 合计 × 费率，一次成形
```

**没有把它改成逐行调 `applyMemberRate`**，理由：

1. 它是**云端 `makeOrder/pricing.js` 的前端对齐件**，改取整时机（逐行 vs 整单）
   会让**多行订单**出现分位差（例：两行 ¥33.33 × 0.9 → 整单 59.99 / 逐行 60.00），
   属于改动钱口径的回归风险；
2. 编排页**天然只有一行**（选中 SKU × 件数）⇒ 在编排页这一侧
   `applyMemberRate(line, rate)` ≡ `round2(line × rate)` ≡ 结算页单行公式，
   **两页本来就等价**；
3. 「同源」的真正风险不是公式，而是**等级/费率取错**与**副本漂移** —— 这两条已被守卫覆盖。

故：编排页走 `applyMemberRate`，结算页保持原样，**由守卫证明两者在单行情形逐点等价**。

### 5.1 费率来源（本次顺带收紧的一处真实分叉）

结算页「当前等级」的费率取**服务端** `stats.discountRate`（`confirm-order:971`），
不是本地按阶梯推的。主包件据此改为**服务端优先、本地阶梯兜底**：

1. `serverRate` 合法（有限且 > 0）→ 归一后照用（`90` / `9` / `0.9` 都归一为 `0.9`）；
2. 否则按 `levelLadder + growthValue + isHonorary` 推（与结算页 `applyProvisionalFromStats` 同函数）；
3. 等级名优先取服务端的 `stats.levelName`。

**为什么这不是「防御性写法」而是必需**（已核云函数源码，非推测）：

- `getUserStats` 的真实返回是**顶层**字段 `level / levelName / discountRate / growthValue /
  levelLadder / userInfo`（`cloudfunctions/getUserStats/index.js:143-163`）—— 与本件读取一致；
- 服务端支持**人工调级**：`resolveMemberLevel(levels, growthValue, isHonorary, userInfo.levelOverride)`
  （同文件 `:141`），`levelOverride.mode==='exact'` 时**锁定**等级、**忽略成长值**
  （`cloudfunctions/makeOrder/memberLevels.js:277-291`）。
  例：某会员成长 500（阶梯本应 L1 / 0.98）但被调级锁定 L4 ⇒ 服务端返回 **0.85**。
  **只按本地阶梯推算会显示 0.98 —— 会员看到比实际贵的价格**。故服务端费率必须优先。
- 未登录时服务端返回 `discountRate: 1.00` + `error: true`（`getUserStats/index.js:94`）——
  这是**合法数值 1**，本件据此得到「原价、不显示会员价标注」，不会误报折扣。
- 客户端那份 `resolveFromLadder` **不含** `levelOverride` 逻辑，只作兜底，这正是它不能当主口径的原因。

## 6. 边界与回落

| 情形 | 行为 |
|------|------|
| 未登录 / `getUserStats` 失败 | 显示**原价**，**不显示**折扣（不假装已享折扣），不弹错 |
| 费率非法（0 / 负数 / NaN / >1 / 非数字） | 一律回落**原价 1.0**，绝不因脏数据把价格算成 0 或负数 |
| 费率落在可信区间之外（`< 0.5` 或 `> 1`） | **不采信**，退回本地阶梯；阶梯也不可信则原价。见下方「1.05 陷阱」 |
| 商品 `memberDiscountEnabled === false` | 不参与折扣，按原价 |
| 折后与折前相等（如 ¥1 × 0.999） | `discounted=false` → 不显示「会员价」标注，避免假折扣文案 |
| 0 元订单 | 仍为 0 |
| 荣誉馆长 | 走阶梯里的 level 99 档（云库为 0.7） |

### 6.1 「1.05 陷阱」（本次发现并堵掉）

`normalizeDiscountRate` 为兼容「9.5 折」「95 百分数」两种写法，会把 `>1` 的值除以 10 或 100。
于是脏数据 `1.05`（本意可能是 105%）会被归一成 **0.105** —— **近乎免费**。
若直接采信，会员会看到 ¥1000 的藏品只要 ¥105。

故 `resolveCurrentRate` 只采信**归一后落在 `[0.5, 1]`** 的费率（最优档是 7 折，0.5 是
「这还能叫会员折扣吗」的下界）；界外的服务端费率退回本地阶梯，阶梯同样越界则原价。
**宁可按阶梯显示一个正常价，也不显示近乎免费的价。**
该边界由守卫的数值断言覆盖（`1.05 / 0.05 / 0.2 / 1.0001 / 200` 五组脏值 + 阶梯脏值 0.1，
全部必须回落原价；同时 `9.5` 这种合法写法仍必须采信为 0.95）。

## 7. 守卫：`check:member-pricing-sync`

`node miniprogram/scripts/check-member-pricing-sync.mjs`（域 cross，已在 `guards/80-cross.txt`）

七条断言：

1. **副本同源**：三个纯函数在主包件与 business 件**逐字一致**；
2. **引用合法**：编排页只引主包件，不出现 `require(...memberPricing...)`；
3. **界面真展示会员价**：底栏主价是 `payablePrice`（不是 `displayPrice`）、
   原价只作为 `.bottom-origin` 划掉对照、且有「以结算页为准」；
4. **折扣判据一致**：三处都是 `memberDiscountEnabled === false` 语义；
5. **结算页乘法形态未变**（`discountedSubtotal * discountRate + nonDiscounted`）；
6. **数值等价（真跑）**：`applyMemberRate` 与 `round2(line × rate)` 在
   9 金额 × 6 费率矩阵上逐点相等；非法费率回落原价；服务端费率优先；阶梯兜底；
7. **取数同源**：两页都用 `getUserStats` 的 `levelLadder` / `growthValue` /
   `userInfo.isHonorary` / `stats.discountRate`。

**自检**：`npm run check:member-pricing-sync:selftest` —— 在**临时目录副本**上注入
6 处真实回归（口径漂移 / 退回原价 / 乘法变形 / 跨包引用 / 偷偷 require / 丢弃服务端费率），
逐条必须被拦下，且**不碰共享工作区的真文件**。

## 8. 验收步骤

1. 用**有等级**的会员账号（如 level 3 流金·研究员，0.9）进任意藏品 → 「赠予」→ 编排页；
2. 底栏「备妥应付」应为**折后价**，旁边划掉原价，下面一行「流金·研究员会员价 · 以结算页为准」；
   例：¥168 藏品 → 应付 **¥151.20**（168 × 0.9），原价 ¥168.00 划掉；
3. 点「支付并备妥」进结算页 —— 该页会员价应与编排页**一致**（同等级、无券、无运费时）；
4. 用**未登录/无等级**账号复验：底栏只显示原价，**不显示**「会员价」标注与划线；
5. 用**人工调级**账号复验（`users.levelOverride = {mode:'exact', level:4}`，且成长值低到本应 L1）：
   底栏应按 **L4 / 8.5 折**计价，而不是按成长值算出的档位 —— 这是 §5.1「服务端优先」的验收点；
6. 静态：`npm run check:domain -- cross` 全绿，且
   `npm run check:member-pricing-sync:selftest` 全绿。
