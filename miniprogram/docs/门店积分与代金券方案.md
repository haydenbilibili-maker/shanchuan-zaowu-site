## 0. 一句话结论

**「积分兑换代金券 → 下单抵扣」这条链路在仓库里已经完整存在并可用**（`rewards`（type=`coupon`）→ `redeemReward` → `user_coupons` → `makeOrder/pricing.js` → `confirmPayment/fulfillOrder.js` 核销）。

真正缺失的只有三块：

1. **线下门店消费 → 积分入账**：目前门店营收只有按天汇总的 `daily_revenues`，没有「哪个顾客花了多少钱」的记录，也没有任何给指定用户加积分的入口。
2. **规则配置化**：`earnPoints` 的积分规则是云函数里的硬编码常量 `RULES`，没有云端配置集合。
3. **幂等 / 流水 / 风控 / 权限**：积分扣减非原子、`redeemReward` 不写流水、店长权限校验存在「环境变量为空即放行所有人」的漏洞。

所以本方案的主体是**补齐门店侧入账 + 配置化 + 账务可靠性**，而不是重建积分与券体系。

**关键缺陷（必须在本方案中解决或明确规避）**

- `point_records` **不是完整流水**：`redeemReward` 扣分时不写记录，导致「余额」与「流水」无法互相校验。
- `growthValue` 计算带 `.limit(100)`：老用户订单超过 100 笔后成长值会失真（现有隐患，本方案不改，但**门店消费不要走 growthValue 口径**）。
- 扣积分与发券**不在同一事务**：`redeemReward` 先 `usedPoints += cost`，再扣库存，再插 `user_coupons`。中途失败会「扣了分没发券」。
- 全仓库 **零处使用 `db.startTransaction` / `runTransaction`**（已全量 grep 确认）。
- `redeemReward` 无幂等键，用户连点会重复扣分发券。
- 券有效期在 `redeemReward` 里**硬编码 30 天**，`minSpend` 缺省为 `value * 2`。

## 2. 业务流程

### 2.1 主流程

```
① 门店收银（POS / 微信收款）完成，实收 ¥X
        ↓
② 店员在小程序「店长后台 → 门店积分」点「录入消费」
        ↓
③ 顾客打开「我的 → 会员码」出示二维码（60s 有效）
   店员扫码 → 云端 verify token → 得到顾客 openid + 会员号 + 等级
        ↓（扫码失败兜底：输入顾客手机号后 4 位 → 列出候选 → 选定）
④ 店员填：实收金额、小票号/POS 流水号（幂等键）、门店（默认当前门店）、备注
        ↓
⑤ 前端调 grantStorePoints(action='preview')：云端按配置试算「应赠积分」并回显规则说明
   店员确认 → grantStorePoints(action='grant')
        ↓
⑥ 云端一次写入：
   store_purchases（消费记录，dedupeKey 唯一）
   point_records（type='earn', source='store_purchase'）
   users.bonusPoints += 赠送积分
        ↓
⑦ 站内信 store_points_granted 推给顾客：「消费 ¥X，已赠 N 积分」
   顾客「我的 → 我的积分」看到余额与明细
        ↓
⑧ 我的积分「兑换」页选代金券档位（rewards, type='coupon'）
   → exchangeCoupon：扣积分 + 发券（幂等 + 流水）
        ↓
⑨ 券进「我的券包」（user_coupons, status='unused'）
        ↓
⑩ 小程序下单 → confirm-order 选券 / getBestCoupon 自动选
   → makeOrder/pricing.js：会员价后再减券面额
        ↓
⑪ 支付成功 → fulfillOrder 把券置 used + 回写 usedOrder
```

### 2.2 异常流程

| 场景 | 处理 |
| --- | --- |
| **同一笔消费重复提交**（店员连点 / 网络重试） | `store_purchases.dedupeKey`（`storeId + ':' + receiptNo`）唯一索引 + 云函数先查后写；命中已存在则返回 `{ success:true, duplicated:true, granted:0 }`，不重复加分 |
| **金额录错（多录/少录）** | 店员在「门店积分 → 流水」里对该条记录点「撤销」→ `grantStorePoints(action='revoke')`：原记录 `status='revoked'`，写反向 `point_records`（`type='revoke'`, `points` 为负），`users.bonusPoints -= 已赠积分`。再重新按正确金额录一笔（新 `receiptNo` 或原号 + `-R1` 后缀） |
| **撤销时积分已被兑换（余额不足）** | 允许 `bonusPoints` 被扣成使总余额为负；`users.pointsDebt` 记录欠账额，前端余额一律 `Math.max(0, ...)` 展示（现有 `getUserStats` 已有此保护）。**不追回已发出的券**，欠账由后续赠分自动抵扣。风控上靠「单笔上限 + 撤销时限」把损失控制住 |
| **门店退货 / 退款** | 与录错同一入口，但 `revokeReason='refund'`。支持部分退货：`action='revoke'` 支持 `revokeAmount`，按比例扣回积分（向上取整扣，对平台有利，避免抹零套利）。若退货发生在 `revokeWindowDays`（默认 30 天）之外，只登记不扣分，需人工判断 |
| **积分长期不兑换** | MVP 阶段积分**不过期**（沿用现状，`bonusPoints` 无过期机制）。改为过期需要引入按批次的 FIFO 账本，列入 P2 |
| **兑换中断（扣分成功但发券失败）** | `exchangeCoupon` 采用状态机：先写 `point_records` 一条 `status='pending'`，再扣 `usedPoints`，再发券，最后置 `status='done'`。定时任务 / 下次进页面时扫 `pending` 超过 5 分钟的记录 → 补发券或回滚 `usedPoints`。详见 §5.4 |
| **券过期未用** | 沿用现有：`user_coupons.expireTime` 到期后前端 `resolveCouponStatus` 判为 `expired`，`getBestCoupon` / `pricing.js` 均已过滤。**不退还积分**（需老板确认，见 §10） |
| **会员码过期（60s）** | `verify` 返回 `expired:true`，店员提示顾客刷新。这是特性不是 bug——正是防截图盗刷的关键 |
| **顾客未注册小程序 / 未授权** | 无 openid 无法入账。店员登记「待认领消费」（`store_purchases.status='pending_claim'`，只存手机号与小票号），顾客后续在小程序绑定手机号后由 `grantStorePoints(action='claim')` 自动/手动认领。**列入 P1**，MVP 直接引导顾客现场扫码进小程序 |
| **顾客换了微信号** | 手机号可查到旧 openid，但积分不迁移。人工兜底（P2 再做迁移工具） |

## 3. 积分获取方式的选型

### 候选方案对比

| 方案 | 门店操作成本 | 防作弊 | 前置依赖 | 结论 |
| --- | --- | --- | --- | --- |
| **A. 扫会员码 + 店员录入金额** | 低。顾客在收银台已经站着，出示码 3 秒；店员多录一个金额 + 小票号 | **高**。会员码 60s TTL，截图/转发失效；扫码人必须是登录态店员；每条记录带 `operatorOpenid` 可倒查 | ✅ `getMemberPass` 已就绪 | **推荐主路径** |
| **B. 手机号 / 会员号搜索用户 + 录入金额** | 中。要问手机号、输入、确认姓名 | 中。手机号可被店员自行编造给自己账号刷分 → 必须配「单店单日发放上限 + 操作人流水审计」 | ✅ `users.phone` 已就绪 | **推荐作为 A 的兜底**（顾客没网/没装小程序/码过期） |
| **C. 顾客自助上传小票，后台审核** | 对店员为 0，但**平台侧多出人工审核工时** | 低~中。小票可复用、可 PS；必须靠 `receiptNo` 去重 + 人工看图 | 需新建审核队列 + 图片存储 + 审核 UI | **P2 补充**，作为「当场忘记录入」的补救 |
| D. 让顾客扫店员/门店码后自填金额 | 最低 | **最低**，顾客可任意填金额 | — | ❌ 不采用 |

### 推荐

**主路径 A（扫会员码）+ 兜底 B（手机号搜索），C 放到 P2。**

理由：

1. **复用度最高**：`getMemberPass` 的 issue/verify、`member_pass_tokens`、店长后台的扫码核销 UI（Tab 3 已有 `wx.scanCode` + `getMemberPass verify` 的完整实现，`manager/index.js:686-734`）全部现成，A 方案基本是「换个 action 复用同一段扫码代码」。
2. **防作弊靠会员码的短 TTL**：这是全套方案里唯一不需要额外风控就成立的环节——顾客不在现场就拿不到有效码。手机号方案没有这个保护，所以必须配额度上限。
3. **门店现实成本可接受**：门店客单价高（会员等级门槛 500/3000/10000/30000 元，说明是高客单低频业态），单笔多花 15 秒录入完全可以承受。若是高频低客单的业态才需要考虑 POS 打通。
4. **A 与 B 共用同一个云函数入参**：`grantStorePoints` 接 `memberToken` 或 `targetOpenid` 二者之一，前端两个入口，云端一套逻辑，不增加维护面。

**明确不推荐**的做法：让顾客自己填消费金额、或用「订单号 + 用户自助」作为主路径——前者等于把发钱的权限交给顾客，后者审核成本会在开业初期就把运营拖死。

**需确认**：门店 POS 是什么系统、是否有开放接口/导出。如果能拿到「小票号 + 金额 + 时间」的日结文件，可在 P2 加一个 `importStorePurchases` 做日终对账，把「店员录入」从记账事实降级为实时体验，风控强度会有质的提升。

沿用 `getSupportConfig` 范式：

- **默认值**：`cloudfunctions/getStorePointRules/defaults.js`（云函数内，代码兜底）
- **云端覆盖**：集合 `store_point_rules`，按 `status:'active'` + `priority desc` 取 1 条；`storeId` 为空表示全门店通用，有值则该门店专属规则优先
- **读取**：新增云函数 `getStorePointRules`，返回 `{ ...默认, ...云端 }`，异常降级返回默认 + `fallback:true`
- **前端镜像**：`config/storePoints.js` 只放**展示用文案与档位兜底**（如「每满 ¥1 赠 1 积分」「100 积分可兑 ¥10 券」的说明文本），**不参与计算**。计算一律在云端，避免前后端口径漂移（现有 `shipping.js` 双份的坑不要再复制到金额计算上）
- **店长后台可改**：`manager` 页新增子 Tab「积分规则」，直接读写 `store_point_rules`（与现有 `booking_configs` / `store_configs` 的管理方式一致）

**为什么不用环境变量**：环境变量改一次要重新部署云函数，老板改不了；而且现有 `MESSAGE_ADMIN_OPENIDS` 的「空值放行」已经证明这条路容易出事。

```json

  "_id": "auto",
  "ruleId": "store_points_default_v2",
  "name": "门店消费赠分-默认规则",
  "status": "active",
  "priority": 100,
  "storeIds": [],

  "mode": "perThreshold",
  "threshold": 1,
  "pointsPerThreshold": 1,
  "ratio": 1,

  "minAmount": 1,
  "maxAmountPerRecord": 50000,
  "roundMode": "floor",

  "applyMemberMultiplier": false,
  "memberMultipliers": { "1": 1.0, "2": 1.0, "3": 1.1, "4": 1.2, "5": 1.5, "99": 1.5 },

  "dailyPointsCapPerUser": 5000,
  "dailyPointsCapPerStore": 50000,
  "dailyRecordCapPerUser": 3,

  "pointsExpireDays": 0,
  "revokeWindowDays": 30,

  "effectiveFrom": "2026-09-01T00:00:00.000Z",

  "notifyUser": true,
  "remark": "开业活动期规则",
  "updatedBy": "openid_xxx",
  "updateTime": "serverDate"
}
```

**`mode` 三种赠送规则（门槛数字可配，禁止写死在业务逻辑里）**

| mode | 语义 | 用到的字段 | 举例（threshold=1, pointsPerThreshold=1, ratio=1） |
| --- | --- | --- | --- |
| `fixed` | 满额送固定值，只送一次 | `threshold`, `pointsPerThreshold` | 消费 50 → 送 1 |
| `perThreshold` | 每满 X 送 Y（阶梯，可多次） | `threshold`, `pointsPerThreshold` | 消费 50 → 满 50 次 → 送 50 |
| `ratio` | 按比例，需先过 `minAmount` 门槛 | `minAmount`, `ratio` | 消费 50 → 送 50 |

**推荐默认值**：`mode='perThreshold'`, `threshold=1`, `pointsPerThreshold=1`（即 **1 元 = 1 积分**），`applyMemberMultiplier=false`（MVP 不叠会员倍率，理由见 §10 Q4）。

**上限的作用点**（三层，缺一不可）

1. `maxAmountPerRecord`：单笔录入金额上限，防止手滑多打一个 0。
2. `dailyPointsCapPerUser` / `dailyRecordCapPerUser`：防止店员对某个自己人账号反复刷。
3. `dailyPointsCapPerStore`：单店单日总发放上限，是最后一道闸。超限时云函数拒绝并给店员提示「今日额度已用尽，请联系管理员」。

## 6. 云函数设计

命名沿用小驼峰动词开头。**云函数间不共享目录**，公共逻辑靠在各函数目录内复制同名文件（照现有 `refundPolicy.js` 的做法）。

### 6.1 `getStorePointRules`（新增）

- **入参**：`{ storeId?: string }`
- **出参**：`{ success, config: {...§4.2}, default: boolean, fallback?: boolean }`
- **权限**：任意登录用户可读（用户侧要展示「门店消费满 X 送 Y」的规则说明）。**但 `dailyPointsCapPerStore` 等风控字段不下发给普通用户**——按调用者是否为 staff 裁剪返回字段。
- **实现要点**：`defaults.js` 兜底 + `store_point_rules` 覆盖 + 浅合并，完全照抄 `getSupportConfig`。

### 6.2 `grantStorePoints`（新增，核心）

单函数多 action，与 `getMemberPass` / `storeCheckIn` 的风格一致。

#### `action = 'identifyMember'`

- **入参**：`{ memberToken?: string, qrPayload?: string, phoneTail?: string }`
- **出参**：`{ success, member: { openid（内部用，可不下发）, memberNo, nickName, phoneMasked, level, levelName, storeSpendTotal, points }, candidates?: [] }`
- 内部复用 `getMemberPass` 的 `verify` 逻辑（复制 `parseToken` + token 查询），或直接 `cloud.callFunction({name:'getMemberPass', data:{action:'verify', token}})`。
  > ⚠️ 现有 `getMemberPass.verify` **不返回 openid**，若走 callFunction 需要在 `getMemberPass` 里加一个仅对 staff 返回的 `memberOpenid` 字段，或在 `grantStorePoints` 内部直接读 `member_pass_tokens`。**推荐后者**（不改动现有函数）。
- `phoneTail` 走手机号后 4 位模糊匹配 `users.phone`，最多返回 5 个候选（脱敏），店员点选。

#### `action = 'preview'`

- **入参**：`{ memberToken|targetOpenid, storeId, amount }`
- **出参**：`{ success, points, ruleSnapshot, ruleText: '每满¥1送1，本单满50次', capWarning?: '本店今日额度剩余 3000' }`
- **不写库**，纯试算，用于店员确认。

#### `action = 'grant'`

- **入参**：
  ```json
  {
    "action": "grant",
    "memberToken": "abc...",
    "targetOpenid": "o_xxx",
    "storeId": "store_shanhaizaowu",
    "amount": 2500,
    "receiptNo": "P20260820001",
    "remark": "开业活动",
    "clientRequestId": "uuid-v4"
  }
  ```
  （`memberToken` 与 `targetOpenid` 二者其一必填，前者优先）
- **出参**：`{ success, purchaseId, pointsGranted, balanceAfter, duplicated?: true, msg }`
- **权限**：`assertStaff(openid, storeId, 'grantStorePoints')`。见 §6.6。
- **校验顺序**：
  1. 店员身份 + 该 `storeId` 的操作权
  2. `amount` 合法（>0、≤ `maxAmountPerRecord`、两位小数）
  3. 顾客 openid 有效（token 未过期 / 用户存在）
  4. **幂等**：`dedupeKey` 查 `store_purchases`，命中 → 直接返回 `duplicated:true`
  5. 配额：用户单日积分/次数上限、门店单日上限、店员单日上限
  6. 取规则（`storeId` 专属 > 全局）→ 计算积分（0 分也照样记录消费，只是不加分）
  7. 抵扣 `users.pointsDebt`（若有欠账，先抵扣再入账）
- **写入顺序**（幂等键在第 1 步就落地，最脏的失败也只会造成「有消费记录、没加分」，靠补偿修）：
  1. `store_purchases.add`（`status='granted'`, `pointsGranted=N`）
  2. `point_records.add`（`type='earn'`, `source='store_purchase'`, `dedupeKey='grant:'+purchaseId`, `status='pending'`）
  3. `users.update({ bonusPoints: _.inc(N), storePointsTotal: _.inc(N), storeSpendTotal: _.inc(amount) })`
  4. `point_records.update({ status:'done', balanceAfter })`
  5. `dispatchMessage`（`store_points_granted`，失败只 warn，不影响主流程 —— 与现有 `order_created` 的处理一致）

#### `action = 'revoke'`

- **入参**：`{ purchaseId, revokeReason, revokeAmount? }`（不传 `revokeAmount` = 全额撤销）
- **权限**：`role in ['owner','manager']`，且需在 `revokeWindowDays` 内；超期需 `owner`。
- **逻辑**：按 `revokeAmount / amount` 比例算扣回积分（`Math.ceil`），写反向 `point_records`（`points` 为负，`source='store_purchase_revoke'`），`users.bonusPoints -= X`；若可用余额不足则把差额记入 `users.pointsDebt`；更新 `store_purchases.status` 与 `revoked*` 字段。
- **幂等**：`dedupeKey = 'revoke:' + purchaseId + ':' + seq`。

#### `action = 'listRecords'`

- **入参**：`{ storeId?, memberOpenid?, operatorOpenid?, status?, dateFrom?, dateTo?, page, pageSize }`
- **出参**：分页流水 + 汇总（`totalAmount`, `totalPoints`, `count`）
- **权限**：`clerk` 只能看自己录入的；`manager` 看本店；`owner` 看全部。

#### `action = 'getStoreDailySummary'`（P1）

供店长后台看「今日已发积分 / 剩余额度 / 笔数 / 客单价」。

### 6.3 `exchangeCoupon`（新增）

**为什么新建而不是改 `redeemReward`**：`redeemReward` 现在同时处理实物/虚拟/券三种 type，且已在线运行。把「券」这条最需要幂等+事务的分支拆出来，可以在不影响实物兑换的前提下做严格账务；`points` 页按 `reward.type` 分流调用即可（改动 5 行）。`redeemReward` 保留处理 `virtual` / `goods`，后续再补流水。

- **入参**：
  ```json
  { "rewardId": "r_xxx", "clientRequestId": "uuid-v4" }
  ```
- **出参**：`{ success, userCouponId, costPoints, leftPoints, coupon: {...}, msg }`
- **权限**：登录用户本人（`wxContext.OPENID`）。
- **校验**：`rewards` 存在且 `type==='coupon'` 且未下架、`stock > 0`、`cost > 0`、`limitPerUser` 未超、用户可用积分 ≥ `cost`。
- **可用积分计算**：**必须复用与 `getUserStats` 完全一致的口径**（`growthValue + bonusPoints − usedPoints`），建议把这段抽成 `pointsBalance.js` 并复制到 `exchangeCoupon` / `redeemReward` / `getUserStats` / `getUserSession` 四处，杜绝口径漂移。
- **原子性**：见 §6.5。
- **幂等**：`dedupeKey = 'exchange:' + openid + ':' + clientRequestId`，前端每次打开兑换弹窗生成一个 uuid，重试沿用同一个。
- **发券**：写 `user_coupons`，`type:'cash'`，`value/minSpend` 取 `rewards`，`expireTime = now + (rewards.expireDays || 30) 天`，`source:'points_exchange'`，`costPoints`，`couponSource:'reward'`。
- **兑换记录**：沿用现有做法在 `orders` 里写 `source:'exchange'` 的记录（`points` 页的「我的兑换」tab 依赖它，`points/index.js:128`），保持前端不用改。

### 6.4 `getPointRecords`（新增）

- **入参**：`{ page, pageSize, type? }`

### 6.5 原子性方案（关键决策）

**结论：MVP 采用「幂等键 + pending 状态机 + 补偿」，不用数据库事务。**

理由：

- 全仓库零事务使用经验，且微信云开发 `runTransaction` 对**跨集合 + 数组/条件更新**有限制，`_.inc` 等原子操作在事务内的行为需要实测。冒然引入会带来未知失败模式。
- 幂等键 + 状态机在本场景已足够：唯一索引挡住重复，`pending` 记录让「扣了分没发券」可被发现和修复。

**具体机制（`exchangeCoupon`）**

```
1. 写 point_records: { type:'spend', points:-cost, status:'pending', dedupeKey }
   ← 唯一索引挡重复；若已存在且 status='done'，直接返回原结果（幂等）
2. users.update({ usedPoints: _.inc(cost) })         ← 原子
3. rewards.update({ stock: _.inc(-1) })              ← 原子；若扣成负数则回滚并报「已兑完」
4. user_coupons.add(...)                             ← 发券
5. point_records.update({ status:'done', refId: userCouponId, balanceAfter })
```

**补偿**：新增定时触发器 `reconcilePointRecords`（每 10 分钟，`config.json` 的 `triggers`，仓库已有 `sendCareReminder` / `sendBookingReminder` 的定时器范式可照抄）：

- 扫 `point_records` 中 `status='pending'` 且 `createTime` 早于 5 分钟的记录
- 若已存在对应 `user_coupons`（按 `sourceRefId` 反查）→ 补置 `done`
- 否则**回滚**：`usedPoints -= cost`、`rewards.stock += 1`、记录置 `rolled_back`
- 每次补偿动作写 `notification_logs` 或新集合 `reconcile_logs` 便于追溯

**`grantStorePoints` 同理**，但方向相反（先落消费记录再加分），最坏情况是「顾客消费已记但分没到」，补偿时补加分即可，对顾客无损。

**并发**：同一用户并发兑换 → 第 2 步 `_.inc` 原子，第 3 步 `stock` 扣成负数时回滚，配合余额校验可能出现极小概率的「超兑」（余额校验与扣减非原子）。缓解：`users` 上加 `pointsVersion` 做乐观锁，或接受风险（单用户手速有限，且损失上限 = 一张券）。**建议 MVP 接受，P1 加乐观锁。**

## 8. 代金券与现有优惠券体系的关系

**推荐：完全复用现有券体系，不新建券类型。**

| 维度 | 决策 | 理由 |
| --- | --- | --- |
| 券实例集合 | 复用 `user_coupons` | 券包页、`getBestCoupon`、`getProductCoupons`、`makeOrder/pricing.js`、`fulfillOrder` 五处已全部对接，新建类型等于把这五处都改一遍 |
| 券 type | 用 `cash`（满减） | `pricing.js:107-109` 的 `default` 分支即 `vipTotal − value`，天然支持 |
| 与 `getBestCoupon` 自动选券 | **自动纳入**，无需改代码 | 该函数只按 `_openid + status:'unused'` 查全部券，按 `savedAmount` 取最大。积分券进来后自动参与竞争 |
| 叠加多张券 | **不支持，保持现状** | `makeOrder` 只接单个 `couponId`。多券叠加是独立需求，不在本方案范围 |
| 与会员价叠加 | **默认叠加**（现状即如此） | `pricing.js`：先按 `discountRate` 打会员折，再减券；**叠加后仍须 ≥ 原价 75%**（`couponDiscountRules.clampCouponAgainstOriginal`） |
| 与免邮活动叠加 | 现状 `FREE_SHIPPING_CAMPAIGN_ENABLED = true` 全场免邮，`freeShipping` 券实际节省额算 0 | 不影响 |
| 适用范围限制 | **MVP 不做** | 加 `scope` 必须同时改 `getBestCoupon`、`getProductCoupons`、`pricing.js`（三份重复的选券/计价逻辑），改动面大且容易漏。MVP 用「全站通用满减 + `minSpend` 门槛」即可达到控制目的 |
| 与 `coupons` 模板集合的关系 | 积分券**不走** `coupons`，`user_coupons.couponId` 存 `rewards._id` 并加 `couponSource:'reward'` | `receiveCoupon` 的 `limitPerUser` 校验按 `couponId` 查询，id 空间不冲突。P1 可考虑统一到 `coupons` 模板 |
| 券能否在门店线下用 | **MVP 不支持**，`channel` 恒为 `online` | 线下核销需要店长后台的券核销 UI + 防重复核销，是独立工作量。列入 P2 |

**风险点**：`getBestCoupon` 会把积分券和运营发的营销券放在一起比大小，若积分券面额很大（如 100 元），会导致「用户下单时自动用掉了辛苦攒的积分券，而不是本该用的新人券」。**缓解**：`confirm-order` 页已支持手动选券（`index.js:304`），且 `getBestCoupon` 只是推荐；建议在券卡片上标注来源，让用户自己判断。P1 可给 `getBestCoupon` 加「同等优惠下优先用即将过期的券」的排序。

### 9.2 退货扣回

- 统一走 `grantStorePoints(action='revoke')`，支持全额/部分（`revokeAmount`）
- 扣回积分 `Math.ceil(pointsGranted × revokeAmount / amount)`，向上取整对平台有利
- 余额不足 → 记 `users.pointsDebt`，后续赠分时优先抵扣，**不追回已发券**
- 超出 `revokeWindowDays`（默认 30 天）需 `owner` 权限
- 每次撤销必须填 `revokeReason`，并给顾客发 `store_points_revoked` 站内信（避免顾客莫名少分来投诉）

### 9.3 日志与审计

- `store_purchases` 自带完整审计字段（操作人、时间、规则快照、撤销人），**不再新建 audit 集合**
- `point_records` 是资金侧唯一真相来源，任何积分变动都必须有对应记录（含 `earnPoints` 的历史行为分，需兼容）
- 补偿动作写 `reconcile_logs`
- 站内信发送已有 `notification_logs`

### 9.4 对账口径

三张表必须自洽：

```
users.bonusPoints  ==  Σ point_records[type in (earn, revoke, adjust) and source != 线上订单].points
users.usedPoints   ==  −Σ point_records[type='spend' and status='done'].points
users.storeSpendTotal == Σ store_purchases[memberOpenid=U, status in (granted, partial_revoked)].amount − Σ revokedAmount
                     + Σ store_receipt_claims[memberOpenid=U, status='approved'].amount
users.onlineSpendTotal == Σ orders[_openid=U, status in (received,signed), source != 'exchange'].totalPrice
```

> 待审（`pending`）不计累计；未达赠分门槛的消费单**计累计但不产生积分流水**（见 §9.8）。

### 9.6 消费累计三口径（2026-09-15 收紧，严格分账）

历史问题：外部平台订单绑定（`bindPlatformOrder`）曾把金额计入 `storeSpendTotal`，导致「门店消费累计」被线上/平台消费污染（实测某账号 ¥917 全部来自门店券核销测试数据）。现已拆成三个互不混淆的累计字段：

| 字段 | 含义 | 入账入口（且仅此三个） |
| --- | --- | --- |
| `users.onlineSpendTotal` | 线上小程序下单累计 | `grantStorePoints.grantOnlineOrder`（由 `confirmOrderReceipt` 确认收货、`managerShipOrder` 自取核销、`manageGift` 领取核销 三条路径互调） |
| `users.storeSpendTotal` | 真实到店消费累计 | `grantStorePoints.grant`（现场赠分）、`claimStoreReceipt`（门店小票认领）、门店券核销 |
| `users.platformSpendTotal` | 外部平台订单累计 | `bindPlatformOrder` 审核通过（天猫/京东/抖音等，店长人工确认） |

要点：

- 三者都**不并入** `growthValue`/`storeGrowthValue` 之外的会员等级计算，等级口径未变。
- 线上消费累计与积分解耦：订单金额一律计入（含未达赠分门槛的订单），按 `orders.onlineSpendCountedAt` 保证只记一次；积分仍按 `store_point_rules` 计算并受 `point_records.dedupeKey = online_order:<orderId>` 幂等保护。
- 金额字段读取时统一 `round2` 保留两位小数，消除浮点尾差。
- 「我的积分」页累计条：线上、门店常显；平台累计 > 0 时才显示。
- 已用 `revoke`（`revokeReason=wrong_amount`）冲正上述某账号 3 笔无小票的门店券核销测试数据（¥150/¥555/¥212），`bonusPoints`/`storePointsTotal`/`storeGrowthValue`/`storeSpendTotal` 各 −917，并用 `grantOnlineOrder` 补录历史已签收订单的线上累计。

### 9.7 云函数互调鉴权（踩坑记录）

线上赠分由云函数互调触发，`grantStorePoints` 入口用 `wxContext.SOURCE` 判定服务端来源。**实测 SOURCE 是逗号分隔列表（云函数互调得到 `",scf"`）**，早期写成 `source === 'scf'` 全等判断导致互调一律被拒（返回「请先登录」），线上赠分静默失效（best-effort 不阻塞签收，因此无报错）。

### 9.8 门店赠分三条链路（2026-09-15 复核 + 加固）

门店消费赠分逻辑**保留并作为主链路**，三条入口都在用，本次统一了口径与安全边界：

| 入口 | UI 位置 | 权限 | 是否强制审核 |
| --- | --- | --- | --- |
| 店员核销代金券 → 输入消费金额 | 现场工作台「券核销」→ 会员码/扫码 | `verifyStoreCoupon` | **强制待审**（店长/超管也不例外） |
| 门店小票认领 | 顾客提交 → 门店审核 | 顾客提交；店长/超管审核 | 提交即待审 |
| 门店现场服务工作台消费赠分 | 现场工作台 Tab0「消费赠分」 | `grantStorePoints` | 店员提交待审；**店长/超管直通** |

统一后的规则：

1. **累计与积分解耦**：`storeSpendTotal` 按消费单只记一次（`store_purchases.spendCountedAt` / `store_receipt_claims.spendCountedAt` 守卫）。**未达赠分门槛（不足 ¥1 取整为 0 分）的到店消费同样计入门店累计**，只是不赠分；此前这类消费会整笔漏计，导致累计与消费单台账对不上。
2. **待审不计累计**：`pending` 期间 `storeSpendTotal` 不变，只有审核通过入账时才累加，驳回/忽略不计。
3. **撤销只针对已入账记录**：`revoke` 限定 `granted` / `partial_revoked`；对 `pending` / `rejected` 直接拒绝（「该笔尚在审核中，请先驳回」/「该笔未入账，无需撤销」），避免凭空扣分。
4. **撤销双回冲**：累计与积分分别回冲（`revokeSpend` / `revokePoints`）。未达门槛的消费单没有积分流水，但累计必须回退，返回 `已撤销该笔消费（¥X），本笔无积分可扣`。
5. **金额录错防线**：单笔金额上限 `maxAmountPerRecord`（默认 ¥50000）；券核销带金额必须上传小票照片（云端与前端双重校验）；现场赠分必须先「试算应赠积分」再二次确认（弹窗写明顾客、金额、预计积分）；超 30 天窗口的撤销转超管审批。
6. **凭证可审**：券核销的小票图片写入 `store_purchases.receiptImages` 并随审批 payload 下发，审核台可直接看图。
