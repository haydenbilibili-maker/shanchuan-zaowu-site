# 馆藏 tab 加载提速（2026-09-29，产品负责人点名）

> 现象：点底部「馆藏」约 5 秒才出内容。范围：只做不改契约的提速（`getEncyclopediaFeed` 出参字段与 `success` 语义不变）。
> 守卫：`npm run test:category-feed-cache`（home 域，14 个内存注入）。

## 1. 改前测量（线上实测，本机 → 上海）

首屏链路原本是**四段串行**：读开关 →（等）→ `listCategories` →（失败）→ 客户端分页读 `categories` → `getEncyclopediaFeed` → 12 张图。

| 段 | 实测 | 说明 |
|---|---|---|
| 内容开关 `getContentDisplayFlags` | 有缓存 ≈ 0；无缓存冷 1.8 s / 热 0.25 s | 首页已拉过，通常命中缓存 |
| **`listCategories`** | **每次 1.26–2.62 s 后失败** | 线上报 `Cannot find module '../seedCategories/categorySeed'`：函数跨目录 require，部署包里没有这个文件，**每次调用都崩**（已修，见 §4） |
| 客户端兜底读分类 | 6 次请求，level2 串行 4 页 × 80–300 ms | 真正拿到分类树的路径 |
| `getEncyclopediaFeed`（首屏 12 件） | 服务端 300–522 ms，往返 0.5–0.7 s；冷启动再加约 0.9 s | 函数内 5 次数据库操作**全部串行**（关联 ID → 档案计数 → 商品计数 → 商品取数 → 换链） |
| 回包 | 6.5 KB / 12 件 | 函数读整条商品记录：12 件 28.8 KB（61 个字段），实际只用约 6.5 KB |
| 换链 `getTempFileURL` | 1 张 / 150 ms | 库里 11/12 已是 https 缩略链，只有 1 张 `cloud://` |
| 图片 | 12 张合计 624 KB | 11 张已是 560 宽缩略；1 张原图 PNG 222 KB |
| setData | 首屏两次（先清空再整页写入）约 7 KB | 不是瓶颈 |
| onShow | 每次切回都重拉分类树（又撞一次崩溃的 `listCategories`） | 后台进行，不阻塞但浪费 |

结论：大头是「`listCategories` 崩溃 + 兜底」（约 1.8–3.5 s）和「全部串行等待」，数据量本身不大。

## 2. 改了什么

1. **首屏缓存秒开（SWR）**：新增 `utils/categoryFeedCache.js`（只用 `utils/cache`，未改它）。
   缓存「全部 + 无筛选第一页」与分类树，只存渲染字段（馆藏卡 wxml 用到的全部字段，含 `themeName`）；
   单条上限 256 KB（按全中文 ×3 估字节，实测两份各约 6.4 KB），超限不写；带版本号；5 分钟内视为新鲜，7 天内可作旧数据先展示。
   `onLoad` 同步水合 → 后台 silent 刷新：不清空、不出骨架屏，回来后整页替换（价格/库存以服务端为准），失败保留旧内容。
2. **并行**：开关有缓存时不再等网络；首屏馆藏请求与分类树**同时发出**（「全部」首屏不依赖分类树），树回来后不重复拉。
3. **云函数**（只部署了 `getEncyclopediaFeed`）：商品查询加字段投影（关键词路径额外带上排序字段，排序结果不变）；
   关联 ID 与档案计数并行、商品计数与取数并行（5 轮串行 → 2 轮）；关联 ID 做 60 s 容器内缓存。
   8 组参数（首屏/档案/翻页/馆别/关键词/关键词翻页/价格/装裱）新旧两版接线上库**出参逐字一致**。
4. **首页空闲预取**：首页 `onLoad` 后 2.5 s 预取馆藏首屏 + 分类树（缓存新鲜则跳过；单页模式不做；失败静默）。
5. 馆藏卡图片过 `thumbUrl`（原图才会补 560 缩略参数，缩略能力未确认时行为不变）；onShow 只在分类树缓存过期时重拉。

| 商品上屏 · 再次进入 / 首页已预取 | ≈ 2.9 s | **≈ 0（同步渲染缓存）** | 同上 |

**证据边界**：页面耗时来自本机模拟（真实页面 JS + 模拟的 `wx`，延迟按线上实测注入），**不含**真机网络抖动、图片下载与渲染；
真机数值需在开发者工具真机调试里看 `Network` 面板复核。`listCategories` 的崩溃是线上真实调用返回的错误。

## 4. 分类云函数崩溃修复（同日，协调者点名授权按 P0 修）

- **根因**：`listCategories/categoryTree.js` 跨目录 `require('../seedCategories/categorySeed')`，`tcb fn deploy` 只打包本函数目录，线上每次 `Cannot find module`。
- **修法**：把 `seedCategories/categorySeed.js` 逐字复制进 `listCategories/`，改为 `require('./categorySeed')`；`seedCategories` 本身未改。
  副本登记进 `check:shared-modules`（`seedCategories` 为真源，逐字一致）。只部署了 `listCategories`。
- **实测**：线上调用 `success=true`，返回 7 个一级馆 / 48 个二级，与客户端 20 条分页兜底（`loadCategoryPickerTree`）**逐字一致**；回包 27 KB（页面缓存只存白名单字段，约 6.4 KB）。
- **防复发**：新守卫 `check:cloudfn-require-scope`（cross 域）扫描全部 143 个云函数 / 519 个 .js，相对 require 越出本函数目录即红；
  修复后全仓 0 处越界（修复前只有这 1 处），基线为空。错题本 E27。
