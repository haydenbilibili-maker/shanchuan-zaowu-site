> 产品负责人 2026-11-23：「将山海造物 ERP 系统中的 AI 智能中心功能复制到小程序，并作为与超管工作台、投资观测台并列的一级员工功能入口」。

| 项 | 做法 |

## 二、与 ERP 的差异（一期刻意不做）

ERP `AICenter.vue`（6,312 行）里的 **工具链 / OpenClaw 虚拟员工 / 辩论模式 / 报表导出 / 多会话管理** 不搬：

- 这些能力依赖 ERP 侧的 `aiHelper.js` 多模型网关与 `/api/ai` 服务端路由，小程序没有等价通道；
- 一期的目标是「员工在手机上能问到对的同事」，不是功能对齐；
- 需要工具链时，走 ERP。

## 三、实现要点

1. **人设只在服务端**：客户端 `roles.js` 只放 id / 名字 / emoji / 一句话描述 / 开场示例；系统提示词在
   `cloudfunctions/askMuseumGuide/staffPersonas.js`，客户端只传 `roleId`，防前端改提示词绕过边界。
2. **角色白名单**：云端 `ROLE_IDS.indexOf(roleId) < 0` 直接拒；客户端与云端 id 集合由守卫 `test:ai-center` 逐一比对。
3. **边界统一写在服务端**：不编数据 / 不越界 / 不输出密钥与隐私 / 中文 300 字内 / 不写 Markdown 标题。
4. **不新增云函数**：复用 `askMuseumGuide` 省掉一把新 Key 的部署（环境变量是按函数配的），也复用已有的内容安全与模型链。
5. **不写库**：员工对话不落库（与博物君「对话只存在这台手机上」同口径）；也避免把经营讨论写进日志。

## 七、经营上下文（2026-11-23 追加：员工「没有任何上下文」）

### 接了什么

云函数侧新增 `staffContext.js`，**只读**五张表，汇总近 30 天事实，拼进 system prompt：

| 表 | 取的字段 | 角色 |
|---|---|---|
| `orders` | status / totalPrice（回退 payAmount / amount）/ refundFee（回退 refundAmount）/ createTime | 财务 / 数据 / 门店 / 市场 |
| `finance_records` | date / cash（回退 cashIncome）/ pos / online / refund | 财务 / 数据 / 门店 / 市场 |
| `products` | isOffShelf / stock / category | 采购 / 创意（+订单量） |
| `users` | createTime（只取数量） | 市场 / 数据 |
| `bookings` | createTime（只取数量） | 门店 |
| `purchase_orders` | totalAmount / paymentStatus / status / createdAt（**不取采购商信息**） | 采购 |
| `stock_movements` | delta / type / createdAt（入库、出库、净变化） | 采购 |
| `ops_purchases` | amount（回退 qty×unitPrice）/ status / scope / deleted / createdAt | 采购、门店 |

输出形如：

```
近 30 天订单 128 笔（已付 121 笔），实付 GMV ¥86,420，客单价 ¥714，退款 ¥1,280；
近 30 天门店日账合计 ¥52,300（现金 ¥12,000 / POS ¥28,300 / 线上 ¥12,000，退款 ¥640）；
近 30 天新增会员 36 人
```

### 口径与边界

- **5 分钟内存缓存**（同一函数实例复用），避免每次提问扫库；表大时只取前 1000 / 500 条；
- 每块独立 `try/catch`：某张表查不到就少一句，**不影响回答**，也不把错误抛给前端；
- 清单 ≤ 520 字；**不取姓名 / 手机 / 账号标识**（守卫 A5 静态拦截）；
- system prompt 里明确「**未出现的指标就是没有数据，不要推算**」——宁可说不知道，不让模型编数。

### 2026-11-23 第二轮补接：采购单 + 库存流水

字段都先在**写它的代码**里核对过：

| 表 | 取的字段 | 来源代码 |
|---|---|---|
| `purchase_orders` | `totalAmount` / `paymentStatus` / `status` / `createdAt` | `cloudfunctions/payB2bPurchase`、`admin/src/utils/b2bFulfillment.js` |
| `stock_movements` | `delta` / `type` / `createdAt` | `admin/src/utils/feishuSync.js`、`b2bFulfillment.js`（`outbound_ship` 等） |

口径：

- 采购额 = 近 30 天 `totalAmount` 求和；「已付」只认 `paymentStatus ∈ paid | marked_paid`；
- 库存流水 = `delta` 正负累计（入库 / 出库 / 净变化），**不区分仓库**（目前主要是 `hq`）；
- **只取金额、状态、增减量**，不取采购商、联系人、SKU 名称等字段；
- 只在**采购专家**的上下文里出现，避免其它角色拿采购额下错结论。

### 还没接（下一步）

- ~~订货履约 `ops_purchases`~~：**已接**（2026-11-23 第三轮补接）——与 B2B `purchase_orders` 是两套账，分别标注为
  「店内采购（门店 / 工作室）」与「B2B 采购单」，不合并成一个金额；跳过 `deleted` 与 `cancelled`，未结口径见上表；
- **飞书库存 `feishu_inventory`**：在途 / 锁定库存，需与 `stock_movements` 对齐口径后再接；
- **内容与投放**：选题、发布、券核销；
- **实时性**：现在 30 天窗口 + 5 分钟缓存；要「今天实时」需加按日聚合或定时快照。

> 原则：**字段先在写它的代码里核对过才接**。宁可少接一张表，也不让模型拿着错口径的数据下结论。

## 九、第三轮：一键任务（2026-11-23 晚）

把 ERP 里「点一下就跑一份分析」的用法搬成**固定任务**，每个员工 2 个，共 12 个：

| 员工 | 任务 |
|---|---|
| 门店运营经理 | 门店转化诊断 · 高峰排班建议 |
| 采购专家 | 库存风险扫描 · 采购成本优化 |
| 创意总监 | 陈列主题提案 · 门店活动创意 |
| 数据分析师 | 经营数据体检 · 复购归因思路 |
| 财务总监 | 现金流体检 · 盈亏平衡测算 |
| 市场总监 | 内容选题 5 条 · 老客回流方案 |

### 安全与实现

- **提示词只在服务端** `cloudfunctions/askMuseumGuide/staffTasks.js`；客户端 `tasks.js` 只放 `id / roleId / title`；
- 请求带 `taskId` 时**任务优先**：角色与问题都由服务端任务表决定，客户端传的 `roleId/question` 被忽略；未知 `taskId` 直接拒；
- 任务消息在气泡里显示「一键任务 · 标题」，消息上记 `taskId`，「重试」按任务重发；
- 任务条按**当前角色**过滤，选了谁就只出现谁的任务。

### 守卫（A6）

- 客户端与服务端 `id+roleId` 逐一一致、12 个任务、每个员工至少 1 个；
- 客户端文件里**不许出现 `question`**（提示词不下发）；
- 云端未知 `taskId` 必须拒；
- 页面有任务条与 `runTask`、请求带 `taskId`、重试按任务重发；
- 新增注入「未知任务不拒」「任务角色对不上」，`--selftest` **10 条注入全检出**。

### 仍未做

- 任务结果**导出 / 复制全文**（现在只能逐条复制）；
- 任务的**参数化**（如「指定门店 / 指定月份」）；
- 任务**定时跑**（日报式），需要定时触发器与落库，涉及新集合，未做。

## 十、第四轮：董事会辩论（2026-11-23 晚）

搬自 ERP AICenter 的「辩论」模式，做成员工端独立页 `subpackages/extra/ai-debate`，入口在 AI 智能中心顶部。

### 玩法

1. 选辩题（自定义，或 3 个预设：营业时间 / 标本画定价 / 双十二力度）；
2. 选 **2–4 位董事**（六位虚拟员工里挑）；
3. 开始后**串行**发言：每位董事一轮，要求「接住前面的人、指出分歧」；
4. 最后**主持人收口**：共识 / 分歧 / 2–3 条可执行建议；
5. 支持**停止**、逐条**复制**，上一场自动留本机（`ai_debate_last`），下次打开可回看。

### 云端契约

`askMuseumGuide` 新增 `mode: 'debate'`：

| 参数 | 说明 |
|---|---|
| `step` | `speak`（一位发言）/ `verdict`（主持人收口） |
| `topic` | 辩题，4–120 字 |
| `members` | 2–4 个 roleId，去重；`speak` 时的 `roleId` 必须在这个名单里 |
| `speeches` | 已发言记录 `[{ roleId, name, text }]`，服务端只读 |

- **一次请求只做一件事**：客户端串行调用，避免单次云函数超时；
- 提示词与规则只在云端，客户端传不了系统提示；
- 发言与收口都过内容安全；不过则整段替换为「已省略」，不让模型输出原样落地。

### 守卫（A7）

页面注册 + AI 中心入口 / 云端 2–4 人限制与名单校验 / 收口独立一步 / 提示词不在客户端 / 串行与停止 / 本机保存；
新增 2 条注入（辩论不分发、允许单人），`--selftest` **12 条注入全检出**。

### 取舍与未做

- **不做** ERP 的「多轮交叉质询 / 投票 / 导出报告」：一期先把「一场能看完的辩论」跑通；
- 辩论**不落库**（与对话同口径），要跨端回看得先设计集合与权限；
- 董事人数上限 4：再多会让单场串行请求时间过长（每次都是一次完整模型调用）。
