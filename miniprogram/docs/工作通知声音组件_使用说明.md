# 工作通知声音组件（需求 #29）· 使用说明

> 面向：超管 / 店长 / 标本师等工作台角色。
> 有新工作信息时用**语音播报**提示（「您有新的订单，请及时处理」「您有新的工单需要处理」……），
> 音频由 AI TTS 生成，随包发货（无网络依赖、无运行时密钥）。

## 1. 它是什么 / 在哪里响

| 位置 | 文件 | 角色 |
|------|------|------|
| 播报引擎（判定「该不该响、响哪句」） | `utils/workNoticeVoice.js` | 全部 |
| 语料与信号清单（**唯一真源**） | `utils/workNoticeCatalog.js` | 全部 |
| 声音组件（铃铛开关 + 试听 + 生命周期） | `subpackages/manager/components/WorkNoticeVoice/` | 全部 |
| 音频资产 + 生成清单 | `subpackages/manager/assets/audio/work-notice/` | 全部 |
| 入口接线 | `subpackages/manager/manager/managerPageConfig.js`（超管/店长 hub）<br>`subpackages/extra/artisan/index.js`（标本师工作台） | — |

界面表现：工作台头部一枚**纯图标**小铃铛 —— **🔔 有声 / 🔕 静音**，**点一下 = 开关**（默认开）、**长按 = 试听**。
> 为什么不带「声音」两个字：它是头部右侧的第二枚元素，窄屏上两个字会被挤成**竖排**，
> 把日期徽标顶下去（2026-09-16 真机截图实测）。守卫 `check:work-notice` 会拦住「把文字加回来」。

## 3. 三条硬规则（改代码前必读）

1. **只播新增**：首次进入工作台（或换角色后首次）只建立基线，**不播**；之后按「计数上涨」判断，
   订单类额外用**消息 id 差集**（读了 1 条又来 1 条时计数不变，但确实是新单）。
2. **判定必须在「待办全部落地后」那一次调用里**：
   hub 里是 `prefetchHubTodoBadges` 的 `finally`，标本师页是 `refreshHomeStats` 成功之后。
   若挂在各个 loader 里（每个 loader 都会 `refreshOpsSignals`），先到的单项会在后续计数补齐时被误判成新增 —— **每次进工作台都会响**。
3. **静音不囤积、节流不丢消息**：
   关掉声音期间照样推进基线（否则重新打开会把攒下的一次性播完）；
   两次播报间隔 < 15 秒时**不推进基线**，这批新增留到下一轮（推进了就等于吞掉）。

## 4. 音频怎么来的（AI TTS）

```bash
npm run tts:work-notice                  # 默认：本机 macOS 神经音色 → MP3（零密钥、可离线复跑）
npm run tts:work-notice -- --voice Sandy # 换音色（Tingting / Sandy / Eddy / Flo / Reed / Rocko / Shelley / Grandma / Grandpa）
npm run tts:work-notice -- --only order,workOrder   # 只重录某几条（其余登记保留）
npm run tts:work-notice:check            # 只校验：清单 ↔ manifest ↔ 磁盘音频是否一致（守卫会调它）

# 接云端 AI 音色（音质更好）：在 admin/.env 配好密钥后
npm run tts:work-notice -- --backend aliyun --voice xiaoyun
#   ALIYUN_NLS_ACCESS_KEY_ID / ALIYUN_NLS_ACCESS_KEY_SECRET / ALIYUN_NLS_APPKEY
```

产物：`assets/audio/work-notice/*.mp3` + `manifest.json`
（manifest 记 `text` / `textHash` / `bytes` / `durationMs`）。

> **改文案必须重录**：`manifest.textHash` 与清单文案不一致时 `npm run check:work-notice` 会直接失败 ——
> 这是这类「音频资产」最常见的漂移（页面写着新话术、耳朵里还是旧的）。
> 音频参数：22050 Hz / 单声道 / 48 kbps；16 条约 280 KB，放在 manager 分包内，不占主包体积。

## 5. 新增一个通知类型（四步）

1. `utils/workNoticeCatalog.js` 的 `NOTICE_TYPES` 加一条
   （`type` / `label` / `text` / `file` / `priority` / `roles` / `source`）；
2. `npm run tts:work-notice`（或 `--only <type>`）生成音频 + 更新 manifest；
3. 确认页面 `data` 里**真的有** `source` 指向的计数（否则永远是 0，等于没接）；
4. `npm run check:work-notice`（含 `--selftest`）必须通过，并把新类型登记到本文档第 2 节。

## 6. 已知边界（真机验证仍是必须项）

- **小程序切后台 / 系统静音键**：`InnerAudioContext` 会被系统限制，静态分析判不出结论。
  代码里已把 `obeyMuteSwitch` 关掉（尽量在静音键下也出声），但**必须真机验证**：
  ① 锁屏/切后台时不应该响；② 静音键打开时是否出声；③ 耳机/蓝牙已连接时的路由。
  音频播不出来时引擎会退化为**一次轻震动**（`wx.vibrateShort`），至少有触感提示。
- **轮询边界**：小程序没有后台定时器，所以播报时机 = **进入工作台 / 从后台回到工作台 / 下拉刷新**。
  真正的「离线推送」要靠订阅消息（见需求 #16/#33），不在本组件范围。
- **一次最多 3 条**（`MAX_ANNOUNCE_PER_CYCLE`）：同时来 5 类待办时只播最要紧的 3 条，其余留角标。
- **声音在本地按角色分别记基线**：换角色不会把上个角色的待办当成新增。

## 7. 守卫

```bash
npm run check:work-notice            # 语料结构 / 音频资产 / 页面接线 / 增量判定 / 无平台降级（12 项）
npm run check:work-notice:selftest   # 用 14 个「被破坏的输入」证明上面每条都会失败
```

两者都已纳入 `npm run check:admin`。
