## 1. 代码取证：B2B 支付到底需要什么

### 1.1 环境变量（逐函数配置，不共享）

| 变量 | 配在哪个函数 | 必填 | 默认值 | 行为 |
|------|--------------|------|--------|------|
| `WX_PAY_SUB_MCH_ID` | **`payB2bPurchase`** | **是** | 空 | 为空 → 返回 `code: B2B_PAY_NOT_CONFIGURED`（前端提示「微信商户未配置，可点待对公」），**不会**拉起支付。填**你们自己的 10 位商户号**（字段名叫 sub，是云开发服务商代调用的约定） |
| `B2B_ALLOW_PREVIEW_MARK` | `payB2bPurchase` | 否 | 未设 = 关 | `=1` 时，**超管**可在「我的采购单」点「验收标记」把单子标为 `marked_paid`（非真实收款） |
| `ALLOW_MOCK_PAY` | `payB2bPurchase` | 否 | 未设 = 关 | 在 B2B 里**只**起一个作用：`=1` 等同打开 `B2B_ALLOW_PREVIEW_MARK`。B2B **没有**「模拟支付成功」路径 |
| `ADMIN_OPS_KEY` | **`payB2bPurchase`** | **是**（ERP 用） | 空 | ERP「确认对公到账 / 微信查单补记 / 微信退款」经 `/api/cloud-fn` 代理注入该口令鉴权为超管；**须与 Cloudflare Pages 及其它管理函数上的值完全一致**。缺失时 ERP 这三个按钮报「云函数未配置 ADMIN_OPS_KEY」，小程序采购商下单/支付不受影响 |
| `TCB_ENV` / `SCF_NAMESPACE` | — | 不用配 | 平台注入；兜底硬编码 `cloud1-8gnkty5bfff9f0bf` | 作为统一下单的 `envId`（回调云函数所在环境） |
| （无） | `b2bPayCallback` | — | — | 回调函数**不读任何环境变量**，无需配置 |

- 环境变量是**按函数**生效的：C 端 `payOrder`/`confirmPayment`/`refundOrder`/`manageStoredValue` 上已经配的 `WX_PAY_SUB_MCH_ID` **不会**自动作用到 `payB2bPurchase`，必须单独再配一次。
- 两个 B2B 函数目录下**没有** `config.json`；`miniprogram/cloudbaserc.json` 已登记两函数（timeout 15s、Nodejs16.13），且**不含** `envVariables`，因此用 CLI 部署**不会覆盖**控制台里配好的环境变量（`deploy-drifted.sh` 头注释亦如此说明）。

### 1.2 统一下单参数（`payB2bPurchase/index.js`）

| 参数 | 取值 | 说明 |
|------|------|------|
| `subMchId` | `WX_PAY_SUB_MCH_ID` | 与 C 端同一个商户号即可 |
| `functionName` | **`b2bPayCallback`**（硬编码） | ✅ 已配置，且与 C 端 `payCallback` **分离**，B2B 回调不会误触 C 端履约 |
| `envId` | `TCB_ENV` → 兜底 `cloud1-8gnkty5bfff9f0bf` | ✅ |
| `tradeType` / `openid` | `JSAPI` / 调用者 openid | ✅ |
| `totalFee` | **服务端按 `price_list_items` 现价重算**，单位：分 | `Σ 固定单价 × 数量`（`b2bPricing.js`）；单内金额与现价不一致 → 回写新金额并返回 `PRICE_CHANGED`（本次不下单，采购商确认后重试）；含区间价/议价/已下架 → `QUOTE_REQUIRED` |
| `outTradeNo` | `B2B` + 时间戳36进制 + 随机数，≤32 位 | 每次点支付换新单号；**历次单号与当时应付分**都记入 `payOutTradeNos` / `payTrades`（最多 20），回调可匹配任一次；`payOutTradeNo` 保留最近一次（兼容） |
| `attach` | 采购单 `_id` | 回调兜底定位（且须核验单号属于该单） |
| `body` | `山海造物·B2B采购` | 用户账单与商户平台可见 |
| `spbillCreateIp` | `127.0.0.1` | 与 C 端一致 |

### 1.3 谁能调用

| 动作 | 权限判定（代码实际行为） |
|------|--------------------------|
| `create` / `list`（下单 / 我的采购单） | 花名册采购类角色（`buyer`/`franchisee`/`channel`，超管亦可）；列表只返回 `_openid` = 本人的单 |
| `pay`（微信支付） | 采购类角色 **且** 采购单 `_openid`（或 `buyerOpenid`）= 本人 **且** `source=buyer_workbench`；**无归属人的单一律拒绝**（`NO_OWNER`） |
| `markOfflinePending`（待对公） | 同上 |
| `markPaidPreview`（验收标记） | 超管（硬编码 2 个 openid 或 `workspace_acl/super_admins`）**且** `B2B_ALLOW_PREVIEW_MARK=1`/`ALLOW_MOCK_PAY=1` **且** 本人单 |
| `supplierList`（供货方需求） | 供货方角色；`supplierId` 取花名册 `staff_members.supplierId`（兜底 openid），客户端传值仅超管预览时采信 |
| `adminConfirmOffline` / `adminReconcile` / `adminRefund` | **仅超管**（ERP 经代理注入 `ADMIN_OPS_KEY`）；退款另需回填完整采购单号 + 退款原因 |
| `b2bPayCallback` | 拒绝小程序端/开发者工具直调（`SOURCE=wx_client/wx_devtools`），与 C 端 `payCallback` 同一判据（**不**用 OPENID 判伪造，符合 2026-09-15 事故复盘红线） |
| ERP 其它写入（确认订货 / 出货 / 改备注 / 意向转单 / 报价单维护） | 经 `manageStoreContent` 代理，**仅超管**；对采购单禁 `remove`/`removeWhere`/`setDoc`，**禁写任何支付字段** |

### 1.4 支付状态机（`purchase_orders.paymentStatus`）

```
unpaid ──点微信支付──▶ pending ──回调 SUCCESS 且金额一致──▶ paid（wechat_jsapi, transactionId, paidFen）──ERP 微信退款──▶ refunded
   │                    │（用户取消：保持 pending，可重试；统一下单失败：回滚 unpaid）
   │                    ├──回调金额不一致 / 缺金额──▶ pay_review（待人工核对，采购商不可再付）
   │                    └──回调丢失──ERP 微信查单补记──▶ paid（金额一致）/ pay_review（不一致）
   ├──点待对公────────▶ offline_pending ──ERP 确认到账──▶ paid（paymentChannel=offline, offlineConfirmedBy）
   └──超管验收标记────▶ marked_paid（paymentChannel=preview_mark，非真实收款）
```

`pricingMode=quote_required`（含区间价/议价）的单只显示「待对公」，不显示「微信支付」。

前端文案映射见 `supplier/utils/buyerPurchaseOrder.js` 的 `PAY_STATUS_LABEL`（`awaiting_config` 只是云函数返回给前端的提示，不写库）。

### 1.5 能否复用 C 端商户号 —— **能**

- 云开发的商户绑定是「**云环境 × 小程序 AppID × 商户号**」级别的，不是按云函数；本环境 `cloud1-8gnkty5bfff9f0bf` 已绑定且 JSAPI/退款已授权（`上线检查清单.md` §支付、`微信支付商户号申请与配置.md` 阶段 C，2026-08-15 用户截图确认）。
- C 端所有支付函数读的都是同一个变量名 `WX_PAY_SUB_MCH_ID`；B2B 沿用同名变量，填**同一个值**即可。
- 业务侧需知道：B2B 货款与 C 端货款会**进同一个商户账户**，对账靠 `outTradeNo` 前缀（`B2B…` vs C 端 `orderNo`）和商品描述区分。是否长期共用，仍是 `供应商工作台_Phase1.md`「需产品负责人点名」第 2 条。
- 官方限制提醒：微信文档注明，按《交易类小程序运营规范》，销售**珠宝玉石、3C 数码、盲盒、服饰内衣、海淘、美妆、酒类、家用电器、玩具、箱包皮具、鞋靴、运动户外**等商品时**不可使用云调用支付**。标本/文创不在列表内，C 端已在用同一通道；若 B2B 价目表未来加入上述品类，需要改走「工作流」接入。

## 3. 逐步操作

### 3.A （仅当 P3–P5 失效时）重新绑定商户号

官方步骤（[云调用对接微信支付](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloud/guide/wechatpay/openapi.html)）：

1. 微信开发者工具，用小程序 `wxf2550373b010b447` 的开发者微信登录 → 打开**云开发控制台** → 选环境 `cloud1-8gnkty5bfff9f0bf`。
2. **设置 → 全局设置** → 微信支付 → **添加商户号**，填 10 位 mchid。
3. **账号绑定**：商户号**超级管理员**微信会收到「微信支付商家助手」消息 → 打开 → 确认授权给 **「1800008281 小程序云开发」**。
   > 官方注意：打开的页面若默认不是云开发服务商，需要**手动下拉选择**「1800008281 小程序云开发」。
4. **JSAPI 与 API 退款权限**：登录 [微信支付商户平台](https://pay.weixin.qq.com) → **我的授权产品** → 对云开发服务商的 JSAPI 支付、API 退款两项点**确认授权**。
5. 回到云开发控制台刷新：商户号「已绑定」，JSAPI/退款「已授权」。

> 本项目走的是 **cloudPay 云调用**（免证书、免签名），**不需要**上传 API 证书/APIv3 密钥，也**不要**去配 CloudBase「集成中心」的微信支付集成（那是另一套）。

### 3.B 给 `payB2bPurchase` 配环境变量（主路径：控制台 UI）

1. 云开发控制台 → **云函数** → 列表中点 **`payB2bPurchase`**。
2. 进入 **函数配置 / 环境变量** → 编辑 → 新增：
   - Key：`WX_PAY_SUB_MCH_ID`　Value：与 C 端 `payOrder` 上**完全相同**的 10 位商户号（可在控制台打开 `payOrder` 的环境变量对照复制；本地备忘在 `miniprogram/scripts/pay.env.local`，已 gitignore）
   - Key：`ADMIN_OPS_KEY`　Value：与 `manageStoreContent` / `manageStaff` 等管理函数上**完全相同**的口令（控制台对照复制；也等于 Cloudflare Pages 与 `admin/.env` 的 `ADMIN_OPS_KEY`）
3. **确认没有** `ALLOW_MOCK_PAY=1`；联调阶段如需超管验收标记，可临时加 `B2B_ALLOW_PREVIEW_MARK=1`（上线后删除，见 §3.D）。
4. 保存。`b2bPayCallback` **不需要**任何变量。

**不要**把商户号写进 `config.json`、`cloudbaserc.json`、源码或任何入库文档。

### 3.B′ 备选：CloudBase CLI 写环境变量

微信开发者工具 CLI **没有**写环境变量的命令；CloudBase CLI（`tcb`）有（[官方：配置操作](https://docs.cloudbase.net/cli-v1/config/manage)）：

```bash
# 在 miniprogram/ 目录执行；务必用 merge，避免覆盖其它变量
tcb config update fn payB2bPurchase \
  --env WX_PAY_SUB_MCH_ID=<你的商户号> \
  --env-mode merge -e cloud1-8gnkty5bfff9f0bf --yes
```

> ⚠️ 2026-09-30 实测：CloudBase CLI **3.8.0 已没有** `--env` / `--env-mode` 参数，上面的命令不可用。
> 脚本方式改用 `@cloudbase/manager-node` 的 `functions.updateFunctionConfig`；它的 `envVariables` 是**整体替换**，
> 必须先 `getFunctionDetail` 读出全量 → 只替换目标键 → 写回 → 再读回核对其它键值未变（见错题本 E29）。

- 必须 `--env-mode merge`；`overwrite` 会**清空**该函数其它环境变量。
- 命令行会留在 shell 历史里：执行后可 `history -d` 或直接用控制台方式。
- 官方说明：`@cloudbase/cli` **< 2.12.0** 时，`cloudbaserc.json` 里若写了 `envVariables` 会**整体覆盖**线上变量。本仓 `cloudbaserc.json` 不含 `envVariables`，保持这样即可。

部署后在控制台再点开 `payB2bPurchase` → 环境变量，确认 `WX_PAY_SUB_MCH_ID` 仍在。

### 3.E 采购商身份开通（花名册勾选）

采购商工作台入口按 `manageStaff` 花名册角色派发；B2B 角色 `buyer`（采购商）/ `franchisee`（加盟商）/ `channel`（渠道商）/ `supplier`（供货方）**只能**进采购商工作台，不能操作门店后台（`staffGuard` 已拦截）。

1. 采购商先在小程序里**登录一次**（生成 openid / 用户档案）。
2. 超管在小程序 → **员工权限**（`subpackages/extra/staff-permissions`，或管理端「店员花名册」`subpackages/manager/staff-directory`）找到此人 → 角色勾选 **「采购商」**（或加盟商/渠道商）→ 保存。
3. 采购商重新进入「我的」→ 看到 **采购商工作台** 瓷砖即开通成功。

## 4. 小额真实支付联调（0.01 元）

代码支持 0.01 元：`totalFee` 最小 1 分即可下单，无最低金额限制。

### 4.1 准备测试价目

1. ERP → 业务 → **报价单配置**（`price_list_items`）→ 新增一条测试 SKU：名称如「【联调】0.01 元测试件」，**单一价** `price = 0.01`（不要用区间价），`status = active`。
2. 联调完**立刻下架/删除**，避免真实采购商下单。

## 6. 退款与对公兜底

### 6.1 退款：ERP「微信退款」（仅超管，2026-09-28 新增）

- 入口：ERP → 订货履约 → 单据详情 → **「微信退款」**（仅 `paymentStatus=paid` 且 `paymentChannel=wechat_jsapi` 显示）。
- 二次确认：须**输入完整订货单号**，再填**退款原因**（写入微信退款单 `refundDesc` 与单上 `refund.reason`）。
- 服务端流程（`payB2bPurchase.adminRefund`）：先 `cloudPay.queryOrder` 确认该笔成功、取实收金额 → 写 `refund.status=refunding` 与 `outRefundNo` → `cloudPay.refund` 全额原路退 → 成功置 `paymentStatus=refunded`，记 `refund.requestedBy/refundedBy/refundedAt`。
  失败置 `refund.status=failed`，**重试沿用同一退款单号**（官方要求，避免重复退款）。
- 只做全额退款；「成功」指微信已受理，实际到账以微信为准（未接退款结果通知，见待决项）。
- 对公款、`payDuplicate` 里的重复到账：仍在 [微信支付商户平台](https://pay.weixin.qq.com) → 交易中心 → 退款 手工处理。

### 6.2 对公线下确认（商户号未通或大额采购时的兜底）

1. 采购商在「我的采购单」点 **「待对公」** → `paymentStatus=offline_pending`、`paymentChannel=offline`。
2. 采购商按对接人给的对公账户转账（备注采购单号 `PO…`）。
3. 财务核实到账后：ERP → 业务 → **订货履约** → 筛选「待对公」→ 该单点 **「确认到账」** → `paymentStatus=paid`、`paidAt`、`payMarkNote='Admin 确认对公到账'`、`offlineConfirmedBy`（经 `payB2bPurchase.adminConfirmOffline` 条件更新）。
4. 只有 `offline_pending` 能确认；已 `paid/marked_paid` 的单重复点会提示已付，不会重复记账。

过渡规则 `auth != null && auth.loginType != 'ANONYMOUS'` 对旧版小程序无影响，但**线上 ERP（main 分支版本）对采购单的列表读、确认订货、取消、改备注、意向转单、出货回写全部是匿名直连**，
一上过渡规则整个「订货履约」模块即不可用；只收写不收读也同样打断确认/出货。按产品负责人口径「影响线上 ERP 采购单模块先报告不应用」，
故过渡规则与正式规则**一起**等第 3 步新版 ERP 上线后再上（新版 ERP 读经 `adminList`、写经 `manageStoreContent`，不再依赖匿名）。
在此之前线上仍是**公网匿名可建单 / 改单**（23:10 探针实测 update 放行；现存 2 条单含联系人手机），风险窗口 = 新版 ERP 上线所需时间。

> 规则 `read: doc._openid == auth.openid` 为纯本人、`write:false`：小程序新版的读写全部走云函数、不受影响；
> 旧版小程序直写建单、按 `supplierId` 直查供货方需求都会被拒 —— 这是第 4 步必须先于第 5 步的原因。
