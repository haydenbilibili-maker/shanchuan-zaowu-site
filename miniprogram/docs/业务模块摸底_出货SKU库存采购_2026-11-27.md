# 业务模块摸底：出货中心 / SKU 维护 / 库存 / 采购（2026-11-27）

> 目的：系统优化前先摸清现状与真问题。结论先行：**四块各自能用，但数据口径是分裂的，
> 交易与台账不联动**——这是后续所有「对不上账 / 超卖 / 成本不准」的根。

## 1. 现状地图（代码事实）

| 模块 | 页面 | 云函数 | 数据集合（SSOT） | 能力 |
|---|---|---|---|---|
| 出货中心 | `extra/shipment-ops`（开单 / 单据 / 总览 / 资料，2072 行） | `manageStoreShipment` | **`ops_shipments`**；SKU 价目 `studio_shipment_skus`；材料价 `studio_material_prices`；包装价 `studio_packaging_prices` | 开单（可搜商品/SKU）、飞书 upsert、改价重算、状态流转、结算状态 |
| SKU 维护 | `extra/shipment-sku`（37 行，重定向壳 → 出货中心「资料」） | 同上 | `studio_shipment_skus` | 维护出货用的 SKU 价目，不是商品 SKU |
| 库存 | `extra/inventory-ops`（成品 / 原材料两档，1408 行）；`manager/raw-inventory-ops` | `manageStudioInventory` / `manageStudioRawInventory` | **`studio_inventory`（成品）** / **`studio_raw_inventory`（原料）** | 粘贴群公告盘点 → 按盘点日**快照覆盖**；飞书 upsert；总览信号灯 |
| 采购 | `extra/purchase-ops`（观测台 + 单据，1406 行） | `managePurchaseOrder` | **`ops_purchases`** | 新建/编辑/状态流转/批量改状态/飞书写回；支付走 `payB2bPurchase` |
| 供应商 | `extra/supplier-desk` | `manageSupplierDesk` | 供应商台账 | 供应商档案 + 对账单（myAccess / myStatement） |
| 电商库存 | C 端商品 | `makeOrder`（`stockUtils.holdOrderProducts`）、`manageProducts` | **`products.stock` / `products.skus[].stock`** | 下单锁库存、商品后台改库存 |

## 2. 真问题（按影响排序）

### P0 口径分裂：同一件东西有 3～4 个"库存"

| 口径 | 存在哪 | 谁在写 |
|---|---|---|
| 可售库存 | `products.stock` / `products.skus[].stock` | 商品后台、下单锁库存 |
| 成品台账 | `studio_inventory` | 飞书同步 / 粘贴盘点**覆盖** |
| 原材料台账 | `studio_raw_inventory` | 同上 |
| 出货 SKU | `studio_shipment_skus` | 出货中心「资料」手维 |

**后果**：C 端卖掉的与出货开单的、盘点看到的，是三本账；孤品/唯一件与数量库存混着用，超卖与"账上有货实际没货"都可能发生。

### P0 交易不产生台账流水

- 采购：`ops_purchases` 只有状态（ordered → shipped → received…），**收货不写入任何库存**（`managePurchaseOrder` 里没有 `studio_inventory` / `studio_raw_inventory` 的写）；
- 出货：`manageStoreShipment` 只读 `studio_inventory` 做 SKU 搜索（779–826 行），**发货不扣台账**；
- 订单：`managerShipOrder` 只管订单状态（orders 集合），不碰库存；电商扣减只在 `makeOrder` 锁 `products.stock`；
- 库存：`commitSnapshot` 按盘点日**整表覆盖**，没有出入库流水 → 任何一笔变化都无法追溯"谁、何时、为什么"。

### P1 单据之间没有关联键

采购单 ↔ 出货单 ↔ C 端订单 ↔ 账本（`studio_bills`）之间没有统一的关联 id。
典型表现：**同一笔快递费要录两次**（出货单里一次、账本里一次），售后/退货的运费更无处归类。

### P1 操作效率与易错点

- 盘点靠**粘贴群公告文本**解析（`parseStudioInventoryText`），格式一变就错、且覆盖式写入没有差异确认；
- 飞书同步是 upsert 覆盖，双方同时改会静默覆盖（没有冲突提示）；
- SKU 批量改价/停用只能一条条改；移动端没有扫码（运单号 / 商品条码）；
- 唯一件（孤品）没有序列号维度，退货回库无法定位"回来了哪一件"。

### P2 权限与审计

- 店长只读、超管可写，但写操作审计散落在各云函数（`admin_operation_logs` 覆盖不全，需逐函数核查）；
- 出货/采购的"删除/作废"没有软删除与恢复入口。

### P2 报表断点

- 商品侧有 `costPrice×stock` 的积压成本估算（`manageProducts`），但**采购真实采购价、出货成本、运费**没有汇到同一张单品成本表；
- 供应商对账（`manageSupplierDesk`）与采购付款状态没打通，靠人核。

## 3. 建议的优化顺序（每步可独立上线）

| 阶段 | 目标 | 关键动作 | 风险 |
|---|---|---|---|
| **S1 口径统一** | 一套库存 + 一条流水 | 新建 `inventory_moves`（入/出/调/盘）作为唯一事实；`studio_inventory` 改为"由流水汇总的视图"；`products.stock` 与唯一件分开（唯一件用 `serialNo`，数量件才用 stock） | 中（要迁移历史快照） |
| **S2 打通三个动作** | 收货入库 / 发货出库 / 支付锁库 | 采购单 `received` → 写入库流水；出货单 `shipped` → 写出库流水并校验可用量；退货 → 回库流水；下单锁定改为引用流水 | 中（并发与幂等要设计） |
| **S3 单据串联** | 一笔业务一条链 | 采购单/出货单/订单/账本互带 id；出货单里录的运费直接生成账本支出草稿，不再录两次 | 低 |
| **S4 操作提效** | 少手工、少出错 | 扫码（运单/条码）、盘点差异确认页（不直接覆盖）、SKU 批量改价/停用、飞书同步冲突提示 | 低-中 |
| **S5 报表与对账** | 成本与对账说得清 | 单品成本（采购价 + 运费摊销）、库存周转/积压、供应商对账单与付款状态联动 | 低 |

## 4. 需要产品负责人先定的三件事

1. **唯一件怎么记**：孤品/唯一件是否引入 `serialNo`（一件一条），数量件继续用 stock？
2. **库存以谁为准**：以"流水汇总"为准（推荐），还是继续以飞书/盘点表为准、流水只做旁路？
3. **运费归属**：出货单里的运费是否允许直接生成账本支出（不再手录），以及按单/按件摊销口径。

## 5. 产品负责人拍板（2026-11-27）与本轮落地

| 问题 | 拍板 |
|---|---|
| 库存以谁为准 | **以出入库流水为准**（授权新增集合 `inventory_moves`，含改受保护的 `admin/src/cloud.js` COLLECTIONS） |
| 唯一件 | **引入 serialNo**，一件一条；数量件继续用 stock |
| 运费归属 | **生成草稿，人工确认** |

### 5.1 摸底复核：上文与代码不符的地方

- **软删除已存在**：出货 / 采购 / 原材料都是 `deleted:true` 软删（缺的是恢复入口，不是软删本身）；真正硬删的是**成品盘点**——
  `commitSnapshot` 整表删除重建，**连飞书同步进来的成品行也一并删掉**（P0，本轮已修）。
- **「运费录两次」与代码不符**：出货单原本**没有运费字段**；`studio_bills` 是门店→工作室货款结算（`ops_settlement_bills`），不是支出账。
  支出侧事实上的账是采购账 `ops_purchases`（预算类型含房租 / 水电），运费草稿落在这里（新增预算类型「物流运费」）。
- **审计**：四个函数都没写 `admin_operation_logs`；另外该集合规则是 `read: auth != null`（任何登录用户可读），
  **不适合**写采购 / 出货金额 —— 库存侧的审计改由流水本身承担（谁 / 何时 / 为什么 / 关联单据）。该规则需产品负责人另行定夺。
- 采购单是**单行**（`itemName` / `qty`），不是 `items[]`；出货单明细已带 `inventoryRecordId`（选 SKU 开单时来自成品台账）。

### 5.2 本轮落地（S1 + S2 + S3 运费 + S4 盘点差异）

| 动作 | 落点 | 口径 |
|---|---|---|
| 流水集合 | `inventory_moves`（三处同步）+ 共享模块 `inventoryMoves.js`（4 份副本，`check:shared-modules`） | `_id = mv_ + sha1(idemKey)` 幂等；首次触达懒开账（opening）；台账 `_.inc` 原子累加 |
| 盘点 | `manageStudioInventory.commitSnapshot` | **不再删表**：观测值与台账的差额记 `count` 流水；没出现的按 0；唯一件不参与按品名盘点 |
| 盘点差异预览 | `diffSnapshot`（只读）+ 库存页「这次盘点会改什么」 | 新增 / 清零 / 改数 / 不变；点名会被清零的飞书行 |
| 飞书同步 | 成品 / 原材料 `upsertFromFeishu` | 数量只经 `count` 流水改，其它字段照旧 |
| 原材料手工改数 / 建档 | `manageStudioRawInventory` | 建档 = `in`；改数 = `count`；库存金额随之刷新 |
| 采购到库 | `managePurchaseOrder.setStatus / batchSetStatus / update` | **工作室 + 标本 / 原材料类**、状态**真的变成**已入库 / 已完成 → 原材料 `in`；工具 / 门店 / 飞书同步不触发 |
| 出货发出 | `manageStoreShipment.setStatus / update / create` | 变成已发货 / 已签收 / 已完成 → 成品 `out`（`inventoryRecordId` / 唯一件 `serialNo` / 品名+规格）；**对不上的行不臆造台账**，单据上点名；扣成负数记「库存不足」但不拦发货 |
| 出货作废 / 发出后改明细 | `remove` / `update` | 已发出的单删除 → `return` 回库；改明细按差额补 out / return |
| 唯一件 | `registerUnique` + 库存页「登记唯一件」；出货明细 `serialNo` | 序列号大写、在库重复拒绝；出货 / 回库按序列号定位 |
| 手工调整 | `adjust` + 单品流水页 | 必须写原因（报损 / 更正 / 自用） |
| 运费草稿 | 出货详情「运费」→ 采购账「物流运费 · 待确认」 | **确认前不计预算**；未确认时跟着改金额；`confirmDraft` 确认 = 已完成并回写出货单，驳回 = 取消 |

守卫：`test:inventory-moves`（settlement 域，**真跑四个云函数真源** + 内存库，12 条注入自检）。

### 5.3 仍未做（下一轮，需要时再点名）

1. **电商库存（`products.stock`）与成品台账对账**：属电商链路（稳定期），本轮没动 `makeOrder`；建议先做只读对账页（台账行关联商品 → 显示差额），再决定是否「以台账为准回写」。
2. **台账行 ↔ 商品关联**（`productId`）的录入口；**历史出货单 / 采购单**不补记流水（历史已体现在盘点里）。
3. SKU 批量改价 / 停用、扫码（运单 / 条码）、飞书同步冲突提示、供应商对账与付款联动、单品成本（采购价 + 运费摊销）。
4. `admin_operation_logs` 读规则收紧（见 5.1）。

### 5.4 上线顺序（必须按序）

1. 先部署 `manageStudioInventory`、`manageStudioRawInventory`、`managePurchaseOrder`、`manageStoreShipment` 四个云函数（`inventory_moves` 集合首次写入时自动建；规则按 `cloudbase/rules/inventory_moves.json` 设为全关）；
2. 再上传小程序（库存页的差异预览 / 流水 / 唯一件、出货详情的运费、采购单的入库与运费确认都依赖新云函数）；
3. 第一次盘点写入时，被触达的台账行会自动补一条「开账」流水 —— 之后每条台账都能用 `verifyLedger` 核对「流水合计 = 台账」。
