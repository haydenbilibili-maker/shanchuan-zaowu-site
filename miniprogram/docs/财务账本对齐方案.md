## 1. 原状与不一致根因

### 1.1 小程序侧（`shanchuanspecimens`）

| 能力 | 原数据源 | 写入方 | 读取方 |
|------|----------|--------|--------|
| 门店日营收 | `daily_revenues`（pos/online/cash/refund/total） | 店长后台手工录入 | 店长看板、趋势图 |
| 小程序订单 | `orders.totalPrice`（含运费的实付） | `makeOrder` → `payCallback`/`confirmPayment` → `fulfillOrder` | 店长看板「在线营收」、会员成长值等 |
| 退款 | `orders.refundFee` + status=`refunded` | `refundOrder` | 订单列表；**未回写日营收** |
| 行为看板 | `user_behaviors` / `analytics_daily` | `trackUserBehavior` | `getAnalyticsDashboard`（**非财务**） |
| 门店积分 | `point_records` 等 | `grantStorePoints` | 会员中心（**不是钱，不进账本**） |

问题：

1. 店长只写 `daily_revenues`，Admin 读写 `finance_records` + `store_ledger` → **双集合、无自动桥接**。
2. 已有 `syncFinanceData` 旧版仅单向 `daily_revenues → finance_records`（已存在则跳过），且店长页**未调用**。
3. 在线 GMV 用 `orders` 实时加总（limit/全量口径不稳），与门店「ONLINE」渠道字段易混淆。
4. 时区：云函数默认 UTC；营业日需按 **Asia/Shanghai** 切日。

### 1.2 Admin 侧（`shanchuanzaowu/admin`）

| 能力 | 数据源 | 说明 |
|------|--------|------|
| 财务核算页 | 本地 `localStorage(shanhai_v12)` + 云 `finance_records` | `admin/src/utils/financeSync.js` |
| 店长桥接 | `store_ledger` | `admin/src/utils/storeLedgerSync.js`；上传时镜像写两边 |
| 店铺管理·门店营收 | `sc_store_bundle_v1.revenueEntries`（本地 bundle） | 提成基数；可与财务账本同步 |
| 旧文档 | `docs/财务数据多端同步说明.md` | 描述双向同步，但正式小程序未接线 |

Admin **直连同一云开发环境**，不是自建 DB；手工录入仍可发生在 Web 本地，靠「同步到云端 / 从云端下载」对齐。

### 1.3 不一致根因（汇总）

1. **双写分裂**：小程序 `daily_revenues` ↔ Admin `finance_records`/`store_ledger`。  
2. **同步未接线**：云函数有雏形，店长页未用。  
3. **口径混用**：门店扫码「ONLINE」≠ 小程序商城 GMV。  
4. **退款未进日账**：退款只改订单，不改日汇总。  
5. **积分≠营收**：门店消费积分不计入会员成长值，也**不得**记入财务营收。

## 2. SSOT 与对齐机制（已选型）

**单一事实来源（门店日结）**：云集合 **`store_ledger`**（键：`storeId|date`）

| 角色 | 行为 |
|------|------|
| 店长小程序 | 读写 `store_ledger`；入账后云函数镜像 `finance_records`；兼容写 `daily_revenues` |
| Admin 财务页 | 继续读写 `finance_records`，并与 `store_ledger` 双向合并（已有逻辑） |
| 小程序商城订单 | **独立口径**：对账写入 `mpOnline` / `mpRefund` / `mpOrderCount` / `mpNet`，**不计入**门店 `netAmount`/`revenue` |
| 积分 | 完全分离，不进账本 |

```
门店录入 / Admin 同步
        ↓
   store_ledger  ←── 三源合并（finance_records + daily_revenues + store_ledger）
        ↓ 镜像
 finance_records  ←── Admin ERP 主读
        ↑
 reconcile_online_orders（仅写 mp* 字段）
```

云函数：`syncFinanceData`（仅 **manager / admin**）

| action | 作用 |
|--------|------|
| `upload_records` | 写 `store_ledger` + 镜像 `finance_records` |
| `download_records` | 读 `store_ledger` |
| `refresh_store_ledger` | 三源合并；`persist:true` 可落库 |
| `sum_month_store_ledger` | 本月门店 NET 汇总 |
| `sync_daily_revenues` | 历史 `daily_revenues` 迁移 |
| `reconcile_online_orders` | 按东八区营业日汇总商城支付/退款 → `mp*` |

## 3. 财务口径（验数必须遵守）

| 指标 | 定义 | 含运费？ | 扣退款？ |
|------|------|----------|----------|
| **门店财务营收** `netAmount` | POS + 遗留现金收入 + **历史** `ledger.online` − 门店退款（**不含**在手现金、**不含**小程序 `mp*`） | 门店侧如实录 | 是（当日退款字段） |
| **在手现金** `cashBalance` | 日报「现金：xxx元」= 门店现存现金余额，**不是**当日现金收入 | — | — |
| **遗留现金收入** `cash` / `cashIncome` | 仅旧数据：无 `cashBalance` 时，`cash` 仍按当日现金收入计入 NET | — | — |
| **小程序 GMV / UI「线上」** | 已付订单 `totalPrice`（`paid`/`paid_awaiting_address`/`shipped`/`received`）；展示与近7日/趋势/GMV 卡的「线上」**仅用此口径**，**不用**账本 `online` | 是 | 看板侧不含已退款单 |
| **小程序对账** `mpOnline` | 同上，由 `reconcile_online_orders` 写入账本日行（不并入 `netAmount`） | 是 | 支付日记全额；退款记入 `mpRefund` |
| **小程序净额** `mpNet` | `mpOnline − mpRefund`（跨日退款按退款日） | — | 是 |
| **店长看板「合计」/ 近7日拆分** | **线上** = 小程序已付 GMV；**门店** = 账本净额（不含 mp） | — | 线上侧不含已退款 |
| **积分** | 与钱无关 | — | — |

**禁止**：把门店账本 `online` / 日报「线上」填成小程序商城成交额（会与看板「线上」双计或展示为 0 误解）。后续门店侧不再有「线上收入」业务；所有线上成交归小程序。

### 旧字段 `ledger.online` 处理

| 场景 | 处理 |
|------|------|
| 展示「线上」条 / 近7日 WEEK / 趋势金柱 | **忽略** `ledger.online`，改用小程序已付 GMV（订单或 `mpOnline`） |
| 门店净额 / NET | **仍计入**历史 `online`（避免旧账突然变少） |
| 月报渠道 | 若 `online>0`，单独标「遗留线上｜账本」，并提示已计入门店净额 |
| 新录入 | 记一笔「遗留线上」字段仅兼容旧日报；默认填 0；小程序 GMV 走商城对账 / 订单 |
| 迁移（可选） | 确认某日 `online` 实为小程序成交且已在订单侧统计后，可将该日 `online` 清零，避免门店净额虚高 |

**多店**：账本键仍为 `storeId|date`；Admin / 店长月报按「店铺管理」主数据切换门店，写入 **canonical** `storeId`（如 `store_shanhaizaowu` / `store_xingchen`），勿另造门店表。

营业日：`YYYY-MM-DD`，**Asia/Shanghai**。

### 迁移说明（现金语义 2026-09）

| 场景 | 处理 |
|------|------|
| 新录入（粘贴含「现金：」） | 写入 `cashBalance`；`cash`/`cashIncome`=0；NET=POS(+历史online)−退款 |
| 旧记录仅有 `cash`、无 `cashBalance` | 仍把 `cash` 当当日现金收入计入 NET（兼容） |
| 若旧数据误把「在手现金」记成收入 | NET 会偏高；需人工按日核验后改写为 `cashBalance` 并清零 `cash` |

正则样例块：

```
山川造物
2026年 9月10日
银联POS收款:1743.3元
订单数:30
线上：0元
退款：0元
现金：985.5元
9月合计：49898.46元
```

→ date=`2026-09-10`，pos=1743.3，online=0，refund=0，cashBalance=985.5，revenue/NET=1743.3，店名兼容「山川造物/山海造物」。看板「线上」另取小程序已付 GMV，与本行 `online:0` 无关。

## 5. 如何验数

1. **云控制台**：确认集合 `store_ledger`、`finance_records` 存在（权限建议仅云函数可写 / 登录用户可读）。  
2. **部署**：上传云函数 `syncFinanceData`（见下文）。  
3. **迁移一次**（店长或开发者工具云函数测试）：  
   `action: sync_daily_revenues`，`storeId: store_shanhaizaowu`。  
4. **店长录入**：店长后台 → 账本 → 记一笔（如 POS 100）→ 云库 `store_ledger` 与 `finance_records` 同日 `revenue/netAmount=100`。  
5. **Admin**：打开财务页 →「从云端下载」→ 同日营收应为 100。  
6. **反向**：Admin 改同日营收 →「同步到云端」→ 店长账本下拉/重进 Tab → 三源合并后一致。  
7. **商城对账**：账本页点「商城对账」→ 有成交日出现「小程序 GMV / 退款」；`netAmount` 不变。  
8. **积分抽检**：`grantStorePoints` 后账本金额不变。

## 6. 部署与你还需做什么

### 已实现（代码）

对齐逻辑与文档已在仓库落地；**支付链路未改**（`fulfillOrder` / `refundOrder` 未插入阻塞逻辑）。

### 需要你操作

1. 微信开发者工具上传并部署云函数 **`syncFinanceData`**（环境 `cloud1-8gnkty5bfff9f0bf`）。  
2. 若集合不存在：新建 `store_ledger`（可参考 `shanchuanzaowu/cloudbase/rules/store_ledger.json`）。  
3. 配置云函数环境变量 `MESSAGE_ADMIN_OPENIDS`（店长 openid），或确保 `staff_members`/`users.isAdmin` 可识别店长。  
4. 执行一次 `sync_daily_revenues` 迁移历史账。  
5. Admin 财务页用「从云端下载」验证；以后以云端为准，减少纯本地手账长期分叉。

### 定时触发（可选 P1）

云开发定时触发器每日 00:30 调用：

```json
{ "action": "reconcile_online_orders", "persist": true }
```

以及可选 `refresh_store_ledger` + `persist:true` 做夜间合并修正。

## 7. Admin 接入说明（若只读小程序 API）

Admin 已直连集合；若改走云函数：

```js
wx.cloud.callFunction({
  name: 'syncFinanceData',
  data: { action: 'download_records', storeId: 'store_shanhaizaowu' }
})
```

上传：

```js
data: { action: 'upload_records', records: [/* finance 行 */], storeId }
```

须使用具备店长身份的调用方（Web 端匿名调用需另行做服务端密钥鉴权，当前 MVP 以集合直连 + 小程序店长云函数为主）。
