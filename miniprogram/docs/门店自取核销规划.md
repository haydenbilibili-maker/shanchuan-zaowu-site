> 环境：`cloud1-8gnkty5bfff9f0bf`

## 1. 用户侧流程

### 1.1 下单

1. 结算页选择 **门店自取**（非礼赠单）。
2. 展示默认主店（`getStoreConfig`）；MVP 单店，后续支持切换分店。
3. **不展示收货地址**；运费行显示「自取免运费」；不调用运费计费结果（服务端 `storePickup` 强制 0）。
4. 支付成功 → 订单 `ready_pickup`，生成 `pickupCode`，跳转订单详情。

### 1.2 凭证

| 字段 | 说明 |
|------|------|
| `pickupCode` | 短 hex 大写（与礼赠 claimCode 同形） |
| 扫码 payload | `PICKUP:{pickupCode}`（与 `GIFT:` / `BOOKING:` / `COUPON:` 分流） |
| 展示 | 订单详情大号码 + 门店名；后续：二维码、可刷新短时 token |

文案建议：「到店出示此码，由店员核销后领取」。勿用电商「提货码」堆叠感；保持 Museum 语气。

### 1.3 到店

1. 用户打开「我的订单」→ 待自取 / 订单详情出示码。
2. 店员扫码或手输码 → 核销成功 → 订单 `received`，用户收到站内信「门店自取已完成」。
3. 可选：核销后引导养护 / 证书入口（与快递签收后一致）。

### 1.4 取消 / 退款 / 过期

| 场景 | 规则建议 |
|------|----------|
| 待支付取消 | 既有 `cancelOrder`；释放库存预占 |
| 已支付待自取退款 | 走 `refundOrder`；未核销可全额；库存回滚规则与「待发货退款」对齐 |
| 核销后售后 | 同「已签收」售后；需证据策略时沿用 `refundPolicy` |
| 过期未取（规划） | 支付后 N 日（默认 14，可配置）提醒；M 日未取 → 审批后退款或转快递（店长决策） |

MVP **不做**自动过期；店长手动跟进 + 用户主动退款即可。

## 2. 店员工作台

### 2.1 入口与权限

| 能力点 | 建议 key | 说明 |
|--------|----------|------|
| 扫码核销普通自取 | `verifyOrderPickup` | 挂在 `staff/field` 与店长扫码 CTA |
| 手输码核销 | 同上 | 弱网 / 码污损 |
| 礼赠自提 | 既有 `verifyGiftPickup` | 勿混入口文案 |

权限：店员 / 店长均可核销本店单；超管可跨店。`staffGuard` + `workspaceFeatures` 增补能力点（同步 `scripts/sync-staff-guard.sh`）。

### 2.2 核销动作（目标态）

1. 解析 payload：`PICKUP:` → 查 `orders.pickupCode`（或索引集合）。
2. 校验：`fulfillmentType=store_pickup`、`status ∈ {ready_pickup,paid}`、`pickupStatus≠claimed`、门店匹配（店员绑定 `storeId`）。
3. 原子更新：`status=received`、`pickupStatus=claimed`、`pickupClaimedAt`、`pickupClaimedByStaff`；写审计日志。
4. 防重复：条件更新 `pickupStatus: 'ready'` → `'claimed'`；已 claimed 返回幂等成功。
5. 通知买家 `order_received`（tip：门店自取已完成）。

**库存 / 出货**：支付履约时已扣库存（与快递单一致）。核销 **不再**扣库存，仅完成履约闭环。若未来「线上下单、门店现货二次校验」，另开 `pickupStockCheck` 开关，默认关。

### 2.3 MVP（已可用）

店长订单待办列表「确认自取」→ `managerShipOrder.completeStorePickup`（无码、店长权限）。  
适合内测与低峰；正式开业前应切换为扫码主路径。

### 2.4 异常

| 异常 | 处理 |
|------|------|
| 码不存在 | 提示核对；可按订单号检索 |
| 已核销 | 展示核销时间与操作人；禁止二次 |
| 已退款 / 售后中 | 拒绝核销 |
| 非本店 | 拒绝；超管可强制（写审计） |
| 礼赠码误扫 | 引导至礼赠核销 Tab |

## 3. 店长工作台

### 3.1 核销记录

- 列表：时间、订单号、商品摘要、门店、操作人、方式（扫码 / 确认自取 / 冲正）。
- 数据源：`orders` 上 `pickupClaimedAt` 过滤；或独立 `pickup_verify_logs`（完整版推荐，便于报表与冲正）。

### 3.2 异常与冲正

- 误核销：店长发起冲正 → **超管审批**（对齐 `booking_verify_reverse` / `docs/审批流体系.md`）。
- 冲正后：`status` 回到 `ready_pickup`，`pickupStatus=ready`，码可复用或轮换（推荐轮换新码）。

### 3.3 权限分级

| 角色 | 核销 | 确认自取（无码） | 冲正 | 改过期规则 | 看全店统计 |
|------|------|------------------|------|------------|------------|
| 店员 | ✅ 本店 | ❌（默认） | ❌ | ❌ | 今日本店件数 |
| 店长 | ✅ | ✅ | 提交审批 | 提交超管 | 本店 |
| 超管 | ✅ | ✅ | ✅ | ✅ | 全店 |

### 3.4 数据统计

- 今日 / 本周：自取下单数、待核销积压、核销完成数、平均等待时长（支付→核销）。
- 与快递单对比：自取占比、免运费金额（运营口径，非会计）。
- 挂载：`getStudioDashboard` / `getAnalyticsDashboard` 增加 `pickupPending`、`pickupVerified`；店长首页信号灯可复用 `signal-lamp` 规范。

## 4. 订单状态机

```
pending_pay
    │ 支付成功 + 履约
    ▼
ready_pickup          ← 普通门店自取（fulfillmentType=store_pickup）
    │ 核销 / 确认自取
    ▼
received

旁路：
  ready_pickup ──退款──► refunding ──► refunded
  ready_pickup ──（禁止）──► shipped   // managerShipOrder 拦截
```

礼赠自提（对照，勿混）：

```
paid (+ giftMeta.claimStatus=ready)
    │ manageGift.verifyPickup
    ▼
received
```

### 与退款 / 部分履约边界

- **整单自取**：MVP 仅支持整单核销；多件一次交清。
- **部分履约（完整版）**：行项目 `pickupLines[]`；订单 `pickupStatus=partial|claimed`；未取行可退款。
- **定金 / 定制**：定金单不走自取；定制单若允许自取，生产状态须已 `packing`/`ready` 才可核销（完整版校验）。

## 5. 数据模型建议

### 5.1 `orders`（已用 / 建议）

| 字段 | 类型 | 说明 |
|------|------|------|
| `fulfillmentType` | string | `express` \| `store_pickup` \| `gift_invite` |
| `storePickup` | bool | 冗余便于查询 |
| `storeId` / `storeName` | string | 自取门店 |
| `pickupCode` | string | 普通自取码 |
| `pickupStatus` | string | `none` \| `ready` \| `claimed` \| `expired` |
| `pickupClaimedAt` | date | 核销时间 |
| `pickupClaimedByStaff` | string | 操作人 openid |
| `pickupExpireAt` | date | 可选，过期策略 |
| `status` | string | 自取待取：`ready_pickup` |

礼赠继续用 `giftMeta.claimCode` / `claimStatus`，**不要**强行合并进 `pickupCode`（历史单与扫码前缀不同）。

### 5.2 建议索引

- `pickupCode` + `fulfillmentType`（核销查码）
- `status=ready_pickup` + `storeId` + `paidTime`（积压列表）
- `pickupClaimedAt` + `storeId`（核销报表）

### 5.3 可选集合 `pickup_verify_logs`

`orderId, orderNo, storeId, code, staffOpenid, channel(scan|manual|manager_confirm), result, createTime`  
便于审计与冲正，不依赖订单文档历史。

## 8. 验收标准

### 8.1 Phase 0（当前必须通过）

1. 结算选「门店自取」→ 应付不含运费；云函数预览 `shippingFee=0`。  
2. 下单不要求收货地址；订单 `fulfillmentType=store_pickup`、`storePickup=true`、有 `storeId`。  
3. 支付后 `status=ready_pickup`，有 `pickupCode`；详情显示「待自取」与码。  
4. 店长待发货列表对该单 **无「确认发货」** 或发货被云函数拒绝；可用「确认自取」→ `received`。  
5. 快递单路径不受影响（仍计运费、可发货）。  
6. 礼赠自提仍走 `GIFT:` 核销，互不串码。

### 8.2 Phase 1

1. 店员扫 `PICKUP:xxx` 一次成功、二次幂等。  
2. 无权限店员被拒。  
3. 错店核销被拒。  
4. 核销后用户站内信与状态「已签收/已完成」一致。

### 8.3 回归

- 免邮活动 / 免邮券 + 自取：运费仍为 0，券可用性提示合理。  
- 钱包支付 + 自取。  
- 定金尾款单：默认不提供自取或明确禁用。

## 13. 本轮落地（2026-09-15 · 凭证页与订单详情解耦）

问题：凭证本体原先内嵌在订单详情页页尾，再靠一枚全屏弹层放大出示。结果是
①订单详情被凭证的长内容挤长、破坏「订单信息」的信息层级；②弹层没有独立路由，无法从
私信 / 扫码 / 二次进入直达；③二维码与屏幕亮度、生命周期都挂在详情页上，容易出现
「离开页面亮度没恢复」「返回后状态陈旧」等副作用。

本轮把凭证做成**独立页面**，订单详情只留一张入口卡。

### 13.1 新增独立凭证页 `subpackages/business/pickup-pass/index`

| 项 | 落地 |
|----|------|
| 路由参数 | `?id=<订单号>&code=<自取码>`；**有 `code` 就先画码**（60ms 后出二维码），有 `id` 再异步拉订单补状态，秒出不等待网络 |
| 展示模型 | 新增共享工具 `subpackages/business/utils/pickupPass.js`（`buildPickupPass` / `groupPickupCode` / `formatPickupTime` / `isStorePickupOrder`），订单详情与凭证页同一套状态口径，不再两处各写一份 |
| 屏幕亮度 | 进页面（`onShow`）自动 `wx.setScreenBrightness(1)`，离开（`onHide`/`onUnload`）恢复原亮度 —— 柜台扫码场景 |
| 二维码 | `drawMemberQr('#passQrCanvas', 'PICKUP:<码>', …, margin:44)`，外层白底静区；**绘制失败 → 自动降级为口报自取码**（`qrFailed`），不再出现「空白方块」 |
| 已交付态 | `pass.statusTone === 'done'` 时收起自取码行，二维码**保留但码面变灰并盖「已自提」水印**（`.pass-qr-used` + `.pass-qr-stamp`），配合对勾回执与核销时间，既联动告知也阻止二次出示 |
| 领取门店 | 楼层 / 营业时间 / 地址 / 坐标（`utils/storeCatalog` 本地缓存补齐，失败静默；同一门店只补一次）+「导航到店 →」走 `wx.openLocation` |
| 复制自取码 | 点自取码行 → 剪贴板 + 轻震动；码按 4 位分组（`0347 57D3 63`）便于口头报码 |
| 状态刷新 | **待领取期间每 3s 静默轮询自己的订单**（`PASS_POLL_MS`，上限 15 分钟 `PASS_POLL_MAX_MS`）→ 店员在柜台核销后顾客端**自动收口**为「本次自取已完成」并给一次震动 + toast；回到前台节流补拉（`PASS_RESUME_MS`）；`onHide`/`onUnload` 停表；并发读库去重（同一时刻只发一次请求）；仍支持**下拉刷新**（`enablePullDownRefresh`）；静默刷新失败时保留上一次已核对状态，不打断出示 |
| 防泄露 | `wx.hideShareMenu()` 关闭转发入口 + 页面明示「自取码仅限本人到店使用，请勿截图或转发」 |
| 兜底 | 只有 `code` 没有 `id`（历史链接）→ 状态标为「以专员核实为准」且**不查库不轮询**（顾客不能按码查他人订单），自取码仍可出示；读库失败同理；`denyOrderAccess` 处理与订单详情一致 |
| 底部操作 | 「联系专员」（`feature/user/support` 带订单上下文）/「查看订单」（有上层页面 → 返回；否则 → `redirectTo` 订单详情） |
